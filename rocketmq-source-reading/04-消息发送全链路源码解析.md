## 一、全局调用链总览

消息发送是 RocketMQ 中最高频、最核心的链路。它横跨"客户端"与"服务端"两个进程，中间经过 Netty 网络传输。下面先给出一张完整的调用链路图，后续章节会逐层展开。

```
【Producer 进程】
DefaultMQProducer.send(msg)                          // 门面(Facade)
  |
  +-- produceAccumulator.tryAddMessage(msg) ?        // 是否开启 autoBatch
  |     |
  |     +-- 是 --> sendByAccumulator(msg, null, null)  // 走累加器批量合并
  |     +-- 否 --> sendDirect(msg, null, null)         // 直接发送
  |
  +-- sendDirect(msg, ...)
        |
        +-- 同步 --> defaultMQProducerImpl.send(msg)             // SYNC
        +-- 异步 --> defaultMQProducerImpl.send(msg, callback)    // ASYNC
        +-- Oneway --> defaultMQProducerImpl.sendOneway(msg)      // ONEWAY
              |
              v
DefaultMQProducerImpl.sendDefaultImpl(msg, mode, callback, timeout)  // ★核心发送方法
  |
  +-- 1. makeSureStateOK()                        // 状态检查(必须RUNNING)
  +-- 2. Validators.checkMessage(msg, producer)   // 消息合法性校验
  +-- 3. tryToFindTopicPublishInfo(topic)         // ★路由查找(本地缓存→NameServer→默认Topic)
  |         |
  |         +-- topicPublishInfoTable.get(topic)  // 本地缓存
  |         +-- mQClientFactory.updateTopicRouteInfoFromNameServer(topic)  // 拉路由
  |         +-- (miss) updateTopicRouteInfoFromNameServer(topic, true, defaultMQProducer)  // 自动建Topic
  |
  +-- 4. for (times = 0; times < timesTotal; times++)   // ★重试循环(SYNC=1+retryTimesWhenSendFailed)
  |         |
  |         +-- selectOneMessageQueue(tpInfo, lastBrokerName, resetIndex)  // ★容错队列选择(MQFaultStrategy)
  |         +-- sendKernelImpl(msg, mq, mode, callback, tpInfo, timeout)   // ★发送内核
  |         |     |
  |         |     +-- findBrokerAddressInPublish(brokerName)  // 解析Broker地址
  |         |     +-- MixAll.brokerVIPChannel(...)            // VIP通道(端口-2)
  |         |     +-- MessageClientIDSetter.setUniqID(msg)    // 生成全局唯一msgId
  |         |     +-- tryToCompressMessage(msg)               // 大消息压缩
  |         |     +-- 构造 SendMessageRequestHeader
  |         |     +-- MQClientAPIImpl.sendMessage(...)        // ★进入网络层
  |         |           |
  |         |           +-- 构造 RemotingCommand (SEND_MESSAGE / SEND_MESSAGE_V2)
  |         |           +-- ONEWAY --> remotingClient.invokeOneway()
  |         |           +-- ASYNC  --> sendMessageAsync() --> remotingClient.invokeAsync()
  |         |           +-- SYNC   --> sendMessageSync()  --> remotingClient.invokeSync()  ★真正网络I/O
  |         |                 |
  |         |                 +-- processSendResponse(brokerName, msg, response, addr)  // 解析响应
  |         |
  |         +-- updateFaultItem(brokerName, latency, isolation, reachable)  // ★更新容错表
  |         +-- 异常分类处理(MQClientException / RemotingException / MQBrokerException / InterruptedException)
  |
  v
=================================== Netty 网络传输 ===================================
  |
  v
【Broker 进程】
SendMessageProcessor.processRequest(ctx, request)       // Netty业务线程池分发
  |
  +-- switch(request.getCode())
  |     +-- CONSUMER_SEND_MSG_BACK --> consumerSendMsgBack()  // 消费失败回传
  |     +-- default:
  |           +-- parseRequestHeader(request)
  |           +-- buildMsgContext(ctx, requestHeader, request)
  |           +-- executeSendMessageHookBefore(context)
  |           +-- requestHeader.isBatch() ? sendBatchMessage() : sendMessage()
  |
  +-- SendMessageProcessor.sendMessage(...)
        |
        +-- 1. preSend(ctx, request, requestHeader)   // 时间戳校验 + msgCheck()
        |         +-- msgCheck(): 权限/Topic合法性/自动建Topic/队列ID校验
        |
        +-- 2. 队列选择(queueIdInt<0 时随机)
        +-- 3. handleRetryAndDLQ()  // 重试Topic → 死信队列判定
        +-- 4. 构造 MessageExtBrokerInner
        +-- 5. 事务预处理(PROPERTY_TRANSACTION_PREPARED)
        +-- 6. 存储:
        |     +-- 异步(默认) --> messageStore.asyncPutMessage(msgInner)
        |     |                    .thenAcceptAsync(result -> handlePutMessageResult(...))
        |     |                    return null  // 立即释放Netty线程
        |     +-- 同步 --------> messageStore.putMessage(msgInner)
        |                          handlePutMessageResult(...)
        |
        +-- handlePutMessageResult(putMessageResult, response, ...)
              +-- PutMessageStatus → ResponseCode 映射
              +-- 成功: 更新统计/指标, 设置响应头(msgId/queueId/queueOffset), 回写客户端
```

这条链路可以拆成两大部分：

- **客户端侧（Producer）**：从门面 `DefaultMQProducer` 一路委托到 `DefaultMQProducerImpl.sendDefaultImpl()`，核心工作是"路由查找 + 容错队列选择 + 重试循环 + 网络发送"。
- **服务端侧（Broker）**：`SendMessageProcessor` 接收请求，经过"校验 → 重试/死信判定 → 构造内部消息 → 存储 → 结果映射 → 回写响应"。

## 二、DefaultMQProducer 入口分析

**源码位置**：`client/src/main/java/org/apache/rocketmq/client/producer/DefaultMQProducer.java`

`DefaultMQProducer` 是暴露给用户的门面类（Facade），它本身几乎不做业务，所有真正的逻辑都委托给内部的 `DefaultMQProducerImpl`。这是一种典型的"门面 + 实现分离"设计，和 Dubbo 中 `ReferenceConfig` 委托给 `ReferenceConfigBase`、`Invoker` 的思路一致：对外暴露一个稳定、简洁的 API，对内保留灵活的实现演进空间。

### 2.1 关键字段

```java
public class DefaultMQProducer extends ClientConfig implements MQProducer {

    /**
     * 内部实现，所有发送逻辑真正的落脚点
     */
    protected final transient DefaultMQProducerImpl defaultMQProducerImpl;

    /**
     * 生产者组，同一个组的 Producer 逻辑上等价，事务消息回查时靠它定位
     */
    private String producerGroup;

    /**
     * 发送同步消息的超时时间，默认 3000ms
     */
    private int sendMsgTimeout = 3000;

    /**
     * 消息体超过该阈值(4KB)时会尝试压缩
     */
    private int compressMsgBodyOverHowmuch = 1024 * 4;

    /**
     * 同步发送失败时的重试次数，默认 2 次
     * 加上第一次，总共最多发 3 次
     */
    private int retryTimesWhenSendFailed = 2;

    /**
     * 异步发送失败时的重试次数，默认 2 次

    /**

     */
    private boolean retryAnotherBrokerWhenNotStoreOK = false;

    /**
     * 需要重试的响应码集合（见下）
     */
    private Set<Integer> retryResponseCodes = new CopyOnWriteArraySet<>(Arrays.asList(
        ResponseCode.TOPIC_NOT_EXIST,
        ResponseCode.SERVICE_NOT_AVAILABLE,
        ResponseCode.SYSTEM_ERROR,
        ResponseCode.SYSTEM_BUSY,
        ResponseCode.NO_PERMISSION,
        ResponseCode.NO_BUYER_ID,
        ResponseCode.NOT_IN_CURRENT_UNIT,
        ResponseCode.GO_AWAY
    ));

    /**
     * 是否开启自动批量（accumulator 攒批）
     */
    private boolean autoBatch = false;

    private ProduceAccumulator produceAccumulator = null;
}
```

**知识点：retryResponseCodes 为什么是这几个？**

这个集合定义了"哪些 Broker 返回的错误码值得客户端切换到另一个 Broker 重试"。它们的共同点是"这个 Broker 暂时不可用，但换一个 Broker 或稍后重试可能成功"：

| 响应码 | 含义 | 为什么重试 |
|---|---|---|
| `TOPIC_NOT_EXIST` | Topic 不存在 | 目标 Broker 上没有该 Topic，换一个可能有 |
| `SERVICE_NOT_AVAILABLE` | 服务不可用 | Broker 处于不可写状态，换一个 |
| `SYSTEM_ERROR` | 系统错误 | 通常是存储层瞬时错误，换一个 |
| `SYSTEM_BUSY` | 系统繁忙 | PageCache 忙 / 堆积，换一个更空闲的 |
| `NO_PERMISSION` | 无权限 | 该 Broker 无写权限，换一个 |
| `NO_BUYER_ID` | 无 buyer id | 定制场景 |
| `NOT_IN_CURRENT_UNIT` | 不在当前单元 | 单元化路由错误，换一个 |
| `GO_AWAY` | 优雅下线信号 | Broker 正在优雅关闭，主动让客户端离开 |

注意：`GO_AWAY` 是较新版本引入的"优雅下线"机制——Broker 准备关闭时不粗暴断连，而是回一个 `GO_AWAY`，让客户端主动换 Broker，从而实现无损发布。

### 2.2 send() —— 门面的第一层分发

```java
@Override
public SendResult send(
    Message msg) throws MQClientException, RemotingException, MQBrokerException, InterruptedException {
    return sendDirect(msg, null, null).getSendResult();
}
```

在开启 `autoBatch` 的情况下，`send()` 内部会先尝试走累加器：

```java
public SendResult sendDirect(Message msg, MessageQueue mq,
    SendCallback sendCallback) throws MQClientException, RemotingException, MQBrokerException, InterruptedException {

    // 自动添加命名空间前缀
    Message copiedMsg = MessageAccessor.toMessageExt(msg, this.getNamespaceV2());
    if (this.getAutoBatch() && !(msg instanceof MessageBatch)) {
        // 开启 autoBatch，交给累加器
        return sendByAccumulator(msg, mq, sendCallback);
    } else {
        // 不开启，直接发
        return this.sendDirect(msg, mq, sendCallback);
    }
}
```

实际的 `sendDirect` 分三种通信模式派发：

```java
private SendResult sendDirect(Message msg, MessageQueue mq,
    SendCallback sendCallback) throws MQClientException, RemotingException, MQBrokerException, InterruptedException {

    boolean isDirectSendAsync = sendCallback != null;
    try {
        if (mq == null) {
            // 无指定队列
            if (isDirectSendAsync) {
                // 异步发送：直接委托 Impl
                this.defaultMQProducerImpl.send(msg, sendCallback);
                return null;
            } else {
                // 同步发送：直接委托 Impl
                return this.defaultMQProducerImpl.send(msg);
            }
        } else {
            // 指定队列发送
            return isDirectSendAsync
                ? this.sendDirect(msg, mq, sendCallback)
                : this.defaultMQProducerImpl.send(msg, mq);
        }
    } finally {
        // 累加器统计
    }
}
```

**核心结论**：门面 `DefaultMQProducer` 的作用就是三件事——

1. 处理命名空间（namespace）；
2. 决定走"累加器攒批"还是"直发"；
3. 按同步/异步/单向三种模式，把调用委托给 `DefaultMQProducerImpl`。

真正的复杂逻辑，全部在 `DefaultMQProducerImpl` 中。

**知识点：ServiceState 状态机**

RocketMQ 的几乎所有可启动组件（Producer/Consumer/MQClientInstance）都遵循同一个状态机：

```
CREATE_JUST  --start()-->  RUNNING  --shutdown()-->  SHUTDOWN_ALREADY
     |
     +-- start() 异常 --> START_FAILED
```

`start()` 方法的第一件事就是检查状态是否为 `CREATE_JUST`，并且在开始时先把状态置为 `START_FAILED`，只有全部初始化成功才置为 `RUNNING`——这是一种"悲观初始化"，防止半启动状态被误用。

### 3.2 start() 全流程

```java
public void start(final boolean startFactory) throws MQClientException {
    switch (this.serviceState) {
        case CREATE_JUST:
            // 1. 悲观置为失败，成功才翻转
            this.serviceState = ServiceState.START_FAILED;

            // 2. 校验配置(producerGroup 合法性等)
            this.checkConfig();

            // 3. 若非 CLIENT_INNER_PRODUCER_GROUP，用 IP 作为 instanceName
            if (!this.defaultMQProducer.getProducerGroup().equals(MixAll.CLIENT_INNER_PRODUCER_GROUP)) {
                this.defaultMQProducer.changeInstanceNameToPID();
            }

            // 4. 获取/创建 MQClientInstance（同一 clientId 共享同一个实例）
            this.mQClientFactory = MQClientManager.getInstance()
                .getOrCreateMQClientInstance(this.defaultMQProducer, rpcHook);

            // 5. 注册自己到工厂（工厂持有本 JVM 所有的 Producer/Consumer）
            boolean registerOK = mQClientFactory.registerProducer(
                this.defaultMQProducer.getProducerGroup(), this);
            if (!registerOK) {
                this.serviceState = ServiceState.CREATE_JUST;
                throw new MQClientException("The producer group[" + ... + "] has been created before", null);
            }

            // 6. 初始化 Topic 路由本地缓存（放入一个空的 TBW102 默认路由）
            if (startFactory) {
                mQClientFactory.start();  // ★启动工厂：Netty客户端/定时任务/拉取服务/负载均衡
            }

            // 7. 启动故障探测器（可选）
            this.mqFaultStrategy.startDetector();

            log.info("the producer [{}] start OK. sendMessageWithVIPChannel={}", ...);
            // 8. 状态翻转为 RUNNING
            this.serviceState = ServiceState.RUNNING;
            break;
        case RUNNING:
        case START_FAILED:
        case SHUTDOWN_ALREADY:
            throw new MQClientException("The producer service state not OK, maybe started once, "
                + this.serviceState + ...);
        default:
            break;
    }

    // 9. 首次发送心跳到所有 Broker，让 Broker 知道有这个 Producer 存在
    this.mQClientFactory.sendHeartbeatToAllBrokerWithLock();

    // 10. 启动一个定时清理请求响应表的任务
    RequestFutureHolder.getInstance().startScheduledTask(this);
}
```

**逐步拆解**：

1. **状态检查**：只有 `CREATE_JUST` 才能启动，否则抛异常。
2. **`getOrCreateMQClientInstance`**：这是 RocketMQ 客户端最重要的复用机制——**同一个 JVM、同一个 `clientId`（IP@instanceName）下的所有 Producer 和 Consumer 共享同一个 `MQClientInstance`**。它内部持有唯一的 Netty 客户端、唯一的路由表、唯一的定时任务调度器。这样即使一个应用创建了 10 个 Producer，也只会有一套底层网络连接。
3. **`registerProducer`**：把自己注册进工厂的 `producerTable`（`ConcurrentMap<group, MQProducerInner>`）。如果同名组已存在，注册失败并回滚状态。
4. **`mQClientFactory.start()`**：真正启动网络与后台线程（详见第十三章）。
5. **`startDetector()`**：启动故障探测器，周期性对隔离中的 Broker 做探活（详见第八章）。
6. **`sendHeartbeatToAllBrokerWithLock()`**：向所有已知 Broker 发送心跳，把本 Producer 的存在告知 Broker。

## 四、sendDefaultImpl() 核心发送逻辑

这是整个客户端发送流程的**心脏**。所有同步/异步/单向发送，最终都汇聚到这个方法。

**源码位置**：`DefaultMQProducerImpl.sendDefaultImpl()`

### 4.1 方法签名与整体骨架

```java
private SendResult sendDefaultImpl(
    Message msg,
    final CommunicationMode communicationMode,
    final SendCallback sendCallback,
    final long timeout
) throws MQClientException, RemotingException, MQBrokerException, InterruptedException {

    // 1. 状态检查
    this.makeSureStateOK();

    // 2. 消息合法性校验
    Validators.checkMessage(msg, this.defaultMQProducer);

    // 一次调用的唯一标识，用于日志追踪
    final long invokeID = random.nextLong();
    long beginTimestampFirst = System.currentTimeMillis();
    long beginTimestampPrev = beginTimestampFirst;
    long endTimestamp = beginTimestampFirst;

    // 3. 查找 Topic 路由（本地缓存 → NameServer → 默认Topic自动创建）
    TopicPublishInfo topicPublishInfo = this.tryToFindTopicPublishInfo(msg.getTopic());

    if (topicPublishInfo != null && topicPublishInfo.ok()) {
        boolean callTimeout = false;
        MessageQueue mq = null;
        Exception exception = null;
        SendResult sendResult = null;

        // 4. 计算重试总次数：SYNC = 1 + retryTimesWhenSendFailed（默认3），其它模式 = 1
        int timesTotal = communicationMode == CommunicationMode.SYNC
            ? 1 + this.defaultMQProducer.getRetryTimesWhenSendFailed()
            : 1;
        int times = 0;
        // 记录每次重试命中的 Broker，用于日志
        String[] brokersSent = new String[timesTotal];
        boolean resetIndex = false;

        // ★重试循环
        for (; times < timesTotal; times++) {
            String lastBrokerName = null == mq ? null : mq.getBrokerName();
            if (times > 0) {
                resetIndex = true;  // 重试时重置队列轮询下标，重新洗牌
            }

            // 4.1 容错队列选择：避开上次失败的 Broker
            MessageQueue mqSelected = this.selectOneMessageQueue(topicPublishInfo, lastBrokerName, resetIndex);
            if (mqSelected != null) {
                mq = mqSelected;
                brokersSent[times] = mq.getBrokerName();
                try {
                    beginTimestampPrev = System.currentTimeMillis();
                    if (times > 0) {
                        // 重试时把 Topic 重置为用户 Topic（去掉命名空间等）
                        msg.setTopic(this.defaultMQProducer.withNamespace(msg.getTopic()));
                    }
                    // 4.2 计算剩余超时时间；若已超时则中断
                    long costTime = beginTimestampPrev - beginTimestampFirst;
                    if (timeout < costTime) {
                        callTimeout = true;
                        break;
                    }

                    // 4.3 ★进入发送内核
                    sendResult = this.sendKernelImpl(msg, mq, communicationMode, sendCallback,
                        topicPublishInfo, timeout - costTime);
                    endTimestamp = System.currentTimeMillis();
                    // 4.4 发送成功：更新容错表(未隔离、可达)
                    this.updateFaultItem(mq.getBrokerName(), endTimestamp - beginTimestampPrev, false, true);

                    switch (communicationMode) {
                        case ASYNC:
                            return null;  // 异步：结果走回调，这里直接返回
                        case ONEWAY:
                            return null;  // 单向：无结果
                        case SYNC:
                            if (sendResult.getSendStatus() != SendStatus.SEND_OK) {
                                // 未存储成功且配置了"换Broker重试"，继续循环
                                if (this.defaultMQProducer.isRetryAnotherBrokerWhenNotStoreOK()) {
                                    continue;
                                }
                            }
                            return sendResult;
                        default:
                            break;
                    }
                } catch (MQClientException e) {
                    // 客户端异常：Broker 仍可达，更新容错并继续重试
                    endTimestamp = System.currentTimeMillis();
                    this.updateFaultItem(mq.getBrokerName(), endTimestamp - beginTimestampPrev, false, true);
                    log.warn(...);
                    exception = e;
                    continue;
                } catch (RemotingException e) {
                    // 网络异常：若探测器未启动，直接隔离该 Broker
                    endTimestamp = System.currentTimeMillis();
                    if (this.mqFaultStrategy.isStartDetectorEnable()) {
                        // 探测器开启：不立即隔离，交给探测器判定可达性
                        this.updateFaultItem(mq.getBrokerName(), endTimestamp - beginTimestampPrev, true, false);
                    } else {
                        this.updateFaultItem(mq.getBrokerName(), endTimestamp - beginTimestampPrev, true, true);
                    }
                    log.warn(...);
                    exception = e;
                    continue;
                } catch (MQBrokerException e) {
                    // Broker 返回错误：隔离该 Broker、标记不可达
                    endTimestamp = System.currentTimeMillis();
                    this.updateFaultItem(mq.getBrokerName(), endTimestamp - beginTimestampPrev, true, false);
                    log.warn(...);
                    exception = e;
                    // 只有响应码在 retryResponseCodes 中才重试，否则直接抛出
                    if (this.defaultMQProducer.getRetryResponseCodes().contains(e.getResponseCode())) {
                        continue;
                    } else {
                        if (sendResult != null) {
                            return sendResult;
                        }
                        throw e;
                    }
                } catch (InterruptedException e) {
                    // 被中断：更新容错后立即抛出，不再重试
                    endTimestamp = System.currentTimeMillis();
                    this.updateFaultItem(mq.getBrokerName(), endTimestamp - beginTimestampPrev, false, true);
                    log.warn(...);
                    throw e;
                }
            } else {
                break;
            }
        }

        if (sendResult != null) {
            return sendResult;
        }

        // 5. 全部重试失败：拼装详细的失败信息（含每次命中的 Broker）
        String info = String.format("Send [%d] times, still failed, cost [%d]ms, Topic: %s, BrokersSent: %s",
            times, System.currentTimeMillis() - beginTimestampFirst, msg.getTopic(),
            Arrays.toString(brokersSent));
        info += FAQUrl.suggestTodo(FAQUrl.SEND_MSG_FAILED);

        MQClientException mqClientException = new MQClientException(info, exception);
        if (callTimeout) {
            // 超时导致的失败，单独抛超时异常
            throw new RemotingTooMuchRequestException("sendDefaultImpl call timeout");
        }
        // 根据底层异常类型设置合适的 ResponseCode
        if (exception instanceof MQBrokerException) {
            mqClientException.setResponseCode(((MQBrokerException) exception).getResponseCode());
        } else if (exception instanceof RemotingConnectException) {
            mqClientException.setResponseCode(ClientErrorCode.CONNECT_BROKER_EXCEPTION);
        } else if (exception instanceof RemotingTimeoutException) {
            mqClientException.setResponseCode(ClientErrorCode.ACCESS_BROKER_TIMEOUT);
        } else if (exception instanceof MQClientException) {
            mqClientException.setResponseCode(ClientErrorCode.BROKER_NOT_EXIST_EXCEPTION);
        }
        throw mqClientException;
    }

    // 路由为空：NameServer 不可用或 Topic 不存在
    validateNameServerSetting();
    throw new MQClientException("No route info of this topic: " + msg.getTopic() + ...,
        null).setResponseCode(ClientErrorCode.NOT_FOUND_TOPIC_EXCEPTION);
}
```

### 4.2 重试次数的精确语义

```java
int timesTotal = communicationMode == CommunicationMode.SYNC
    ? 1 + this.defaultMQProducer.getRetryTimesWhenSendFailed()  // 1 + 2 = 3
    : 1;
```

- **同步（SYNC）**：`timesTotal = 1 + retryTimesWhenSendFailed`。默认 `retryTimesWhenSendFailed=2`，所以同步发送**最多在这个循环里发 3 次**。
- **异步（ASYNC）/ 单向（ONEWAY）**：`timesTotal = 1`。**注意**：异步的重试不在这个循环里，而是在 `MQClientAPIImpl.onExceptionImpl()` 里递归实现（详见第十一章）。这是初学者最容易搞混的地方——**同步重试在 `sendDefaultImpl`，异步重试在 `onExceptionImpl`**。

### 4.3 异常分类处理表

这是理解 RocketMQ 容错的关键。不同异常代表不同的"Broker 健康状态"，因此隔离策略也不同：

| 异常类型 | isolation | reachable | 是否重试 | 语义 |
|---|---|---|---|---|
| `MQClientException` | false | true | 继续重试 | 客户端侧问题（如参数），Broker 本身没病 |
| `RemotingException`（探测器开） | true | false | 继续重试 | 网络问题，隔离但交探测器复活 |
| `RemotingException`（探测器关） | true | true | 继续重试 | 网络问题，隔离并按超时时长复活 |
| `MQBrokerException` | true | false | 视响应码 | Broker 明确报错，隔离并标不可达 |
| `InterruptedException` | false | true | **立即抛出** | 线程被中断，不该继续占用 |

`updateFaultItem(brokerName, latency, isolation, reachable)` 的四个参数含义：
- `brokerName`：要更新的 Broker；
- `latency`：本次调用耗时（用于计算隔离时长）；
- `isolation`：是否强制隔离（true 时用 10000ms 作为 latency 参与计算，对应最长隔离）；
- `reachable`：Broker 当前是否可达（影响后续队列选择的 `reachableFilter`）。

## 五、tryToFindTopicPublishInfo() 路由查找

发送消息前，必须先知道"这个 Topic 有哪些队列、分布在哪些 Broker 上"，这就是路由查找。

**源码位置**：`DefaultMQProducerImpl.tryToFindTopicPublishInfo()`

```java
private TopicPublishInfo tryToFindTopicPublishInfo(final String topic) {
    // 1. 先查本地缓存
    TopicPublishInfo topicPublishInfo = this.topicPublishInfoTable.get(topic);

    // 2. 缓存不存在或不可用：从 NameServer 拉取
    if (null == topicPublishInfo || !topicPublishInfo.ok()) {
        this.topicPublishInfoTable.putIfAbsent(topic, new TopicPublishInfo());
        this.mQClientFactory.updateTopicRouteInfoFromNameServer(topic);
        topicPublishInfo = this.topicPublishInfoTable.get(topic);
    }

    // 3. 拉到了有效路由，直接返回
    if (topicPublishInfo.isHaveTopicRouterInfo() || topicPublishInfo.ok()) {
        return topicPublishInfo;
    } else {
        // 4. 仍然拉不到：这可能是一个尚未创建的新 Topic
        //    用"默认 Topic"(TBW102)的路由 + 开启自动创建，向 Broker 申请自动建 Topic
        this.mQClientFactory.updateTopicRouteInfoFromNameServer(topic, true, this.defaultMQProducer);
        topicPublishInfo = this.topicPublishInfoTable.get(topic);
        return topicPublishInfo;
    }
}
```

**三级查找策略**：

1. **本地缓存命中**：`topicPublishInfoTable.get(topic)` 且 `ok()`——最快路径，绝大多数发送都走这里。
2. **NameServer 拉取**：缓存 miss 时，调用 `updateTopicRouteInfoFromNameServer(topic)` 去 NameServer 拉最新路由，回填缓存。
3. **默认 Topic 自动创建**：如果 NameServer 上也没有（新 Topic 第一次发送），则用 `defaultMQProducer` 携带默认 Topic（`TBW102`）的路由信息，`isDefault=true` 再拉一次。这一步会触发 Broker 端的"自动建 Topic"逻辑（前提是 Broker 开启了 `autoCreateTopicEnable`）。

**知识点：isHaveTopicRouterInfo 与 ok() 的区别**

- `ok()`：表示"当前有可用的写队列"（`messageQueueList != null && !isEmpty()`）。
- `isHaveTopicRouterInfo`：表示"曾经从 NameServer 拉到过这个 Topic 的路由信息"（即使当前队列列表暂时为空）。

这个区分的意义在于：如果 Topic 确实存在（有路由信息），就不该走"默认 Topic 自动创建"逻辑，避免把一个真实存在但暂时无队列的 Topic 误当成新 Topic。

## 六、sendKernelImpl() 网络发送准备

选好队列后，`sendKernelImpl` 负责"把 Message 变成一个可以通过网络发出的请求"——解析地址、生成 msgId、压缩、构造请求头、执行钩子。

**源码位置**：`DefaultMQProducerImpl.sendKernelImpl()`

```java
private SendResult sendKernelImpl(final Message msg,
    final MessageQueue mq,
    final CommunicationMode communicationMode,
    final SendCallback sendCallback,
    final TopicPublishInfo topicPublishInfo,
    final long timeout) throws MQClientException, RemotingException, MQBrokerException, InterruptedException {

    long beginStartTime = System.currentTimeMillis();

    // 1. 解析 Broker 地址
    String brokerName = this.mQClientFactory.getBrokerNameFromMessageQueue(mq);
    String brokerAddr = this.mQClientFactory.findBrokerAddressInPublish(brokerName);
    if (null == brokerAddr) {
        // 地址找不到，重新拉一次路由再解析
        tryToFindTopicPublishInfo(mq.getTopic());
        brokerName = this.mQClientFactory.getBrokerNameFromMessageQueue(mq);
        brokerAddr = this.mQClientFactory.findBrokerAddressInPublish(brokerName);
    }

    SendMessageContext context = null;
    if (brokerAddr != null) {
        // 2. VIP 通道：若开启，使用 端口-2 的独立通道
        brokerAddr = MixAll.brokerVIPChannel(this.defaultMQProducer.isVipChannelEnabled(), brokerAddr);

        // 保存原始 body，发送后要还原（因为可能被压缩/克隆）
        byte[] prevBody = msg.getBody();
        try {
            // 3. 消息预处理
            // 3.1 生成全局唯一 msgId（批量消息不设，因为每条子消息各自有）
            if (!(msg instanceof MessageBatch)) {
                MessageClientIDSetter.setUniqID(msg);
            }

            // 3.2 命名空间处理
            boolean topicWithNamespace = false;
            if (null != this.mQClientFactory.getClientConfig().getNamespace()) {
                msg.setInstanceId(this.mQClientFactory.getClientConfig().getNamespace());
                topicWithNamespace = true;
            }

            // 3.3 大消息压缩，压缩后在 sysFlag 打上 COMPRESSED_FLAG
            int sysFlag = 0;
            boolean msgBodyCompressed = false;
            if (this.tryToCompressMessage(msg)) {
                sysFlag |= MessageSysFlag.COMPRESSED_FLAG;
                sysFlag |= compressType.getCompressionFlag();
                msgBodyCompressed = true;
            }

            // 3.4 事务预处理标记
            final String tranMsg = msg.getProperty(MessageConst.PROPERTY_TRANSACTION_PREPARED);
            if (Boolean.parseBoolean(tranMsg)) {
                sysFlag |= MessageSysFlag.TRANSACTION_PREPARED_TYPE;
            }

            // 4. 执行钩子（before）
            // 4.1 禁止发送钩子
            if (hasCheckForbiddenHook()) {
                CheckForbiddenContext checkForbiddenContext = new CheckForbiddenContext();
                // ... 填充上下文
                this.executeCheckForbiddenHook(checkForbiddenContext);
            }
            // 4.2 发送消息钩子(before)
            if (this.hasSendMessageHook()) {
                context = new SendMessageContext();
                context.setProducer(this);
                context.setProducerGroup(this.defaultMQProducer.getProducerGroup());
                context.setCommunicationMode(communicationMode);
                context.setBornHost(this.defaultMQProducer.getClientIP());
                context.setBrokerAddr(brokerAddr);
                context.setMessage(msg);
                context.setMq(mq);
                context.setNamespace(this.defaultMQProducer.getNamespace());
                String isTrans = msg.getProperty(MessageConst.PROPERTY_TRANSACTION_PREPARED);
                if (isTrans != null && isTrans.equals("true")) {
                    context.setMsgType(MessageType.Trans_Msg_Half);
                }
                if (msg.getProperty("__STARTDELIVERTIME") != null
                    || msg.getProperty(MessageConst.PROPERTY_DELAY_TIME_LEVEL) != null) {
                    context.setMsgType(MessageType.Delay_Msg);
                }
                this.executeSendMessageHookBefore(context);
            }

            // 5. 构造发送请求头
            SendMessageRequestHeader requestHeader = new SendMessageRequestHeader();
            requestHeader.setProducerGroup(this.defaultMQProducer.getProducerGroup());
            requestHeader.setTopic(msg.getTopic());
            requestHeader.setDefaultTopic(this.defaultMQProducer.getCreateTopicKey());
            requestHeader.setDefaultTopicQueueNums(this.defaultMQProducer.getDefaultTopicQueueNums());
            requestHeader.setQueueId(mq.getQueueId());
            requestHeader.setSysFlag(sysFlag);
            requestHeader.setBornTimestamp(System.currentTimeMillis());
            requestHeader.setFlag(msg.getFlag());
            requestHeader.setProperties(MessageDecoder.messageProperties2String(msg.getProperties()));
            requestHeader.setReconsumeTimes(0);
            requestHeader.setUnitMode(this.isUnitMode());
            requestHeader.setBatch(msg instanceof MessageBatch);
            requestHeader.setBrokerName(brokerName);

            // 5.1 重试 Topic：从消息属性里提取 reconsumeTimes / maxReconsumeTimes
            if (requestHeader.getTopic().startsWith(MixAll.RETRY_GROUP_TOPIC_PREFIX)) {
                String reconsumeTimes = MessageAccessor.getReconsumeTime(msg);
                if (reconsumeTimes != null) {
                    requestHeader.setReconsumeTimes(Integer.valueOf(reconsumeTimes));
                    MessageAccessor.clearProperty(msg, MessageConst.PROPERTY_RECONSUME_TIME);
                }
                String maxReconsumeTimes = MessageAccessor.getMaxReconsumeTimes(msg);
                if (maxReconsumeTimes != null) {
                    requestHeader.setMaxReconsumeTimes(Integer.valueOf(maxReconsumeTimes));
                    MessageAccessor.clearProperty(msg, MessageConst.PROPERTY_MAX_RECONSUME_TIMES);
                }
            }

            // 6. 按通信模式发送
            SendResult sendResult = null;
            switch (communicationMode) {
                case ASYNC:
                    Message tmpMessage = msg;
                    boolean messageCloned = false;
                    if (msgBodyCompressed) {
                        // 压缩过：克隆消息以便发送后还原原始 body
                        tmpMessage = MessageAccessor.cloneMessage(msg);
                        messageCloned = true;
                        msg.setBody(prevBody);
                    }
                    if (topicWithNamespace) {
                        if (!messageCloned) {
                            tmpMessage = MessageAccessor.cloneMessage(msg);
                            messageCloned = true;
                        }
                        msg.setTopic(NamespaceUtil.withoutNamespace(msg.getTopic(),
                            this.mQClientFactory.getClientConfig().getNamespace()));
                    }
                    long costTimeAsync = System.currentTimeMillis() - beginStartTime;
                    if (timeout < costTimeAsync) {
                        throw new RemotingTooMuchRequestException("sendKernelImpl call timeout");
                    }
                    sendResult = this.mQClientFactory.getMQClientAPIImpl().sendMessage(
                        brokerAddr, brokerName, tmpMessage, requestHeader, timeout - costTimeAsync,
                        communicationMode, sendCallback, topicPublishInfo, this.mQClientFactory,
                        this.defaultMQProducer.getRetryTimesWhenSendAsyncFailed(), context, this);
                    break;
                case ONEWAY:
                case SYNC:
                    long costTimeSync = System.currentTimeMillis() - beginStartTime;
                    if (timeout < costTimeSync) {
                        throw new RemotingTooMuchRequestException("sendKernelImpl call timeout");
                    }
                    sendResult = this.mQClientFactory.getMQClientAPIImpl().sendMessage(
                        brokerAddr, brokerName, msg, requestHeader, timeout - costTimeSync,
                        communicationMode, context, this);
                    break;
                default:
                    assert false;
                    break;
            }

            // 7. 执行钩子(after)
            if (this.hasSendMessageHook()) {
                context.setSendResult(sendResult);
                this.executeSendMessageHookAfter(context);
            }
            return sendResult;
        } catch (...) {
            // 异常时也执行 after 钩子
            if (this.hasSendMessageHook()) {
                context.setException(e);
                this.executeSendMessageHookAfter(context);
            }
            throw e;
        } finally {
            // 8. 还原原始 body 与 topic
            msg.setBody(prevBody);
            msg.setTopic(NamespaceUtil.withoutNamespace(msg.getTopic(),
                this.mQClientFactory.getClientConfig().getNamespace()));
        }
    }

    throw new MQClientException("The broker[" + brokerName + "] not exist", null);
}
```

**几个关键设计点**：

1. **VIP 通道（`brokerVIPChannel`）**：RocketMQ 早期为了避免"发送消息"与"拉取消息"抢占同一条 Netty 连接导致互相阻塞，为发送单独开了一条"VIP 通道"，端口是主端口 `-2`。`MixAll.brokerVIPChannel(isVip, addr)` 会把地址端口减 2。新版本默认关闭 VIP。

2. **全局唯一 msgId（`MessageClientIDSetter.setUniqID`）**：客户端在发送前就生成一个全局唯一 ID（基于 IP + 进程 + 时间 + 自增序列），放进消息属性 `UNIQ_KEY`。这是"客户端侧 msgId"，与 Broker 返回的"offsetMsgId"（含物理偏移量）不同。前者用于幂等，后者用于定位物理位置。

3. **压缩与克隆的配合**：如果消息被压缩了，异步发送时会先克隆一份压缩后的消息去发送，然后把原消息 body 还原成未压缩状态——因为异步发送是"发了就返回"，用户可能马上复用这个 Message 对象，必须保证它的 body 是原始的。同步发送则在 `finally` 里统一还原。

4. **请求头的 `defaultTopic`**：即 `createTopicKey`，默认是 `TBW102`。当目标 Topic 不存在时，Broker 会参照这个默认 Topic 的配置来自动创建。

## 七、MQFaultStrategy 容错策略详解

这是 RocketMQ 客户端"高可用"的核心。它解决一个问题：**当某个 Broker 变慢或宕机时，如何让后续消息自动避开它，同时又能在它恢复后重新使用它。**

**源码位置**：`client/src/main/java/org/apache/rocketmq/client/latency/MQFaultStrategy.java`

### 7.1 两个核心数组

```java
// 延迟等级（毫秒）
private long[] latencyMax = {50L, 100L, 550L, 1000L * 2, 1000L * 3, 1000L * 15};
// 实际源码为：{50L, 100L, 550L, 1800L, 3000L, 5000L, 15000L}
private long[] latencyMax = {50L, 100L, 550L, 1800L, 3000L, 5000L, 15000L};

// 对应的隔离时长（毫秒）
private long[] notAvailableDuration = {0L, 0L, 2000L, 5000L, 6000L, 10000L, 30000L};
```

这两个数组是一一对应的"延迟 → 隔离时长"映射表。语义是：

> 如果一次发送耗时落在某个延迟等级，就把该 Broker 隔离对应的时长。耗时越长，说明 Broker 越"病重"，隔离越久。

| 本次发送耗时 ≥ | 隔离时长 |
|---|---|
| 15000ms | 30000ms |
| 5000ms | 10000ms |
| 3000ms | 6000ms |
| 1800ms | 5000ms |
| 550ms | 2000ms |
| 100ms | 0ms |
| 50ms | 0ms |

可见：只有耗时超过 550ms 才会真正被隔离（前两档隔离时长为 0）。一次发送如果超过 15 秒，该 Broker 会被隔离整整 30 秒不再被选中。

### 7.2 computeNotAvailableDuration()

```java
private long computeNotAvailableDuration(final long currentLatency) {
    // 从高到低遍历延迟等级，返回第一个"当前延迟 >= 该等级"对应的隔离时长
    for (int i = latencyMax.length - 1; i >= 0; i--) {
        if (currentLatency >= latencyMax[i]) {
            return this.notAvailableDuration[i];
        }
    }
    return 0;  // 比最小等级还小，不隔离
}
```

从数组尾部（最大延迟）往前扫，找到第一个"当前耗时 ≥ latencyMax[i]"的档位，返回对应隔离时长。这样做保证了"耗时越大匹配到越靠后的档，隔离越久"。

### 7.3 三个过滤器（渐进式）

```java
// 1. Broker 过滤器：借助 ThreadLocal 记住"上次失败的 Broker"，本次选队列时避开它
private final ThreadLocal<BrokerFilter> threadBrokerFilter = ThreadLocal.withInitial(BrokerFilter::new);

// 2. 可达性过滤器：只保留 reachableFlag=true 的 Broker
private QueueFilter reachableFilter = new QueueFilter() {
    @Override
    public boolean filter(MessageQueue mq) {
        return latencyFaultTolerance.isReachable(mq.getBrokerName());
    }
};

// 3. 可用性过滤器：只保留"隔离期已过"的 Broker
private QueueFilter availableFilter = new QueueFilter() {
    @Override
    public boolean filter(MessageQueue mq) {
        return latencyFaultTolerance.isAvailable(mq.getBrokerName());
    }
};
```

三者含义有层次：
- **availableFilter**：最严格——隔离时间已过（`now >= startTimestamp`）。
- **reachableFilter**：中等——探测器认为它网络可达（`reachableFlag=true`）。
- **BrokerFilter**：只避开"上一次刚失败的那个"，粒度最粗。

### 7.4 selectOneMessageQueue() —— 三层兜底

```java
public MessageQueue selectOneMessageQueue(final TopicPublishInfo tpInfo,
    final String lastBrokerName, final boolean resetIndex) {

    BrokerFilter brokerFilter = threadBrokerFilter.get();
    brokerFilter.setLastBrokerName(lastBrokerName);

    if (this.sendLatencyFaultEnable) {
        if (resetIndex) {
            tpInfo.resetIndex();  // 重试时重置轮询下标，重新洗牌
        }
        // 【第一层】可用 且 非上次失败的 Broker（最理想）
        MessageQueue mq = tpInfo.selectOneMessageQueue(availableFilter, brokerFilter);
        if (mq != null) {
            return mq;
        }

        // 【第二层】可达 且 非上次失败的 Broker（退而求其次）
        mq = tpInfo.selectOneMessageQueue(reachableFilter, brokerFilter);
        if (mq != null) {
            return mq;
        }

        // 【第三层】完全兜底：不带任何过滤器，随便选一个
        return tpInfo.selectOneMessageQueue();
    }

    // 未开启延迟容错：只避开上次失败的 Broker
    MessageQueue mq = tpInfo.selectOneMessageQueue(brokerFilter);
    if (mq != null) {
        return mq;
    }
    return tpInfo.selectOneMessageQueue();
}
```

**三层兜底策略**（`sendLatencyFaultEnable=true` 时）：

1. **最优**：`availableFilter + brokerFilter` —— 挑一个"隔离已过期 且 不是上次失败"的队列。
2. **次优**：`reachableFilter + brokerFilter` —— 如果所有 Broker 都还在隔离期，退而挑"网络可达 且 不是上次失败"的。
3. **兜底**：无过滤器 —— 实在没得挑（全都不可达），随便选一个碰运气，总比不发好。

这种"逐级放宽条件"的设计，保证了"正常时避开坏 Broker，极端时也不至于完全发不出去"。

### 7.5 updateFaultItem()

```java
public void updateFaultItem(final String brokerName, final long currentLatency,
    boolean isolation, boolean reachable) {
    if (this.sendLatencyFaultEnable) {
        // isolation=true 时用 10000ms 作为"虚拟延迟"参与计算（映射到 30000ms 隔离）
        // 注意：10000 < 15000，实际映射到 10000 档 → 隔离 30000？
        // 源码用 30000 作为 isolation 的延迟值
        long duration = computeNotAvailableDuration(
            isolation ? this.defaultDurationWhenIsolation : currentLatency);
        this.latencyFaultTolerance.updateFaultItem(brokerName, currentLatency, duration, reachable);
    }
}
```

当 `isolation=true`（发生了网络异常或 Broker 报错），不管实际耗时多少，都用一个较大的固定值（源码中 `defaultDurationWhenIsolation`，逻辑上对应最长隔离）去计算隔离时长，实现"一出错就重罚"。

## 八、LatencyFaultToleranceImpl 故障隔离实现

`MQFaultStrategy` 是"策略"，真正存储每个 Broker 故障状态的是 `LatencyFaultToleranceImpl`。

**源码位置**：`client/src/main/java/org/apache/rocketmq/client/latency/LatencyFaultToleranceImpl.java`

### 8.1 FaultItem 内部类

```java
class FaultItem implements Comparable<FaultItem> {
    private final String name;                  // brokerName
    private volatile long currentLatency;       // 最近一次发送耗时
    private volatile long startTimestamp;       // 隔离结束时间点(now+duration)
    private volatile long checkStamp;           // 下次探测时间点
    private volatile boolean reachableFlag;     // 是否网络可达

    // 隔离期是否已过
    public boolean isAvailable() {
        return System.currentTimeMillis() >= startTimestamp;
    }

    // 只延长隔离，从不缩短
    public void updateNotAvailableDuration(long notAvailableDuration) {
        if (notAvailableDuration > 0) {
            long newStart = System.currentTimeMillis() + notAvailableDuration;
            if (newStart > this.startTimestamp) {
                this.startTimestamp = newStart;
            }
        }
    }

    // 排序：可用优先，然后延迟低优先，最后隔离结束早优先
    @Override
    public int compareTo(final FaultItem other) {
        if (this.isAvailable() != other.isAvailable()) {
            if (this.isAvailable()) return -1;
            if (other.isAvailable()) return 1;
        }
        if (this.currentLatency < other.currentLatency) return -1;
        else if (this.currentLatency > other.currentLatency) return 1;
        if (this.startTimestamp < other.startTimestamp) return -1;
        else if (this.startTimestamp > other.startTimestamp) return 1;
        return 0;
    }
}
```

**知识点：`updateNotAvailableDuration` 为什么"只延长不缩短"？**

设想一个 Broker 已经因为一次超长耗时被隔离 30 秒，此时又来了一次耗时 600ms 的请求（映射隔离 2 秒）。如果允许缩短，隔离就会被改成 2 秒，等于"惩罚被减轻"。而实际上，一个刚被判定为重病的 Broker，不该因为一次偶然的快速响应就提前解禁。所以设计成"取较大值"，只延长不缩短，保证隔离足够保守。

### 8.3 pickOneAtLeast()

```java
public String pickOneAtLeast() {
    // 把所有 FaultItem 收集起来
    final List<FaultItem> tmpList = new LinkedList<>(this.faultItemTable.values());

        Collections.shuffle(tmpList);
        for (FaultItem faultItem : tmpList) {
            if (faultItem.reachableFlag) {
                return faultItem.name;  // 返回第一个可达的
            }
        }
    }
    return null;
}
```

这是"最后一根稻草"——当所有过滤器都选不出队列时，从故障表里随机挑一个"还算可达"的 Broker。`shuffle` 保证了在多个可达 Broker 间做负载分散。

### 9.2 selectOneMessageQueue() —— 带过滤器的轮询

```java
public MessageQueue selectOneMessageQueue(QueueFilter... filter) {
    return selectOneMessageQueue(this.messageQueueList, this.sendWhichQueue, filter);
}

private MessageQueue selectOneMessageQueue(List<MessageQueue> messageQueueList,
    ThreadLocalIndex sendQueue, QueueFilter... filter) {
    if (messageQueueList == null || messageQueueList.isEmpty()) {
        return null;
    }

    if (filter != null && filter.length != 0) {
        // 带过滤器：遍历一轮所有队列，返回第一个"通过全部过滤器"的队列
        for (int i = 0; i < messageQueueList.size(); i++) {
            int index = Math.abs(sendQueue.incrementAndGet() % messageQueueList.size());
            MessageQueue mq = messageQueueList.get(index);
            boolean filterResult = true;
            for (QueueFilter f : filter) {
                Preconditions.checkNotNull(f);
                filterResult &= f.filter(mq);  // 必须通过所有过滤器
            }
            if (filterResult) {
                return mq;
            }
        }
        return null;  // 一轮下来没有满足的
    }

    // 无过滤器：纯轮询，直接按下标取
    int index = Math.abs(sendQueue.incrementAndGet() % messageQueueList.size());
    return messageQueueList.get(index);
}
```

**核心机制**：

1. **轮询（round-robin）**：靠 `ThreadLocalIndex` 的 `incrementAndGet() % size` 实现。之所以用 `ThreadLocal`，是因为多个发送线程各自维护自己的轮询下标，互不干扰，避免竞争。
2. **带过滤器时**：从当前下标开始，最多遍历一整轮，返回第一个通过所有过滤器（如 available + brokerFilter）的队列；一轮内都没有则返回 null，触发上层的降级。
3. **无过滤器时**：纯轮询，直接返回下标对应的队列。
4. **`resetIndex()`**：重试时调用，把轮询计数器重置，让重试从一个新的"随机起点"开始，避免总是撞到同一批队列。

### 10.1 sendMessage() —— 构造 RemotingCommand

```java
public SendResult sendMessage(
    final String addr, final String brokerName, final Message msg,
    final SendMessageRequestHeader requestHeader, final long timeoutMillis,
    final CommunicationMode communicationMode, final SendCallback sendCallback,
    final TopicPublishInfo topicPublishInfo, final MQClientInstance instance,
    final int retryTimesWhenSendFailed, final SendMessageContext context,
    final DefaultMQProducerImpl producer
) throws RemotingException, MQBrokerException, InterruptedException {

    long beginStartTime = System.currentTimeMillis();
    RemotingCommand request = null;
    String msgType = msg.getProperty(MessageConst.PROPERTY_MESSAGE_TYPE);
    boolean isReply = msgType != null && msgType.equals(MixAll.REPLY_MESSAGE_FLAG);

    if (isReply) {
        // 回复消息（RPC 场景）
        if (sendSmartMsg) {
            SendMessageRequestHeaderV2 requestHeaderV2 =
                SendMessageRequestHeaderV2.createSendMessageRequestHeaderV2(requestHeader);
            request = RemotingCommand.createRequestCommand(
                RequestCode.SEND_REPLY_MESSAGE_V2, requestHeaderV2);
        } else {
            request = RemotingCommand.createRequestCommand(
                RequestCode.SEND_REPLY_MESSAGE, requestHeader);
        }
    } else {
        // 普通消息
        if (sendSmartMsg || msg instanceof MessageBatch) {
            // 智能压缩头 / 批量消息：用 V2 紧凑头
            SendMessageRequestHeaderV2 requestHeaderV2 =
                SendMessageRequestHeaderV2.createSendMessageRequestHeaderV2(requestHeader);
            request = RemotingCommand.createRequestCommand(
                msg instanceof MessageBatch ? RequestCode.SEND_BATCH_MESSAGE : RequestCode.SEND_MESSAGE_V2,
                requestHeaderV2);
        } else {
            // 普通单条：V1 头
            request = RemotingCommand.createRequestCommand(
                RequestCode.SEND_MESSAGE, requestHeader);
        }
    }
    // 设置请求体为消息内容
    request.setBody(msg.getBody());

    // 按通信模式分发
    switch (communicationMode) {
        case ONEWAY:
            this.remotingClient.invokeOneway(addr, request, timeoutMillis);
            return null;
        case ASYNC:
            final AtomicInteger times = new AtomicInteger();
            long costTimeAsync = System.currentTimeMillis() - beginStartTime;
            if (timeoutMillis < costTimeAsync) {
                throw new RemotingTooMuchRequestException("sendMessage call timeout");
            }
            this.sendMessageAsync(addr, brokerName, msg, timeoutMillis - costTimeAsync, request,
                sendCallback, topicPublishInfo, instance, retryTimesWhenSendFailed, times, context, producer);
            return null;
        case SYNC:
            long costTimeSync = System.currentTimeMillis() - beginStartTime;
            if (timeoutMillis < costTimeSync) {
                throw new RemotingTooMuchRequestException("sendMessage call timeout");
            }
            return this.sendMessageSync(addr, brokerName, msg, timeoutMillis - costTimeSync, request);
        default:
            assert false;
            break;
    }
    return null;
}
```

**知识点：V1 头 vs V2 头**

`SendMessageRequestHeaderV2` 是 V1 的"紧凑版"——它把字段名从 `producerGroup`、`topic` 这样的长字符串换成了 `a`、`b`、`c` 这种单字母，减少网络传输的字节数。因为发送消息是最高频操作，请求头哪怕省几个字节，在海量 QPS 下也能显著降低带宽。是否使用 V2 由 `sendSmartMsg` 开关控制（默认开启）。

### 10.2 三种通信模式概览

| 模式 | 方法 | 是否等待响应 | 是否有回调 | 返回值 |
|---|---|---|---|---|
| ONEWAY | `invokeOneway` | 否 | 否 | null（不关心结果） |
| ASYNC | `sendMessageAsync` | 否（回调） | 是 | null（结果走回调） |
| SYNC | `sendMessageSync` | 是（阻塞） | 否 | SendResult |

## 十一、sendMessageSync / sendMessageAsync / onExceptionImpl 三种模式

### 11.1 sendMessageSync() —— 同步阻塞

```java
private SendResult sendMessageSync(
    final String addr, final String brokerName, final Message msg,
    final long timeoutMillis, final RemotingCommand request
) throws RemotingException, MQBrokerException, InterruptedException {
    // ★真正的网络 I/O：阻塞等待 Broker 响应
    RemotingCommand response = this.remotingClient.invokeSync(addr, request, timeoutMillis);
    assert response != null;
    // 解析响应
    return this.processSendResponse(brokerName, msg, response, addr);
}
```

这里的 `remotingClient.invokeSync()` 就是 `NettyRemotingClient.invokeSync()`——它会：
1. 把 `request` 编码后写入 Channel；
2. 创建一个 `ResponseFuture` 放进 `responseTable`；
3. 当前线程在 `ResponseFuture` 上 `countDownLatch.await(timeout)` 阻塞；
4. 当 Broker 的响应回来时，Netty 的 IO 线程会根据 `opaque`（请求 ID）找到对应的 `ResponseFuture`，填入响应并 `countDown`，唤醒发送线程。

这是整条链路里"客户端真正发出网络包并等待应答"的地方。

### 11.2 sendMessageAsync() —— 异步回调

```java
private void sendMessageAsync(
    final String addr, final String brokerName, final Message msg, final long timeoutMillis,
    final RemotingCommand request, final SendCallback sendCallback,
    final TopicPublishInfo topicPublishInfo, final MQClientInstance instance,
    final int retryTimesWhenSendFailed, final AtomicInteger times,
    final SendMessageContext context, final DefaultMQProducerImpl producer
) throws InterruptedException, RemotingException {
    final long beginStartTime = System.currentTimeMillis();
    this.remotingClient.invokeAsync(addr, request, timeoutMillis, new InvokeCallback() {
        @Override
        public void operationComplete(final ResponseFuture responseFuture) {
            // 兼容旧接口
        }

        @Override
        public void operationSucceed(RemotingCommand response) {
            long cost = System.currentTimeMillis() - beginStartTime;
            if (null == sendCallback && response != null) {
                // 无回调但成功：仅更新容错
                try {
                    SendResult sendResult = MQClientAPIImpl.this.processSendResponse(brokerName, msg, response, addr);
                    if (context != null && sendResult != null) {
                        context.setSendResult(sendResult);
                        context.getProducer().executeSendMessageHookAfter(context);
                    }
                } catch (Throwable e) {
                }
                producer.updateFaultItem(brokerName, System.currentTimeMillis() - responseFuture.getBeginTimestamp(), false, true);
                return;
            }
            if (response != null) {
                try {
                    // 解析响应
                    SendResult sendResult = MQClientAPIImpl.this.processSendResponse(brokerName, msg, response, addr);
                    assert sendResult != null;
                    if (context != null) {
                        context.setSendResult(sendResult);
                        context.getProducer().executeSendMessageHookAfter(context);
                    }
                    try {
                        // ★回调成功
                        sendCallback.onSuccess(sendResult);
                    } catch (Throwable e) {
                    }
                    // 成功：更新容错(未隔离、可达)
                    producer.updateFaultItem(brokerName, System.currentTimeMillis() - responseFuture.getBeginTimestamp(), false, true);
                } catch (Exception e) {
                    // 解析出错也算失败：更新容错并走重试逻辑
                    producer.updateFaultItem(brokerName, System.currentTimeMillis() - responseFuture.getBeginTimestamp(), true, true);
                    onExceptionImpl(brokerName, msg, timeoutMillis - cost, request, sendCallback, topicPublishInfo,
                        instance, retryTimesWhenSendFailed, times, e, context, false, producer);
                }
            }
        }

        @Override
        public void operationFail(Throwable throwable) {
            long cost = System.currentTimeMillis() - beginStartTime;
            // 失败：先隔离
            producer.updateFaultItem(brokerName, System.currentTimeMillis() - responseFuture.getBeginTimestamp(), true, true);
            if (throwable instanceof RemotingSendRequestException) {
                // 请求根本没发出去：需要重试
                MQClientException ex = new MQClientException("send request failed to " + addr, throwable);
                onExceptionImpl(brokerName, msg, timeoutMillis - cost, request, sendCallback, topicPublishInfo,
                    instance, retryTimesWhenSendFailed, times, ex, context, true, producer);
            } else if (throwable instanceof RemotingTimeoutException) {
                // 超时：需要重试
                MQClientException ex = new MQClientException("wait response timeout " + timeoutMillis + "ms", throwable);
                onExceptionImpl(brokerName, msg, timeoutMillis - cost, request, sendCallback, topicPublishInfo,
                    instance, retryTimesWhenSendFailed, times, ex, context, true, producer);
            } else {
                // 其它异常：除"请求过多"外都重试
                MQClientException ex = new MQClientException("unknown exception", throwable);
                onExceptionImpl(brokerName, msg, timeoutMillis - cost, request, sendCallback, topicPublishInfo,
                    instance, retryTimesWhenSendFailed, times, ex, context,
                    !(throwable instanceof RemotingTooMuchRequestException), producer);
            }
        }
    });
}
```

**异步失败分类**：

| 底层异常 | needRetry | 语义 |
|---|---|---|
| `RemotingSendRequestException` | true | 请求发送失败（连接问题），值得换 Broker 重试 |
| `RemotingTimeoutException` | true | 等待响应超时，值得重试 |
| `RemotingTooMuchRequestException` | false | 客户端主动限流/请求过多，重试也没用 |
| 其它 | true | 兜底重试 |

### 11.3 onExceptionImpl() —— 异步重试的递归实现

这是异步发送**最精妙**的部分。同步的重试在 `sendDefaultImpl` 的 for 循环里，而异步没有循环——它靠**回调里递归调用 `sendMessageAsync`** 实现重试。

```java
private void onExceptionImpl(final String brokerName, final Message msg, final long timeoutMillis,
    final RemotingCommand request, final SendCallback sendCallback, final TopicPublishInfo topicPublishInfo,
    final MQClientInstance instance, final int timesTotal, final AtomicInteger curTimes,
    final Exception e, final SendMessageContext context, final boolean needRetry,
    final DefaultMQProducerImpl producer) {

    // 重试次数 +1
    int tmp = curTimes.incrementAndGet();

    if (needRetry && tmp <= timesTotal && timeoutMillis > 0) {
        // 满足重试条件：换一个 Broker 递归重发
        String retryBrokerName = brokerName;  // 默认还是原 Broker
        if (topicPublishInfo != null) {
            // 选一个新队列（避开当前 brokerName）
            MessageQueue mqChosen = producer.selectOneMessageQueue(topicPublishInfo, brokerName, false);
            retryBrokerName = instance.getBrokerNameFromMessageQueue(mqChosen);
        }
        // 解析新 Broker 地址
        String addr = instance.findBrokerAddressInPublish(retryBrokerName);
        log.warn("async send msg by retry {} times. topic={}, brokerAddr={}, brokerName={}",
            tmp, msg.getTopic(), addr, retryBrokerName, e);
        // ★关键：换一个新的请求 ID，避免与上一次的响应表项冲突
        request.setOpaque(RemotingCommand.createNewRequestId());
        try {
            // ★递归重发
            sendMessageAsync(addr, retryBrokerName, msg, timeoutMillis, request, sendCallback,
                topicPublishInfo, instance, timesTotal, curTimes, context, producer);
        } catch (InterruptedException e1) {
            onExceptionImpl(retryBrokerName, msg, timeoutMillis, request, sendCallback, topicPublishInfo,
                instance, timesTotal, curTimes, e1, context, false, producer);
        } catch (RemotingConnectException e1) {
            producer.updateFaultItem(brokerName, 3000, true, true);
            onExceptionImpl(retryBrokerName, msg, timeoutMillis, request, sendCallback, topicPublishInfo,
                instance, timesTotal, curTimes, e1, context, true, producer);
        } catch (Throwable e1) {
            producer.updateFaultItem(brokerName, 3000, true, false);
            onExceptionImpl(retryBrokerName, msg, timeoutMillis, request, sendCallback, topicPublishInfo,
                instance, timesTotal, curTimes, e1, context, false, producer);
        }
    } else {
        // 重试次数用尽 或 不需重试：最终失败，回调 onException
        if (context != null) {
            context.setException(e);
            context.getProducer().executeSendMessageHookAfter(context);
        }
        try {
            sendCallback.onException(e);
        } catch (Exception ignored) {
        }
    }
}
```

**知识点：为什么异步重试要 `setOpaque(createNewRequestId())`？**

`opaque` 是请求的唯一 ID，Netty 用它把"响应"匹配回"请求"（`responseTable` 里以 opaque 为 key）。上一次异步请求失败（比如超时）后，它的 opaque 可能还残留在响应表里，或者迟到的响应还会回来。如果重试沿用同一个 opaque，就可能出现"新请求的响应"和"旧请求的迟到响应"互相串扰。所以每次重试都生成一个全新的 opaque，保证请求-响应一一对应，互不干扰。

**知识点：同步重试 vs 异步重试**

| 维度 | 同步（SYNC） | 异步（ASYNC） |
|---|---|---|
| 重试位置 | `sendDefaultImpl` 的 for 循环 | `onExceptionImpl` 递归 |
| 重试次数 | `retryTimesWhenSendFailed`（默认2） | `retryTimesWhenSendAsyncFailed`（默认2） |
| 阻塞与否 | 发送线程阻塞等待 | 发送线程立即返回，回调线程处理 |
| 换 Broker | 每次循环重新 selectOneMessageQueue | 每次递归重新 selectOneMessageQueue |

## 十二、processSendResponse() 响应处理

无论同步还是异步，收到 Broker 的响应后都要经过 `processSendResponse` 把 `RemotingCommand` 翻译成用户可见的 `SendResult`。

**源码位置**：`MQClientAPIImpl.processSendResponse()`

```java
private SendResult processSendResponse(
    final String brokerName, final Message msg,
    final RemotingCommand response, final String addr
) throws MQBrokerException, RemotingCommandException {
    SendStatus sendStatus;
    switch (response.getCode()) {
        case ResponseCode.FLUSH_DISK_TIMEOUT:
            sendStatus = SendStatus.FLUSH_DISK_TIMEOUT;
            break;
        case ResponseCode.FLUSH_SLAVE_TIMEOUT:
            sendStatus = SendStatus.FLUSH_SLAVE_TIMEOUT;
            break;
        case ResponseCode.SLAVE_NOT_AVAILABLE:
            sendStatus = SendStatus.SLAVE_NOT_AVAILABLE;
            break;
        case ResponseCode.SUCCESS:
            sendStatus = SendStatus.SEND_OK;
            break;
        default:
            // 其它任何码都视为失败，抛 MQBrokerException
            throw new MQBrokerException(response.getCode(), response.getRemark(), addr);
    }

    SendMessageResponseHeader responseHeader =
        (SendMessageResponseHeader) response.decodeCommandCustomHeader(SendMessageResponseHeader.class);

    // 处理静态 Topic（逻辑队列）的 topic/queueId 重映射
    String topic = msg.getTopic();
    MessageQueue messageQueue = new MessageQueue(topic, brokerName, responseHeader.getQueueId());

    // 客户端侧唯一 msgId（UNIQ_KEY）
    String uniqMsgId = MessageClientIDSetter.getUniqID(msg);
    if (msg instanceof MessageBatch) {
        // 批量消息：拼接每条的 uniqId
        StringBuilder sb = new StringBuilder();
        for (Message message : (MessageBatch) msg) {
            sb.append(sb.length() == 0 ? "" : ",").append(MessageClientIDSetter.getUniqID(message));
        }
        uniqMsgId = sb.toString();
    }

    // 构造 SendResult
    SendResult sendResult = new SendResult(sendStatus,
        uniqMsgId,                          // 客户端唯一 msgId
        responseHeader.getMsgId(),          // offsetMsgId（含物理偏移，Broker 生成）
        messageQueue,                       // 消息落到的队列
        responseHeader.getQueueOffset());   // 队列逻辑偏移
    sendResult.setTransactionId(responseHeader.getTransactionId());
    sendResult.setRecallHandle(responseHeader.getRecallHandle());

    // regionId / traceOn 从响应扩展字段读取
    String regionId = response.getExtFields() == null ? null
        : response.getExtFields().get(MessageConst.PROPERTY_MSG_REGION);
    String traceOn = response.getExtFields() == null ? null
        : response.getExtFields().get(MessageConst.PROPERTY_TRACE_SWITCH);
    if (regionId == null || regionId.isEmpty()) {
        regionId = MixAll.DEFAULT_TRACE_REGION_ID;
    }
    sendResult.setTraceOn(!Boolean.FALSE.toString().equals(traceOn));
    sendResult.setRegionId(regionId);
    return sendResult;
}
```

**响应码到 SendStatus 的映射**：

| ResponseCode | SendStatus | 含义 |
|---|---|---|
| `SUCCESS` | `SEND_OK` | 完全成功 |
| `FLUSH_DISK_TIMEOUT` | `FLUSH_DISK_TIMEOUT` | 同步刷盘超时（消息已写入内存但落盘慢） |
| `FLUSH_SLAVE_TIMEOUT` | `FLUSH_SLAVE_TIMEOUT` | 同步复制到 Slave 超时 |
| `SLAVE_NOT_AVAILABLE` | `SLAVE_NOT_AVAILABLE` | Slave 不可用（无法同步复制） |
| 其它 | —— | 抛 `MQBrokerException` |

**知识点：两个 msgId 的区别**

- `uniqMsgId`（`UNIQ_KEY`）：**客户端生成**，发送前就有，用于业务幂等、消息追踪。
- `offsetMsgId`（`responseHeader.getMsgId()`）：**Broker 生成**，包含 Broker IP + 物理偏移量，可以直接反解出消息在 CommitLog 中的物理位置，运维排查时用它精准定位。

注意：`FLUSH_DISK_TIMEOUT`、`FLUSH_SLAVE_TIMEOUT`、`SLAVE_NOT_AVAILABLE` 这三种状态**消息其实已经写入了主节点内存**，只是刷盘/复制没在超时内完成。业务需要根据可靠性要求决定是否重发（重发可能导致重复，需配合幂等）。

### 13.2 startScheduledTask() —— 五大定时任务

```java
private void startScheduledTask() {
    // 任务1：每 2 分钟从 HTTP 端点刷新 NameServer 地址（若未静态配置）
    if (null == this.clientConfig.getNamesrvAddr()) {
        this.scheduledExecutorService.scheduleAtFixedRate(() -> {
            try {
                MQClientInstance.this.mQClientAPIImpl.fetchNameServerAddr();
            } catch (Exception e) {
                log.error("ScheduledTask fetchNameServerAddr exception", e);
            }
        }, 1000 * 10, 1000 * 60 * 2, TimeUnit.MILLISECONDS);
    }

    // 任务2：每 pollNameServerInterval(默认30s) 更新所有 Topic 的路由
    this.scheduledExecutorService.scheduleAtFixedRate(() -> {
        try {
            MQClientInstance.this.updateTopicRouteInfoFromNameServer();
        } catch (Exception e) {
            log.error("ScheduledTask updateTopicRouteInfoFromNameServer exception", e);
        }
    }, 10, this.clientConfig.getPollNameServerInterval(), TimeUnit.MILLISECONDS);

    // 任务3：每 heartbeatBrokerInterval(默认30s) 清理下线 Broker + 发送心跳
    this.scheduledExecutorService.scheduleAtFixedRate(() -> {
        try {
            MQClientInstance.this.cleanOfflineBroker();
            MQClientInstance.this.sendHeartbeatToAllBrokerWithLockV2(false);
        } catch (Exception e) {
            log.error("ScheduledTask sendHeartbeatToAllBroker exception", e);
        }
    }, 1000, this.clientConfig.getHeartbeatBrokerInterval(), TimeUnit.MILLISECONDS);

    // 任务4：每 persistConsumerOffsetInterval(默认5s) 持久化消费位点
    this.scheduledExecutorService.scheduleAtFixedRate(() -> {
        try {
            MQClientInstance.this.persistAllConsumerOffset();
        } catch (Exception e) {
            log.error("ScheduledTask persistAllConsumerOffset exception", e);
        }
    }, 1000 * 10, this.clientConfig.getPersistConsumerOffsetInterval(), TimeUnit.MILLISECONDS);

    // 任务5：每 1 分钟调整消费线程池大小
    this.scheduledExecutorService.scheduleAtFixedRate(() -> {
        try {
            MQClientInstance.this.adjustThreadPool();
        } catch (Exception e) {
            log.error("ScheduledTask adjustThreadPool exception", e);
        }
    }, 1, 1, TimeUnit.MINUTES);
}
```

**五大定时任务一览**：

| 任务 | 周期 | 作用 |
|---|---|---|
| fetchNameServerAddr | 2 分钟 | 动态刷新 NameServer 地址（HTTP 寻址时） |
| updateTopicRouteInfoFromNameServer | 30 秒 | 刷新本地路由缓存（这就是路由"最终一致"的来源） |
| cleanOfflineBroker + sendHeartbeat | 30 秒 | 剔除下线 Broker + 心跳保活 |
| persistAllConsumerOffset | 5 秒 | 持久化消费位点 |
| adjustThreadPool | 1 分钟 | 动态调整消费线程池 |

**知识点：路由的最终一致性**

Producer 的路由不是实时的——它靠"每 30 秒刷新一次"和"发送时 miss 才拉取"两种方式更新。这意味着 Topic 扩容/Broker 上下线后，最长可能有 30 秒的路由"陈旧窗口"。这段时间内发送可能命中已下线的 Broker，此时就靠前面讲的"容错重试"机制来兜底。

### 14.1 processRequest() —— 请求分发

```java
@Override
public RemotingCommand processRequest(ChannelHandlerContext ctx,
    RemotingCommand request) throws RemotingCommandException {
    SendMessageContext sendMessageContext;
    switch (request.getCode()) {
        case RequestCode.CONSUMER_SEND_MSG_BACK:
            // 消费失败回传：单独处理
            return this.consumerSendMsgBack(ctx, request);
        default:
            // 普通发送
            SendMessageRequestHeader requestHeader = parseRequestHeader(request);
            if (requestHeader == null) {
                return null;
            }
            TopicQueueMappingContext mappingContext =
                this.brokerController.getTopicQueueMappingManager().buildTopicQueueMappingContext(requestHeader, true);
            RemotingCommand rewriteResult =
                this.brokerController.getTopicQueueMappingManager().rewriteRequestForStaticTopic(requestHeader, mappingContext);
            if (rewriteResult != null) {
                return rewriteResult;
            }
            // 构造发送上下文
            sendMessageContext = buildMsgContext(ctx, requestHeader, request);
            try {
                // 执行发送前钩子
                this.executeSendMessageHookBefore(sendMessageContext);
            } catch (AbortProcessException e) {
                final RemotingCommand errorResponse = RemotingCommand.createResponseCommand(e.getResponseCode(), e.getErrorMessage());
                errorResponse.setOpaque(request.getOpaque());
                return errorResponse;
            }
            // 清理保留属性（防止客户端伪造系统属性）
            clearReservedProperties(requestHeader);

            RemotingCommand response;
            if (requestHeader.isBatch()) {
                // 批量消息
                response = this.sendBatchMessage(ctx, request, sendMessageContext, requestHeader, mappingContext,
                    (ctx1, response1) -> executeSendMessageHookAfter(response1, ctx1));
            } else {
                // 单条消息
                response = this.sendMessage(ctx, request, sendMessageContext, requestHeader, mappingContext,
                    (ctx12, response12) -> executeSendMessageHookAfter(response12, ctx12));
            }
            return response;
    }
}
```

`rejectRequest()` 在业务线程池处理请求前被调用，用于"快速失败"——当 Broker 已经过载（PageCache 忙、存储池不足）或角色不对（Slave 不该收写），直接拒绝，避免请求进入队列继续堆积。被拒绝的请求会收到 `SYSTEM_BUSY`，客户端据此换 Broker 重试。

### 14.3 sendMessage() —— 核心处理

```java
public RemotingCommand sendMessage(final ChannelHandlerContext ctx,
    final RemotingCommand request, final SendMessageContext sendMessageContext,
    final SendMessageRequestHeader requestHeader, final TopicQueueMappingContext mappingContext,
    final SendMessageCallback sendMessageCallback) throws RemotingCommandException {

    // 1. 前置处理：时间戳校验 + msgCheck()
    final RemotingCommand response = preSend(ctx, request, requestHeader);
    if (response.getCode() != -1) {
        // code != -1 说明校验失败，直接返回
        return response;
    }
    final SendMessageResponseHeader responseHeader = (SendMessageResponseHeader) response.readCustomHeader();

    final byte[] body = request.getBody();

    // 2. 队列选择：queueIdInt < 0 时随机选一个写队列
    int queueIdInt = requestHeader.getQueueId();
    TopicConfig topicConfig = this.brokerController.getTopicConfigManager().selectTopicConfig(requestHeader.getTopic());
    if (queueIdInt < 0) {
        queueIdInt = randomQueueId(topicConfig.getWriteQueueNums());
    }

    // 3. 构造 Broker 内部消息对象
    MessageExtBrokerInner msgInner = new MessageExtBrokerInner();
    msgInner.setTopic(requestHeader.getTopic());
    msgInner.setQueueId(queueIdInt);

    // 3.1 重试与死信判定
    Map<String, String> oriProps = MessageDecoder.string2messageProperties(requestHeader.getProperties());
    if (!handleRetryAndDLQ(requestHeader, response, request, msgInner, topicConfig, oriProps)) {
        return response;
    }

    msgInner.setBody(body);
    msgInner.setFlag(requestHeader.getFlag());
    // 处理 lite topic 多分发
    ...
    MessageAccessor.setProperties(msgInner, oriProps);
    msgInner.setBornTimestamp(requestHeader.getBornTimestamp());
    msgInner.setBornHost(ctx.channel().remoteAddress());
    msgInner.setStoreHost(this.getStoreHost());
    msgInner.setReconsumeTimes(requestHeader.getReconsumeTimes() == null ? 0 : requestHeader.getReconsumeTimes());
    String clusterName = this.brokerController.getBrokerConfig().getBrokerClusterName();
    MessageAccessor.putProperty(msgInner, MessageConst.PROPERTY_CLUSTER, clusterName);
    msgInner.setPropertiesString(MessageDecoder.messageProperties2String(msgInner.getProperties()));
    // 计算 tagsCode
    msgInner.setTagsCode(MessageExtBrokerInner.tagsString2tagsCode(...));

    // 4. 事务预处理
    boolean sendTransactionPrepareMessage = false;
    String traFlag = oriProps.get(MessageConst.PROPERTY_TRANSACTION_PREPARED);
    if (Boolean.parseBoolean(traFlag)
        && !(msgInner.getReconsumeTimes() > 0 && msgInner.getDelayTimeLevel() > 0)) {
        // 是事务半消息
        sendTransactionPrepareMessage = true;
    }

    long beginTimeMillis = this.brokerController.getMessageStore().now();

    // 5. 存储
    if (brokerController.getBrokerConfig().isAsyncSendEnable()) {
        // ★异步存储路径（默认）
        CompletableFuture<PutMessageResult> asyncPutMessageFuture;
        if (sendTransactionPrepareMessage) {
            asyncPutMessageFuture = this.brokerController.getTransactionalMessageService().asyncPrepareMessage(msgInner);
        } else {
            asyncPutMessageFuture = this.brokerController.getMessageStore().asyncPutMessage(msgInner);
        }

        final int finalQueueIdInt = queueIdInt;
        final MessageExtBrokerInner finalMsgInner = msgInner;
        asyncPutMessageFuture.thenAcceptAsync(putMessageResult -> {
            RemotingCommand responseFuture =
                handlePutMessageResult(putMessageResult, response, request, finalMsgInner, responseHeader,
                    sendMessageContext, ctx, finalQueueIdInt, beginTimeMillis, mappingContext, BrokerMetricsManager.getMessageType(requestHeader));
            if (responseFuture != null) {
                doResponse(ctx, request, responseFuture);  // 异步回写响应
            }
            // 释放消息体引用
            sendMessageCallback.onComplete(sendMessageContext, response);
        }, this.brokerController.getPutMessageFutureExecutor());
        // ★立即返回 null：不占用 Netty 业务线程，等存储完成再异步回写
        return null;
    } else {
        // 同步存储路径
        PutMessageResult putMessageResult = null;
        if (sendTransactionPrepareMessage) {
            putMessageResult = this.brokerController.getTransactionalMessageService().prepareMessage(msgInner);
        } else {
            putMessageResult = this.brokerController.getMessageStore().putMessage(msgInner);
        }
        handlePutMessageResult(putMessageResult, response, request, msgInner, responseHeader, sendMessageContext, ctx,
            queueIdInt, beginTimeMillis, mappingContext, BrokerMetricsManager.getMessageType(requestHeader));
        sendMessageCallback.onComplete(sendMessageContext, response);
        return response;
    }
}
```

## 十五、msgCheck() 校验逻辑

**源码位置**：`broker/src/main/java/org/apache/rocketmq/broker/processor/AbstractSendMessageProcessor.java`

```java
protected RemotingCommand msgCheck(final ChannelHandlerContext ctx,
    final SendMessageRequestHeader requestHeader, final RemotingCommand request,
    final RemotingCommand response) {

    // 1. 权限校验：Broker 不可写 且 是顺序 Topic → 无权限
    if (!PermName.isWriteable(this.brokerController.getBrokerConfig().getBrokerPermission())
        && this.brokerController.getTopicConfigManager().isOrderTopic(requestHeader.getTopic())) {
        response.setCode(ResponseCode.NO_PERMISSION);
        response.setRemark("the broker[" + this.brokerController.getBrokerConfig().getBrokerIP1()
            + "] sending message is forbidden");
        return response;
    }

    // 2. Topic 名称合法性校验
    TopicValidator.ValidateTopicResult result = TopicValidator.validateTopic(requestHeader.getTopic());
    if (!result.isValid()) {
        response.setCode(ResponseCode.SYSTEM_ERROR);
        response.setRemark(result.getRemark());
        return response;
    }

    // 3. 禁止发送的系统 Topic 校验
    if (TopicValidator.isNotAllowedSendTopic(requestHeader.getTopic())) {
        response.setCode(ResponseCode.NO_PERMISSION);
        response.setRemark("Sending message to topic[" + requestHeader.getTopic() + "] is forbidden.");
        return response;
    }

    // 4. 查找 Topic 配置
    TopicConfig topicConfig =
        this.brokerController.getTopicConfigManager().selectTopicConfig(requestHeader.getTopic());
    if (null == topicConfig) {
        // 5. Topic 不存在：尝试自动创建
        int topicSysFlag = 0;
        if (requestHeader.isUnitMode()) {
            if (requestHeader.getTopic().startsWith(MixAll.RETRY_GROUP_TOPIC_PREFIX)) {
                topicSysFlag = TopicSysFlag.buildSysFlag(false, true);
            } else {
                topicSysFlag = TopicSysFlag.buildSysFlag(true, false);
            }
        }
        if (requestHeader.getTopic().startsWith(MixAll.RETRY_GROUP_TOPIC_PREFIX)) {
            // 重试 Topic 用专门方法创建
            topicConfig = this.brokerController.getTopicConfigManager().createTopicInSendMessageBackMethod(
                requestHeader.getTopic(), 1, PermName.PERM_WRITE | PermName.PERM_READ, false, topicSysFlag);
        } else {
            // 普通 Topic：参照默认 Topic(AUTO_CREATE_TOPIC_KEY_TOPIC)自动创建
            topicConfig = this.brokerController.getTopicConfigManager().createTopicInSendMessageMethod(
                requestHeader.getTopic(), requestHeader.getDefaultTopic(),
                RemotingHelper.parseChannelRemoteAddr(ctx.channel()),
                requestHeader.getDefaultTopicQueueNums(), topicSysFlag);
        }
        if (null == topicConfig) {
            response.setCode(ResponseCode.TOPIC_NOT_EXIST);
            response.setRemark("topic[" + requestHeader.getTopic() + "] not exist, apply first please!");
            return response;
        }
    }

    // 6. 队列 ID 校验：不能超过 max(读队列数, 写队列数)
    int queueIdInt = requestHeader.getQueueId();
    int idValid = Math.max(topicConfig.getWriteQueueNums(), topicConfig.getReadQueueNums());
    if (queueIdInt >= idValid) {
        response.setCode(ResponseCode.SYSTEM_ERROR);
        response.setRemark("request queueId[" + queueIdInt + "] is illegal, ...");
        return response;
    }
    return response;
}
```

**六步校验**：

1. **权限校验**：不可写 Broker 拒绝顺序 Topic 的写入。
2. **Topic 名称合法性**：长度、字符集校验。
3. **禁止发送的系统 Topic**：如 `SCHEDULE_TOPIC_XXXX` 等内部 Topic 不允许直接发送。
4. **Topic 配置查找**：从 `TopicConfigManager` 查本地 Topic 配置。
5. **自动创建 Topic**：Topic 不存在时，参照默认 Topic 模板自动创建（这就是"发送时自动建 Topic"的服务端实现）。
6. **队列 ID 校验**：客户端指定的 queueId 不能超过 Topic 的最大队列数。

**知识点：自动创建 Topic 的两条路径**

- 普通 Topic：走 `createTopicInSendMessageMethod`，参照 `AUTO_CREATE_TOPIC_KEY_TOPIC`（`TBW102`）模板，继承默认队列数和权限。这要求 Broker 开启 `autoCreateTopicEnable`（生产环境建议关闭）。
- 重试 Topic（`%RETRY%` 前缀）：走 `createTopicInSendMessageBackMethod`，队列数固定为 1。重试 Topic 的自动创建始终允许，因为消费重试是框架内部行为。

## 十六、handleRetryAndDLQ() 重试与死信

**源码位置**：`SendMessageProcessor.java`

```java
private boolean handleRetryAndDLQ(SendMessageRequestHeader requestHeader, RemotingCommand response,
    RemotingCommand request, MessageExt msg, TopicConfig topicConfig, Map<String, String> properties) {
    String newTopic = requestHeader.getTopic();
    // 只处理重试 Topic
    if (null != newTopic && newTopic.startsWith(MixAll.RETRY_GROUP_TOPIC_PREFIX)) {
        String groupName = newTopic.substring(MixAll.RETRY_GROUP_TOPIC_PREFIX.length());
        // 1. 查订阅组配置
        SubscriptionGroupConfig subscriptionGroupConfig =
            this.brokerController.getSubscriptionGroupManager().findSubscriptionGroupConfig(groupName);
        if (null == subscriptionGroupConfig) {
            response.setCode(ResponseCode.SUBSCRIPTION_GROUP_NOT_EXIST);
            response.setRemark("subscription group not exist, " + groupName + " " + FAQUrl.suggestTodo(FAQUrl.SUBSCRIPTION_GROUP_NOT_EXIST));
            return false;
        }

        // 2. 计算最大重试次数（请求头优先，否则用订阅组配置）
        int maxReconsumeTimes = subscriptionGroupConfig.getRetryMaxTimes();
        if (request.getVersion() >= MQVersion.Version.V3_4_9.ordinal()) {
            Integer times = requestHeader.getMaxReconsumeTimes();
            if (times != null) {
                maxReconsumeTimes = times;
            }
        }
        int reconsumeTimes = requestHeader.getReconsumeTimes() == null ? 0 : requestHeader.getReconsumeTimes();

        // 3. 超过最大重试次数 或 顺序消息锁未过期 → 转投死信队列
        if (reconsumeTimes > maxReconsumeTimes || isBornForDLQ(...)) {
            properties.put(MessageConst.PROPERTY_DELAY_TIME_LEVEL, "-1");
            // 死信 Topic：%DLQ% + 消费组名
            newTopic = MixAll.getDLQTopic(groupName);
            int queueIdInt = randomQueueId(DLQ_NUMS_PER_GROUP);
            // 4. 创建死信 Topic（如不存在）
            topicConfig = this.brokerController.getTopicConfigManager().createTopicInSendMessageBackMethod(newTopic,
                DLQ_NUMS_PER_GROUP, PermName.PERM_WRITE | PermName.PERM_READ, false, 0);
            if (null == topicConfig) {
                response.setCode(ResponseCode.SYSTEM_ERROR);
                response.setRemark("topic[" + newTopic + "] not exist");
                return false;
            }
            msg.setDelayTimeLevel(0);
        }
    }
    int sysFlag = requestHeader.getSysFlag();
    if (TopicFilterType.MULTI_TAG == topicConfig.getTopicFilterType()) {
        sysFlag |= MessageSysFlag.MULTI_TAGS_FLAG;
    }
    msg.setTopic(newTopic);
    msg.setQueueId(...);
    ...
    return true;
}
```

**重试与死信的流转逻辑**：

```
消费失败
  → Consumer 回传 CONSUMER_SEND_MSG_BACK
    → Broker 将消息投递到 %RETRY%<consumerGroup>
      → 按 delayLevel 延迟后重新投递给消费者
        → 再次失败，reconsumeTimes++
          → 当 reconsumeTimes > maxReconsumeTimes(默认16)
            → 转投 %DLQ%<consumerGroup>（死信队列，需人工干预）
```

**知识点：死信队列（DLQ）**

- DLQ Topic 命名：`%DLQ%` + 消费组名。
- DLQ 队列数固定为 `DLQ_NUMS_PER_GROUP`（1）。
- DLQ 消息的 `delayTimeLevel` 被设为 -1（不再参与延迟重投）。
- DLQ 消息默认**只写不读**（权限 `PERM_WRITE | PERM_READ` 但业务上不消费），需要人工排查后手动处理。

## 十八、异步发送的 CompletableFuture 链

默认配置下（`isAsyncSendEnable()=true`），Broker 端存储走的是完全异步的 `CompletableFuture` 链，这是 RocketMQ 高吞吐的关键设计之一。

### 18.1 为什么要异步存储？

Netty 的业务线程池（`SendMessageProcessor` 运行所在的线程）数量有限。如果每个发送请求都在业务线程里**同步等待刷盘/复制完成**，那么在同步刷盘或同步复制模式下，业务线程会被 I/O 阻塞，线程池很快耗尽，吞吐量急剧下降。

异步存储的思路是：

```
Netty 业务线程                    存储线程池(putMessageFutureExecutor)
     |                                       |
  接收请求                                   |
  校验/构造 msgInner                         |
  asyncPutMessage() -----返回Future----->    |
  thenAcceptAsync(处理结果, 存储线程池)        |
  return null  ← 立即释放业务线程              |
     |                                       |
  (处理下一个请求)                     刷盘/复制完成
                                     handlePutMessageResult()
                                     doResponse() 回写响应
```

业务线程只负责"接收 + 校验 + 提交存储任务"，然后立即返回 `null` 释放自己，去处理下一个请求。真正耗时的"刷盘 + 复制 + 回写响应"由存储线程池 `putMessageFutureExecutor` 完成。

### 18.2 CompletableFuture 链的关键代码

```java
CompletableFuture<PutMessageResult> asyncPutMessageFuture =
    this.brokerController.getMessageStore().asyncPutMessage(msgInner);

asyncPutMessageFuture.thenAcceptAsync(putMessageResult -> {
    // 这个 lambda 在 putMessageFutureExecutor 线程池执行
    RemotingCommand responseFuture =
        handlePutMessageResult(putMessageResult, response, request, finalMsgInner, responseHeader,
            sendMessageContext, ctx, finalQueueIdInt, beginTimeMillis, mappingContext, ...);
    if (responseFuture != null) {
        doResponse(ctx, request, responseFuture);
    }
    sendMessageCallback.onComplete(sendMessageContext, response);
}, this.brokerController.getPutMessageFutureExecutor());

return null;  // 立即释放 Netty 业务线程
```

**要点**：

1. `asyncPutMessage()` 内部又是一条 CompletableFuture 链：`CommitLog.asyncPutMessage()` → 写入 MappedFile → `submitFlushRequest()`（刷盘 Future）→ `submitReplicaRequest()`（复制 Future）→ 三者组合。
2. `thenAcceptAsync(action, executor)` 指定了回调执行的线程池是 `putMessageFutureExecutor`，而不是默认的 ForkJoinPool，保证存储回调不会污染其它线程池。
3. `return null` 是异步模式的灵魂——它告诉 Netty 框架"响应稍后由我自己通过 `doResponse` 回写，你不用管"。

### 18.3 asyncPutMessage 内部的 Future 组合（简化）

```java
// CommitLog.asyncPutMessage() 简化示意
public CompletableFuture<PutMessageResult> asyncPutMessage(MessageExtBrokerInner msg) {
    // 1. 写入 MappedFile（内存映射）
    AppendMessageResult result = mappedFile.appendMessage(msg, ...);
    PutMessageResult putMessageResult = new PutMessageResult(PutMessageStatus.PUT_OK, result);

    // 2. 刷盘 Future
    CompletableFuture<PutMessageStatus> flushResultFuture = submitFlushRequest(result, msg);
    // 3. 复制 Future（HA / 同步复制）
    CompletableFuture<PutMessageStatus> replicaResultFuture = submitReplicaRequest(result, msg);

    // 4. 组合：两者都完成后，取最"坏"的状态作为最终状态
    return flushResultFuture.thenCombine(replicaResultFuture, (flushStatus, replicaStatus) -> {
        if (flushStatus != PutMessageStatus.PUT_OK) {
            putMessageResult.setPutMessageStatus(flushStatus);   // 如 FLUSH_DISK_TIMEOUT
        }
        if (replicaStatus != PutMessageStatus.PUT_OK) {
            putMessageResult.setPutMessageStatus(replicaStatus); // 如 FLUSH_SLAVE_TIMEOUT / SLAVE_NOT_AVAILABLE
        }
        return putMessageResult;
    });
}
```

这解释了为什么 `PutMessageStatus` 会出现 `FLUSH_DISK_TIMEOUT` / `FLUSH_SLAVE_TIMEOUT`——它们分别来自刷盘 Future 和复制 Future 的超时结果，通过 `thenCombine` 合并进最终结果。

**知识点：批量消息的限制**

批量消息（`MessageBatch`）有诸多限制：同一批消息必须属于**同一个 Topic**、**同一个刷盘方式**、**不能是延迟消息或事务消息**、总大小不超过 `maxMessageSize`（默认 4MB）。这些限制在客户端 `batch()` 打包时和服务端校验时都会检查。批量的价值在于用一次网络往返发送多条消息，显著降低网络开销、提升吞吐。

### 19.2 核心设计思想

**1. 门面模式（Facade）**

`DefaultMQProducer` 是门面，所有逻辑委托给 `DefaultMQProducerImpl`。用户面对简洁的 API，复杂实现被隐藏。这与 Dubbo 的 `ReferenceConfig` / `ServiceConfig` 门面思路一致。

**2. 客户端容错（MQFaultStrategy）**

通过 `latencyMax` 和 `notAvailableDuration` 两个数组，把"发送延迟"映射为"隔离时长"。延迟越高，隔离越久（15s 延迟 → 隔离 30s）。三级 fallback（available → reachable → 任意）保证即使所有 Broker 都被标记过故障，也总能选出一个队列，不会死锁。这是"尽力而为"的可用性设计。

**3. 故障探测（LatencyFaultToleranceImpl）**

除了被动隔离，还有主动探测：每 3 秒对被隔离的 Broker 发起 `getMaxOffset` 探测，一旦恢复就提前解除隔离，不必等到隔离期满。`FaultItem.compareTo` 保证选队列时优先选"可用、低延迟、隔离结束早"的 Broker。

**4. 同步 vs 异步重试**

同步靠 for 循环重试，异步靠回调递归重试。异步重试每次都换新 opaque，避免请求响应串扰。两者都通过 `selectOneMessageQueue` 换 Broker，规避故障节点。

**5. 路由最终一致**

Producer 路由靠"30 秒定时刷新 + miss 时拉取"更新，存在陈旧窗口，靠容错重试兜底。这是典型的"最终一致 + 客户端容错"组合，避免了强一致路由所需的复杂协调。

**6. Broker 异步存储**

业务线程只做"接收 + 校验 + 提交"，立即返回 `null` 释放自己；真正的刷盘/复制/回写由存储线程池异步完成。`CompletableFuture.thenCombine` 组合刷盘 Future 和复制 Future，取最坏状态。这是高吞吐的关键。

**7. 两个 msgId**

- `uniqMsgId`（UNIQ_KEY）：客户端生成，用于幂等/追踪。
- `offsetMsgId`：Broker 生成，含物理偏移，用于精准定位。

**8. 重试 → 死信的完整链路**

消费失败 → `%RETRY%` Topic 延迟重投 → 超过 maxReconsumeTimes → `%DLQ%` 死信队列 → 人工介入。

### 19.5 面试高频问题

**Q1：RocketMQ 发送消息如何保证高可用？**

多重保障：① 客户端重试（同步 3 次、异步 2 次）；② 每次重试换 Broker（selectOneMessageQueue 避开上次失败节点）；③ MQFaultStrategy 延迟容错隔离故障 Broker；④ 主动故障探测提前恢复；⑤ Broker 端 rejectRequest 快速失败 + SYSTEM_BUSY 让客户端换节点。

**Q2：同步发送和异步发送的重试机制有何不同？**

同步在 `sendDefaultImpl` 的 for 循环里重试；异步在 `onExceptionImpl` 里通过回调递归调用 `sendMessageAsync` 重试，且每次换新 opaque 避免响应串扰。

**Q3：为什么 Broker 端发送要用 CompletableFuture 异步存储？**

避免 Netty 业务线程在同步刷盘/同步复制时被 I/O 阻塞导致线程池耗尽。业务线程提交存储任务后立即返回 null 释放自己，存储回调在专用线程池 putMessageFutureExecutor 中完成刷盘/复制/回写。

**Q4：FLUSH_DISK_TIMEOUT 状态下消息丢了吗？**

没丢（在同步刷盘超时的语义下，消息已写入主节点内存），只是刷盘没在超时内完成。是否重发由业务的可靠性要求决定，重发需配合幂等去重。

**Q5：延迟容错（sendLatencyFaultEnable）为什么默认关闭？**

因为开启后会根据历史延迟隔离 Broker，在 Broker 数量少或抖动敏感的场景下可能把本可用的 Broker 误隔离，反而降低可用性。是否开启需结合集群规模和 SLA 权衡。

## 结语

本文从 `DefaultMQProducer.send()` 一路追踪到 Broker 的 `messageStore.asyncPutMessage()`，覆盖了发送全链路的每一个关键环节：门面委托、路由查找、容错选队列、故障隔离与探测、三种通信模式、响应处理、Broker 校验、重试死信、异步存储。

串起来看，RocketMQ 发送链路的设计哲学是：**客户端尽力而为（重试 + 容错 + 探测），服务端快速失败 + 异步高吞吐（rejectRequest + CompletableFuture）**。两端配合，在"最终一致的路由"之上构建出高可用、高吞吐的消息发送能力。

理解了这条链路，再去看消费链路（04 之后的文档）、存储链路（05 文档）会更顺畅——它们共享同样的设计基因：门面模式、异步化、容错兜底、最终一致。
