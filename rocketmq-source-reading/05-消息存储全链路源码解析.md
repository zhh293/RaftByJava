## 1. 全局调用链总览

### 1.1 一条消息的完整生命周期

当 Producer 发送一条消息到 Broker 时，消息在存储层经历的完整链路如下：

```
Producer
  │
  ▼
SendMessageProcessor.processRequest()          ← Netty 线程接收请求
  │
  ▼
DefaultMessageStore.putMessage(msg)             ← 同步包装器
  │
  ▼
DefaultMessageStore.asyncPutMessage(msg)        ← 真正入口：校验 + 钩子
  │
  ▼
CommitLog.asyncPutMessage(msg)                  ← ★ 核心写入路径
  │
  ├── 1. 设置 storeTimestamp / bodyCRC / 消息版本
  ├── 2. HA 副本数检查
  ├── 3. topicQueueLock.lock()                  ← Topic-Queue 粒度锁
  ├── 4. assignOffset(msg)                      ← 分配 ConsumeQueue 逻辑偏移
  ├── 5. encoder.encode(msg)                    ← 序列化为 ByteBuf
  ├── 6. putMessageLock.lock()                  ← ★ 全局串行锁
  │     │
  │     ├── 刷新 storeTimestamp
  │     ├── getLastMappedFile()                 ← 获取/创建 MappedFile
  │     ├── mappedFile.appendMessage()          ← 追加写入
  │     │     │
  │     │     ▼
  │     │   DefaultAppendMessageCallback.doAppend()
  │     │     ├── 检查剩余空间 → END_OF_FILE 则填充空白 + 新文件
  │     │     ├── 回填 QUEUEOFFSET / PHYSICALOFFSET / STORETIMESTAMP
  │     │     └── byteBuffer.put(preEncoded)    ← 真正写入内存
  │     │
  │     └── onCommitLogAppend()
  │
  ├── 7. putMessageLock.unlock()
  ├── 8. increaseOffset(msg)
  └── 9. handleDiskFlushAndHA()                 ← 刷盘 + HA 异步等待
        │
        ├── FlushManager.flush()
        │     ├── SYNC_FLUSH  → GroupCommitService (双缓冲交换)
        │     └── ASYNC_FLUSH → FlushRealTimeService (定时刷盘)
        │
        └── HAService.replicate()
              └── 等待从节点同步确认
```

写入完成后，消息已经落地在 CommitLog 文件中。接下来是异步分发：

```
ReputMessageService (独立线程，持续运行)
  │
  ▼
doReput()
  ├── commitLog.getData(reputFromOffset)        ← 从 CommitLog 读取消息
  ├── 解析 DispatchRequest
  └── doDispatch(dispatchRequest)
        │
        ├── CommitLogDispatcherBuildConsumeQueue
        │     └── ConsumeQueue.putMessagePositionInfo()
        │           └── 写入 20 字节索引条目
        │
        └── CommitLogDispatcherBuildIndex
              └── IndexService.buildIndex()
                    └── IndexFile.putKey()
                          └── Hash 槽 + 链表写入
```

### 1.2 调用链关键角色

| 角色 | 职责 | 线程模型 |
|------|------|----------|
| `DefaultMessageStore` | 存储门面，校验+钩子 | Netty Worker 线程 |
| `CommitLog` | 顺序写入 CommitLog 文件 | Netty Worker → 全局锁串行化 |
| `DefaultAppendMessageCallback` | 消息序列化 + 追加回调 | 持有全局锁的线程 |
| `DefaultMappedFile` | 单个内存映射文件的读写 | 多线程共享 |
| `MappedFileQueue` | MappedFile 的有序集合管理 | 多线程共享 |
| `ReputMessageService` | 异步分发 CommitLog → 索引 | 独立后台线程 |
| `ConsumeQueue` | 消费队列索引文件 | ReputMessageService 线程 |
| `IndexFile` | 消息 Key 的哈希索引 | ReputMessageService 线程 |
| `FlushManager` | 刷盘策略管理 | 独立后台线程 |
| `StoreCheckpoint` | 存储检查点 | 多个线程 |

### 1.3 为什么要理解全链路

理解 RocketMQ 存储全链路有以下几个核心价值：

1. **性能调优**：知道锁的粒度和位置，才能精准定位瓶颈
2. **故障排查**：理解刷盘和 HA 机制，才能在消息丢失时快速定位原因
3. **二次开发**：理解扩展点（钩子、分发器），才能安全地添加自定义逻辑
4. **架构借鉴**：RocketMQ 的存储设计是工业级消息队列的典范

## 2. 存储架构设计哲学

### 2.1 为什么选择顺序写

RocketMQ 存储层最核心的设计决策是：**所有 Topic 的消息混合写入同一个 CommitLog 文件**。

```
传统方案（如 Kafka）：
  TopicA-Partition0 → 独立文件
  TopicA-Partition1 → 独立文件
  TopicB-Partition0 → 独立文件
  ...
  Topic 数量多时 → 大量随机写 → 性能急剧下降

RocketMQ 方案：
  所有 Topic 所有 Queue → 统一写入 CommitLog
  CommitLog → 纯顺序追加写（append-only）
  Topic 级别的索引 → ConsumeQueue（异步构建）
```

这个设计的核心洞察是：

```
// 磁盘顺序写速度 ≈ 内存随机写速度
// 
// SSD 顺序写：500MB/s ~ 3GB/s
// SSD 随机写：50MB/s ~ 500MB/s (4K块)
// HDD 顺序写：100MB/s ~ 200MB/s
// HDD 随机写：0.5MB/s ~ 2MB/s (4K块)
//
// 结论：顺序写比随机写快 1~2 个数量级
```

### 3.2 putMessage() — 同步写入包装器

```java
/**
 * 同步写入消息。这是一个简单的同步包装器，内部调用 asyncPutMessage()
 * 然后阻塞等待结果。
 *
 * 设计意图：
 * - 对外提供简单的同步 API
 * - 内部统一使用异步实现，避免代码重复
 * - 通过 waitForPutResult() 实现同步语义
 */
@Override
public PutMessageResult putMessage(MessageExtBrokerInner msg) {
    // 核心就一行：异步写入 + 同步等待
    return waitForPutResult(asyncPutMessage(msg));
}

/**
 * waitForPutResult 的实现非常直白：
 */
private PutMessageResult waitForPutResult(CompletableFuture<PutMessageResult> putResultFuture) {
    try {
        // 默认超时时间 = syncFlushTimeout + 5000ms（给 HA 留余量）
        int timeout = this.messageStoreConfig.getSyncFlushTimeout() + 5000;
        return putResultFuture.get(timeout, TimeUnit.MILLISECONDS);
    } catch (ExecutionException | InterruptedException e) {
        return new PutMessageResult(PutMessageStatus.UNKNOWN_ERROR, null);
    } catch (TimeoutException e) {
        // 超时通常意味着刷盘或 HA 同步超时
        log.error("put message wait result timeout, sync flush timeout={}",
                  this.messageStoreConfig.getSyncFlushTimeout());
        return new PutMessageResult(PutMessageStatus.UNKNOWN_ERROR, null);
    }
}
```

> **Dubbo 风格旁注**：这种"同步包装异步"的模式在中间件中非常常见。Dubbo 的同步调用
> 本质上也是 `AsyncRpcResult.get()`，底层都是异步实现。这样做的好处是核心逻辑只需
> 维护一份异步实现，同步语义通过简单的 `Future.get()` 实现。

### 3.3 asyncPutMessage() — 异步写入核心入口

```java
/**
 * 异步写入消息 — DefaultMessageStore 的核心方法。
 *
 * 这个方法不做真正的写入，它的职责是：
 * 1. 前置校验（运行状态、Topic 合法性、消息大小等）
 * 2. 执行写入前钩子
 * 3. 委托给 CommitLog 执行真正的写入
 * 4. 执行写入后钩子
 * 5. 记录统计信息
 *
 * 典型的模板方法模式（Template Method Pattern）。
 */
@Override
public CompletableFuture<PutMessageResult> asyncPutMessage(MessageExtBrokerInner msg) {

    // =============== 第一步：前置校验 ===============

    // 1.1 检查存储服务是否可用
    // 如果 Broker 正在关闭或者存储层还没初始化完成，直接拒绝
    PutMessageStatus checkStoreStatus = this.checkStoreStatus();
    if (checkStoreStatus != PutMessageStatus.PUT_OK) {
        return CompletableFuture.completedFuture(
            new PutMessageResult(checkStoreStatus, null));
    }

    // 1.2 检查消息合法性
    // 包括：Topic 长度、消息体大小、Properties 大小等
    PutMessageStatus msgCheckStatus = this.checkMessage(msg);
    if (msgCheckStatus == PutMessageStatus.MESSAGE_ILLEGAL) {
        return CompletableFuture.completedFuture(
            new PutMessageResult(PutMessageStatus.MESSAGE_ILLEGAL, null));
    }

    // 1.3 检查 LMQ (Light Message Queue) 相关
    PutMessageStatus lmqMsgCheckStatus = this.checkLmqMessage(msg);
    if (lmqMsgCheckStatus == PutMessageStatus.LMQ_CONSUME_QUEUE_NUM_EXCEEDED) {
        return CompletableFuture.completedFuture(
            new PutMessageResult(lmqMsgCheckStatus, null));
    }

    // =============== 第二步：记录存储时间 ===============

    long beginTime = this.getSystemClock().now();
    // 给消息设置存储时间戳，后续可能在锁内被刷新
    msg.setStoreTimestamp(beginTime);

    // =============== 第三步：执行写入前钩子 ===============

    // 钩子机制允许用户在消息写入前做自定义处理
    // 例如：消息轨迹记录、权限校验、消息转换等
    if (this.putMessageHookList != null && !this.putMessageHookList.isEmpty()) {
        PutMessageContext putMessageContext = new PutMessageContext(
            generateKey(msg.getTopic(), msg.getQueueId()));

        for (PutMessageHook hook : this.putMessageHookList) {
            // 如果任何一个钩子返回失败，直接中止写入
            PutMessageResult handleResult = hook.executeBeforePutMessage(msg);
            if (handleResult != null) {
                return CompletableFuture.completedFuture(handleResult);
            }
        }
    }

    // =============== 第四步：委托 CommitLog 写入 ===============

    // 这里是真正的写入调用，所有核心逻辑都在 CommitLog 中
    CompletableFuture<PutMessageResult> putResultFuture = 
        this.commitLog.asyncPutMessage(msg);

    // =============== 第五步：写入后处理 ===============

    putResultFuture.thenAccept(result -> {
        // 5.1 记录存储耗时统计
        long elapsedTime = this.getSystemClock().now() - beginTime;
        if (elapsedTime > 500) {
            log.warn("putMessage not in lock elapsed time(ms)={}, bodyLength={}",
                     elapsedTime, msg.getBody().length);
        }

        // 5.2 更新统计计数器
        this.storeStatsService.setPutMessageEntireTimeMax(elapsedTime);
        this.storeStatsService.getSinglePutMessageTopicTimesTotal(
            msg.getTopic()).add(1);
        this.storeStatsService.getSinglePutMessageTopicSizeTotal(
            msg.getTopic()).add(result.getAppendMessageResult().getWroteBytes());

        // 5.3 执行写入后钩子
        if (this.putMessageHookList != null && !this.putMessageHookList.isEmpty()) {
            for (PutMessageHook hook : this.putMessageHookList) {
                hook.executeAfterPutMessage(result);
            }
        }
    });

    return putResultFuture;
}
```

### 3.4 checkStoreStatus() — 前置校验详解

```java
/**
 * 检查存储服务的运行状态。
 * 任何一个条件不满足，都会拒绝消息写入。
 */
private PutMessageStatus checkStoreStatus() {

    // 1. 存储服务是否已关闭
    if (this.shutdown) {
        log.warn("message store has shutdown, reject put message");
        return PutMessageStatus.SERVICE_NOT_AVAILABLE;
    }

    // 2. 如果是 SLAVE 角色，不接受写入
    // （SLAVE 只做数据同步，不直接接受 Producer 的写入请求）
    if (BrokerRole.SLAVE == this.messageStoreConfig.getBrokerRole()) {
        long value = this.printTimes.getAndIncrement();
        if ((value % 50000) == 0) {
            log.warn("not allowed to put message in SLAVE mode, times={}", value);
        }
        return PutMessageStatus.SERVICE_NOT_AVAILABLE;
    }

    // 3. 存储服务是否可写
    // runningFlags 是一个位标记，标记磁盘满、写入异常等状态
    if (!this.runningFlags.isWriteable()) {
        long value = this.printTimes.getAndIncrement();
        if ((value % 50000) == 0) {
            log.warn("store not writeable, running flags={}", 
                     this.runningFlags.getFlagBits());
        }
        return PutMessageStatus.SERVICE_NOT_AVAILABLE;
    }

    // 4. 操作系统 PageCache 是否繁忙
    // 如果上一次刷盘耗时超过 osPageCacheBusyTimeOutMills（默认 1000ms），
    // 认为 PageCache 繁忙，暂时拒绝写入以保护系统
    if (this.isOSPageCacheBusy()) {
        return PutMessageStatus.OS_PAGECACHE_BUSY;
    }

    return PutMessageStatus.PUT_OK;
}

/**
 * 判断 OS PageCache 是否繁忙。
 * 核心指标：上一次 appendMessage 在锁内的耗时。
 */
public boolean isOSPageCacheBusy() {
    long begin = this.commitLog.getBeginTimeInLock();
    long diff = this.systemClock.now() - begin;

    // 如果距离上次锁内开始时间超过了阈值（默认 1000ms），说明：
    // 上一个写入线程可能被 PageCache 刷盘阻塞了（发生了 page fault 或 fsync 阻塞）
    return diff < 10000000  // 排除无意义的大值
        && diff > this.messageStoreConfig.getOsPageCacheBusyTimeOutMills();
}
```

> **深入理解 PageCache 繁忙检测**：
>
> 这是 RocketMQ 的一个重要自保护机制。当操作系统的 dirty page 积压过多时，
> 内核会触发 writeback，此时对 mmap 区域的写入可能会被内核阻塞（所谓的
> "dirty throttling"）。RocketMQ 通过监控锁内耗时来间接检测这种情况，
> 并主动拒绝新的写入请求，避免雪崩。

### 3.5 checkMessage() — 消息合法性校验

```java
/**
 * 检查消息的合法性。
 */
private PutMessageStatus checkMessage(MessageExtBrokerInner msg) {

    // Topic 长度检查
    // V1 版本 Topic 最长 127 字节（1 字节长度字段）
    // V2 版本 Topic 最长 65535 字节（2 字节长度字段）
    if (msg.getTopic() != null) {
        if (msg.getTopic().length() > Byte.MAX_VALUE) {
            log.warn("putMessage topic length too long, topic={}", msg.getTopic());
            return PutMessageStatus.MESSAGE_ILLEGAL;
        }
    }

    // Properties 长度检查（最大 32KB）
    if (msg.getPropertiesString() != null 
        && msg.getPropertiesString().length() > Short.MAX_VALUE) {
        log.warn("putMessage properties length too long, length={}",
                 msg.getPropertiesString().length());
        return PutMessageStatus.MESSAGE_ILLEGAL;
    }

    return PutMessageStatus.PUT_OK;
}
```

## 4. CommitLog.asyncPutMessage() 核心写入

### 4.1 方法总览

这是 RocketMQ 消息存储的**最核心方法**，也是本文的重点中的重点。
这个方法完成了从消息对象到磁盘字节的全部转换工作。

让我们逐段拆解。

### 4.2 第一阶段：消息预处理

```java
/**
 * CommitLog 的异步写入方法 — RocketMQ 存储层的心脏。
 *
 * 方法的整体结构：
 * 1. 消息预处理（设置时间戳、CRC、版本等）
 * 2. HA 副本检查
 * 3. Topic-Queue 粒度锁 + 分配偏移量
 * 4. 消息编码
 * 5. 全局写入锁
 * 6. 追加写入 MappedFile
 * 7. 释放锁 + 推进偏移量
 * 8. 刷盘 + HA 处理
 */
public CompletableFuture<PutMessageResult> asyncPutMessage(
        final MessageExtBrokerInner msg) {

    // ============ 第一阶段：消息预处理 ============

    // 1. 设置存储时间戳
    // 注意：这里设置的时间戳后续在锁内会被刷新为更精确的值
    msg.setStoreTimestamp(System.currentTimeMillis());

    // 2. 计算消息体的 CRC32 校验码
    // 用于消费时验证消息体是否被损坏
    msg.setBodyCRC(UtilAll.crc32(msg.getBody()));

    // 3. 设置 IPv6 标志
    // 如果 BornHost 或 StoreHost 是 IPv6 地址，需要在 SysFlag 中标记
    // 因为 IPv4 地址占 8 字节（4 IP + 4 Port），IPv6 占 20 字节（16 IP + 4 Port）
    // 消息二进制格式的长度会因此不同
    InetSocketAddress bornSocketAddress = (InetSocketAddress) msg.getBornHost();
    if (bornSocketAddress.getAddress() instanceof Inet6Address) {
        msg.setBornHostV6Flag();
    }
    InetSocketAddress storeSocketAddress = (InetSocketAddress) msg.getStoreHost();
    if (storeSocketAddress.getAddress() instanceof Inet6Address) {
        msg.setStoreHostV6Flag();
    }

    // 4. 设置消息版本
    // V1：兼容老版本，Topic 长度字段为 1 字节
    // V2：新版本，Topic 长度字段为 2 字节，支持更长的 Topic 名
    MessageVersion messageVersion = MessageVersion.MESSAGE_VERSION_V1;
    String topicLengthStr = msg.getProperty(MessageConst.PROPERTY_MESSAGE_VERSION);
    if (topicLengthStr != null) {
        messageVersion = MessageVersion.valueOfMagicCode(
            Integer.parseInt(topicLengthStr));
    }
    msg.setVersion(messageVersion);
```

### 4.3 第二阶段：HA 副本数检查

```java
    // ============ 第二阶段：HA 副本数检查 ============

    // 这是 RocketMQ 5.x 新增的特性：同步确认副本数
    // 类似于 Kafka 的 min.insync.replicas 配置
    //
    // 当 inSyncReplicasNums < minInSyncReplicas 时，拒绝写入
    // 这保证了每条被确认的消息至少存在于 minInSyncReplicas 个节点上

    if (this.defaultMessageStore.getMessageStoreConfig().isDuplicationEnable()
        && this.defaultMessageStore.getMessageStoreConfig()
            .getBrokerRole() != BrokerRole.SLAVE) {
        // DLedger 模式下的特殊处理
    }

    // 检查 HA 连接数是否满足最小同步副本数要求
    if (this.defaultMessageStore.getBrokerConfig().isEnableSlaveActingMaster()) {
        // 获取当前 CommitLog 的最大偏移量
        long currOffset = this.defaultMessageStore.getCommitLog().getMaxOffset();

        // 检查：当前同步的副本数量 >= 配置的最小同步副本数
        if (this.defaultMessageStore.getHaService()
                .inSyncReplicasNums(currOffset)
            < this.defaultMessageStore.getMessageStoreConfig()
                .getMinInSyncReplicas()) {

            // 副本数不足，拒绝写入
            // 这样做的目的是保证数据可靠性：
            // 如果当前存活的从节点太少，写入可能会在 Leader 宕机后丢失
            return CompletableFuture.completedFuture(
                new PutMessageResult(
                    PutMessageStatus.IN_SYNC_REPLICAS_NOT_ENOUGH, null));
        }

        // 额外检查：如果启用了 AutoSlave，还需要检查 haMaxGapNotInSync
        if (this.defaultMessageStore.getHaService()
                .inSyncReplicasNums(currOffset)
            < this.defaultMessageStore.getMessageStoreConfig()
                .getTotalReplicas()) {
            // 记录告警日志，但不阻止写入
            // 区别：minInSyncReplicas 是硬限制，totalReplicas 是软限制
        }
    }
```

### 4.4 第三阶段：Topic-Queue 锁 + 偏移量分配

```java
    // ============ 第三阶段：Topic-Queue 锁 + 偏移量分配 ============

    // 构造锁的 key：topic-queueId
    // 例如："OrderTopic-3" 表示 OrderTopic 的第 3 个队列
    String topicQueueKey = msg.getTopic() + "-" + msg.getQueueId();

    // 获取 Topic-Queue 粒度的锁
    // 注意：这个锁的粒度比全局写入锁要细
    // 它的作用是保证同一个 Topic-Queue 的偏移量分配是顺序的
    topicQueueLock.lock(topicQueueKey);
    try {
        // 设置消息的存储时间戳（默认值，后续在全局锁内会刷新）
        boolean needAssignOffset = true;

        // 如果启用了 DLedger 模式，偏移量分配逻辑不同
        if (defaultMessageStore.getMessageStoreConfig().isDuplicationEnable()
            && defaultMessageStore.getMessageStoreConfig()
                .getBrokerRole() != BrokerRole.SLAVE) {
            needAssignOffset = false;
        }

        if (needAssignOffset) {
            // assignOffset：为消息分配 ConsumeQueue 中的逻辑偏移量
            // 这个偏移量是单调递增的，每个 Topic-Queue 独立维护
            //
            // 实现原理：
            // - 内部维护一个 ConcurrentMap<String, Long> topicQueueTable
            // - key = topic-queueId, value = nextOffset
            // - 每次分配后 +1（单条消息）或 +batchCount（批量消息）
            defaultMessageStore.assignOffset(msg);
        }
    } finally {
        topicQueueLock.unlock(topicQueueKey);
    }
```

> **为什么需要两层锁？**
>
> Topic-Queue 锁保证偏移量分配的正确性（每个 Queue 独立递增），
> 全局写入锁保证 CommitLog 文件追加的原子性（所有 Topic 共享）。
>
> 如果只用一个全局锁，偏移量分配和文件追加虽然也是正确的，
> 但锁的持有时间更长（因为编码操作也在锁内），吞吐量会下降。
>
> 将偏移量分配提到外层的细粒度锁中，可以让消息编码在两层锁之间执行，
> 减少全局锁的持有时间。

### 4.6 第五阶段：全局写入锁 — 追加消息

```java
    // ============ 第五阶段：全局写入锁 — 追加消息 ============

    // 这是整个写入路径中最关键的临界区
    // 在这个锁内，完成消息到 MappedFile 的实际写入

    // 记录锁内开始时间，用于 PageCache 繁忙检测
    long elapsedTimeInLock = 0;
    MappedFile unlockMappedFile = null;

    // 获取全局写入锁
    // putMessageLock 有三种实现：
    //   - PutMessageSpinLock：自旋锁，适合锁持有时间极短的场景（默认）
    //   - PutMessageReentrantLock：JDK ReentrantLock，适合锁持有时间较长的场景
    //   - AdaptiveLock：自适应，根据锁竞争程度动态切换
    putMessageLock.lock();
    try {
        // 记录锁获取后的时间
        long beginLockTimestamp = this.defaultMessageStore.getSystemClock().now();
        this.beginTimeInLock = beginLockTimestamp;

        // ---- 5.1 刷新存储时间戳 ----
        // 为什么要在锁内再次设置时间戳？
        // 因为从消息进入到获取锁之间可能有排队等待时间，
        // 锁内的时间戳更能反映消息的真实存储时间
        msg.setStoreTimestamp(beginLockTimestamp);

        // ---- 5.2 获取最后一个 MappedFile ----
        // 如果不存在或者已写满，会创建新的
        MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();

        if (null == mappedFile) {
            // 当前没有任何 MappedFile，创建第一个
            // startOffset = 0
            mappedFile = this.mappedFileQueue.getLastMappedFile(0, true);
        }

        if (null == mappedFile) {
            // 创建失败，通常是磁盘空间不足
            log.error("create mapped file error, topic={} clientAddr={}",
                      msg.getTopic(), msg.getBornHostString());
            return CompletableFuture.completedFuture(
                new PutMessageResult(
                    PutMessageStatus.CREATE_MAPPED_FILE_FAILED, null));
        }

        // ---- 5.3 追加消息到 MappedFile ----
        AppendMessageResult result = mappedFile.appendMessage(
            msg, this.appendMessageCallback, putMessageContext);

        // ---- 5.4 处理追加结果 ----
        switch (result.getStatus()) {
            case PUT_OK:
                // 写入成功
                // onCommitLogAppend 回调通知各组件
                onCommitLogAppend(msg, result, mappedFile);
                break;

            case END_OF_FILE:
                // 当前文件剩余空间不足以容纳本条消息
                // MappedFile 会自动写入空白填充（BLANK_MAGIC_CODE）
                // 需要解锁当前文件（后续会 warmup 或 unmap）
                unlockMappedFile = mappedFile;

                // 创建新的 MappedFile
                mappedFile = this.mappedFileQueue.getLastMappedFile(0, true);
                if (null == mappedFile) {
                    log.error("create mapped file error after END_OF_FILE");
                    return CompletableFuture.completedFuture(
                        new PutMessageResult(
                            PutMessageStatus.CREATE_MAPPED_FILE_FAILED,
                            result));
                }

                // 在新文件中重试
                result = mappedFile.appendMessage(
                    msg, this.appendMessageCallback, putMessageContext);

                if (result.getStatus() == AppendMessageStatus.PUT_OK) {
                    onCommitLogAppend(msg, result, mappedFile);
                }
                break;

            case MESSAGE_SIZE_EXCEEDED:
            case PROPERTIES_SIZE_EXCEEDED:
                // 消息过大，返回失败
                return CompletableFuture.completedFuture(
                    new PutMessageResult(
                        PutMessageStatus.MESSAGE_ILLEGAL, result));

            case UNKNOWN_ERROR:
                return CompletableFuture.completedFuture(
                    new PutMessageResult(
                        PutMessageStatus.UNKNOWN_ERROR, result));

            default:
                return CompletableFuture.completedFuture(
                    new PutMessageResult(
                        PutMessageStatus.UNKNOWN_ERROR, result));
        }

        // 计算锁内耗时
        elapsedTimeInLock = this.defaultMessageStore.getSystemClock().now() 
                            - beginLockTimestamp;

    } finally {
        // ---- 5.5 释放全局锁 ----
        beginTimeInLock = 0;
        putMessageLock.unlock();
    }

    // 性能告警：如果锁持有时间超过 500ms，发出警告
    if (elapsedTimeInLock > 500) {
        log.warn("[NOTIFYME]putMessage in lock cost time(ms)={}, "
                 + "bodyLength={} AppendMessageResult={}",
                 elapsedTimeInLock, msg.getBody().length, result);
    }
```

### 4.8 PutMessageLock — 锁策略详解

```java
/**
 * 自旋锁实现 — 适合锁持有时间极短的场景（微秒级）。
 * 
 * RocketMQ 默认使用自旋锁，因为锁内操作（buffer copy）通常在微秒级完成。
 * 自旋锁避免了线程上下文切换的开销（通常在 1~10 微秒）。
 */
public class PutMessageSpinLock implements PutMessageLock {

    // 使用 AtomicBoolean 实现 CAS 自旋
    private AtomicBoolean putMessageSpinLock = new AtomicBoolean(true);

    @Override
    public void lock() {
        boolean needNotify = false;
        // CAS 自旋：尝试将 true 改为 false
        // 成功则获得锁，失败则继续自旋
        while (!this.putMessageSpinLock.compareAndSet(true, false)) {
            // busy spin - 不做任何操作，纯 CPU 自旋
            // 注意：没有 Thread.yield() 或 LockSupport.parkNanos()
            // 这是有意的：在极端高并发下保持最低延迟
        }
    }

    @Override
    public void unlock() {
        this.putMessageSpinLock.compareAndSet(false, true);
    }
}

/**
 * ReentrantLock 实现 — 适合锁竞争激烈或锁持有时间较长的场景。
 * 
 * 当 TransientStorePool 开启时，写入可能涉及 DirectByteBuffer 操作，
 * 耗时更长，此时使用 ReentrantLock 更合适。
 */
public class PutMessageReentrantLock implements PutMessageLock {

    private ReentrantLock putMessageNormalLock = new ReentrantLock();

    @Override
    public void lock() {
        putMessageNormalLock.lock();
    }

    @Override
    public void unlock() {
        putMessageNormalLock.unlock();
    }
}
```

> **锁选择的工程考量**：
>
> | 场景 | 推荐锁类型 | 原因 |
> |------|-----------|------|
> | 默认（异步刷盘，无 TransientStorePool） | SpinLock | 锁内操作极快，自旋开销 < 上下文切换 |
> | 同步刷盘 | ReentrantLock | 刷盘耗时可能较长 |
> | TransientStorePool 开启 | ReentrantLock | DirectBuffer copy 较慢 |
> | 消息 body 很大（>256KB） | ReentrantLock | 编码+copy 耗时增加 |

## 5. DefaultAppendMessageCallback.doAppend()

### 5.1 方法签名与职责

`doAppend()` 是消息实际写入 MappedFile 的回调方法。它在 `MappedFile.appendMessage()` 
内部被调用，此时已经持有了全局写入锁。

```java
/**
 * DefaultAppendMessageCallback 是 CommitLog 的内部类。
 * 实现了 AppendMessageCallback 接口。
 * 
 * 职责：
 * 1. 检查文件剩余空间
 * 2. 处理文件末尾的空白填充
 * 3. 回填运行时才能确定的字段（物理偏移量、队列偏移量等）
 * 4. 执行真正的 buffer 写入
 */
class DefaultAppendMessageCallback implements AppendMessageCallback {

    // 文件末尾预留空间，用于写入 BLANK_MAGIC_CODE + 文件大小
    // 最小 8 字节：4 字节 TOTALSIZE + 4 字节 MAGICCODE
    private static final int END_FILE_MIN_BLANK_LENGTH = 4 + 4;

    // 用于存储消息 ID 的临时 buffer
    private final ByteBuffer msgIdMemory;
    private final ByteBuffer msgIdV6Memory;

    // 存储宿主地址的临时 buffer
    private final ByteBuffer msgStoreItemMemory;

    // CommitLog 文件大小（默认 1GB）
    private final int maxMessageBodySize;

    // 消息编码器引用
    private final MessageSerializer serializer;
```

### 5.2 doAppend() — 单条消息追加

```java
    /**
     * 追加单条消息到 MappedFile。
     *
     * @param fileFromOffset  当前文件的起始物理偏移量（文件名即偏移量）
     * @param byteBuffer      文件对应的 ByteBuffer（mmap 或 DirectBuffer）
     * @param maxBlank         文件剩余可写空间
     * @param msgInner         待写入的消息
     * @param putMessageContext 写入上下文
     * @return 追加结果
     */
    public AppendMessageResult doAppend(
            final long fileFromOffset,
            final ByteBuffer byteBuffer,
            final int maxBlank,
            final MessageExtBrokerInner msgInner,
            PutMessageContext putMessageContext) {

        // ============ 步骤1：获取预编码的 buffer ============

        // 消息已经在锁外完成了编码（第四阶段），这里直接获取编码结果
        ByteBuffer preEncodeBuffer = msgInner.getEncodedBuff();
        if (preEncodeBuffer == null) {
            // 理论上不应该走到这里
            // 如果 preEncodeBuffer 为 null，可能是编码阶段被跳过了
            return new AppendMessageResult(AppendMessageStatus.UNKNOWN_ERROR);
        }

        // 消息总长度
        final int msgLen = preEncodeBuffer.remaining();

        // ============ 步骤2：计算物理偏移量 ============

        // 当前写入位置在整个 CommitLog 中的物理偏移量
        // = 文件起始偏移量 + buffer 当前位置
        //
        // 例如：文件 00000000001073741824 (1GB)，buffer.position() = 1024
        // 则 wroteOffset = 1073741824 + 1024 = 1073742848
        long wroteOffset = fileFromOffset + byteBuffer.position();

        // ============ 步骤3：生成消息 ID ============

        // 消息 ID 由 StoreHost(IP:Port) + CommitLog物理偏移量 组成
        // 这保证了每条消息的 ID 全局唯一
        Supplier<String> msgIdSupplier = () -> {
            int sysflag = msgInner.getSysFlag();
            int msgIdLen = (sysflag & MessageSysFlag.STOREHOSTADDRESS_V6_FLAG) == 0 
                           ? 4 + 4 + 8   // IPv4: 4(IP) + 4(Port) + 8(Offset)
                           : 16 + 4 + 8; // IPv6: 16(IP) + 4(Port) + 8(Offset)
            ByteBuffer msgIdBuffer = ByteBuffer.allocate(msgIdLen);
            MessageExt.socketAddress2ByteBuffer(
                msgInner.getStoreHost(), msgIdBuffer);
            msgIdBuffer.clear();
            msgIdBuffer.putLong(msgIdLen - 8, wroteOffset);
            return UtilAll.bytes2string(msgIdBuffer.array());
        };

        // ============ 步骤4：检查文件剩余空间 ============

        // 核心判断：如果消息长度 + 文件结尾标记(8字节) > 剩余空间
        // 则需要切换到新文件
        if ((msgLen + END_FILE_MIN_BLANK_LENGTH) > maxBlank) {

            // 重置预编码 buffer 的位置（因为本次写入没有消费它）
            this.msgStoreItemMemory.clear();

            // ---- 写入文件末尾的空白填充 ----
            // 格式：
            //   TOTALSIZE (4 bytes) = maxBlank (剩余空间大小)
            //   MAGICCODE (4 bytes) = BLANK_MAGIC_CODE (0xcbd43194)
            //
            // 消费者在读取 CommitLog 时遇到 BLANK_MAGIC_CODE 就知道
            // 本文件到此结束，需要跳转到下一个文件

            this.msgStoreItemMemory.putInt(maxBlank);           // TOTALSIZE
            this.msgStoreItemMemory.putInt(                     // MAGICCODE
                CommitLog.BLANK_MAGIC_CODE);

            // 写入文件
            byteBuffer.put(this.msgStoreItemMemory.array(), 0, 
                          END_FILE_MIN_BLANK_LENGTH);

            // 如果剩余空间 > 8 字节，将多余部分填零
            // （实际上 mmap 的内存默认就是零，这一步可以省略）
            if (maxBlank > END_FILE_MIN_BLANK_LENGTH) {
                byteBuffer.put(new byte[maxBlank - END_FILE_MIN_BLANK_LENGTH]);
            }

            // 返回 END_OF_FILE，通知调用者需要创建新文件并重试
            return new AppendMessageResult(
                AppendMessageStatus.END_OF_FILE,
                wroteOffset,
                maxBlank,       // 本次"写入"的字节数（空白填充）
                msgIdSupplier,
                msgInner.getStoreTimestamp(),
                msgInner.getQueueOffset(),
                this.defaultMessageStore.getSystemClock().now() - beginTimeMills);
        }

        // ============ 步骤5：回填运行时字段 ============

        // 预编码阶段有些字段是"留空"的，需要在这里回填。
        // 因为这些字段的值依赖于写入时的状态（物理偏移量、精确时间等）。

        // 5.1 回填 QUEUEOFFSET（位置：偏移量 20 字节处）
        //     这是消息在 ConsumeQueue 中的逻辑偏移量
        //     在 Topic-Queue 锁阶段分配
        final int queueOffsetPosition = 4  // TOTALSIZE
                                       + 4  // MAGICCODE
                                       + 4  // BODYCRC
                                       + 4  // QUEUEID
                                       + 4; // FLAG
        // = 20
        preEncodeBuffer.putLong(queueOffsetPosition, msgInner.getQueueOffset());

        // 5.2 回填 PHYSICALOFFSET（位置：偏移量 28 字节处）
        //     这是消息在 CommitLog 中的物理偏移量
        //     只有在 doAppend 中才能确定（因为依赖文件写入位置）
        final int physicalOffsetPosition = queueOffsetPosition + 8;
        // = 28
        preEncodeBuffer.putLong(physicalOffsetPosition, wroteOffset);

        // 5.3 回填 STORETIMESTAMP（位置：取决于是否 IPv6）
        //     使用锁内的精确时间戳
        int sysFlag = msgInner.getSysFlag();
        int bornHostLength = (sysFlag & MessageSysFlag.BORNHOST_V6_FLAG) == 0 
                             ? 4 + 4 : 16 + 4;
        int storeTimestampPosition = physicalOffsetPosition + 8  // PHYSICALOFFSET
                                   + 4                           // SYSFLAG
                                   + 8                           // BORNTIMESTAMP
                                   + bornHostLength;             // BORNHOST
        preEncodeBuffer.putLong(storeTimestampPosition, 
                               msgInner.getStoreTimestamp());

        // 5.4 重新计算 CRC32（因为内容可能有变化）
        //     Body CRC 位置固定在 offset 8
        //     注意：这里不重新计算 CRC，因为 body 本身没有变化
        //     变化的是 header 中的运行时字段

        // ============ 步骤6：执行真正的写入 ============

        // 将预编码的 buffer 写入 MappedFile 的 ByteBuffer
        // 这是一次内存拷贝：preEncodeBuffer → mmap/DirectBuffer
        //
        // 对于 mmap 模式：写入后数据进入 Page Cache
        // 对于 TransientStorePool：写入后数据在 DirectBuffer 中
        byteBuffer.put(preEncodeBuffer);

        // ============ 步骤7：构造返回结果 ============

        return new AppendMessageResult(
            AppendMessageStatus.PUT_OK,       // 状态：成功
            wroteOffset,                       // 物理偏移量
            msgLen,                            // 消息长度
            msgIdSupplier,                     // 消息 ID（延迟计算）
            msgInner.getStoreTimestamp(),       // 存储时间戳
            msgInner.getQueueOffset(),          // 队列偏移量
            this.defaultMessageStore.getSystemClock().now() - beginTimeMills  // 耗时
        );
    }
```

## 6. 消息二进制格式详解

### 6.1 整体布局

RocketMQ 的每条消息在 CommitLog 中以固定格式存储。理解这个二进制格式是阅读存储源码的基础。

```
┌──────────────────────────────────────────────────────────────────────┐
│                        消息二进制格式 (Message Binary Format)          │
├──────────┬──────────┬───────────────────────────────────────────────┤
│  Offset  │   Size   │                    Field                      │
├──────────┼──────────┼───────────────────────────────────────────────┤
│    0     │    4     │  TOTALSIZE        — 消息总长度（含自身4字节）     │
│    4     │    4     │  MAGICCODE        — 魔数，标识消息版本           │
│    8     │    4     │  BODYCRC          — 消息体 CRC32 校验码         │
│   12     │    4     │  QUEUEID          — 队列 ID                    │
│   16     │    4     │  FLAG             — 消息标志位                  │
│   20     │    8     │  QUEUEOFFSET      — 在 ConsumeQueue 中的逻辑偏移│
│   28     │    8     │  PHYSICALOFFSET   — 在 CommitLog 中的物理偏移    │
│   36     │    4     │  SYSFLAG          — 系统标志位                  │
│   40     │    8     │  BORNTIMESTAMP    — 消息产生时间戳              │
│   48     │  8/20   │  BORNHOST         — 生产者地址 (IPv4:8/IPv6:20) │
│  56/68   │    8     │  STORETIMESTAMP   — 消息存储时间戳              │
│  64/76   │  8/20   │  STOREHOSTADDRESS — Broker 存储地址              │
│  72/96   │    4     │  RECONSUMETIMES   — 消息重试消费次数            │
│  76/100  │    8     │  PreparedTransactionOffset — 事务消息偏移量     │
│  84/108  │    4     │  BODYLENGTH       — 消息体长度                  │
│  88/112  │   var    │  BODY             — 消息体（变长）               │
│   ...    │  1/2     │  TOPICLENGTH      — Topic 名称长度(V1:1B/V2:2B)│
│   ...    │   var    │  TOPIC            — Topic 名称（变长）           │
│   ...    │    2     │  PROPERTIESLENGTH — 属性长度                    │
│   ...    │   var    │  PROPERTIES       — 消息属性（变长，KV 格式）     │
└──────────┴──────────┴───────────────────────────────────────────────┘
```

### 6.5 编码实现

```java
/**
 * MessageSerializer.encode() — 消息编码为二进制。
 * 这个方法将 MessageExtBrokerInner 对象序列化为 ByteBuffer。
 * 
 * 在全局锁之外调用，减少锁持有时间。
 */
public PutMessageResult encode(MessageExtBrokerInner msgInner) {

    // 获取 ThreadLocal 的编码 buffer
    ByteBuffer encoderBuffer = this.encoderBuffer.get();
    if (encoderBuffer == null) {
        encoderBuffer = ByteBuffer.allocateDirect(
            this.maxMessageBodySize + 64 * 1024);
        this.encoderBuffer.set(encoderBuffer);
    }
    encoderBuffer.clear();

    // -------- 计算各部分长度 --------

    // Body 长度
    final byte[] body = msgInner.getBody();
    final int bodyLength = body == null ? 0 : body.length;

    // Topic 长度（UTF-8 编码后的字节长度）
    final byte[] topicData = msgInner.getTopic().getBytes(MessageDecoder.CHARSET_UTF8);
    final int topicLength = topicData.length;

    // Properties 长度
    final byte[] propertiesData = msgInner.getPropertiesString() == null ? null
        : msgInner.getPropertiesString().getBytes(MessageDecoder.CHARSET_UTF8);
    final short propertiesLength = propertiesData == null ? 0 
        : (short) propertiesData.length;

    // BornHost 和 StoreHost 长度（取决于 IPv4/IPv6）
    int sysFlag = msgInner.getSysFlag();
    int bornHostLength = (sysFlag & MessageSysFlag.BORNHOST_V6_FLAG) == 0 ? 8 : 20;
    int storeHostLength = (sysFlag & MessageSysFlag.STOREHOSTADDRESS_V6_FLAG) == 0 ? 8 : 20;

    // Topic 长度字段大小（V1=1字节, V2=2字节）
    int topicLengthSize = msgInner.getVersion().getTopicLengthSize();

    // -------- 计算消息总长度 --------

    final int msgLen = 4           // TOTALSIZE
        + 4                        // MAGICCODE
        + 4                        // BODYCRC
        + 4                        // QUEUEID
        + 4                        // FLAG
        + 8                        // QUEUEOFFSET
        + 8                        // PHYSICALOFFSET
        + 4                        // SYSFLAG
        + 8                        // BORNTIMESTAMP
        + bornHostLength           // BORNHOST
        + 8                        // STORETIMESTAMP
        + storeHostLength          // STOREHOSTADDRESS
        + 4                        // RECONSUMETIMES
        + 8                        // Prepared Transaction Offset
        + 4 + bodyLength           // BODYLENGTH + BODY
        + topicLengthSize + topicLength  // TOPICLENGTH + TOPIC
        + 2 + propertiesLength;    // PROPERTIESLENGTH + PROPERTIES

    // 消息大小校验
    if (msgLen > this.maxMessageBodySize) {
        log.warn("message size exceeded, msg total size: {}, maxMessageSize: {}",
                 msgLen, this.maxMessageBodySize);
        return new PutMessageResult(
            PutMessageStatus.MESSAGE_ILLEGAL, null);
    }

    // -------- 写入各字段 --------

    // 1. TOTALSIZE
    encoderBuffer.putInt(msgLen);
    // 2. MAGICCODE
    encoderBuffer.putInt(msgInner.getVersion().getMagicCode());
    // 3. BODYCRC
    encoderBuffer.putInt(msgInner.getBodyCRC());
    // 4. QUEUEID
    encoderBuffer.putInt(msgInner.getQueueId());
    // 5. FLAG
    encoderBuffer.putInt(msgInner.getFlag());
    // 6. QUEUEOFFSET — 占位，后续回填
    encoderBuffer.putLong(0L);
    // 7. PHYSICALOFFSET — 占位，后续回填
    encoderBuffer.putLong(0L);
    // 8. SYSFLAG
    encoderBuffer.putInt(msgInner.getSysFlag());
    // 9. BORNTIMESTAMP
    encoderBuffer.putLong(msgInner.getBornTimestamp());
    // 10. BORNHOST
    encoderBuffer.put(msgInner.getBornHostBytes());
    // 11. STORETIMESTAMP — 占位，后续回填
    encoderBuffer.putLong(0L);
    // 12. STOREHOSTADDRESS
    encoderBuffer.put(msgInner.getStoreHostBytes());
    // 13. RECONSUMETIMES
    encoderBuffer.putInt(msgInner.getReconsumeTimes());
    // 14. Prepared Transaction Offset
    encoderBuffer.putLong(msgInner.getPreparedTransactionOffset());
    // 15. BODYLENGTH + BODY
    encoderBuffer.putInt(bodyLength);
    if (bodyLength > 0) {
        encoderBuffer.put(body);
    }
    // 16. TOPICLENGTH + TOPIC
    msgInner.getVersion().putTopicLength(encoderBuffer, topicLength);
    encoderBuffer.put(topicData);
    // 17. PROPERTIESLENGTH + PROPERTIES
    encoderBuffer.putShort(propertiesLength);
    if (propertiesLength > 0) {
        encoderBuffer.put(propertiesData);
    }

    // flip 准备读取
    encoderBuffer.flip();

    // 保存到消息对象中，后续在 doAppend() 中使用
    msgInner.setEncodedBuff(encoderBuffer);

    return null; // null 表示编码成功
}
```

## 7. DefaultMappedFile 内存映射

### 7.1 核心概念：三位置模型

DefaultMappedFile 是 RocketMQ 对内存映射文件的封装。它有三个关键的位置指针，
理解它们的关系是理解整个存储层的关键。

```
                    0                                              fileSize (1GB)
                    │                                                │
                    ▼                                                ▼
  MappedFile:       ┌────────────┬──────────┬──────────┬─────────────┐
                    │  已刷盘数据  │ 已提交数据 │ 已写入数据 │   空闲空间    │
                    └────────────┴──────────┴──────────┴─────────────┘
                    ▲            ▲          ▲          ▲
                    │            │          │          │
               fileFromOffset  flushed   committed   wrote
                              Position   Position   Position

  关系约束：
  flushedPosition <= committedPosition <= wrotePosition <= fileSize

  注意：只有在 TransientStorePool 模式下，committedPosition 才有意义。
  普通模式下 committedPosition 始终等于 wrotePosition。
```

### 7.2 类定义与核心字段

```java
/**
 * DefaultMappedFile — RocketMQ 内存映射文件的核心实现。
 * 
 * 每个 DefaultMappedFile 对应磁盘上的一个文件。
 * CommitLog 的文件大小默认 1GB，ConsumeQueue 的文件大小默认 6MB。
 * 文件名即起始偏移量。
 */
public class DefaultMappedFile extends AbstractMappedFile {

    // ======== 静态统计 ========
    // 全局维度的 mmap 虚拟内存占用和 page cache 占用统计
    public static final AtomicLong TOTAL_MAPPED_VIRTUAL_MEMORY = new AtomicLong(0);
    public static final AtomicInteger TOTAL_MAPPED_FILES = new AtomicInteger(0);

    // ======== 位置指针 ========
    // 已写入位置：通过 CAS 更新，保证并发安全
    protected final AtomicInteger wrotePosition = new AtomicInteger(0);
    // 已提交位置：仅 TransientStorePool 模式下使用
    protected final AtomicInteger committedPosition = new AtomicInteger(0);
    // 已刷盘位置
    protected final AtomicInteger flushedPosition = new AtomicInteger(0);

    // ======== 文件属性 ========
    protected int fileSize;              // 文件大小
    protected long fileFromOffset;       // 文件起始偏移量（文件名）
    protected File file;                 // 文件对象
    protected String fileName;           // 文件名

    // ======== 内存映射 ========
    protected FileChannel fileChannel;          // 文件通道
    protected MappedByteBuffer mappedByteBuffer; // mmap 映射的 ByteBuffer

    // ======== TransientStorePool 模式 ========
    // 堆外内存缓冲区，用于写入
    // 启用后：写入 writeBuffer → commit → fileChannel
    // 不启用：直接写入 mappedByteBuffer
    protected ByteBuffer writeBuffer = null;
    protected TransientStorePool transientStorePool = null;

    // ======== 时间戳 ========
    private volatile long storeTimestamp = 0;     // 最近一次存储的时间戳
    private long firstCreateInQueue = Long.MAX_VALUE; // 首次创建时间

    // ======== 生命周期 ========
    private volatile boolean available = true;     // 是否可用
    private final AtomicInteger referenceCount = new AtomicInteger(1); // 引用计数
```

### 7.3 初始化 — init()

```java
/**
 * 初始化 MappedFile。
 * 核心操作：创建文件、建立 mmap 映射。
 */
private void init(final String fileName, final int fileSize) throws IOException {

    this.fileName = fileName;
    this.fileSize = fileSize;
    this.file = new File(fileName);
    this.fileFromOffset = Long.parseLong(
        this.file.getName()); // 文件名就是起始偏移量！

    boolean ok = false;

    // 确保父目录存在
    MappedFile.ensureDirOK(this.file.getParent());

    try {
        // 打开文件通道（读写模式）
        this.fileChannel = new RandomAccessFile(
            this.file, "rw").getChannel();

        // ★★★ 核心：建立内存映射 ★★★
        // FileChannel.map() 调用底层的 mmap() 系统调用
        // 参数：
        //   MapMode.READ_WRITE — 可读可写
        //   position = 0       — 从文件开头映射
        //   size = fileSize    — 映射整个文件（默认 1GB）
        //
        // 注意：此时并没有真正分配物理内存！
        // 只是在进程的虚拟地址空间中预留了一段区域。
        // 实际的物理内存分配发生在第一次访问时（Page Fault）。
        this.mappedByteBuffer = this.fileChannel.map(
            FileChannel.MapMode.READ_WRITE, 0, fileSize);

        // 更新统计
        TOTAL_MAPPED_VIRTUAL_MEMORY.addAndGet(fileSize);
        TOTAL_MAPPED_FILES.incrementAndGet();

        ok = true;
    } catch (FileNotFoundException e) {
        log.error("Failed to create file " + this.fileName, e);
        throw e;
    } catch (IOException e) {
        log.error("Failed to map file " + this.fileName, e);
        throw e;
    } finally {
        if (!ok && this.fileChannel != null) {
            this.fileChannel.close();
        }
    }
}
```

### 7.4 appendMessagesInner() — 追加消息

```java
/**
 * 在 MappedFile 内部追加消息。
 * 由 CommitLog 调用，此时已持有全局写入锁。
 *
 * @param msg      消息对象
 * @param cb       回调（DefaultAppendMessageCallback）
 * @param ctx      写入上下文
 * @return 追加结果
 */
public AppendMessageResult appendMessagesInner(
        final MessageExt msg,
        final AppendMessageCallback cb,
        PutMessageContext ctx) {

    assert msg != null;
    assert cb != null;

    // ---- 步骤1：获取当前写入位置 ----
    int currentPos = this.wrotePosition.get();

    // 安全检查：写入位置不能超过文件大小
    if (currentPos >= this.fileSize) {
        log.error("MappedFile.appendMessage return null, "
                  + "wrotePosition: {} fileSize: {}",
                  currentPos, this.fileSize);
        return new AppendMessageResult(AppendMessageStatus.UNKNOWN_ERROR);
    }

    // ---- 步骤2：获取写入 buffer ----
    // 关键选择：使用 writeBuffer 还是 mappedByteBuffer？
    //
    // 如果 writeBuffer != null（TransientStorePool 模式）：
    //   写入 writeBuffer（堆外直接内存）
    //   后续通过 commit() 写入 fileChannel
    //   优点：写入不经过 Page Cache，避免脏页回写干扰
    //
    // 如果 writeBuffer == null（普通模式）：
    //   写入 mappedByteBuffer（mmap 映射的内存）
    //   数据直接进入 Page Cache
    //   优点：实现简单，一次 copy

    ByteBuffer byteBuffer = this.writeBuffer != null 
                            ? this.writeBuffer.slice() 
                            : this.mappedByteBuffer.slice();

    // 设置 buffer 的写入起始位置
    byteBuffer.position(currentPos);

    // ---- 步骤3：回调执行真正的写入 ----
    AppendMessageResult result;
    if (msg instanceof MessageExtBrokerInner) {
        // 单条消息
        result = cb.doAppend(
            this.getFileFromOffset(),  // 文件起始偏移量
            byteBuffer,                // 写入的 buffer
            this.fileSize - currentPos, // 剩余可写空间
            (MessageExtBrokerInner) msg,
            ctx);
    } else if (msg instanceof MessageExtBatch) {
        // 批量消息
        result = cb.doAppend(
            this.getFileFromOffset(),
            byteBuffer,
            this.fileSize - currentPos,
            (MessageExtBatch) msg,
            ctx);
    } else {
        return new AppendMessageResult(AppendMessageStatus.UNKNOWN_ERROR);
    }

    // ---- 步骤4：CAS 更新写入位置 ----
    // 注意：这里使用 CAS 而不是简单的 set
    // 虽然在全局锁保护下理论上不需要 CAS，
    // 但这是一种防御性编程，确保在异常情况下的正确性
    this.wrotePosition.addAndGet(result.getWroteBytes());

    // ---- 步骤5：记录最新的存储时间戳 ----
    this.storeTimestamp = result.getStoreTimestamp();

    return result;
}
```

### 7.5 flush() — 刷盘

```java
/**
 * 将内存中的数据刷写到磁盘。
 *
 * @param flushLeastPages 最少刷几页（0 = 强制刷，不管有多少数据）
 * @return 刷盘后的位置
 */
public int flush(final int flushLeastPages) {

    // 检查是否有足够的数据需要刷盘
    if (this.isAbleToFlush(flushLeastPages)) {

        // 增加引用计数，防止刷盘过程中文件被关闭
        if (this.hold()) {
            int value = getReadPosition();

            try {
                // 根据模式选择刷盘方式
                if (this.writeBuffer != null 
                    || this.fileChannel.position() != 0) {
                    // TransientStorePool 模式：
                    // 数据已经通过 commit() 写入了 fileChannel
                    // 这里调用 force() 刷盘
                    this.fileChannel.force(false);
                } else {
                    // 普通 mmap 模式：
                    // 数据在 mappedByteBuffer 中（Page Cache）
                    // 调用 force() 将 dirty pages 写入磁盘
                    this.mappedByteBuffer.force();
                }
            } catch (Throwable e) {
                log.error("Error occurred when force data to disk.", e);
            }

            // 更新刷盘位置
            this.flushedPosition.set(value);

            // 释放引用
            this.release();
        } else {
            log.warn("in flush, hold failed, flush offset = " 
                     + this.flushedPosition.get());
            this.flushedPosition.set(getReadPosition());
        }
    }
    return this.getFlushedPosition();
}

/**
 * 判断是否需要刷盘。
 *
 * @param flushLeastPages 最少页数阈值
 *   0 = 有数据就刷
 *   >0 = 积攒到指定页数后才刷
 */
private boolean isAbleToFlush(final int flushLeastPages) {
    int flushed = this.flushedPosition.get();
    int write = getReadPosition();

    // 文件已满，强制刷盘
    if (this.isFull()) {
        return true;
    }

    // 如果指定了最少页数
    if (flushLeastPages > 0) {
        // 计算待刷数据的页数
        // OS_PAGE_SIZE = 4096 (4KB)
        return ((write / OS_PAGE_SIZE) - (flushed / OS_PAGE_SIZE)) 
               >= flushLeastPages;
    }

    // flushLeastPages=0 且有新数据，则刷盘
    return write > flushed;
}
```

### 7.6 commit() — 提交（TransientStorePool 模式）

```java
/**
 * 将 writeBuffer 中的数据提交到 fileChannel。
 * 仅在 TransientStorePool 模式下有意义。
 *
 * 数据流：writeBuffer → fileChannel → 磁盘
 * 两步操作：commit (writeBuffer→fileChannel) + flush (fileChannel→磁盘)
 *
 * @param commitLeastPages 最少提交页数
 * @return 提交后的位置
 */
public int commit(final int commitLeastPages) {

    // 如果没有 writeBuffer，说明不是 TransientStorePool 模式
    // 直接返回已写入位置
    if (this.writeBuffer == null) {
        return this.wrotePosition.get();
    }

    // 检查是否有足够的数据需要提交
    if (this.isAbleToCommit(commitLeastPages)) {
        if (this.hold()) {
            this.commit0();
            this.release();
        } else {
            log.warn("in commit, hold failed, commit offset = " 
                     + this.committedPosition.get());
        }
    }

    // 如果所有数据都已提交且文件已满，归还 writeBuffer
    if (this.writeBuffer != null 
        && this.transientStorePool != null 
        && this.fileSize == this.committedPosition.get()) {
        this.transientStorePool.returnBuffer(this.writeBuffer);
        this.writeBuffer = null;
    }

    return this.committedPosition.get();
}

/**
 * 实际的提交操作：writeBuffer → fileChannel
 */
protected void commit0() {
    int writePos = this.wrotePosition.get();
    int lastCommittedPosition = this.committedPosition.get();

    if (writePos - lastCommittedPosition > 0) {
        try {
            // 创建 writeBuffer 的 slice
            ByteBuffer byteBuffer = this.writeBuffer.slice();
            byteBuffer.position(lastCommittedPosition);
            byteBuffer.limit(writePos);

            // 设置 fileChannel 的写入位置
            this.fileChannel.position(lastCommittedPosition);

            // 执行写入
            this.fileChannel.write(byteBuffer);

            // 更新已提交位置
            this.committedPosition.set(writePos);
        } catch (Throwable e) {
            log.error("Error occurred when commit data to FileChannel.", e);
        }
    }
}
```

### 7.7 warmMappedFile() — 预热

```java
/**
 * 预热 MappedFile。
 * 通过预先访问每个 page，触发 Page Fault，将文件数据加载到物理内存。
 * 避免运行时的随机 Page Fault 导致延迟抖动。
 *
 * @param type    刷盘类型
 * @param pages   需要预热的页数
 */
public void warmMappedFile(FlushDiskType type, int pages) {

    long beginTime = System.currentTimeMillis();
    ByteBuffer byteBuffer = this.mappedByteBuffer.slice();

    long flush = 0;
    long time = System.currentTimeMillis();

    // 遍历文件的每一个 page（4KB），写入 0 字节
    // 这会触发操作系统为每个 page 分配物理内存
    for (long i = 0, j = 0; i < this.fileSize; i += DefaultMappedFile.OS_PAGE_SIZE, j++) {

        // 写入 0 到每个 page 的第一个字节
        byteBuffer.put((int) i, (byte) 0);

        // 如果是同步刷盘模式，每写 pages 个 page 就刷一次
        if (type == FlushDiskType.SYNC_FLUSH) {
            if ((i / OS_PAGE_SIZE) - (flush / OS_PAGE_SIZE) >= pages) {
                flush = i;
                mappedByteBuffer.force();
            }
        }

        // 避免一直占用 CPU，适当 yield
        // 每处理 1000 个 page 打印一次日志
        if (j % 1000 == 0) {
            log.info("j={}, currentTime(ms)={}, costTime(ms)={}",
                     j, System.currentTimeMillis(),
                     System.currentTimeMillis() - time);
            time = System.currentTimeMillis();
            try {
                Thread.sleep(0); // 让出 CPU
            } catch (InterruptedException e) {
                log.error("Interrupted", e);
            }
        }
    }

    // 最后一次刷盘
    if (type == FlushDiskType.SYNC_FLUSH) {
        log.info("mapped file warm-up done, force to disk, mappedFile={}, costTime(ms)={}",
                 this.getFileName(),
                 System.currentTimeMillis() - beginTime);
        mappedByteBuffer.force();
    }

    log.info("mapped file warm-up done, mappedFile={}, costTime(ms)={}",
             this.getFileName(),
             System.currentTimeMillis() - beginTime);

    // ★★★ 调用 mlock() ★★★
    // 将映射区域锁定在物理内存中，防止被 swap 出去
    this.mlock();
}

/**
 * mlock — 锁定内存页。
 * 通过 JNA 调用 Linux 的 mlock() 系统调用。
 * 
 * 效果：
 * 1. 将 mmap 映射的内存页锁定在物理 RAM 中
 * 2. 防止操作系统将这些页 swap 到磁盘
 * 3. 保证消息读写的低延迟
 *
 * 注意：mlock() 需要足够的 RLIMIT_MEMLOCK 配额。
 * 生产环境通常需要配置 /etc/security/limits.conf。
 */
public void mlock() {
    final long beginTime = System.currentTimeMillis();
    final long address = ((DirectBuffer) this.mappedByteBuffer).address();
    Pointer pointer = new Pointer(address);

    // 调用 mlock
    int ret = CLibrary.INSTANCE.mlock(pointer, new NativeLong(this.fileSize));
    log.info("mlock {} {} {} ret = {} time = {}",
             address, this.fileName, this.fileSize,
             ret, System.currentTimeMillis() - beginTime);

    // 调用 madvise，通知内核这段内存会被顺序访问
    // MADV_WILLNEED: 提示内核提前预读
    ret = CLibrary.INSTANCE.madvise(
        pointer, new NativeLong(this.fileSize), 3 /* MADV_WILLNEED */);
    log.info("madvise {} {} {} ret = {} time = {}",
             address, this.fileName, this.fileSize,
             ret, System.currentTimeMillis() - beginTime);
}
```

## 8. MappedFileQueue 文件队列

### 8.1 核心概念

MappedFileQueue 管理一组 MappedFile，它们按偏移量顺序排列，
共同构成了一个逻辑上连续的存储空间。

```
  MappedFileQueue 的逻辑视图：

  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
  │ MappedFile 0 │ │ MappedFile 1 │ │ MappedFile 2 │ │ MappedFile 3 │
  │ offset=0     │ │ offset=1GB   │ │ offset=2GB   │ │ offset=3GB   │
  │ size=1GB     │ │ size=1GB     │ │ size=1GB     │ │ size=1GB     │
  │ [已删除]      │ │ [已满,只读]   │ │ [已满,只读]   │ │ [写入中]      │
  └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
  │←─── flushed ──→│←──────────── active ────────────────────────→│
```

### 8.3 getLastMappedFile() — 获取/创建最后一个文件

```java
/**
 * 获取最后一个 MappedFile。
 * 如果不存在或已满，根据 needCreate 决定是否创建新文件。
 *
 * @param startOffset  如果需要创建，以此偏移量为起点
 * @param needCreate   是否自动创建
 * @return MappedFile 或 null
 */
public MappedFile getLastMappedFile(final long startOffset, boolean needCreate) {

    // 计算新文件的起始偏移量
    // 关键逻辑：对齐到 mappedFileSize 的整数倍
    long createOffset = -1;

    MappedFile mappedFileLast = getLastMappedFile();

    if (mappedFileLast == null) {
        // 没有任何文件，创建第一个
        // 起始偏移量向下对齐到 mappedFileSize
        createOffset = startOffset - (startOffset % this.mappedFileSize);
    } else if (mappedFileLast.isFull()) {
        // 最后一个文件已满，计算下一个文件的起始偏移量
        createOffset = mappedFileLast.getFileFromOffset() + this.mappedFileSize;
    }

    if (createOffset != -1 && needCreate) {
        // 创建文件名：偏移量左补零到 20 位
        // 例如：offset=1073741824 → "00000000001073741824"
        String nextFilePath = this.storePath + File.separator 
            + UtilAll.offset2FileName(createOffset);

        // 预创建下一个文件（异步预分配，提高性能）
        String nextNextFilePath = this.storePath + File.separator 
            + UtilAll.offset2FileName(createOffset + this.mappedFileSize);

        MappedFile mappedFile = null;

        if (this.allocateMappedFileService != null) {
            // 异步创建：提交两个创建请求（当前文件 + 下一个文件）
            // 下一个文件的预创建可以在后台进行，减少写入时的等待
            mappedFile = this.allocateMappedFileService.putRequestAndReturnMappedFile(
                nextFilePath, nextNextFilePath, this.mappedFileSize);
        } else {
            // 同步创建
            try {
                mappedFile = new DefaultMappedFile(nextFilePath, this.mappedFileSize);
            } catch (IOException e) {
                log.error("create mappedFile exception", e);
            }
        }

        if (mappedFile != null) {
            // 标记是否为队列中的第一个文件
            if (this.mappedFiles.isEmpty()) {
                mappedFile.setFirstCreateInQueue(true);
            }
            // 加入文件列表
            this.mappedFiles.add(mappedFile);
        }

        return mappedFile;
    }

    return mappedFileLast;
}
```

### 8.4 findMappedFileByOffset() — O(1) 定位文件

```java
/**
 * 根据物理偏移量定位 MappedFile。
 * 
 * 这个方法的巧妙之处在于：利用文件等大小的特性，
 * 通过简单的数学运算实现 O(1) 定位。
 *
 * 原理：
 *   index = (targetOffset / fileSize) - (firstFileOffset / fileSize)
 *
 * 例如：
 *   文件大小 = 1GB = 1073741824
 *   第一个文件 offset = 2147483648 (2GB)
 *   目标 offset = 3221225472 (3GB)
 *   index = (3221225472 / 1073741824) - (2147483648 / 1073741824) = 3 - 2 = 1
 *   → 定位到列表中第 2 个文件（index=1）
 */
public MappedFile findMappedFileByOffset(
        final long offset, 
        final boolean returnFirstOnNotFound) {

    try {
        MappedFile firstMappedFile = this.getFirstMappedFile();
        MappedFile lastMappedFile = this.getLastMappedFile();

        if (firstMappedFile != null && lastMappedFile != null) {
            // 边界检查
            if (offset < firstMappedFile.getFileFromOffset() 
                || offset >= lastMappedFile.getFileFromOffset() 
                           + this.mappedFileSize) {

                log.warn("Offset not matched. Request offset: {}, "
                         + "firstOffset: {}, lastOffset: {}, "
                         + "mappedFileSize: {}, mappedFiles count: {}",
                         offset,
                         firstMappedFile.getFileFromOffset(),
                         lastMappedFile.getFileFromOffset() 
                             + this.mappedFileSize,
                         this.mappedFileSize,
                         this.mappedFiles.size());
            } else {
                // ★★★ O(1) 定位 ★★★
                int index = (int) (
                    (offset / this.mappedFileSize) 
                    - (firstMappedFile.getFileFromOffset() / this.mappedFileSize)
                );

                MappedFile targetFile = null;
                try {
                    targetFile = this.mappedFiles.get(index);
                } catch (Exception ignored) {
                }

                // 验证偏移量确实在这个文件的范围内
                if (targetFile != null 
                    && offset >= targetFile.getFileFromOffset()
                    && offset < targetFile.getFileFromOffset() 
                               + this.mappedFileSize) {
                    return targetFile;
                }

                // 如果 O(1) 定位失败（可能因为中间有文件被删除），
                // 回退到线性扫描
                for (MappedFile tmpMappedFile : this.mappedFiles) {
                    if (offset >= tmpMappedFile.getFileFromOffset()
                        && offset < tmpMappedFile.getFileFromOffset() 
                                   + this.mappedFileSize) {
                        return tmpMappedFile;
                    }
                }
            }

            if (returnFirstOnNotFound) {
                return firstMappedFile;
            }
        }
    } catch (Exception e) {
        log.error("findMappedFileByOffset Exception", e);
    }

    return null;
}
```

### 8.5 flush() 与 commit() — 队列级别的刷盘和提交

```java
/**
 * 队列级别的刷盘。
 * 从 flushedWhere 开始，找到对应的 MappedFile 并刷盘。
 *
 * @param flushLeastPages 最少刷盘页数
 * @return 是否有数据被刷盘
 */
public boolean flush(final int flushLeastPages) {
    boolean result = true;

    // 找到 flushedWhere 所在的 MappedFile
    MappedFile mappedFile = this.findMappedFileByOffset(
        this.flushedWhere, this.flushedWhere == 0);

    if (mappedFile != null) {
        // 获取最新存储时间戳
        long tmpTimeStamp = mappedFile.getStoreTimestamp();

        // 执行刷盘
        int offset = mappedFile.flush(flushLeastPages);

        // 计算刷盘后的全局偏移量
        long where = mappedFile.getFileFromOffset() + offset;
        result = where == this.flushedWhere;

        // 更新全局刷盘位置
        this.flushedWhere = where;

        if (0 == flushLeastPages) {
            this.storeTimestamp = tmpTimeStamp;
        }
    }

    return result;
}

/**
 * 队列级别的提交（TransientStorePool 模式）。
 */
public boolean commit(final int commitLeastPages) {
    boolean result = true;

    MappedFile mappedFile = this.findMappedFileByOffset(
        this.committedWhere, this.committedWhere == 0);

    if (mappedFile != null) {
        int offset = mappedFile.commit(commitLeastPages);
        long where = mappedFile.getFileFromOffset() + offset;
        result = where == this.committedWhere;
        this.committedWhere = where;
    }

    return result;
}
```

## 9. ConsumeQueue 索引构建

### 9.1 ConsumeQueue 概述

ConsumeQueue 是 RocketMQ 为消费场景设计的轻量级索引。
每条 ConsumeQueue 条目固定 20 字节，记录了消息在 CommitLog 中的物理位置。

```
  ConsumeQueue 条目格式（CQ_STORE_UNIT_SIZE = 20 字节）：

  ┌──────────────────┬──────────────┬──────────────────┐
  │  physicalOffset  │   bodySize   │     tagHash      │
  │     (8 bytes)    │  (4 bytes)   │    (8 bytes)     │
  ├──────────────────┼──────────────┼──────────────────┤
  │ CommitLog 中的    │ 消息体大小    │ Tag 的 hashCode  │
  │ 物理偏移量        │ （含头部）    │ 用于消费时过滤    │
  └──────────────────┴──────────────┴──────────────────┘

  单个 ConsumeQueue 文件大小：
  300000 条目 × 20 字节 = 6,000,000 字节 = 6MB

  消费流程：
  1. Consumer 提供 topic + queueId + logicOffset
  2. 定位 ConsumeQueue 文件和条目（O(1)：offset * 20 → file position）
  3. 读取 20 字节条目，获得 physicalOffset + bodySize
  4. 用 physicalOffset 从 CommitLog 中读取完整消息
  5. 如果 Consumer 订阅了 Tag 过滤，先比较 tagHash，不匹配则跳过
```

### 9.2 ConsumeQueue 类结构

```java
/**
 * ConsumeQueue — 消费队列索引。
 * 每个 Topic 的每个 QueueId 对应一个 ConsumeQueue 实例。
 *
 * 存储路径：~/store/consumequeue/{topic}/{queueId}/
 */
public class ConsumeQueue implements ConsumeQueueInterface, FileQueueLifeCycle {

    // 单条索引大小：20 字节
    public static final int CQ_STORE_UNIT_SIZE = 20;

    // 文件队列（管理多个 MappedFile）
    private final MappedFileQueue mappedFileQueue;

    // 所属 Topic
    private final String topic;
    // 队列 ID
    private final int queueId;

    // 临时写入 buffer（20 字节）
    private final ByteBuffer byteBufferIndex;

    // 存储路径
    private final String storePath;
    // 单文件大小（默认 6MB = 300000 * 20）
    private final int mappedFileSize;

    // 最大物理偏移量（对应 CommitLog 中的偏移量）
    private long maxPhysicOffset = -1;

    // 最小逻辑偏移量（已清理的旧数据之后的起始偏移量）
    private volatile long minLogicOffset = 0;

    // 关联的消息存储
    private final DefaultMessageStore defaultMessageStore;

    public ConsumeQueue(final String topic, final int queueId,
                        final String storePath, final int mappedFileSize,
                        final DefaultMessageStore defaultMessageStore) {
        this.storePath = storePath;
        this.mappedFileSize = mappedFileSize;
        this.defaultMessageStore = defaultMessageStore;
        this.topic = topic;
        this.queueId = queueId;

        // 构造存储路径：~/store/consumequeue/{topic}/{queueId}/
        String queueDir = this.storePath
            + File.separator + topic
            + File.separator + queueId;

        // 初始化文件队列
        this.mappedFileQueue = new MappedFileQueue(
            queueDir, mappedFileSize, null);

        // 分配 20 字节的临时 buffer
        this.byteBufferIndex = ByteBuffer.allocate(CQ_STORE_UNIT_SIZE);
    }
}
```

### 9.3 putMessagePositionInfo() — 写入索引条目

```java
/**
 * 向 ConsumeQueue 写入一条索引条目。
 * 
 * 由 ReputMessageService 通过 dispatcherList 调用。
 * 每条 CommitLog 消息被解析后，都会在对应的 ConsumeQueue 中写入一条 20 字节索引。
 *
 * @param offset     消息在 CommitLog 中的物理偏移量
 * @param size       消息的大小（字节数）
 * @param tagsCode   Tag 的 hashCode（long 类型）
 * @param cqOffset   在 ConsumeQueue 中的逻辑偏移量
 * @return 是否写入成功
 */
private boolean putMessagePositionInfo(
        final long offset,
        final int size,
        final long tagsCode,
        final long cqOffset) {

    // 如果这条消息已经被处理过（物理偏移量小于已知最大值），跳过
    if (offset + size <= this.maxPhysicOffset) {
        log.warn("Maybe try to build consume queue repeatedly, "
                 + "maxPhysicOffset={}, offset={}",
                 maxPhysicOffset, offset);
        return true;
    }

    // ---- 填充 20 字节的临时 buffer ----
    this.byteBufferIndex.flip();
    this.byteBufferIndex.limit(CQ_STORE_UNIT_SIZE);

    // 8 字节：物理偏移量
    this.byteBufferIndex.putLong(offset);
    // 4 字节：消息大小
    this.byteBufferIndex.putInt(size);
    // 8 字节：Tag 哈希值
    this.byteBufferIndex.putLong(tagsCode);

    // ---- 定位 MappedFile ----
    // ConsumeQueue 的文件偏移量 = 逻辑偏移量 × 20
    final long expectLogicOffset = cqOffset * CQ_STORE_UNIT_SIZE;

    // 获取或创建 MappedFile
    MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile(
        expectLogicOffset);

    if (mappedFile != null) {
        // 特殊处理：如果这是队列的第一个文件且不是从 offset=0 开始
        // 需要用空白填充前面的空间
        if (mappedFile.isFirstCreateInQueue() 
            && cqOffset != 0 
            && mappedFile.getWrotePosition() == 0) {

            // 设置最小逻辑偏移量
            this.minLogicOffset = expectLogicOffset;

            // 填充空白：从文件开头到 expectLogicOffset 之间填零
            this.fillPreBlank(mappedFile, expectLogicOffset);
            log.info("fill pre blank space, topic={}, queue={}, offset={}",
                     topic, queueId, expectLogicOffset);
        }

        // 验证：当前写入位置应该等于期望的逻辑偏移量（相对于文件）
        if (expectLogicOffset != 0L) {
            long currentLogicOffset = mappedFile.getFileFromOffset() 
                                     + mappedFile.getWrotePosition();
            if (expectLogicOffset < currentLogicOffset) {
                log.warn("Build consume queue repeatedly, "
                         + "expect={}, current={}, topic={}, queueId={}",
                         expectLogicOffset, currentLogicOffset,
                         topic, queueId);
                return true;
            }

            if (expectLogicOffset != currentLogicOffset) {
                log.warn("[BUG]logic queue order error, expect={}, "
                         + "current={}, topic={}, queueId={}, diff={}",
                         expectLogicOffset, currentLogicOffset,
                         topic, queueId,
                         expectLogicOffset - currentLogicOffset);
            }
        }

        // ---- 追加 20 字节到 MappedFile ----
        this.maxPhysicOffset = offset + size;
        return mappedFile.appendMessage(
            this.byteBufferIndex.array());
    }

    return false;
}
```

### 9.4 ConsumeQueue 恢复

```java
/**
 * 恢复 ConsumeQueue。
 * Broker 启动时调用，从最后一个文件向前扫描，找到有效数据的边界。
 *
 * 恢复策略：
 * 1. 从倒数第 3 个文件开始扫描（安全边界）
 * 2. 每次读取 20 字节，验证物理偏移量和大小的合法性
 * 3. 遇到全零的条目则停止
 * 4. 截断后面的无效数据
 */
public void recover() {
    final List<MappedFile> mappedFiles = this.mappedFileQueue.getMappedFiles();
    if (!mappedFiles.isEmpty()) {

        // 从倒数第 3 个文件开始
        int index = mappedFiles.size() - 3;
        if (index < 0) {
            index = 0;
        }

        int mappedFileSizeLogics = this.mappedFileSize;
        MappedFile mappedFile = mappedFiles.get(index);
        ByteBuffer byteBuffer = mappedFile.sliceByteBuffer();
        long processOffset = mappedFile.getFileFromOffset();
        long mappedFileOffset = 0;

        long maxExtAddr = 1;

        while (true) {
            // 每次处理 20 字节
            for (int i = 0; i < mappedFileSizeLogics; i += CQ_STORE_UNIT_SIZE) {
                // 读取 20 字节
                long offset = byteBuffer.getLong();   // 物理偏移量
                int size = byteBuffer.getInt();        // 消息大小
                long tagsCode = byteBuffer.getLong();   // Tag 哈希

                // 验证有效性
                if (offset >= 0 && size > 0) {
                    mappedFileOffset = i + CQ_STORE_UNIT_SIZE;
                    this.maxPhysicOffset = offset + size;
                } else {
                    // 遇到无效条目，恢复完成
                    log.info("recover current consume queue file over, "
                             + "file={}, offset={}",
                             mappedFile.getFileName(), i);
                    break;
                }
            }

            // 如果当前文件全部有效，继续下一个文件
            if (mappedFileOffset == mappedFileSizeLogics) {
                index++;
                if (index >= mappedFiles.size()) {
                    // 所有文件都有效
                    log.info("recover last consume queue file over, "
                             + "last mapped file={}",
                             mappedFile.getFileName());
                    break;
                } else {
                    mappedFile = mappedFiles.get(index);
                    byteBuffer = mappedFile.sliceByteBuffer();
                    processOffset = mappedFile.getFileFromOffset();
                    mappedFileOffset = 0;
                    log.info("recover next consume queue file, {}",
                             mappedFile.getFileName());
                }
            } else {
                // 当前文件只有部分有效
                log.info("recover current consume queue file done, "
                         + "file={}, offset={}",
                         mappedFile.getFileName(), processOffset + mappedFileOffset);
                break;
            }
        }

        // 截断后面的无效数据
        processOffset += mappedFileOffset;
        this.mappedFileQueue.setFlushedWhere(processOffset);
        this.mappedFileQueue.setCommittedWhere(processOffset);
        this.mappedFileQueue.truncateDirtyFiles(processOffset);
    }
}
```

## 10. ReputMessageService 异步分发

### 10.1 设计思想

ReputMessageService 是连接 CommitLog 和 ConsumeQueue/IndexFile 的桥梁。
它作为一个后台线程，持续从 CommitLog 中读取新写入的消息，
然后将索引信息分发到 ConsumeQueue 和 IndexFile。

```
  ReputMessageService 工作流程：

  CommitLog (写入完成)
       │
       │ reputFromOffset (追赶进度)
       ▼
  ReputMessageService.doReput()
       │
       ├─ commitLog.getData(reputFromOffset)  ← 读取 CommitLog 数据
       │
       ├─ parseDispatchRequest()               ← 解析消息格式
       │
       ├─ doDispatch(dispatchRequest)          ← 分发到各构建器
       │       │
       │       ├─ CommitLogDispatcherBuildConsumeQueue
       │       │       └─ consumeQueueStore.putMessagePositionInfoWrapper()
       │       │
       │       └─ CommitLogDispatcherBuildIndex
       │               └─ indexService.buildIndex()
       │
       └─ advance reputFromOffset              ← 推进分发进度
```

### 10.2 核心实现

```java
/**
 * ReputMessageService — 消息重放/分发服务。
 * 
 * 继承 ServiceThread，是一个后台守护线程。
 * 以 1ms 的间隔不断从 CommitLog 中读取新消息并分发。
 */
class ReputMessageService extends ServiceThread {

    // 当前重放进度（CommitLog 中的物理偏移量）
    private volatile long reputFromOffset = 0;

    @Override
    public void run() {
        DefaultMessageStore.log.info(
            this.getServiceName() + " service started");

        while (!this.isStopped()) {
            try {
                // 每隔 1ms 执行一次重放
                Thread.sleep(1);
                this.doReput();
            } catch (Exception e) {
                DefaultMessageStore.log.warn(
                    this.getServiceName() + " service has exception.", e);
            }
        }

        DefaultMessageStore.log.info(
            this.getServiceName() + " service end");
    }
}
```

### 10.3 doReput() — 核心重放逻辑

```java
/**
 * 执行消息重放。
 * 从 CommitLog 中读取数据，解析消息，分发到 ConsumeQueue 和 IndexFile。
 */
private void doReput() {

    // 确保 reputFromOffset 不低于 CommitLog 的最小偏移量
    if (this.reputFromOffset < DefaultMessageStore.this
            .commitLog.getMinOffset()) {
        log.warn("The reputFromOffset={} is smaller than "
                 + "commitLog's minOffset={}",
                 this.reputFromOffset,
                 DefaultMessageStore.this.commitLog.getMinOffset());
        this.reputFromOffset = DefaultMessageStore.this
            .commitLog.getMinOffset();
    }

    // 循环处理：只要还有新数据就继续
    for (boolean doNext = true; this.isCommitLogAvailable() && doNext; ) {

        // ---- 步骤1：从 CommitLog 读取数据 ----
        // getData() 返回从 reputFromOffset 开始的连续数据
        // 通常是一个 MappedFile 的 slice
        SelectMappedBufferResult result = DefaultMessageStore.this
            .commitLog.getData(reputFromOffset);

        if (result != null) {
            try {
                this.reputFromOffset = result.getStartOffset();

                // ---- 步骤2：逐条解析消息 ----
                for (int readSize = 0; readSize < result.getSize() && doNext; ) {

                    // 解析一条消息，构造 DispatchRequest
                    DispatchRequest dispatchRequest = DefaultMessageStore.this
                        .commitLog.checkMessageAndReturnSize(
                            result.getByteBuffer(),
                            false,  // checkCRC
                            false   // readBody
                        );

                    int size = dispatchRequest.getBufferSize() == -1 
                               ? dispatchRequest.getMsgSize() 
                               : dispatchRequest.getBufferSize();

                    if (dispatchRequest.isSuccess()) {
                        if (size > 0) {
                            // ---- 步骤3：分发到各构建器 ----
                            DefaultMessageStore.this.doDispatch(dispatchRequest);

                            // 如果 Broker 不是 SLAVE，且开启了长轮询
                            // 通知等待的消费者有新消息到来
                            if (BrokerRole.SLAVE 
                                != DefaultMessageStore.this
                                    .getMessageStoreConfig().getBrokerRole()
                                && DefaultMessageStore.this.brokerConfig
                                    .isLongPollingEnable()
                                && DefaultMessageStore.this
                                    .messageArrivingListener != null) {

                                DefaultMessageStore.this
                                    .messageArrivingListener.arriving(
                                        dispatchRequest.getTopic(),
                                        dispatchRequest.getQueueId(),
                                        dispatchRequest.getConsumeQueueOffset() + 1,
                                        dispatchRequest.getTagsCode(),
                                        dispatchRequest.getStoreTimestamp(),
                                        dispatchRequest.getBitMap(),
                                        dispatchRequest.getPropertiesMap());
                            }

                            // ---- 步骤4：推进重放偏移量 ----
                            this.reputFromOffset += size;
                            readSize += size;

                            // 统计
                            if (DefaultMessageStore.this
                                .getMessageStoreConfig().getBrokerRole() 
                                == BrokerRole.SLAVE) {
                                DefaultMessageStore.this
                                    .storeStatsService
                                    .getSinglePutMessageTopicTimesTotal(
                                        dispatchRequest.getTopic())
                                    .add(1);
                                DefaultMessageStore.this
                                    .storeStatsService
                                    .getSinglePutMessageTopicSizeTotal(
                                        dispatchRequest.getTopic())
                                    .add(dispatchRequest.getMsgSize());
                            }
                        } else if (size == 0) {
                            // 遇到文件末尾的空白填充
                            // 跳转到下一个文件
                            this.reputFromOffset = DefaultMessageStore.this
                                .commitLog.rollNextFile(
                                    this.reputFromOffset);
                            readSize = result.getSize();
                        }
                    } else {
                        // 解析失败（消息损坏等）
                        doNext = false;
                        if (size > 0) {
                            log.error("[BUG]read total count not equals msg total size."
                                      + " reputFromOffset={}", reputFromOffset);
                            this.reputFromOffset += size;
                        }
                    }
                }
            } finally {
                result.release();
            }
        } else {
            doNext = false;
        }
    }
}
```

## 11. IndexFile 哈希索引

### 11.1 IndexFile 布局

IndexFile 是 RocketMQ 用于按消息 Key 检索消息的哈希索引结构。
它允许用户通过 `UNIQ_KEY`、`KEYS`、`TAG` 等维度快速查找消息的物理位置。

```
  IndexFile 文件布局：

  ┌─────────────────────────────────────────────────────────────────┐
  │                      IndexHeader (40 字节)                       │
  ├──────────────┬──────────────┬──────────────┬──────────────┬─────┤
  │ BeginTimestamp│ EndTimestamp │BeginPhyOffset│EndPhyOffset  │ ... │
  │    (8B)       │    (8B)      │    (8B)      │    (8B)      │     │
  ├──────────────┴──────────────┴──────────────┴──────────────┴─────┤
  │              HashSlots (5,000,000 × 4 字节 = 20MB)              │
  │  ┌──────┬──────┬──────┬──────┬─────────────────────────────────┐│
  │  │Slot 0│Slot 1│Slot 2│Slot 3│  ...    Slot 4,999,999          ││
  │  │ (4B) │ (4B) │ (4B) │ (4B) │                                 ││
  │  └──────┴──────┴──────┴──────┴─────────────────────────────────┘│
  ├────────────────────────────────────────────────────────────────────┤
  │           IndexEntries (20,000,000 × 20 字节 = 400MB)            │
  │  ┌──────────────────────────────────────────────────────────────┐│
  │  │Entry 0: keyHash(4) + phyOffset(8) + timeDiff(4) + prev(4)  ││
  │  │Entry 1: keyHash(4) + phyOffset(8) + timeDiff(4) + prev(4)  ││
  │  │  ...                                                        ││
  │  │Entry 19,999,999                                             ││
  │  └──────────────────────────────────────────────────────────────┘│
  └────────────────────────────────────────────────────────────────────┘

  文件总大小：40 + 5,000,000 × 4 + 20,000,000 × 20
            = 40 + 20,000,000 + 400,000,000
            = 420,000,040 字节 ≈ 400.5 MB
```

### 11.2 IndexHeader 详解

```java
/**
 * IndexHeader — IndexFile 的文件头。
 * 固定 40 字节，记录文件的基本统计信息。
 */
public class IndexHeader {

    public static final int INDEX_HEADER_SIZE = 40;

    // 索引覆盖的时间范围
    private final AtomicLong beginTimestamp = new AtomicLong(0);  // 最早消息的存储时间
    private final AtomicLong endTimestamp = new AtomicLong(0);    // 最晚消息的存储时间

    // 索引覆盖的物理偏移量范围
    private final AtomicLong beginPhyOffset = new AtomicLong(0);  // 最小物理偏移量
    private final AtomicLong endPhyOffset = new AtomicLong(0);    // 最大物理偏移量

    // 计数器
    private final AtomicInteger hashSlotCount = new AtomicInteger(0);  // 已使用的槽数
    private final AtomicInteger indexCount = new AtomicInteger(1);     // 已使用的索引条目数
    // 注意：indexCount 从 1 开始，0 表示"无前驱"（链表终止条件）

    // 基于 mmap 的 ByteBuffer
    private final ByteBuffer byteBuffer;

    /**
     * 将 header 写入 ByteBuffer。
     */
    public void updateByteBuffer() {
        this.byteBuffer.putLong(0, this.beginTimestamp.get());     // offset 0
        this.byteBuffer.putLong(8, this.endTimestamp.get());       // offset 8
        this.byteBuffer.putLong(16, this.beginPhyOffset.get());    // offset 16
        this.byteBuffer.putLong(24, this.endPhyOffset.get());      // offset 24
        this.byteBuffer.putInt(32, this.hashSlotCount.get());      // offset 32
        this.byteBuffer.putInt(36, this.indexCount.get());         // offset 36
    }
}
```

### 11.3 IndexFile.putKey() — 写入索引

```java
/**
 * 向 IndexFile 写入一个索引条目。
 * 使用头插法解决哈希冲突（类似 HashMap 1.7 之前的实现）。
 *
 * @param key        索引键（例如 "topic#UNIQ_KEY_VALUE"）
 * @param phyOffset  消息在 CommitLog 中的物理偏移量
 * @param storeTimestamp 消息的存储时间戳
 * @return 是否写入成功（文件未满则成功）
 */
public boolean putKey(
        final String key,
        final long phyOffset,
        final long storeTimestamp) {

    // 检查是否已满
    if (this.indexHeader.getIndexCount() < this.indexNum) {

        // ---- 步骤1：计算哈希值和槽位 ----
        int keyHash = indexKeyHashMethod(key);
        int slotPos = keyHash % this.hashSlotNum;
        // 注意：hashSlotNum 默认 5,000,000

        // 计算槽位在文件中的绝对偏移量
        int absSlotPos = IndexHeader.INDEX_HEADER_SIZE 
                         + slotPos * hashSlotSize;

        // ---- 步骤2：读取当前槽位的值 ----
        // 槽位存储的是该哈希桶的链表头索引
        // 0 表示空桶（因为 indexCount 从 1 开始）
        int slotValue;
        try {
            slotValue = this.mappedByteBuffer.getInt(absSlotPos);
        } catch (Exception e) {
            slotValue = 0;
        }

        // 处理无效的槽值
        if (slotValue <= invalidIndex || slotValue > this.indexHeader.getIndexCount()) {
            slotValue = invalidIndex;  // invalidIndex = 0
        }

        // ---- 步骤3：计算时间差 ----
        // 存储时间差而不是绝对时间，节省空间（4字节 vs 8字节）
        // timeDiff = (当前消息时间 - 文件起始时间) / 1000
        // 4 字节可以表示约 49 天的时间范围
        long timeDiff = storeTimestamp - this.indexHeader.getBeginTimestamp();
        timeDiff = timeDiff / 1000; // 精度降至秒级

        if (this.indexHeader.getBeginTimestamp() <= 0) {
            timeDiff = 0;
        } else if (timeDiff > Integer.MAX_VALUE) {
            timeDiff = Integer.MAX_VALUE;
        } else if (timeDiff < 0) {
            timeDiff = 0;
        }

        // ---- 步骤4：计算索引条目在文件中的位置 ----
        int absIndexPos = IndexHeader.INDEX_HEADER_SIZE 
                         + this.hashSlotNum * hashSlotSize  // 跳过 HashSlots 区域
                         + this.indexHeader.getIndexCount() * indexSize;

        // ---- 步骤5：写入索引条目（20 字节）----
        // 格式：keyHash(4) + phyOffset(8) + timeDiff(4) + prevSlotValue(4)
        this.mappedByteBuffer.putInt(absIndexPos, keyHash);
        this.mappedByteBuffer.putLong(absIndexPos + 4, phyOffset);
        this.mappedByteBuffer.putInt(absIndexPos + 4 + 8, (int) timeDiff);
        // ★★★ 头插法：新条目指向原来的链表头 ★★★
        this.mappedByteBuffer.putInt(absIndexPos + 4 + 8 + 4, slotValue);

        // ---- 步骤6：更新槽位（指向新的链表头）----
        this.mappedByteBuffer.putInt(absSlotPos, 
                                    this.indexHeader.getIndexCount());

        // ---- 步骤7：更新 Header ----
        if (this.indexHeader.getIndexCount() <= 1) {
            this.indexHeader.setBeginPhyOffset(phyOffset);
            this.indexHeader.setBeginTimestamp(storeTimestamp);
        }

        if (invalidIndex == slotValue) {
            // 新的哈希桶
            this.indexHeader.incHashSlotCount();
        }

        this.indexHeader.incIndexCount();
        this.indexHeader.setEndPhyOffset(phyOffset);
        this.indexHeader.setEndTimestamp(storeTimestamp);

        return true;
    } else {
        // 文件已满
        log.warn("Over index file capacity: index count = {} "
                 + "index max num = {}",
                 this.indexHeader.getIndexCount(), this.indexNum);
        return false;
    }
}
```

### 11.4 IndexFile.selectPhyOffset() — 查询索引

```java
/**
 * 根据 Key 和时间范围查询消息的物理偏移量列表。
 *
 * @param phyOffsets    输出参数，收集匹配的物理偏移量
 * @param key           查询的 Key
 * @param maxNum        最大返回数量
 * @param begin         时间范围起始
 * @param end           时间范围结束
 */
public void selectPhyOffset(
        final List<Long> phyOffsets,
        final String key,
        final int maxNum,
        final long begin,
        final long end) {

    if (this.mappedFile.hold()) {
        // ---- 步骤1：定位哈希桶 ----
        int keyHash = indexKeyHashMethod(key);
        int slotPos = keyHash % this.hashSlotNum;
        int absSlotPos = IndexHeader.INDEX_HEADER_SIZE 
                         + slotPos * hashSlotSize;

        try {
            // 读取哈希桶的链表头
            int slotValue = this.mappedByteBuffer.getInt(absSlotPos);

            if (slotValue <= invalidIndex 
                || slotValue > this.indexHeader.getIndexCount()
                || this.indexHeader.getIndexCount() <= 1) {
                // 空桶或无效值
            } else {
                // ---- 步骤2：遍历哈希链表 ----
                // 从链表头开始，逐个检查
                for (int nextIndexToRead = slotValue; ; ) {

                    if (phyOffsets.size() >= maxNum) {
                        break; // 已收集够了
                    }

                    // 计算条目在文件中的位置
                    int absIndexPos = IndexHeader.INDEX_HEADER_SIZE
                        + this.hashSlotNum * hashSlotSize
                        + nextIndexToRead * indexSize;

                    // 读取 20 字节条目
                    int keyHashRead = this.mappedByteBuffer.getInt(absIndexPos);
                    long phyOffsetRead = this.mappedByteBuffer.getLong(
                        absIndexPos + 4);
                    int timeDiff = this.mappedByteBuffer.getInt(
                        absIndexPos + 4 + 8);
                    int prevIndexRead = this.mappedByteBuffer.getInt(
                        absIndexPos + 4 + 8 + 4);

                    // 时间差转绝对时间
                    long timeRead = this.indexHeader.getBeginTimestamp() 
                                    + (long) timeDiff * 1000;

                    // 时间范围过滤
                    boolean timeMatched = (timeRead >= begin) 
                                         && (timeRead <= end);

                    // ★★★ 哈希匹配 + 时间匹配 ★★★
                    // 注意：这里只比较 keyHash，不比较原始 key
                    // 因此可能有哈希冲突导致的误匹配
                    // 调用者需要在读取完整消息后再次验证
                    if (keyHash == keyHashRead && timeMatched) {
                        phyOffsets.add(phyOffsetRead);
                    }

                    // ---- 步骤3：跟踪链表的下一个节点 ----
                    if (prevIndexRead <= invalidIndex
                        || prevIndexRead > this.indexHeader.getIndexCount()
                        || prevIndexRead == nextIndexToRead) {
                        // 链表结束或检测到环
                        break;
                    }

                    // 移动到链表的下一个节点
                    nextIndexToRead = prevIndexRead;
                }
            }
        } catch (Exception e) {
            log.error("selectPhyOffset exception", e);
        } finally {
            this.mappedFile.release();
        }
    }
}
```

> **头插法 vs 尾插法**：
>
> IndexFile 使用头插法构建哈希链表，这意味着：
> - 写入时间复杂度 O(1)：只需要读旧槽值、写新条目、更新槽位
> - 查询时先遇到最新的条目（对按时间倒序查询友好）
> - 不需要遍历整个链表来找到尾部
>
> 这与 JDK HashMap 1.7 的策略相同。但与 HashMap 不同的是，
> IndexFile 不需要担心并发安全问题，因为只有 ReputMessageService
> 这一个线程在写入。

### 11.5 IndexService.buildIndex() — 构建索引

```java
/**
 * 为一条消息构建索引。
 * 会根据消息的多个维度分别建立索引条目。
 *
 * @param req 分发请求（包含消息元数据）
 */
public void buildIndex(DispatchRequest req) {
    // 获取或创建 IndexFile
    IndexFile indexFile = retryGetAndCreateIndexFile();
    if (indexFile != null) {
        long endPhyOffset = indexFile.getEndPhyOffset();
        DispatchRequest msg = req;
        String topic = msg.getTopic();
        String keys = msg.getKeys();
        String uniqKey = msg.getUniqKey();

        // 如果消息的物理偏移量小于当前 IndexFile 的末尾偏移量，
        // 说明这条消息已经被索引过了，跳过
        if (msg.getCommitLogOffset() < endPhyOffset) {
            return;
        }

        final int tranType = MessageSysFlag.getTransactionValue(
            msg.getSysFlag());

        // 事务消息的特殊处理
        switch (tranType) {
            case MessageSysFlag.TRANSACTION_NOT_TYPE:
            case MessageSysFlag.TRANSACTION_PREPARED_TYPE:
            case MessageSysFlag.TRANSACTION_COMMIT_TYPE:
                break;
            case MessageSysFlag.TRANSACTION_ROLLBACK_TYPE:
                return; // Rollback 消息不建索引
        }

        // ============ 索引维度1：UNIQ_KEY ============
        // topic#UNIQ_KEY_VALUE
        // UNIQ_KEY 是 Producer 端生成的全局唯一 ID
        if (uniqKey != null && uniqKey.length() > 0) {
            indexFile = putKey(indexFile, msg, 
                buildKey(topic, uniqKey));
            if (indexFile == null) {
                log.error("putKey error commitlog {} uniqKey {}",
                          req.getCommitLogOffset(), uniqKey);
                return;
            }
        }

        // ============ 索引维度2：KEYS ============
        // topic#key1, topic#key2, ...
        // KEYS 支持空格分隔的多个 key
        if (keys != null && keys.length() > 0) {
            String[] keyArray = keys.split(
                MessageConst.KEY_SEPARATOR);
            for (int i = 0; i < keyArray.length; i++) {
                String key = keyArray[i];
                if (key.length() > 0) {
                    indexFile = putKey(indexFile, msg, 
                        buildKey(topic, key));
                    if (indexFile == null) {
                        log.error("putKey error commitlog {} key {}",
                                  req.getCommitLogOffset(), key);
                        return;
                    }
                }
            }
        }
    } else {
        log.error("build index error, stop building index");
    }
}

/**
 * 构建索引 Key。
 * 格式：topic + "#" + key
 */
private String buildKey(final String topic, final String key) {
    return topic + "#" + key;
}

/**
 * 写入索引条目，如果当前 IndexFile 已满则创建新文件。
 */
private IndexFile putKey(IndexFile indexFile, DispatchRequest msg, String idxKey) {
    for (boolean ok = indexFile.putKey(
            idxKey, 
            msg.getCommitLogOffset(),
            msg.getStoreTimestamp()); !ok; ) {
        // 当前 IndexFile 已满，创建新的
        log.warn("Index file [{}] is over, trying to create a new index file.",
                 indexFile.getFileName());
        indexFile = retryGetAndCreateIndexFile();
        if (null == indexFile) {
            return null;
        }
        ok = indexFile.putKey(
            idxKey, 
            msg.getCommitLogOffset(),
            msg.getStoreTimestamp());
    }
    return indexFile;
}
```

## 12. FlushManager 刷盘机制

### 12.1 刷盘策略概览

RocketMQ 支持两种刷盘策略，通过 `flushDiskType` 配置：

```
刷盘策略选择：

  ┌─────────────────────────────────────────────────────────────┐
  │                     FlushManager                             │
  │                                                               │
  │  flushDiskType = SYNC_FLUSH                                   │
  │    └─ GroupCommitService (同步刷盘)                             │
  │         └─ 双缓冲交换策略                                       │
  │         └─ 每条消息写入后等待刷盘完成                              │
  │         └─ 数据安全性最高                                       │
  │         └─ 吞吐量相对较低                                       │
  │                                                               │
  │  flushDiskType = ASYNC_FLUSH                                  │
  │    ├─ FlushRealTimeService (异步刷盘)                          │
  │    │     └─ 定时刷盘（默认 500ms 间隔）                          │
  │    │     └─ 页数阈值（默认 4 页 = 16KB）                        │
  │    │     └─ 吞吐量高，极端情况可能丢失少量数据                      │
  │    │                                                           │
  │    └─ CommitRealTimeService (TransientStorePool 模式)          │
  │          └─ writeBuffer → fileChannel 的定时提交                 │
  │          └─ 默认 200ms 间隔                                     │
  └─────────────────────────────────────────────────────────────┘
```

### 12.2 GroupCommitService — 同步刷盘

```java
/**
 * GroupCommitService — 同步刷盘服务。
 * 
 * 核心设计：双缓冲交换（Double Buffer Swap）。
 *
 * 为什么使用双缓冲？
 * - 写入线程提交刷盘请求到 requestsWrite
 * - 刷盘线程从 requestsRead 中读取并处理
 * - 两个列表定期交换
 * - 这样写入线程和刷盘线程互不阻塞
 *
 * 类似于图形渲染中的双缓冲技术。
 */
class GroupCommitService extends FlushCommitLogService {

    // 写入缓冲：接收写入线程的刷盘请求
    private volatile LinkedList<GroupCommitRequest> requestsWrite 
        = new LinkedList<>();

    // 读取缓冲：刷盘线程处理的请求列表
    private volatile LinkedList<GroupCommitRequest> requestsRead 
        = new LinkedList<>();

    // 读写锁保护交换操作
    private final PutMessageSpinLock lock = new PutMessageSpinLock();

    /**
     * 提交刷盘请求（由写入线程调用）。
     */
    public synchronized void putRequest(final GroupCommitRequest request) {
        lock.lock();
        try {
            this.requestsWrite.add(request);
        } finally {
            lock.unlock();
        }
        // 唤醒刷盘线程
        this.wakeup();
    }

    /**
     * 交换读写缓冲区。
     * 这是双缓冲的核心操作。
     */
    private void swapRequests() {
        lock.lock();
        try {
            LinkedList<GroupCommitRequest> tmp = this.requestsWrite;
            this.requestsWrite = this.requestsRead;
            this.requestsRead = tmp;
        } finally {
            lock.unlock();
        }
    }

    /**
     * 执行刷盘。
     */
    private void doCommit() {
        if (!this.requestsRead.isEmpty()) {
            for (GroupCommitRequest req : this.requestsRead) {
                // 判断刷盘是否已经追上了请求的偏移量
                boolean flushOK = CommitLog.this.mappedFileQueue
                    .getFlushedWhere() >= req.getNextOffset();

                // 最多尝试 2 次
                for (int i = 0; i < 2 && !flushOK; i++) {
                    // 执行刷盘：flushLeastPages=0 表示强制刷
                    CommitLog.this.mappedFileQueue.flush(0);

                    flushOK = CommitLog.this.mappedFileQueue
                        .getFlushedWhere() >= req.getNextOffset();
                }

                // 通知等待的写入线程
                req.wakeupCustomer(flushOK 
                    ? PutMessageStatus.PUT_OK 
                    : PutMessageStatus.FLUSH_DISK_TIMEOUT);
            }

            // 更新 StoreCheckpoint 的 physicMsgTimestamp
            long storeTimestamp = CommitLog.this.mappedFileQueue
                .getStoreTimestamp();
            if (storeTimestamp > 0) {
                CommitLog.this.defaultMessageStore
                    .getStoreCheckpoint()
                    .setPhysicMsgTimestamp(storeTimestamp);
            }

            // 清空已处理的请求列表（为下次复用做准备）
            this.requestsRead = new LinkedList<>();
        } else {
            // 没有请求也刷一次（处理残留的脏数据）
            CommitLog.this.mappedFileQueue.flush(0);
        }
    }

    @Override
    public void run() {
        CommitLog.log.info(this.getServiceName() + " service started");

        while (!this.isStopped()) {
            try {
                // 等待唤醒或超时（默认 10ms）
                this.waitForRunning(10);

                // 执行刷盘
                this.doCommit();
            } catch (Exception e) {
                CommitLog.log.warn(this.getServiceName() 
                    + " service has exception.", e);
            }
        }

        // 停止前最后处理一次
        // 正常关闭时确保所有数据都刷盘
        try {
            Thread.sleep(10);
        } catch (InterruptedException e) {
            CommitLog.log.warn(this.getServiceName() 
                + " interrupted", e);
        }

        // 交换 + 处理剩余请求
        synchronized (this) {
            this.swapRequests();
        }
        this.doCommit();

        CommitLog.log.info(this.getServiceName() + " service end");
    }

    @Override
    protected void onWaitEnd() {
        // waitForRunning 结束后，交换读写缓冲区
        this.swapRequests();
    }
}
```

### 12.3 GroupCommitRequest — 刷盘请求

```java
/**
 * 同步刷盘请求。
 * 每条消息写入后创建一个请求，等待刷盘完成。
 */
public static class GroupCommitRequest {

    // 需要刷盘到的目标偏移量
    // = 消息的物理偏移量 + 消息大小
    // 刷盘完成的判断条件：flushedWhere >= nextOffset
    private final long nextOffset;

    // 使用 CompletableFuture 实现异步等待
    private CompletableFuture<PutMessageStatus> flushOKFuture 
        = new CompletableFuture<>();

    // 超时时间（默认 5000ms）
    private final long deadLine;

    public GroupCommitRequest(long nextOffset, long timeoutMillis) {
        this.nextOffset = nextOffset;
        this.deadLine = System.nanoTime() 
                        + (timeoutMillis * 1_000_000);
    }

    public long getNextOffset() {
        return nextOffset;
    }

    /**
     * 唤醒等待的写入线程。
     */
    public void wakeupCustomer(final PutMessageStatus putMessageStatus) {
        this.flushOKFuture.complete(putMessageStatus);
    }

    /**
     * 获取刷盘结果的 Future。
     * 写入线程通过这个 Future 等待刷盘完成。
     */
    public CompletableFuture<PutMessageStatus> future() {
        return flushOKFuture;
    }
}
```

### 12.4 FlushRealTimeService — 异步刷盘

```java
/**
 * FlushRealTimeService — 异步刷盘服务。
 * 
 * 定时刷盘，不等待每条消息。
 * 在性能和数据安全之间取得平衡。
 */
class FlushRealTimeService extends FlushCommitLogService {

    // 上次刷盘时间
    private long lastFlushTimestamp = 0;
    // 打印次数（控制日志输出频率）
    private long printTimes = 0;

    @Override
    public void run() {
        CommitLog.log.info(this.getServiceName() + " service started");

        while (!this.isStopped()) {
            // 从配置中读取参数
            // flushCommitLogTimed: 是否使用固定间隔（而非 sleep 后立即刷）
            boolean flushCommitLogTimed = CommitLog.this
                .defaultMessageStore.getMessageStoreConfig()
                .isFlushCommitLogTimed();

            // flushIntervalCommitLog: 刷盘间隔，默认 500ms
            int interval = CommitLog.this.defaultMessageStore
                .getMessageStoreConfig().getFlushIntervalCommitLog();

            // flushCommitLogLeastPages: 最少刷盘页数，默认 4 页 = 16KB
            int flushPhysicQueueLeastPages = CommitLog.this
                .defaultMessageStore.getMessageStoreConfig()
                .getFlushCommitLogLeastPages();

            // flushCommitLogThoroughInterval: 强制刷盘间隔，默认 10s
            // 即使不满 4 页，超过 10s 也强制刷一次
            int flushPhysicQueueThoroughInterval = CommitLog.this
                .defaultMessageStore.getMessageStoreConfig()
                .getFlushCommitLogThoroughInterval();

            // 检查是否到了强制刷盘时间
            boolean printFlushProgress = false;
            long currentTimeMillis = System.currentTimeMillis();
            if (currentTimeMillis >= (this.lastFlushTimestamp 
                                      + flushPhysicQueueThoroughInterval)) {
                this.lastFlushTimestamp = currentTimeMillis;
                flushPhysicQueueLeastPages = 0; // 0 = 强制刷
                printFlushProgress = (printTimes++ % 10) == 0;
            }

            try {
                // 等待间隔
                if (flushCommitLogTimed) {
                    Thread.sleep(interval);
                } else {
                    this.waitForRunning(interval);
                }

                if (printFlushProgress) {
                    this.printFlushProgress();
                }

                // 开始刷盘
                long begin = System.currentTimeMillis();
                CommitLog.this.mappedFileQueue.flush(
                    flushPhysicQueueLeastPages);

                long past = System.currentTimeMillis() - begin;
                if (past > 500) {
                    log.info("Flush data to disk costs {} ms", past);
                }

                // 更新 StoreCheckpoint
                long storeTimestamp = CommitLog.this.mappedFileQueue
                    .getStoreTimestamp();
                if (storeTimestamp > 0) {
                    CommitLog.this.defaultMessageStore
                        .getStoreCheckpoint()
                        .setPhysicMsgTimestamp(storeTimestamp);
                }
            } catch (Throwable e) {
                CommitLog.log.warn(this.getServiceName() 
                    + " service has exception.", e);
                this.printFlushProgress();
            }
        }

        // 停止时确保所有数据刷盘
        boolean result = false;
        for (int i = 0; i < RETRY_TIMES_OVER && !result; i++) {
            result = CommitLog.this.mappedFileQueue.flush(0);
            CommitLog.log.info(this.getServiceName() 
                + " service shutdown, retry " + (i + 1) 
                + " times " + (result ? "OK" : "Not OK"));
        }

        this.printFlushProgress();
        CommitLog.log.info(this.getServiceName() + " service end");
    }
}
```

### 12.5 CommitRealTimeService — TransientStorePool 提交

```java
/**
 * CommitRealTimeService — TransientStorePool 模式下的提交服务。
 * 
 * 当启用 TransientStorePool 时，数据先写入 DirectByteBuffer（writeBuffer），
 * 然后由 CommitRealTimeService 定时将数据从 writeBuffer 提交到 fileChannel，
 * 最后再由 FlushRealTimeService 将 fileChannel 的数据刷到磁盘。
 *
 * 数据流：writeBuffer → fileChannel → 磁盘
 *         (commit)        (flush)
 */
class CommitRealTimeService extends FlushCommitLogService {

    // 上次提交时间
    private long lastCommitTimestamp = 0;

    @Override
    public void run() {
        CommitLog.log.info(this.getServiceName() + " service started");

        while (!this.isStopped()) {
            // commitIntervalCommitLog: 提交间隔，默认 200ms
            int interval = CommitLog.this.defaultMessageStore
                .getMessageStoreConfig()
                .getCommitIntervalCommitLog();

            // commitCommitLogLeastPages: 最少提交页数，默认 4 页
            int commitDataLeastPages = CommitLog.this
                .defaultMessageStore.getMessageStoreConfig()
                .getCommitCommitLogLeastPages();

            // commitCommitLogThoroughInterval: 强制提交间隔，默认 200ms
            int commitDataThoroughInterval = CommitLog.this
                .defaultMessageStore.getMessageStoreConfig()
                .getCommitCommitLogThoroughInterval();

            // 检查是否到了强制提交时间
            long begin = System.currentTimeMillis();
            if (begin >= (this.lastCommitTimestamp 
                          + commitDataThoroughInterval)) {
                this.lastCommitTimestamp = begin;
                commitDataLeastPages = 0; // 强制提交
            }

            try {
                // 执行提交：writeBuffer → fileChannel
                boolean result = CommitLog.this.mappedFileQueue
                    .commit(commitDataLeastPages);

                long end = System.currentTimeMillis();
                if (!result) {
                    // 有数据被提交了，更新时间戳并唤醒刷盘线程
                    this.lastCommitTimestamp = end;
                    // 唤醒 FlushRealTimeService 进行刷盘
                    flushCommitLogService.wakeup();
                }

                if (end - begin > 500) {
                    log.info("Commit data to file costs {} ms", end - begin);
                }

                // 等待间隔
                this.waitForRunning(interval);
            } catch (Throwable e) {
                CommitLog.log.warn(this.getServiceName() 
                    + " service has exception.", e);
            }
        }

        // 停止时强制提交
        boolean result = false;
        for (int i = 0; i < RETRY_TIMES_OVER && !result; i++) {
            result = CommitLog.this.mappedFileQueue.commit(0);
            CommitLog.log.info(this.getServiceName() 
                + " service shutdown, retry " + (i + 1) 
                + " times " + (result ? "OK" : "Not OK"));
        }

        CommitLog.log.info(this.getServiceName() + " service end");
    }
}
```

> **TransientStorePool 的设计动机**：
>
> 在普通 mmap 模式下，写入数据直接进入 Page Cache。当 Page Cache 中的
> dirty page 积压过多时，操作系统会触发 writeback（pdflush/kswapd），
> 这会导致写入线程被阻塞（dirty throttling），表现为写入延迟抖动。
>
> TransientStorePool 的解决方案是：
> 1. 预分配一批 DirectByteBuffer（堆外内存），不经过 Page Cache
> 2. 消息先写入 DirectByteBuffer
> 3. CommitRealTimeService 定时将数据从 DirectByteBuffer 提交到 fileChannel
> 4. FlushRealTimeService 再从 fileChannel 刷到磁盘
>
> 这样写入线程永远不会被 Page Cache 的 writeback 阻塞，
> 代价是多了一次内存拷贝（DirectBuffer → FileChannel）和宕机时可能丢失更多数据。

## 13. handleDiskFlushAndHA

### 13.1 方法实现

```java
/**
 * 处理刷盘和 HA 同步的组合结果。
 * 
 * 这个方法的核心思想是：
 * 将刷盘结果和 HA 同步结果合并为一个最终的写入结果。
 * 两个操作可以并行进行，最终取最差的状态。
 *
 * @param result            追加消息的结果
 * @param putMessageResult  写入结果对象
 * @param msg               消息
 * @param flushResultFuture 刷盘结果 Future
 * @param replicaResultFuture HA 同步结果 Future
 * @return 最终的写入结果 Future
 */
public CompletableFuture<PutMessageResult> handleDiskFlushAndHA(
        AppendMessageResult result,
        PutMessageResult putMessageResult,
        MessageExt msg,
        CompletableFuture<PutMessageStatus> flushResultFuture,
        CompletableFuture<PutMessageStatus> replicaResultFuture) {

    // ★★★ 核心逻辑：合并刷盘和 HA 的 Future ★★★
    //
    // thenCombine 的语义：
    // 当 flushResultFuture 和 replicaResultFuture 都完成后，
    // 执行合并逻辑，取"最差"的状态作为最终状态
    return flushResultFuture.thenCombine(replicaResultFuture, 
        (flushStatus, replicaStatus) -> {

        // 检查刷盘结果
        if (flushStatus != PutMessageStatus.PUT_OK) {
            putMessageResult.setPutMessageStatus(
                PutMessageStatus.FLUSH_DISK_TIMEOUT);
        }

        // 检查 HA 同步结果
        if (replicaStatus != PutMessageStatus.PUT_OK) {
            putMessageResult.setPutMessageStatus(replicaStatus);
        }

        return putMessageResult;
    });
}
```

### 13.2 submitFlushRequest() — 提交刷盘请求

```java
/**
 * 提交刷盘请求。
 * 根据刷盘策略的不同，行为不同。
 */
public CompletableFuture<PutMessageStatus> submitFlushRequest(
        AppendMessageResult result, 
        MessageExt msg) {

    if (FlushDiskType.SYNC_FLUSH == this.defaultMessageStore
            .getMessageStoreConfig().getFlushDiskType()) {

        // ======== 同步刷盘 ========
        final GroupCommitService service = 
            (GroupCommitService) this.flushCommitLogService;

        // 判断消息是否需要等待刷盘完成
        if (msg.isWaitStoreMsgOK()) {
            // 创建刷盘请求
            // nextOffset = 消息的物理偏移量 + 消息大小
            GroupCommitRequest request = new GroupCommitRequest(
                result.getWroteOffset() + result.getWroteBytes(),
                this.defaultMessageStore.getMessageStoreConfig()
                    .getSyncFlushTimeout());

            // 提交到 GroupCommitService
            service.putRequest(request);

            // 返回 Future，调用者可以异步等待
            return request.future();
        } else {
            // 不需要等待，唤醒刷盘线程就返回
            service.wakeup();
            return CompletableFuture.completedFuture(
                PutMessageStatus.PUT_OK);
        }
    } else {
        // ======== 异步刷盘 ========
        if (!this.defaultMessageStore.getMessageStoreConfig()
                .isTransientStorePoolEnable()) {
            // 普通模式：唤醒 FlushRealTimeService
            flushCommitLogService.wakeup();
        } else {
            // TransientStorePool 模式：唤醒 CommitRealTimeService
            commitLogService.wakeup();
        }

        // 异步刷盘不等待，立即返回成功
        return CompletableFuture.completedFuture(
            PutMessageStatus.PUT_OK);
    }
}
```

### 13.3 submitReplicaRequest() — 提交 HA 同步请求

```java
/**
 * 提交 HA 同步请求。
 * 
 * HA 同步策略：
 * - SYNC_MASTER：同步复制，等待从节点确认
 * - ASYNC_MASTER：异步复制，不等待
 */
public CompletableFuture<PutMessageStatus> submitReplicaRequest(
        AppendMessageResult result,
        MessageExt msg) {

    if (BrokerRole.SYNC_MASTER == this.defaultMessageStore
            .getMessageStoreConfig().getBrokerRole()) {

        // 同步复制模式
        HAService service = this.defaultMessageStore.getHaService();
        if (msg.isWaitStoreMsgOK()) {
            if (service.isSlaveOK(
                    this.defaultMessageStore.getMessageStoreConfig()
                        .getHaSlaveFallbehindMax())) {

                // 创建 HA 同步请求
                GroupCommitRequest request = new GroupCommitRequest(
                    result.getWroteOffset() + result.getWroteBytes(),
                    this.defaultMessageStore.getMessageStoreConfig()
                        .getSlaveTimeout());

                // 提交并等待
                service.putRequest(request);
                service.getWaitNotifyObject().wakeupAll();

                return request.future();
            } else {
                // Slave 落后太多，报告错误但不阻塞写入
                return CompletableFuture.completedFuture(
                    PutMessageStatus.SLAVE_NOT_AVAILABLE);
            }
        }
    }

    // 异步复制或不需要等待：直接返回成功
    return CompletableFuture.completedFuture(
        PutMessageStatus.PUT_OK);
}
```

### 13.4 刷盘 + HA 的状态组合矩阵

```
┌──────────────────┬────────────────────┬──────────────────────┐
│  Flush 结果       │   HA 结果           │  最终 PutMessage 状态  │
├──────────────────┼────────────────────┼──────────────────────┤
│  PUT_OK          │  PUT_OK            │  PUT_OK              │
│  PUT_OK          │  SLAVE_NOT_AVAILABLE│  SLAVE_NOT_AVAILABLE │
│  PUT_OK          │  FLUSH_SLAVE_TIMEOUT│  FLUSH_SLAVE_TIMEOUT │
│  FLUSH_DISK_TIMEOUT│ PUT_OK           │  FLUSH_DISK_TIMEOUT  │
```

## 14. StoreCheckpoint 崩溃恢复

### 14.1 StoreCheckpoint 概述

StoreCheckpoint 是 RocketMQ 存储层的"崩溃恢复锚点"。
它记录了 CommitLog、ConsumeQueue、IndexFile 各自的刷盘进度，
Broker 异常重启后通过这些检查点来确定恢复的起始位置。

### 14.2 数据结构

```java
/**
 * StoreCheckpoint — 存储检查点。
 * 
 * 底层是一个 mmap 映射的小文件（单文件），
 * 存储 6 个 long 类型的检查点值。
 */
public class StoreCheckpoint {

    // 底层的内存映射文件
    private final MappedFile mappedFile;
    // 映射的 ByteBuffer
    private final MappedByteBuffer mappedByteBuffer;

    // ======== 6 个检查点 ========

    // CommitLog 最后刷盘的消息时间戳
    private volatile long physicMsgTimestamp = 0;

    // ConsumeQueue 最后刷盘的消息时间戳
    private volatile long logicsMsgTimestamp = 0;

    // IndexFile 最后索引的消息时间戳
    private volatile long indexMsgTimestamp = 0;

    // Master 的刷盘偏移量
    private volatile long masterFlushedOffset = 0;

    // 确认的物理偏移量
    private volatile long confirmPhyOffset = 0;

    // ConsumeQueue 对应的 CommitLog 物理偏移量
    private volatile long logicsPhysicalOffset = 0;

    /**
     * 构造方法：打开或创建检查点文件。
     */
    public StoreCheckpoint(final String scpPath) throws IOException {
        // 创建底层文件
        this.mappedFile = new DefaultMappedFile(scpPath, 
            MappedFile.OS_PAGE_SIZE); // 一个 page 就够了

        this.mappedByteBuffer = this.mappedFile.getMappedByteBuffer();

        // 从文件中读取已有的检查点值
        this.physicMsgTimestamp = this.mappedByteBuffer.getLong(0);
        this.logicsMsgTimestamp = this.mappedByteBuffer.getLong(8);
        this.indexMsgTimestamp = this.mappedByteBuffer.getLong(16);
        this.masterFlushedOffset = this.mappedByteBuffer.getLong(24);
        this.confirmPhyOffset = this.mappedByteBuffer.getLong(32);

        // 如果文件足够大（48 字节），读取第 6 个值
        if (this.mappedByteBuffer.capacity() > 40) {
            this.logicsPhysicalOffset = this.mappedByteBuffer.getLong(40);
        }

        log.info("store checkpoint: physicMsgTimestamp={}, "
                 + "logicsMsgTimestamp={}, indexMsgTimestamp={}",
                 new Timestamp(physicMsgTimestamp),
                 new Timestamp(logicsMsgTimestamp),
                 new Timestamp(indexMsgTimestamp));
    }
}
```

### 14.3 flush() — 持久化检查点

```java
/**
 * 将检查点值刷写到磁盘。
 * 在 CommitLog/ConsumeQueue/IndexFile 的刷盘操作之后调用。
 */
public void flush() {
    // 将各检查点值写入 ByteBuffer
    this.mappedByteBuffer.putLong(0, this.physicMsgTimestamp);
    this.mappedByteBuffer.putLong(8, this.logicsMsgTimestamp);
    this.mappedByteBuffer.putLong(16, this.indexMsgTimestamp);
    this.mappedByteBuffer.putLong(24, this.masterFlushedOffset);
    this.mappedByteBuffer.putLong(32, this.confirmPhyOffset);
    this.mappedByteBuffer.putLong(40, this.logicsPhysicalOffset);

    // 强制刷盘
    this.mappedByteBuffer.force();
}
```

### 14.4 getMinTimestamp() — 安全恢复时间

```java
/**
 * 获取最小检查点时间戳 — 用于确定恢复起始点。
 * 
 * 关键设计：取 physicMsgTimestamp 和 logicsMsgTimestamp 的最小值，
 * 然后再减去 3000ms 的安全裕量。
 *
 * 为什么取最小值？
 * - physicMsgTimestamp 是 CommitLog 的刷盘时间
 * - logicsMsgTimestamp 是 ConsumeQueue 的刷盘时间
 * - 取最小值确保从"最落后"的那个时间点开始恢复
 * - 这样不会遗漏任何未索引的消息
 *
 * 为什么减 3000ms？
 * - 安全裕量，覆盖时间戳的精度误差
 * - 宁可多恢复一些（重复处理是安全的），也不要少恢复（数据丢失）
 *
 * @return 安全的最小时间戳
 */
public long getMinTimestamp() {
    long min = Math.min(this.physicMsgTimestamp, this.logicsMsgTimestamp);
    // 减去 3 秒安全裕量
    min -= 3000;
    if (min < 0) {
        min = 0;
    }
    return min;
}
```

### 14.5 恢复流程概述

```
Broker 启动时的恢复流程：

1. 检查 abort 文件是否存在
   ├── 存在 → 上次是异常退出 → 需要完整恢复
   └── 不存在 → 上次是正常退出 → 可以快速恢复

2. 加载 CommitLog 文件
   └── 恢复 wrotePosition / flushedPosition

3. 加载 ConsumeQueue 文件
   └── 恢复到有效边界

4. 加载 IndexFile
   └── 检查时间戳是否在 StoreCheckpoint 之前

5. 恢复策略：
   ├── 正常恢复（recoverNormally）
   │     └── 从最后 3 个 CommitLog 文件开始扫描
   │     └── 验证每条消息的 MAGIC_CODE 和 CRC
   │     └── 截断无效数据
   │
   └── 异常恢复（recoverAbnormally）
         └── 从 StoreCheckpoint.getMinTimestamp() 开始
         └── 找到该时间点对应的 CommitLog 文件
         └── 逐条验证并重建索引
         └── 更加保守，耗时更长

6. 重建分发进度
   └── ReputMessageService.reputFromOffset = CommitLog.maxOffset
   └── 如果 ConsumeQueue 落后于 CommitLog → 从落后处开始重新分发

7. 删除 abort 文件
   └── 标记本次启动为正常状态

8. 创建新的 abort 文件
   └── 如果正常关闭时会删除它
   └── 如果异常退出则保留，供下次启动检测
```

### 14.6 恢复代码核心片段

```java
/**
 * 正常恢复：从最后 3 个 CommitLog 文件开始扫描。
 */
public void recoverNormally(long maxPhyOffsetOfConsumeQueue) {
    // 是否检查 CRC
    boolean checkCRCOnRecover = this.defaultMessageStore
        .getMessageStoreConfig().isCheckCRCOnRecover();

    final List<MappedFile> mappedFiles = this.mappedFileQueue.getMappedFiles();

    if (!mappedFiles.isEmpty()) {
        // 从倒数第 3 个文件开始（安全边界）
        int index = mappedFiles.size() - 3;
        if (index < 0) {
            index = 0;
        }

        MappedFile mappedFile = mappedFiles.get(index);
        ByteBuffer byteBuffer = mappedFile.sliceByteBuffer();
        long processOffset = mappedFile.getFileFromOffset();
        long mappedFileOffset = 0;

        while (true) {
            // 解析消息并验证合法性
            DispatchRequest dispatchRequest = this.checkMessageAndReturnSize(
                byteBuffer, checkCRCOnRecover, true);

            int size = dispatchRequest.getMsgSize();

            if (dispatchRequest.isSuccess() && size > 0) {
                // 有效消息，继续
                mappedFileOffset += size;
            } else if (dispatchRequest.isSuccess() && size == 0) {
                // 到达文件末尾，切换到下一个文件
                index++;
                if (index >= mappedFiles.size()) {
                    // 所有文件都处理完了
                    log.info("recover last commit log file over, "
                             + "file={}", mappedFile.getFileName());
                    break;
                } else {
                    mappedFile = mappedFiles.get(index);
                    byteBuffer = mappedFile.sliceByteBuffer();
                    processOffset = mappedFile.getFileFromOffset();
                    mappedFileOffset = 0;
                    log.info("recover next commit log file, {}",
                             mappedFile.getFileName());
                }
            } else if (!dispatchRequest.isSuccess()) {
                // 消息验证失败，停止恢复
                log.info("recover commit log file end, {}",
                         mappedFile.getFileName());
                break;
            }
        }

        // 计算有效数据的结束位置
        processOffset += mappedFileOffset;

        // 截断后面的无效数据
        this.mappedFileQueue.setFlushedWhere(processOffset);
        this.mappedFileQueue.setCommittedWhere(processOffset);
        this.mappedFileQueue.truncateDirtyFiles(processOffset);

        // 清理 ConsumeQueue 中多余的数据
        if (maxPhyOffsetOfConsumeQueue >= processOffset) {
            log.warn("maxPhyOffsetOfConsumeQueue({}) >= processOffset({}), "
                     + "truncate dirty logic files.",
                     maxPhyOffsetOfConsumeQueue, processOffset);
            this.defaultMessageStore.truncateDirtyLogicFiles(processOffset);
        }
    } else {
        // 没有 CommitLog 文件，重置所有偏移量
        log.warn("The commitlog files are deleted, "
                 + "and delete the consume queue files");
        this.mappedFileQueue.setFlushedWhere(0);
        this.mappedFileQueue.setCommittedWhere(0);
        this.defaultMessageStore.destroyLogics();
    }
}
```

### 16.2 性能优化要点

```
1. 顺序写 vs 随机写
   ├── 所有 Topic 混合写入同一个 CommitLog → 纯顺序追加
   ├── 利用磁盘顺序写的高带宽（HDD 100MB/s+，SSD 1GB/s+）
   └── 避免随机 I/O 导致的性能悬崖

2. 锁优化
   ├── 两层锁设计：Topic-Queue 细粒度锁 + 全局串行锁
   ├── 预编码在锁外执行，最小化锁持有时间
   ├── 自旋锁 vs ReentrantLock 可配置
   └── 锁内操作时间通常在微秒级

3. 内存映射 (mmap)
   ├── FileChannel.map() → 零拷贝，避免用户态/内核态数据拷贝
   ├── warmMappedFile() → 预加载，避免运行时 Page Fault
   ├── mlock() → 内存锁定，防止被 swap
   └── madvise(MADV_WILLNEED) → 提示内核预读

4. 异步分发
   ├── CommitLog 写入和索引构建解耦
   ├── ReputMessageService 独立线程异步分发
   ├── 写入路径只需等待 CommitLog 写入完成
   └── ConsumeQueue/IndexFile 的构建不影响写入延迟

5. 文件预分配
   ├── AllocateMappedFileService 异步预创建下一个文件
   ├── 避免写满切换时的文件创建延迟
   └── 提前 warmup 新文件

6. 批量刷盘
   ├── 攒够一定页数再刷（flushCommitLogLeastPages）
   ├── GroupCommitService 批量处理多个刷盘请求
   └── 减少 fsync 调用次数
```

### 16.3 数据可靠性保障

```
1. CRC32 校验
   ├── 消息写入时计算 bodyCRC
   ├── 消费时验证，检测数据损坏
   └── 恢复时可选 checkCRC

2. 魔数验证
   ├── MESSAGE_MAGIC_CODE (0xdaa320a7) → 正常消息
   ├── BLANK_MAGIC_CODE (0xcbd43194) → 文件末尾空白
   └── 扫描时通过魔数判断消息边界

3. StoreCheckpoint
   ├── 记录 CommitLog/ConsumeQueue/IndexFile 的刷盘进度
   ├── 异常重启后从检查点开始恢复
   └── 3 秒安全裕量（getMinTimestamp() - 3000ms）

4. abort 文件
   ├── 启动时创建，正常关闭时删除
   ├── 如果启动时 abort 存在 → 上次异常退出 → 完整恢复
   └── 如果启动时 abort 不存在 → 上次正常退出 → 快速恢复

5. 同步刷盘（SYNC_FLUSH）
   ├── 每条消息等待 fsync 完成后才返回
   └── 保证数据不会因为进程崩溃而丢失

6. 同步复制（SYNC_MASTER）
   ├── 消息写入后等待至少一个 Slave 确认
   ├── Master 宕机后 Slave 可以无损接管
   └── 配合 minInSyncReplicas 保证多副本
```

### 16.5 面试高频问题

**Q1：RocketMQ 为什么所有 Topic 混合写入一个 CommitLog？**

```
A：核心原因是保证顺序写。如果每个 Topic 独立文件（像 Kafka），
当 Topic 数量很多时（上万级），磁盘会退化为随机写，性能急剧下降。
混合写入 CommitLog 后，无论有多少 Topic，磁盘始终是顺序追加写入，
吞吐量与 Topic 数量无关。代价是消费时需要额外的索引（ConsumeQueue）
来定位消息，增加了一次随机读，但读可以通过 Page Cache 缓解。
```

**Q2：RocketMQ 如何保证消息不丢失？**

```
A：三个层面：
1. 写入层：同步刷盘（SYNC_FLUSH）保证消息落盘后才返回 ACK
2. 复制层：同步复制（SYNC_MASTER）保证至少一个 Slave 确认
3. 恢复层：StoreCheckpoint + abort 文件 + CRC 校验，保证崩溃后数据恢复

最高可靠性配置：SYNC_FLUSH + SYNC_MASTER
此时消息被刷盘到 Master 磁盘 + 同步到至少一个 Slave 后才返回成功。
```

**Q3：CommitLog 的写入锁为什么默认用自旋锁？**

```
A：因为锁内操作极快（只是 buffer copy + CAS 更新位置），
通常在微秒级完成。自旋锁在这种场景下的性能优于 ReentrantLock，
因为避免了线程上下文切换的开销（通常 1~10 微秒）。
但如果启用了 TransientStorePool 或消息体很大，锁持有时间变长，
应切换为 ReentrantLock。
```

**Q4：ConsumeQueue 的作用是什么？为什么不直接从 CommitLog 消费？**

```
A：ConsumeQueue 是消费索引，每条 20 字节，记录消息在 CommitLog 中的位置。
如果直接从 CommitLog 消费，每个消费者都需要扫描整个 CommitLog，
过滤出属于自己 Topic-Queue 的消息，效率极低。
ConsumeQueue 提供了按 Topic-Queue 维度的有序索引，
消费者通过 offset 可以 O(1) 定位到目标消息的物理位置。
```

**Q5：IndexFile 如何处理哈希冲突？**

```
A：使用链表法（头插法）。每个 HashSlot 存储链表头的索引编号，
每个 IndexEntry 有一个 prevSlotValue 字段指向前一个条目。
查询时从链表头开始遍历，比较 keyHash 和时间范围。
注意：IndexFile 只比较 keyHash 不比较原始 key，
因此存在哈希冲突导致的误匹配，调用者需二次验证。
```

**Q6：TransientStorePool 解决了什么问题？**

```
A：解决了 mmap 写入时可能被 OS Page Cache 的 dirty page 回写阻塞的问题。
当 dirty page 积压过多时，内核的 dirty throttling 机制会阻塞写入线程，
导致写入延迟抖动。TransientStorePool 使用 DirectByteBuffer 绕过 Page Cache，
写入线程永远不会被阻塞。代价是多一次内存拷贝和更大的数据丢失窗口。
```

**Q7：ReputMessageService 如果挂了怎么办？**

```
A：ReputMessageService 挂掉不会影响消息写入（CommitLog 写入是独立的），
但会导致 ConsumeQueue 和 IndexFile 停止更新，消费者无法消费到新消息。
Broker 重启后，ReputMessageService 会从 reputFromOffset 继续分发，
这个偏移量等于 ConsumeQueue 的最大物理偏移量，所以不会丢失消息。
```

**Q8：MappedFile 的三个 Position 的更新时机分别是什么？**

```
A：
- wrotePosition：在 appendMessage() 成功后通过 CAS 立即更新
  （此时数据在 mmap 内存或 DirectBuffer 中）

- committedPosition：仅 TransientStorePool 模式，由 CommitRealTimeService
  定时将 DirectBuffer 的数据写入 FileChannel 后更新
  （普通模式下始终等于 wrotePosition）

- flushedPosition：由 FlushRealTimeService 或 GroupCommitService
  调用 force() 将数据刷到磁盘后更新
  （此时数据真正持久化）

关系：flushedPosition <= committedPosition <= wrotePosition
```
