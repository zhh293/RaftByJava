## 一、HA 协议设计 —— 为什么不用 Netty？

### 1.1 协议特点

RocketMQ 的 HA 复制使用**原始 Java NIO**（`SocketChannel` + `Selector`），而非项目通用的 Netty Remoting 框架。这是一个关键的工程决策：

**协议格式极其简单**：

```
Master → Slave 推送帧:
┌─────────────────────┬───────────────┬──────────────────────┐
│  physicOffset (8B)   │  bodySize (4B) │  commitLog body (变长) │
└─────────────────────┴───────────────┴──────────────────────┘
TRANSFER_HEADER_SIZE = 12 字节

Slave → Master ACK:
┌─────────────────────┐
│  slaveAckOffset (8B) │
└─────────────────────┘
REPORT_HEADER_SIZE = 8 字节
```

### 1.2 为什么选择原始 NIO 而非 Netty

1. **极致吞吐**：HA 复制是全量 CommitLog 字节的流式传输，不需要 RemotingCommand 的编解码开销
2. **零拷贝**：可以直接使用 `ByteBuffer` 的 `transferTo` 和 `FileChannel` 的零拷贝能力
3. **协议极简**：只有两种消息类型（数据推送 + ACK），不需要复杂的请求-响应匹配机制
4. **连接复用**：一个连接持续推送数据，不需要像 RPC 那样频繁创建销毁请求

**知识点：与 Raft AppendEntries 的对比**

Raft 的 AppendEntries RPC 也携带日志条目，但它是基于 RPC 的——每次发送一个 AppendEntries 请求，等待多数派响应。而 RocketMQ 的 HA 是**流式推送**——Master 持续向 Slave 推送新的 CommitLog 数据，Slave 持续发送 ACK，不需要请求-响应配对。这种设计在吞吐量上更优，但牺牲了灵活性（无法精确控制单个日志条目的复制状态）。

```java
    }
```

```java
    this.haConnectionStateNotificationService = 
        new HAConnectionStateNotificationService(this, defaultMessageStore);
}
```

### 2.4 关键方法

#### isSlaveOK() —— 判断Slave是否可用

```java
public boolean isSlaveOK(long masterPutWhere) {
    boolean result = this.connectionCount.get() > 0;
    result = result && 
        ((masterPutWhere - this.push2SlaveMaxOffset.get()) 
         < defaultMessageStore.getMessageStoreConfig().getHaMaxGapNotInSync());
    return result;
}
```

判断条件：有连接 **且** Master写入位置与Slave已确认位置之差小于 `haMaxGapNotInSync`（默认256MB）。如果差距太大，认为Slave已经"落后太多"，不可用。

#### notifyTransferSome() —— 通知数据已传输

```java
public void notifyTransferSome(long offset) {
    for (;;) {
        long current = this.push2SlaveMaxOffset.get();
        if (current >= offset) break;
        // CAS更新：只增不减
        if (this.push2SlaveMaxOffset.compareAndSet(current, offset)) {
            // 唤醒GroupTransferService检查是否有请求可以完成
            this.groupTransferService.notifyTransferSome();
            break;
        }
    }
}
```

这个方法使用 CAS 循环确保 `push2SlaveMaxOffset` 单调递增。每当 Slave 的 ACK 更新了这个值，就会唤醒 `GroupTransferService` 检查等待中的复制请求是否已满足法定数。

#### inSyncReplicasNums() —— 统计同步副本数

```java
public int inSyncReplicasNums(long masterPutWhere) {
    int inSyncReplicas = 1;  // Master自己算1个
    for (HAConnection conn : this.connectionList) {
        if (conn.getSlaveAckOffset() >= 0) {
            long gap = masterPutWhere - conn.getSlaveAckOffset();
            if (gap < defaultMessageStore.getMessageStoreConfig()
                .getHaMaxGapNotInSync()) {
                inSyncReplicas++;
            }
        }
    }
    return inSyncReplicas;
}
```

遍历所有 Slave 连接，统计 ACK 位置与 Master 当前位置差距在 `haMaxGapNotInSync` 以内的连接数。

## 三、AcceptSocketService —— 接受 Slave 连接

**源码位置**: `DefaultHAService` 的内部类 `DefaultAcceptSocketService`

这是一个经典的 NIO 接受器循环：

```java
class DefaultAcceptSocketService extends ServiceThread {
    private final ServerSocketChannel serverSocketChannel;
    private final Selector selector;
    
    public void beginAccept() throws IOException {
        this.serverSocketChannel = ServerSocketChannel.open();
        this.serverSocketChannel.configureBlocking(false);
        this.serverSocketChannel.socket().setReuseAddress(true);
        this.serverSocketChannel.socket().bind(
            new InetSocketAddress(this.port));
        this.selector = RemotingUtil.openSelector();
        this.serverSocketChannel.register(this.selector, SelectionKey.OP_ACCEPT);
    }
    
    @Override
    public void run() {
        while (!this.isStopped()) {
            try {
                this.selector.select(1000);
                Iterator<SelectionKey> iter = this.selector.selectedKeys().iterator();
                while (iter.hasNext()) {
                    SelectionKey key = iter.next();
                    iter.remove();
                    if (key.isAcceptable()) {
                        SocketChannel socketChannel = 
                            ((ServerSocketChannel) key.channel()).accept();
                        if (socketChannel != null) {
                            HAConnection conn = createConnection(socketChannel);
                            addConnection(conn);
                            conn.start();
                        }
                    }
                }
            } catch (Exception e) {
                log.error("acceptSocketService exception", e);
            }
        }
    }
}
```

当接受到一个新的 Slave 连接时：
1. `createConnection(socketChannel)` 创建一个 `DefaultHAConnection` 对象
2. `addConnection(conn)` 将连接加入 `connectionList`
3. `conn.start()` 启动该连接的读写服务线程

## 五、ReadSocketService —— 读取 Slave ACK

```java
class ReadSocketService extends ServiceThread {
    private static final int READ_MAX_BUFFER_SIZE = 1024 * 1024;  // 1MB
    private final ByteBuffer byteBufferRead = ByteBuffer.allocate(READ_MAX_BUFFER_SIZE);
    private final Selector selector;
    private int processPosition = 0;  // 已处理位置
    
    @Override
    public void run() {
        while (!this.isStopped()) {
            try {
                this.selector.select(1000);
                boolean ok = this.processReadEvent();
                if (!ok) {
                    // 读取失败，关闭连接
                    DefaultHAConnection.this.shutdown();
                    break;
                }
                
                // 空闲检测
                long interval = System.currentTimeMillis() - lastReadTimestamp;
                if (interval > haHousekeepingInterval) {
                    log.warn("ha housekeeping, found connection expired...");
                    DefaultHAConnection.this.shutdown();
                    break;
                }
            } catch (Exception e) {
                DefaultHAConnection.this.shutdown();
                break;
            }
        }
    }
}
```

### processReadEvent() —— 处理读取事件

```java
private boolean processReadEvent() {
    int readSizeZeroTimes = 0;
    
    while (this.byteBufferRead.hasRemaining()) {
        int readSize = this.socketChannel.read(this.byteBufferRead);
        if (readSize > 0) {
            readSizeZeroTimes = 0;
            lastReadTimestamp = System.currentTimeMillis();
            
            // 处理已读取的数据
            if (this.byteBufferRead.position() - this.processPosition 
                >= DefaultHAClient.REPORT_HEADER_SIZE) {  // 8字节
                
                // 取最后一个完整的8字节作为slaveAckOffset
                int pos = this.byteBufferRead.position() 
                    - (this.byteBufferRead.position() % 8);
                long slaveAckOffset = this.byteBufferRead.getLong(pos - 8);
                
                this.slaveAckOffset = slaveAckOffset;
                
                // 第一次收到ACK，记录Slave请求的起始偏移量
                if (slaveRequestOffset < 0) {
                    slaveRequestOffset = slaveAckOffset;
                    // 通知WriteSocketService可以开始推送数据了
                    DefaultHAConnection.this.writeSocketService.wakeup();
                }
                
                // 通知HAService数据已传输到该位置
                DefaultHAConnection.this.haService.notifyTransferSome(slaveAckOffset);
                
                // 更新处理位置
                this.processPosition = pos;
            }
        } else if (readSize == 0) {
            if (++readSizeZeroTimes >= 3) return true;  // 无数据可读，返回
        } else {
            return false;  // 读取异常
        }
    }
    return true;
}
```

**知识点：slaveRequestOffset 的语义**

Slave 第一次发送的 ACK 实际上是它当前的 CommitLog 最大物理偏移量，告诉 Master："我的日志到这里了，请从这里开始给我推送数据。"这就是隐式握手——不需要专门的握手协议，第一个 8 字节报告就是"请求"。

## 六、WriteSocketService —— 推送 CommitLog 数据到 Slave

```java
class WriteSocketService extends ServiceThread {
    private final Selector selector;
    private long nextTransferFromWhere = -1;  // 下次传输的起始位置
    private boolean lastWriteOver = true;
    private long lastWriteTimestamp = System.currentTimeMillis();
    
    @Override
    public void run() {
        while (!this.isStopped()) {
            try {
                // 1. 等待Slave的第一次ACK（获取slaveRequestOffset）
                if (-1 == slaveRequestOffset) {
                    this.waitForRunning(1000);
                    continue;
                }
                
                // 2. 等待数据到达或超时
                if (-1 == nextTransferFromWhere) {
                    if (0 == slaveRequestOffset) {
                        // Slave是全新的，从当前CommitLog开始
                        long masterOffset = defaultMessageStore.getCommitLog()
                            .getMaxOffset();
                        masterOffset = masterOffset - 
                            (masterOffset % defaultMessageStore.getMessageStoreConfig()
                                .getMappedFileSizeCommitLog());
                        this.nextTransferFromWhere = masterOffset;
                    } else {
                        // 从Slave请求的位置开始
                        this.nextTransferFromWhere = slaveRequestOffset;
                    }
                }
                
                // 3. 检查是否有新数据
                long maxOffsetInCommitLog = defaultMessageStore.getCommitLog()
                    .getMaxOffset();
                
                if (this.nextTransferFromWhere >= maxOffsetInCommitLog) {
                    // 没有新数据
                    if (System.currentTimeMillis() - lastWriteTimestamp 
                        > haSendHeartbeatInterval) {
                        // 超过心跳间隔，发送空心跳帧
                        this.transferData(null);
                    }
                    // 等待新数据到达
                    this.waitForRunning(100);
                    continue;
                }
                
                // 4. 获取CommitLog数据
                SelectMappedBufferResult selectResult = defaultMessageStore
                    .getCommitLogData(this.nextTransferFromWhere);
                
                if (selectResult == null || selectResult.getSize() <= 0) {
                    this.waitForRunning(100);
                    continue;
                }
                
                // 5. 限制传输大小
                int size = Math.min(selectResult.getSize(), 
                    defaultMessageStore.getMessageStoreConfig().getHaTransferBatchSize());
                size = Math.min(size, flowMonitor.canTransferMaxByteNum());
                
                // 6. 构建传输数据
                this.nextTransferFromWhere += size;
                selectResult.getByteBuffer().limit(size);
                
                // 7. 传输
                this.transferData(selectResult);
                selectResult.release();
                
            } catch (Exception e) {
                DefaultHAConnection.this.shutdown();
                break;
            }
        }
    }
}
```

### transferData() —— 实际传输

```java
private void transferData(SelectMappedBufferResult selectResult) throws IOException {
    // 构建12字节头
    ByteBuffer headerBuffer = ByteBuffer.allocate(TRANSFER_HEADER_SIZE);
    headerBuffer.putLong(this.nextTransferFromWhere);  // physicOffset
    headerBuffer.putInt(selectResult == null ? 0 : selectResult.getSize());  // bodySize
    headerBuffer.flip();
    
    // 写入头部（循环写入直到完成）
    while (headerBuffer.hasRemaining()) {
        int writeSize = this.socketChannel.write(headerBuffer);
        if (writeSize <= 0) {
            // 写入失败处理...
        }
    }
    
    // 写入body（CommitLog数据）
    if (selectResult != null) {
        int writeSize = this.socketChannel.write(selectResult.getByteBuffer());
        lastWriteOver = writeSize > 0;
        lastWriteTimestamp = System.currentTimeMillis();
    }
    
    flowMonitor.addByteCountTransferred(headerBuffer.limit() + 
        (selectResult == null ? 0 : selectResult.getSize()));
}
```

**知识点：心跳帧**

当没有新数据可推送时，Master 会定期发送一个 `bodySize=0` 的空帧，仅包含 12 字节头部。这个心跳帧有两个作用：
1. 保持连接活跃（防止被空闲检测关闭）
2. 告知 Slave Master 当前的最新偏移量

### 7.2 主循环

```java
    log.info(this.getServiceName() + " service started");
    
    while (!this.isStopped()) {
        try {
            switch (this.currentState) {
                case SHUTDOWN:
                    return;
                case READY:
                    if (!connectMaster()) {
                        waitForRunning(5000);  // 5秒后重试
                    }
                    break;
                case TRANSFER:
                    if (!transferFromMaster()) {
                        closeMasterAndWait();
                    }
                    break;
                default:
                    waitForRunning(2000);
                    break;
            }
        } catch (Exception e) {
            log.warn(this.getServiceName() + " service has exception. ", e);
            this.changeCurrentState(HAConnectionState.READY);
            waitForRunning(2000);
        }
    }
    log.info(this.getServiceName() + " service end");
}
```

### 7.3 connectMaster() —— 连接 Master

```java
private boolean connectMaster() throws IOException {
    if (null == socketChannel) {
        String addr = masterHaAddress.get();
        if (addr != null) {
            SocketAddress socketAddress = NetworkUtil.string2SocketAddress(addr);
            this.socketChannel = RemotingHelper.connect(socketAddress);
            
            if (this.socketChannel != null) {
                this.socketChannel.register(this.selector, SelectionKey.OP_READ);
                // 直接进入TRANSFER状态——没有显式握手
                this.changeCurrentState(HAConnectionState.TRANSFER);
                
                // 当前CommitLog最大偏移量作为第一次"请求"
                this.currentReportedOffset = defaultMessageStore.getMaxPhyOffset();
                
                lastReadTimestamp = System.currentTimeMillis();
            }
        }
    }
    return this.socketChannel != null;
}
```

**关键点**：
- Slave 连接 Master 后直接进入 `TRANSFER` 状态
- 没有"你好"握手指令
- Slave 的第一次 `reportSlaveMaxOffset` 就是隐式握手——告诉 Master "我的日志到这里了"

```java
    if (isTimeToReportOffset()) {
        boolean result = reportSlaveMaxOffset(currentReportedOffset);
        if (!result) return false;
```

### 7.5 reportSlaveMaxOffset() —— 发送 ACK

```java
private boolean reportSlaveMaxOffset(final long maxOffset) {
    if (null == socketChannel) return false;
    
    this.byteBufferReport.position(0);
    this.byteBufferReport.limit(8);
    this.byteBufferReport.putLong(maxOffset);
    this.byteBufferReport.flip();
    
    int writeZeroTimes = 0;
    while (this.byteBufferReport.hasRemaining()) {
        int writeSize = this.socketChannel.write(this.byteBufferReport);
        if (writeSize > 0) {
            writeZeroTimes = 0;
        } else {
            writeZeroTimes++;
            if (writeZeroTimes >= 3) return false;
        }
    }
    return true;
}
```

ACK 就是一个 8 字节的 long 值——Slave 当前的 CommitLog 最大物理偏移量。

### 7.6 dispatchReadRequest() —— 解析 Master 推送的数据

这是最关键的方法，包含**安全校验**：

```java
private boolean dispatchReadRequest() {
    int readSocketBuffer = byteBufferRead.position() - dispatchPosition;
    
    while (true) {
        int diff = byteBufferRead.position() - dispatchPosition;
        
        if (diff >= TRANSFER_HEADER_SIZE) {  // 12字节
            // 读取头部
            long masterPhyOffset = byteBufferRead.getLong(dispatchPosition);
            int bodySize = byteBufferRead.getInt(dispatchPosition + 8);
            
            // 获取Slave本地的CommitLog最大偏移量
            long slavePhyOffset = defaultMessageStore.getMaxPhyOffset();
            
            // ★★★ 关键安全校验 ★★★
            if (slavePhyOffset != 0 && slavePhyOffset != masterPhyOffset) {
                log.error("master pushed offset not equal the max phy offset in slave"
                    + ", slave={}, master={}", slavePhyOffset, masterPhyOffset);
                return false;  // 致命错误：偏移量不匹配，断开连接
            }
            
            // 检查是否有完整的body
            if (diff >= TRANSFER_HEADER_SIZE + bodySize) {
                // 提取body数据
                byte[] bodyData = byteBufferRead.array();
                int dataStart = dispatchPosition + TRANSFER_HEADER_SIZE;
                
                // 追加到本地CommitLog
                defaultMessageStore.appendToCommitLog(
                    masterPhyOffset, bodyData, dataStart, bodySize);
                
                // 更新已处理位置
                dispatchPosition += TRANSFER_HEADER_SIZE + bodySize;
                
                // 立即发送ACK
                currentReportedOffset = masterPhyOffset + bodySize;
                reportSlaveMaxOffset(currentReportedOffset);
                
                hasReadData = true;
                continue;
            }
        }
        
        // 处理buffer边界
        if (!byteBufferRead.hasRemaining()) {
            reallocateByteBuffer();
        }
        break;
    }
    
    return true;
}
```

**知识点：偏移量校验——Raft 的 prevLogIndex 等价物**

在追加任何数据之前，Slave 会检查 `masterPhyOffset == slavePhyOffset`，即 Master 推送的数据起始位置必须等于 Slave 本地日志的末尾。这与 Raft 的 `prevLogIndex/prevLogTerm` 一致性检查是同一思想——确保日志的连续性。

如果校验失败（例如 Master 和 Slave 的日志不一致），Slave 会断开连接并重新连接。重新连接后，Slave 报告自己当前的最大偏移量，Master 从该位置开始推送。如果偏移量差距太大，Slave 可能需要从更早的位置重新同步。

**知识点：reallocateByteBuffer() 双缓冲**

当读取的数据跨越了 ByteBuffer 的边界时，需要将未处理的数据移到新的缓冲区。这个方法实现了"交换缓冲区"的操作：

```java
private void reallocateByteBuffer() {
    int remain = byteBufferRead.position() - dispatchPosition;
    if (remain > 0) {
        // 将未处理的数据复制到备份缓冲区
        byteBufferRead.position(dispatchPosition);
        byteBufferBackup.clear();
        byteBufferBackup.put(byteBufferRead);
        // 交换缓冲区
        swapByteBuffer();
    }
    // 重置位置
    byteBufferRead.position(remain);
    dispatchPosition = 0;
}
```

## 八、GroupTransferService —— 同步复制 ACK 等待

**源码位置**: `store/src/main/java/org/apache/rocketmq/store/ha/GroupTransferService.java`

这是实现 **SYNC_MASTER（同步复制）** 语义的核心组件。当消息发送要求 Slave 确认时，发送线程会阻塞在这里，等待足够多的 Slave ACK。

### 8.1 双缓冲交换模式

```java
class GroupTransferService extends ServiceThread {
    // 写入队列：新请求放这里
    private final List<CommitLog.GroupCommitRequest> requestsWrite = 
        new ArrayList<>();
    // 读取队列：服务线程从这里处理
    private final List<CommitLog.GroupCommitRequest> requestsRead = 
        new ArrayList<>();
    
    // 提交请求
    public void putRequest(final CommitLog.GroupCommitRequest request) {
        lock.lock();
        try {
            requestsWrite.add(request);
        } finally {
            lock.unlock();
        }
        this.wakeup();
    }
    
    // 在waitForRunning()返回后交换队列
    @Override
    protected void onWaitEnd() {
        lock.lock();
        try {
            // 交换读写队列
            List<CommitLog.GroupCommitRequest> tmp = requestsWrite;
            requestsWrite = requestsRead;
            requestsRead = tmp;
        } finally {
            lock.unlock();
        }
    }
}
```

**知识点：双缓冲交换设计**

这个模式将生产者（发送线程）和消费者（GroupTransferService线程）的锁竞争降到最低：
- 生产者只在 `putRequest` 时短暂获取锁，将请求放入 `requestsWrite`
- 消费者在 `waitForRunning` 返回后交换两个队列，之后处理 `requestsRead` 时无需任何锁
- 处理完成后清空 `requestsRead`，等待下一轮

### 8.2 doWaitTransfer() —— 等待 ACK

```java
private void doWaitTransfer() {
    if (!this.requestsRead.isEmpty()) {
        for (CommitLog.GroupCommitRequest req : this.requestsRead) {
            boolean transferOK = false;
            long deadLine = req.getDeadLine();
            boolean allAckInSyncStateSet = 
                req.getAckNums() == MixAll.ALL_ACK_IN_SYNC_STATE_SET;
            
            for (int i = 0; !transferOK && deadLine - System.nanoTime() > 0; i++) {
                // 每隔1ms轮询一次
                if (i > 0) {
                    notifyTransferObject.waitForRunning(1);
                }
                
                if (!allAckInSyncStateSet && req.getAckNums() <= 1) {
                    // 只需Master自己确认（ackNums<=1）
                    transferOK = haService.getPush2SlaveMaxOffset().get() 
                        >= req.getNextOffset();
                    continue;
                }
                
                if (allAckInSyncStateSet && haService instanceof AutoSwitchHAService) {
                    // Controller模式：只统计SyncStateSet中的副本ACK
                    AutoSwitchHAService autoSwitchHAService = (AutoSwitchHAService) haService;
                    int ackNums = 1;  // Master算1个
                    for (Long brokerId : autoSwitchHAService.getSyncStateSet()) {
                        if (brokerId == MixAll.MASTER_ID) continue;
                        HAConnection conn = findConnectionByBrokerId(brokerId);
                        if (conn != null && conn.getSlaveAckOffset() >= req.getNextOffset()) {
                            ackNums++;
                        }
                    }
                    if (ackNums >= req.getAckNums()) transferOK = true;
                } else {
                    // 经典模式：统计所有连接的ACK
                    int ackNums = 1;  // Master算1个
                    for (HAConnection conn : haService.getConnectionList()) {
                        if (conn.getSlaveAckOffset() >= req.getNextOffset()) {
                            ackNums++;
                        }
                        if (ackNums >= req.getAckNums()) {
                            transferOK = true;
                            break;
                        }
                    }
                }
            }
            
            // 唤醒等待的发送线程
            req.wakeupCustomer(
                transferOK ? PutMessageStatus.PUT_OK 
                           : PutMessageStatus.FLUSH_SLAVE_TIMEOUT);
        }
    }
    
    this.requestsRead.clear();
}
```

**知识点：与 Raft 的 commit 等待对比**

这个等待循环与 Raft Leader 等待 AppendEntries ACK 的逻辑非常相似：

| 方面 | Raft | RocketMQ GroupTransferService |
|------|------|-------------------------------|
| 等待什么 | 多数派节点 ACK AppendEntries | N 个 Slave ACK 消息复制 |
| 如何计算多数 | majority = (N/2)+1 | ackNums >= req.getAckNums() |
| 超时处理 | 请求过期后 Leader 重试 | deadline 到期后返回 FLUSH_SLAVE_TIMEOUT |
| 唤醒机制 | 收到 RPC 响应后更新 matchIndex | notifyTransferSome() 被调用后唤醒 |
| 安全保证 | committed entries 不被覆盖 | slaveAckOffset >= nextOffset |

**关键区别**：Raft 使用 term（任期号）来防止过期 Leader 的干扰，而 RocketMQ 的经典 HA 没有这个概念。在 `AutoSwitchHAService`（Controller模式）中引入了 epoch 机制来弥补这一点。

### 8.3 主循环

```java
@Override
public void run() {
    log.info(this.getServiceName() + " service started");
    
    while (!this.isStopped()) {
        try {
            // 等待被唤醒或超时（10ms）
            this.waitForRunning(10);
            
            // 处理等待中的请求
            this.doWaitTransfer();
        } catch (Exception e) {
            log.warn(this.getServiceName() + " service has exception. ", e);
        }
    }

    log.info(this.getServiceName() + " service end");
}
```

## 九、handleDiskFlushAndHA —— 组合刷盘与复制

**源码位置**: `CommitLog.java`

在消息写入 CommitLog 后，需要同时处理刷盘和 HA 复制：

```java
private CompletableFuture<PutMessageResult> handleDiskFlushAndHA(
    PutMessageResult putMessageResult, MessageExt messageExt, 
    int needAckNums, boolean needHandleHA) {
    
    // 提交刷盘请求
    CompletableFuture<PutMessageStatus> flushResultFuture = 
        submitFlushRequest(putMessageResult, messageExt);
    
    // 提交HA复制请求
    CompletableFuture<PutMessageStatus> replicaResultFuture;
    if (!needHandleHA) {
        replicaResultFuture = CompletableFuture.completedFuture(PutMessageStatus.PUT_OK);
    } else {
        replicaResultFuture = submitReplicaRequest(putMessageResult, needAckNums);
    }
    
    // 组合两个Future：刷盘和复制都成功才算成功
    return flushResultFuture.thenCombine(replicaResultFuture, 
        (flushStatus, replicaStatus) -> {
            if (flushStatus != PutMessageStatus.PUT_OK) {
                putMessageResult.setPutMessageStatus(flushStatus);
            }
            if (replicaStatus != PutMessageStatus.PUT_OK) {
                putMessageResult.setPutMessageStatus(replicaStatus);
            }
            return putMessageResult;
        });
}
```

### submitReplicaRequest()

```java
public CompletableFuture<PutMessageStatus> submitReplicaRequest(
    PutMessageResult putMessageResult, int needAckNums) {
    
    CompletableFuture<PutMessageStatus> result = new CompletableFuture<>();
    
    if (brokerRole == BrokerRole.SLAVE) {
        // Slave不需要复制到其他节点
        result.complete(PutMessageStatus.PUT_OK);
        return result;
    }
    
    if (needAckNums <= 0) {
        // 不需要Slave确认
        result.complete(PutMessageStatus.PUT_OK);
        return result;
    }
    
    // 创建组提交请求
    CommitLog.GroupCommitRequest request = new CommitLog.GroupCommitRequest(
        putMessageResult.getAppendMessageResult().getWroteOffset() 
            + putMessageResult.getAppendMessageResult().getWroteBytes(),
        needAckNums,
        this.messageStoreConfig.getSyncFlushTimeout());
    
    // 提交给GroupTransferService
    haService.putRequest(request);
    
    // 当请求完成时，完成Future
    request.getFuture().whenComplete((status, ex) -> {
        if (ex != null) {
            result.complete(PutMessageStatus.FLUSH_SLAVE_TIMEOUT);
        } else {
            result.complete(status);
        }
    });
    
    return result;
}
```

**知识点：刷盘与复制并行**

使用 `CompletableFuture.thenCombine()`，刷盘和 HA 复制是并行执行的。这意味着：
- 刷盘和复制同时开始
- 只有两者都完成，消息才算写入成功
- 刷盘超时和复制超时中任意一个先超时，整个操作就超时

### 10.1 三种角色

### 10.2 复制策略矩阵

| BrokerRole | 刷盘方式 | 返回条件 | 数据安全 |
|-----------|---------|---------|---------|
| ASYNC_MASTER | ASYNC_FLUSH | 写入PageCache即返回 | 最低（宕机可能丢数据） |

## 十一、FlowMonitor —— 流量控制

```java
public class FlowMonitor {
    private final AtomicLong transferredByteCount = new AtomicLong(0);
    private final AtomicLong transferredTimeCount = new AtomicLong(0);
    private volatile long maxByteNum = Long.MAX_VALUE;
    
    // 判断可以传输多少字节
    public int canTransferMaxByteNum() {
        if (maxByteNum == Long.MAX_VALUE) return Integer.MAX_VALUE;
        
        long currentTransferred = transferredByteCount.get();
        if (currentTransferred >= maxByteNum) return 0;
        
        return (int) Math.min(maxByteNum - currentTransferred, Integer.MAX_VALUE);
    }
    
    // 每10ms重置计数器
    public void start() {
        scheduledExecutorService.scheduleAtFixedRate(() -> {
            // 更新最大传输量（根据配置的带宽限制）
            maxByteNum = (long)(bandwidthLimit * 10 / 1000);
            transferredByteCount.set(0);
        }, 10, 10, TimeUnit.MILLISECONDS);
    }
}
```

FlowMonitor 在 Master 端和 Slave 端都有，用于限制 HA 复制的带宽使用，避免 HA 流量抢占正常请求的网络带宽。

## 十二、AutoSwitchHAService —— Controller 模式下的增强 HA

在 Controller 模式（`enableControllerMode=true`）下，使用 `AutoSwitchHAService` 替代 `DefaultHAService`，引入了 **epoch（纪元）** 机制：

### 12.1 Epoch 机制

- 每个 Master 都有一个递增的 epoch 号
- Slave 在连接 Master 时会检查 epoch
- 如果 Slave 的 epoch 高于 Master，拒绝连接（防止过期 Master 的数据污染）
- 如果 Slave 的 epoch 等于 Master，检查 offset 是否连续
- 如果 Slave 的 epoch 低于 Master，Slave 需要截断日志到 epoch 边界

### 12.2 HAConnectionState 完整使用

在 AutoSwitch 模式下，`HAConnectionState` 的所有状态都被使用：

```
READY → HANDSHAKE → TRANSFER → (SUSPEND → TRANSFER)* → SHUTDOWN
```

- `READY`: 初始状态
- `HANDSHAKE`: 执行 epoch/offset 一致性检查
- `TRANSFER`: 正常数据传输
- `SUSPEND`: 暂停传输（例如 Controller 正在进行主从切换）
- `SHUTDOWN`: 关闭

### 12.3 Controller 的角色

Controller（基于 JRaft 实现）负责：
1. 选举 Master
2. 维护 SyncStateSet（同步副本集合）
3. 在 Master 宕机时选择新的 Master
4. 通知 Broker 角色变更

**关键 RequestCode**:

| Code | 名称 | 说明 |
|------|------|------|
| 1002 | CONTROLLER_ELECT_MASTER | 选举新Master |
| 1003 | CONTROLLER_REGISTER_BROKER | Broker向Controller注册 |
| 1008 | NOTIFY_BROKER_ROLE_CHANGED | 通知Broker角色变更 |

**关键 ResponseCode**:

| Code | 名称 | 说明 |
|------|------|------|
| 2000 | CONTROLLER_FENCED_MASTER_EPOCH | 过期epoch被拒绝 |
| 2007 | CONTROLLER_NOT_LEADER | 不是Leader（重定向） |

## 十三、与 Raft 协议的深度对比分析

### 13.1 架构对比

| 方面 | Raft | RocketMQ HA |
|------|------|-------------|
| 日志格式 | term + index + command | 纯字节流（物理偏移量） |
| 复制方式 | AppendEntries RPC | 流式推送 |
| 一致性检查 | prevLogIndex + prevLogTerm | masterPhyOffset == slavePhyOffset |
| 提交确认 | majority ACK | needAckNums ACK |
| 日志截断 | 通过term和index | 无（断开重连重新同步） |
| Leader选举 | RequestVote RPC | 外部Controller/DLedger |
| 防脑裂 | term + voting | epoch fencing (AutoSwitch) |

### 13.2 相似之处

1. **日志连续性检查**：Raft 检查 `prevLogIndex/prevLogTerm`，RocketMQ 检查 `masterPhyOffset == slavePhyOffset`
2. **多数派提交**：Raft 等待 majority ACK，RocketMQ 等待 `needAckNums` ACK
3. **Leader 推送**：Raft Leader 主动发送 AppendEntries，RocketMQ Master 主动推送 CommitLog
4. **Follower 被动**：Raft Follower 等待 Leader 推送，RocketMQ Slave 等待 Master 推送

### 13.3 关键差异

1. **日志条目 vs 字节流**：Raft 的日志是结构化的（每个条目有 term 和 index），RocketMQ 是纯字节流（只有物理偏移量）。这使得 RocketMQ 更高效但安全性更弱。

2. **日志截断**：Raft 在发现不一致时会截断日志到冲突点之前。RocketMQ 不截断，而是断开连接重新同步。这可能导致全量重传。

3. **选举机制**：Raft 有内置的选举协议（RequestVote），RocketMQ 依赖外部组件（Controller 或 DLedger）。

4. **Term/Epoch**：Raft 的 term 是核心安全机制，贯穿所有操作。RocketMQ 的经典 HA 没有 term，只有 AutoSwitch 模式才引入了 epoch。

### 13.4 对 RaftByJava 项目的启发

1. **GroupTransferService 的设计模式**可以直接用于 Raft 的 commit 等待——双缓冲队列 + 轮询 + 超时
2. **流式复制的效率**值得借鉴，但需要加入 term 检查保证安全性
3. **双缓冲交换模式**在减少锁竞争方面非常有效
4. **FlowMonitor 的带宽控制**在高负载场景下很重要
5. **WaitNotifyObject 的防丢唤醒**设计（AtomicBoolean hasNotified）值得参考

## 十四、知识点总结

### 14.1 HA 协议设计哲学

RocketMQ 的 HA 协议追求极致简单：只有两种消息类型（12字节数据推送 + 8字节ACK），没有复杂的握手和协商过程。这种极简设计带来了极高的吞吐量，但牺牲了一些安全保证（没有 term 概念，没有日志截断）。

### 14.2 为什么选择原始 NIO

Netty 的 RemotingCommand 框架是为 RPC 设计的——每个请求都需要编解码、请求-响应匹配、opaque ID 管理。而 HA 复制是单向流式传输，不需要这些机制。使用原始 NIO 可以避免不必要的开销，直接操作 ByteBuffer 获得最高效率。

### 14.3 双缓冲交换模式

GroupTransferService 的 `requestsWrite`/`requestsRead` 双缓冲交换是一个经典的生产者-消费者优化模式。生产者只需短暂加锁放入请求，消费者在无锁状态下处理所有请求。这种模式在 Raft 的日志复制确认中也可以使用。

### 14.4 安全校验：masterPhyOffset == slavePhyOffset

这是整个 HA 复制安全性的基石。Master 推送的每一帧数据都携带起始偏移量，Slave 在追加前验证这个偏移量等于自己的日志末尾。如果不等，说明日志不一致，立即断开连接。这个检查等价于 Raft 的 `prevLogIndex/prevLogTerm` 检查。

### 14.5 并行刷盘与复制

使用 `CompletableFuture.thenCombine()` 实现刷盘和复制的并行执行。这是一个优雅的工程实现——两个独立的操作可以同时进行，只有都完成才算写入成功。

### 14.6 Controller 模式的 epoch fencing

AutoSwitchHAService 引入了 epoch 机制，防止过期 Master 的数据污染。这类似于 Raft 的 term 机制——每次主从切换时 epoch 递增，旧 Master 的操作会被拒绝（`CONTROLLER_FENCED_MASTER_EPOCH`）。

## 十五、HA 数据恢复流程详解

### 15.1 Master 端的数据读取

`WriteSocketService` 在推送数据时，通过 `defaultMessageStore.getCommitLogData(nextTransferFromWhere)` 获取 CommitLog 数据。这个方法通过 MappedFileQueue 找到对应的 MappedFile，返回一个 `SelectMappedBufferResult`（零拷贝视图），数据直接从操作系统的 Page Cache 传输到网络。

### 15.2 Slave 端的数据写入

`dispatchReadRequest()` 中调用 `defaultMessageStore.appendToCommitLog()` 将数据追加到本地 CommitLog。追加前进行安全校验 `masterPhyOffset == slavePhyOffset`，追加后唤醒 `ReputMessageService` 分发到 ConsumeQueue 和 IndexFile。这意味着 Slave 上的索引是本地异步构建的，不是从 Master 复制的。

### 15.3 Slave 全量同步场景

全新的 Slave 第一次连接 Master 时，`currentReportedOffset = 0`，Master 将 `nextTransferFromWhere` 对齐到当前 CommitLog 的起始文件位置，从该位置开始推送所有历史数据。这个全量同步过程可能持续很长时间，在此期间 Slave 不能正常提供消费服务。

## 十六、HA 连接生命周期管理

### 16.1 连接建立流程

Slave 启动 → DefaultHAClient 进入 READY 状态 → connectMaster() 连接 Master 的 haListenPort → 连接成功进入 TRANSFER 状态 → 发送第一个 8 字节 ACK。Master 端 AcceptSocketService 接受连接 → 创建 DefaultHAConnection → 启动 ReadSocketService + WriteSocketService → 收到第一个 ACK 后记录 slaveRequestOffset → 唤醒 WriteSocketService 开始推送数据。

### 16.2 连接保活机制

两端都使用 `haHousekeepingInterval`（默认20秒）作为空闲超时。Master 的 WriteSocketService 在没有新数据时每隔 `haSendHeartbeatInterval`（默认5秒）发送空帧。Slave 在 `isTimeToReportOffset()` 返回 true 时发送 ACK。

### 16.3 连接断开与重连

Master 端关闭 ReadSocketService + WriteSocketService，移除连接。Slave 端关闭 socketChannel，重置缓冲区，回到 READY 状态，等待 2 秒后重试连接。重连后 Slave 重新发送 `currentReportedOffset`，Master 从该位置继续推送增量数据。

## 十七、HA 性能优化分析

### 17.1 批量传输
`haTransferBatchSize`（默认32KB）控制单次传输的最大数据量。增大可减少网络往返但增加延迟。

### 17.2 流量控制
`FlowMonitor` 每10ms重置计数器，根据 `bandwidthLimit` 计算允许传输的最大字节数，防止 HA 占满网络带宽。

### 17.3 异步分发
Slave 的 CommitLog 写入是同步的，ConsumeQueue 构建是异步的，实现了复制和索引的解耦。

### 17.4 内存映射
Master 使用 MappedFile 的内存映射，数据直接从 Page Cache 传输到网络，实现零拷贝。

## 十八、HA 故障场景分析

### 18.1 Master 宕机
NameServer 检测心跳超时 → 移除 Master 路由 → 客户端获取更新路由 → SYNC_MASTER 下消费者可切换到 Slave → ASYNC_MASTER 下可能丢失未复制消息。

### 18.2 Slave 宕机
Master 检测连接断开 → 移除 Slave 连接 → `inSyncReplicasNums` 减少 → 如果低于 `minInSyncReplicas` 拒绝新写入 → Slave 恢复后增量同步。

### 18.3 网络分区
经典模式：Slave 断开 → Master 继续写入 → 分区恢复后增量同步。Controller 模式：Controller 检测失联 → 选举新 Master → 旧 Master 被 epoch fencing。

### 18.4 数据不一致风险
ASYNC_MASTER 下 Master 宕机可能丢失 PageCache 中未复制未刷盘的消息。SYNC_MASTER + needAckNums>=2 可大幅降低风险。所有节点同时宕机仍可能丢失 PageCache 未刷盘数据。

## 二十一、HA 协议二进制格式深度解析

### 21.1 Master→Slave 传输格式

Master 向 Slave 推送数据时，使用如下二进制格式：

```
┌─────────────────────────────────────────────────────────────┐
│                    Transfer Header (12 bytes)                │
├────────────────┬────────────────────────────────────────────┤
│ Body Size (8)  │ Physic Offset (4) → 实际是 body 的起始偏移  │
│ (long)         │ (int)                                       │
├────────────────┴────────────────────────────────────────────┤
│                    Body (variable length)                    │
│  = CommitLog 中从 physicOffset 开始的数据                     │
│  长度 = Body Size                                           │
└─────────────────────────────────────────────────────────────┘
```

**关键代码**（`WriteSocketService` 的 `transferFromService` 方法）：

```java
private boolean transferFromService() throws Exception {
    // ... 选择 MappedFile ...
    SelectMappedBufferResult selectResult = mappedFile.selectMappedBuffer(nextTransferFromWhere);
    if (selectResult == null) {
        // 没有新数据，发送心跳
        this.lastWriteOver = this.haConnection.getWriteSocketService().sendData(
            this.haConnection.getHaService().getDefaultMessageStore().getCommitLog()
                .getMaxOffset(), true);
        return true;
    }
    
    // 计算本次传输大小
    int size = selectResult.getSize();
    if (size > haConnection.getHaService().getHaTransferBatchSize()) {
        size = haConnection.getHaService().getHaTransferBatchSize();
    }
    
    long thisOffset = nextTransferFromWhere;
    this.nextTransferFromWhere += size;
    
    selectResult.getByteBuffer().limit(size);
    
    // 构建 Header: bodySize(8) + physicOffset(4... 实际是高32位)
    ByteBuffer byteBuffer = this.byteBufferHeader;
    byteBuffer.position(0);
    byteBuffer.putLong(size);
    byteBuffer.putInt((int) (thisOffset % Integer.MAX_VALUE));
    byteBuffer.flip();
    
    // 发送 Header + Body
    this.lastWriteOver = this.haConnection.getWriteSocketService().sendData(
        selectResult, false);
    
    // 更新统计
    this.haConnection.getHaService().getHAClientStatistics().getTransferredByteInAdd()
        .addAndGet(size);
    // ...
    return true;
}
```

**知识点：为什么 physicOffset 只用 4 字节？**

CommitLog 文件由多个 1GB 的 MappedFile 组成，单个文件内偏移量最多 1GB（2^30），而 4 字节 int 的最大值是 2^31-1 ≈ 2GB。因此在单个文件范围内，4 字节足以表示偏移量。Slave 通过 `slaveRequest` 中携带的 `masterPhyOffset` 来定位应该写入哪个 MappedFile，再结合这个偏移量定位到文件内的具体位置。

### 21.2 Slave→Master ACK 格式

Slave 向 Master 报告同步进度时，使用极简的 8 字节格式：

```
┌─────────────────────────────────┐
│  Slave ACK (8 bytes)            │
│  ┌─────────────────────────┐    │
│  │ Slave Phy Offset (8)    │    │
│  │ (long)                  │    │
│  └─────────────────────────┘    │
│                                 │
│  含义：Slave 已经成功写入到      │
│  这个物理偏移量位置              │
└─────────────────────────────────┘
```

**关键代码**（`DefaultHAClient.reportSlaveMaxOffset`）：

```java
private boolean reportSlaveMaxOffsetPlus(final long maxOffset) {
    boolean result = true;
    
    // 检查是否有新的进度需要上报
    if (maxOffset == this.currentReportedOffset) {
        return true;  // 没有新进度，跳过
    }
    
    // 构建ACK
    if (this.byteBufferHeader.position() == 0) {
        this.byteBufferHeader.position(0);
        this.byteBufferHeader.putLong(maxOffset);
        this.byteBufferHeader.flip();
        
        // 发送（如果发送不完整，下次心跳时会继续）
        result = this.writeData(this.byteBufferHeader);
        if (result) {
            this.currentReportedOffset = maxOffset;
        }
    }
    
    return result;
}
```

**知识点：ACK 的捎带机制**

Slave 不会主动发送 ACK 请求。ACK 数据被"捎带"在每次对 Master 数据的读取响应中。具体来说，Slave 在 `dispatchReadRequest` 处理完 Master 推送的数据后，立即调用 `reportSlaveMaxOffsetPlus` 通过同一 TCP 连接发送 ACK。这种设计避免了额外的网络往返，提高了效率。

### 21.3 完整数据交互时序

```
Master (WriteSocketService)          Slave (DefaultHAClient)
     │                                      │
     │  <── Slave ACK (8 bytes) ──────────  │  初始上报 slavePhyOffset
     │                                      │
     │  检查 masterPhyOffset == slavePhyOffset│
     │  ✓ 匹配，开始推送                      │

     │                                      │  写入 CommitLog

     │                                      │

     │  ✓ 有，继续推送                        │
```

## 二十二、AutoSwitchHAService 深度源码解析

### 22.1 AutoSwitchHAService 概述

`AutoSwitchHAService` 是 Controller 模式下的 HA 实现，它在经典 HA 的基础上引入了 **Epoch（纪元）** 机制，实现了类似 Raft 的日志截断和安全性保证。

**核心数据结构**：

```java

    // 当前节点的 Epoch

    // 所有连接的 Epoch 缓存
    private ConcurrentMap<String/*address*/, Long/*epoch*/> connectionEpochMap;
    
    // SyncStateSet（同步副本集合，类似 Raft 的 matchIndex）
    private Set<String/*brokerAddr*/> syncStateSet = new HashSet<>();
    
    // 是否需要截断
    private volatile boolean truncationCME = false;
}
```

### 22.2 Epoch 机制详解

Epoch 是一个单调递增的整数，每次 Master 切换时递增。它的作用类似于 Raft 中的 term：

1. **选举安全**：每个 Epoch 内最多一个 Master
2. **日志截断**：新 Master 根据副本的 Epoch 和 Offset 信息决定是否截断
3. **一致性保证**：确保已提交的日志不会被覆盖

**EpochFileStore 持久化格式**：

```
┌─────────────────────────────────────────────┐
│  EpochFileStore 文件格式                      │
├──────────────────┬──────────────────────────┤
│ Epoch (4 bytes)  │ StartOffset (8 bytes)    │
│ (int)            │ (long)                    │
├──────────────────┼──────────────────────────┤
│ Epoch 1          │ 0                         │
│ Epoch 2          │ 1073741824 (1GB位置)      │
│ Epoch 3          │ 2147483648 (2GB位置)      │
│ ...              │ ...                       │
└──────────────────┴──────────────────────────┘
```

每个 Epoch 记录了该 Epoch 开始时的 CommitLog 偏移量。通过这个信息，可以确定某个偏移量的消息属于哪个 Epoch。

### 22.3 Master 切换时的日志截断

当 Controller 选举新 Master 时，新 Master 执行以下截断流程：


**截断决策逻辑**：

```java
public void processSyncStateSetChanged() {

    // 对于每个 Slave:
    //   - 获取其 epoch 和 offset
    //   - 比较与 Master 的 epoch 序列

    //   → 说明该副本有 Master 没有的旧数据
    //   → 截断该副本的超长部分

    //   → 说明该副本落后，需要追赶
```

### 22.5 SyncStateSet 的维护

```java
// AutoSwitchHAService.updateSyncStateSet()
private void updateSyncStateSet() {
    Set<String> newSyncStateSet = new HashSet<>();
    
    for (Map.Entry<String, HAConnection> entry : connectionMap.entrySet()) {
        HAConnection conn = entry.getValue();
        // 检查该副本是否已追上 Master
        long slaveAckOffset = conn.getSlaveAckOffset();
        long masterOffset = defaultMessageStore.getMaxPhyOffset();
        
        if (masterOffset - slaveAckOffset < haLagThreshold) {
            newSyncStateSet.add(entry.getKey());

    newSyncStateSet.add(masterAddr);
    
    // 如果 syncStateSet 变化，通知 Controller
    if (!newSyncStateSet.equals(this.syncStateSet)) {
        this.syncStateSet = newSyncStateSet;
        notifyControllerSyncStateSetChanged();
    }
}
```

```
    │   │         刷盘失败 → PUT_RESULT = FLUSH_DISK_TIMEOUT
    │   │
    │   └─ NO → GroupCommitService 异步刷盘
    │            不等待，立即返回
    │
    ├─► brokerRole = SYNC_MASTER?
    │   ├─ YES → 需要等待 Slave ACK
    │   │         │
    │   │         ├─► needAckNums = 1?
    │   │         │   └─ YES → 等待至少 1 个 Slave ACK
    │   │         │             超时(5秒) → FLUSH_SLAVE_TIMEOUT
    │   │         │
    │   │         ├─► needAckNums > 1?
    │   │         │   └─ YES → 等待 needAckNums 个 Slave ACK
    │   │         │             超时(5秒) → FLUSH_SLAVE_TIMEOUT
    │   │         │
    │   │         └─► allAckInSyncStateSet = true?
    │   │             └─ YES → 等待 SyncStateSet 中所有副本 ACK
    │   │                       (Controller 模式专属)
    │   │
    │   └─ NO (ASYNC_MASTER / SLAVE)
    │       └─ 不等待 Slave ACK，立即返回
    │
    └─► 返回最终的 putMessageResult
```

### 24.2 GroupTransferService 的等待机制

```java
// GroupTransferService.doWaitTransfer()
private void doWaitTransfer() {
    if (!this.requestsRead.isEmpty()) {
        for (GroupCommitRequest req : this.requestsRead) {
            // 检查是否已满足条件
            boolean transferOK = false;
            for (HAConnection conn : haService.getConnectionList()) {
                if (conn.getSlaveAckOffset() >= req.getNextOffset()) {
                    transferOK = true;
                    break;
                }
            }
            
            if (transferOK) {
                req.wakeupCustomer(PutMessageStatus.PUT_OK);
            } else {
                // 未满足，继续等待
                // 下次循环再检查
                req.park(this);
            }
        }
        
        // 将未完成的请求转移到下次处理
        this.requestsRead.removeAll(doneRequests);
    }
}
```

### 24.3 GroupCommitRequest 的唤醒机制

```java
public static class GroupCommitRequest {
    private final long nextOffset;
    private final CompletableFuture<PutMessageStatus> flushOKFuture;
    
    // 被 HA Connection 回调
    public void wakeupCustomer(final PutMessageStatus status) {
        this.flushOKFuture.complete(status);
    }
    
    // 被 GroupTransferService 调用
    public void park(CountDownLatch2 latch) {
        // 等待 HA 回调或超时
        try {
            latch.await(5, TimeUnit.SECONDS);
        } catch (InterruptedException e) {
            // ...
        }
    }
}
```

**知识点：为什么是 5 秒超时？**

5 秒是 `messageStoreConfig.getSyncFlushTimeout()` 的默认值。这个值需要足够长以允许正常的 Slave 同步完成，但又不能太长以免阻塞生产者。在实际生产环境中，如果 Slave 同步经常超过 5 秒，说明网络或 Slave 性能有问题。

## 二十五、HA 性能优化技术详解

### 25.1 批量传输

Master 每次向 Slave 推送的数据量由 `haTransferBatchSize` 控制（默认 32KB）：

```java
int size = selectResult.getSize();
if (size > haConnection.getHaService().getHaTransferBatchSize()) {
    size = haConnection.getHaService().getHaTransferBatchSize();
}
```

**调优建议**：
- 网络带宽充足时可增大到 64KB 或 128KB
- 网络带宽有限时应减小，避免阻塞
- 值越大，单次传输效率越高，但延迟也越大

### 25.2 零拷贝优化

HA 模块使用了 MappedByteBuffer 的零拷贝特性：

```java
// SelectMappedBufferResult 持有 MappedByteBuffer 的 slice
SelectMappedBufferResult selectResult = mappedFile.selectMappedBuffer(pos);
// selectResult.getByteBuffer() 直接映射到文件内存
// 通过 socketChannel.write(byteBuffer) 直接从内存页发送到网卡
// 避免了数据从用户空间到内核空间的拷贝
```

### 25.3 FlowMonitor 带宽控制

```java
public class FlowMonitor {
    private final LongAdder transferredByte = new LongAdder();
    private final AtomicLong maxTransferByte = new AtomicLong(0);
    private final long windowSize = 1000;  // 1秒窗口
    
    // 每秒重置一次
    public void calculate() {
        long current = transferredByte.sumThenReset();
        if (current > maxTransferByte.get()) {
            maxTransferByte.set(current);
        }
    }
    
    // 检查是否超过限制
    public boolean canTransfer(int size) {
        if (maxTransferByte.get() == 0) return true;  // 无限制
        return transferredByte.sum() + size <= maxTransferByte.get();
    }
}
```

**使用场景**：当 Slave 数量较多时，Master 的 HA 推送可能占用大量带宽，影响正常消息收发。通过 FlowMonitor 可以限制 HA 传输速率，确保正常业务不受影响。

### 25.4 写入优化：writeData 方法

```java
// DefaultHAClient.writeData()
private boolean writeData(final ByteBuffer byteBuffer) {
    int writtenSize = 0;
    while (writtenSize < byteBuffer.remaining()) {
        int writeSize = this.socketChannel.write(byteBuffer);
        if (writeSize > 0) {
            writtenSize += writeSize;
        } else {
            // 写缓冲区满，注册 OP_WRITE 等待
            this.selector.select(1000);  // 最多等 1 秒
            // 如果 1 秒后还是写不出去，返回 false
            if (this.selector.selectedKeys().isEmpty()) {
                return false;
            }
            this.selector.selectedKeys().clear();
        }
    }
    return true;
}
```

**知识点：为什么不用 Selector 异步写？**

HA 是一个流式协议，每次写入量很小（ACK 8 字节，数据 32KB+），使用同步写入更简单且延迟更低。异步写入虽然能处理写缓冲区满的情况，但增加了复杂性。这里的 fallback 是通过 `selector.select(1000)` 短暂等待来实现的。

## 二十六、HA 故障场景全景分析

### 26.1 场景一：Slave 宕机

```
时间线:
  t1: Slave 正常运行，ACK offset = 1000
  t2: Slave 宕机
  t3: Master 继续写入到 offset = 1500
  
Master 端:
  - AcceptSocketService 检测到连接断开
  - 移除 HAConnection
  - 不影响 Master 写入
  - 如果是 SYNC_MASTER，后续消息的 Slave ACK 超时

恢复后:
  t4: Slave 重启，连接 Master
  t5: Slave 上报 offset = 1000
  t6: Master 从 1000 开始推送增量数据
  t7: Slave 追赶到 1500
```

### 26.2 场景二：Master 宕机（ASYNC_MASTER）

```
时间线:
  t1: Master offset = 1000, Slave offset = 800 (有 200 延迟)
  t2: Master 宕机

影响:
  - 800~1000 之间的消息未同步到 Slave
  - 这些消息在 Master 的 PageCache 中，可能未刷盘
  - 如果 Master 重启且 PageCache 未丢失 → 数据不丢
  - 如果 Master 磁盘损坏 → 200 条消息丢失

处理:
  - Slave 被提升为新 Master (需手动或通过 Controller)
  - 客户端切换到新 Master
  - 旧 Master 恢复后作为 Slave 加入
```

### 26.3 场景三：Master 宕机（SYNC_MASTER, needAckNums=1）

```
时间线:
  t1: Master offset = 1000, Slave offset = 1000 (完全同步)
  t2: Master 宕机

影响:
  - 所有已确认的消息都已同步到 Slave
  - 0 条消息丢失
  - 但 Master 写入吞吐量受 Slave 同步速度限制

处理:
  - Slave 提升为新 Master
  - 客户端切换
  - 旧 Master 恢复后作为 Slave
```

### 26.4 场景四：网络分区

```
时间线:
  t1: Master 和 Slave 之间网络断开
  t2: ASYNC_MASTER → Master 继续写入，Slave 停止同步
  t3: SYNC_MASTER → Master 写入阻塞 (等待 ACK 超时)

如果网络恢复:
  - Slave 重新连接，增量同步
  - 数据最终一致

如果网络不恢复 (Controller 模式):
  - Controller 检测到 Master 失联
  - 选举 Slave 为新 Master (epoch + 1)
  - 旧 Master 恢复后被 epoch fencing，强制截断
```

### 26.5 场景五：双写冲突（脑裂）

```
经典模式:
  - 无自动切换，不会脑裂
  - 但也没有高可用

Controller 模式:
  - 理论上 Controller 是单点，不会脑裂
  - 但如果 Controller 自身网络分区:
    - 旧 Master 认为 Controller 挂了，继续服务
    - 新 Master 被选举出来
    - → 脑裂！
  
  解决方案:
  - Controller 集群自身使用 Raft 保证一致性
  - Epoch fencing 确保旧 Master 无法写入
  - 但在 fencing 生效前仍有短暂窗口
```

## 二十七、HA 与消息存储的协作关系

### 27.1 消息写入时 HA 的参与

```
Producer → SendMessageProcessor → CommitLog.asyncPutMessage()
    │
    ├─► 写入 MappedFile (内存)
    │
    ├─► ReputMessageService 异步分发到 ConsumeQueue/IndexFile
    │
    └─► handleDiskFlushAndHA()
        ├─► 刷盘 (FlushManager)
        └─► HA 同步 (DefaultHAService)
            ├─► GroupTransferService 等待 Slave ACK
            └─► WriteSocketService 推送数据到 Slave
```

### 27.2 HA 对 ReputMessageService 的影响

在 SYNC_MASTER 模式下，消息必须等待 Slave ACK 后才能视为"成功"。但 ReputMessageService 是异步的，它不等待 HA 完成：

```java
// ReputMessageService 在 Master 和 Slave 上都运行
// Master: 分发自己写入的消息
// Slave: 分发从 Master 同步过来的消息

// 这意味着 ConsumeQueue 的构建是异步的
// 消费者可能在 HA 同步完成前就拉取到消息
// 如果此时 Master 宕机且消息未同步到 Slave
// → 消费者可能消费到"丢失"的消息
```

**知识点：这是 ASYNC_MASTER 的一个固有风险**

在 ASYNC_MASTER 模式下，Master 写入成功后立即通知 ReputMessageService 分发，不等 Slave 同步。如果 Master 此时宕机，消费者可能已经消费了未同步的消息。SYNC_MASTER 模式通过等待 ACK 降低了这个风险，但仍然存在 ReputMessageService 分发早于 HA 完成的窗口。

### 27.3 Slave 的消息分发

```java
// Slave 端 HA 接收到数据后的处理链
DefaultHAClient.dispatchReadRequest()
    │
    ├─► 解析 Header (bodySize + physicOffset)
    │
    ├─► 写入 CommitLog (mappedFile.appendMessage)
    │
    ├─► 更新 slavePhyOffset
    │
    ├─► reportSlaveMaxOffsetPlus() → ACK Master
    │
    └─► ReputMessageService 自动分发新写入的消息
        ├─► 构建 ConsumeQueue 条目
        └─► 构建 IndexFile 条目
```

**知识点：Slave 的 ReputMessageService 是共享的**

Slave 和 Master 使用相同的 `DefaultMessageStore` 实现，`ReputMessageService` 是其中的一个服务。无论消息是本地写入还是 HA 同步过来的，`ReputMessageService` 都会通过检查 `CommitLog` 的最大偏移量来发现新消息并分发。这种设计使得 Slave 的存储逻辑与 Master 完全一致，简化了实现。

## 二十八、总结与对比

### 28.1 RocketMQ HA 与 Raft 的核心差异

| 维度 | RocketMQ HA (经典) | RocketMQ HA (Controller) | Raft |
|------|--------------------|--------------------------|------|
| 复制方式 | 流式推送 | 流式推送 + Epoch | 日志条目 |
| 一致性检查 | 字节偏移量 | Epoch 前缀匹配 | prevLogIndex + prevLogTerm |
| 日志格式 | 纯字节流 | 字节流 + Epoch | {term, index, command} |
| 选举 | 无（静态配置） | 外部 Controller | 内置 RequestVote |
| 日志截断 | 不支持 | 支持（基于 Epoch） | 支持（基于 prevLogTerm） |
| 提交等待 | GroupTransferService | GroupTransferService + syncStateSet | matchIndex + majority |
| 安全性 | 弱（可能丢数据） | 中（Epoch fencing） | 强（Leader Completeness） |
| 分区容忍 | 低 | 中 | 高 |

### 28.2 RaftByJava 实现建议总结

基于 RocketMQ HA 的分析，RaftByJava 的实现建议：

1. **日志格式**：每条日志必须包含 {term, index, command}，不能用纯字节流
2. **一致性检查**：使用 prevLogIndex + prevLogTerm，而非字节偏移量
3. **复制方式**：可参考流式批量推送，但每个请求必须携带 term
4. **提交等待**：参考 GroupTransferService 的双缓冲设计，但使用 matchIndex 的多数派判断
5. **角色切换**：参考 changeSpecialServiceStatus 的设计，但需要内置选举
6. **日志截断**：必须实现，参考 AutoSwitchHAService 的 Epoch 机制
7. **连接管理**：可参考 AcceptSocketService 和 DefaultHAClient 的设计
8. **故障恢复**：参考 StoreCheckpoint 的设计，但需要更复杂的恢复逻辑（包含 term 信息）
