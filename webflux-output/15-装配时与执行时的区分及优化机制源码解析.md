## 一、全局调用链总览图

以下 ASCII 图展示了从 `flux.map(fn).filter(pred).subscribe(subscriber)` 这一行代码开始，装配时与执行时两条截然不同的执行路径：

```
═══════════════════════════════════════════════════════════════════════════
                      装配时 (Assembly Time) — 构建操作符链
═══════════════════════════════════════════════════════════════════════════

  flux.map(fn)                    flux.filter(pred)
  ┌──────────────────┐            ┌──────────────────┐
  │ FluxMap 构造器    │            │ FluxFilter 构造器 │
  │ 1. 存 source 引用 │            │ 1. 存 source 引用 │
  │ 2. 存 fn 参数     │            │ 2. 存 pred 参数   │
  └────────┬─────────┘            └────────┬─────────┘
           │                                │
           ▼                                ▼
  onAssembly(new FluxMap(source, fn))  onAssembly(new FluxFilter(source, pred))
           │                                │
           ├─► Hooks.onEachOperatorHook? ──► 是则包装
           ├─► Hooks.GLOBAL_TRACE? ────────► 是则插入 FluxOnAssembly
           └─► 返回新 Flux（没有任何数据流动！）

  最终链路: FluxFilter → FluxMap → Source Flux

═══════════════════════════════════════════════════════════════════════════
                      执行时 (Execution Time) — subscribe 触发
═══════════════════════════════════════════════════════════════════════════

  subscriber.subscribe() 调用最外层 FluxFilter

  ┌─ InternalFluxOperator.subscribe(subscriber) ──────────────────────────┐
  │                                                                       │
  │  operator = FluxFilter (this)                                         │
  │  while(true) {                                                        │
  │      subscriber = operator.subscribeOrReturn(subscriber)              │
  │      // ↑ 创建 FilterSubscriber，包装了下游 subscriber                 │
  │                                                                       │
  │      newSource = operator.nextOptimizableSource()                     │
  │      // ↑ 返回 FluxMap（链中的上一个 OptimizableOperator）             │
  │                                                                       │
  │      operator = newSource  // 继续向上游走                            │
  │                                                                       │
  │      subscriber = operator.subscribeOrReturn(subscriber)              │
  │      // ↑ 创建 MapSubscriber，包装了 FilterSubscriber                  │
  │                                                                       │
  │      newSource = operator.nextOptimizableSource()                     │
  │      // ↑ 返回 null（Source Flux 不是 OptimizableOperator）            │
  │                                                                       │
  │      operatorSource = operator.source()  // 获取原始 Source Flux       │
  │      operatorSource.subscribe(subscriber)  // 真正订阅 Source！        │
  │      return;                                                          │
  │  }                                                                    │
  └───────────────────────────────────────────────────────────────────────┘

  订阅建立后的信号传播方向：

  onSubscribe:  Source ──► MapSubscriber ──► FilterSubscriber ──► subscriber
  request:      subscriber ──► FilterSubscriber ──► MapSubscriber ──► Source
  onNext:       Source ──► MapSubscriber ──► FilterSubscriber ──► subscriber
  onComplete:   Source ──► MapSubscriber ──► FilterSubscriber ──► subscriber
  onError:      Source ──► MapSubscriber ──► FilterSubscriber ──► subscriber
```

这张图揭示了 Reactor 最核心的设计哲学之一：**构造阶段纯粹是声明式的，不产生任何数据流动；只有 `subscribe()` 被调用时，数据管道才真正接通。**

## 二、装配时发生了什么

### 2.1 操作符构造器：只做两件事

在 Reactor 中，每一个操作符（如 `map`、`filter`、`flatMap`）本质上都是一个装饰器类，它们继承自 `FluxOperator` 或 `MonoOperator`。以 `FluxOperator` 为例：

源码文件：`reactor/core/publisher/FluxOperator.java`

```java
public abstract class FluxOperator<I, O> extends Flux<O> implements Scannable {

    protected final Flux<? extends I> source;

    protected FluxOperator(Flux<? extends I> source) {
        this.source = Objects.requireNonNull(source);
    }
    // ...
}
```

构造器只做一件事：**保存上游 source 的引用**。而具体的操作符子类（如 `FluxMap`）会额外保存操作参数（如 `mapper` 函数）。这就是装配时操作符构造器做的两件事：

1. 存储上游 `source` 引用
2. 存储操作符参数（如 `Function`、`Predicate` 等）

**没有任何数据流动，没有任何副作用，没有线程调度，没有订阅发生。**

### 2.2 onAssembly：装配时的统一入口

所有 Reactor 内建操作符在构造完成后，都会经过 `Flux.onAssembly()` 方法。这是装配时的核心入口：

源码文件：`reactor/core/publisher/Flux.java`

```java
@SuppressWarnings("unchecked")
protected static <T> Flux<T> onAssembly(Flux<T> source) {
    Function<Publisher, Publisher> hook = Hooks.onEachOperatorHook;
    if(hook != null) {
        source = (Flux<T>) hook.apply(source);
    }
    if (Hooks.GLOBAL_TRACE) {
        AssemblySnapshot stacktrace = new AssemblySnapshot(null, Traces.callSiteSupplierFactory.get());
        source = (Flux<T>) Hooks.addAssemblyInfo(source, stacktrace);
    }
    return source;
}
```

这段代码做了两件事：

1. **检查 `Hooks.onEachOperatorHook`**：如果用户注册了全局的 `onEachOperator` 钩子，对刚创建的操作符 Publisher 应用该函数。这个钩子是一个 `Function<Publisher, Publisher>`，可以将原始 Publisher 替换为另一个 Publisher。
2. **检查 `Hooks.GLOBAL_TRACE`**：如果全局调试模式已开启（通过 `Hooks.onOperatorDebug()` 或系统属性 `reactor.trace.operatorStacktrace`），则创建一个 `AssemblySnapshot` 捕获当前调用堆栈，并通过 `Hooks.addAssemblyInfo()` 将其包装为 `FluxOnAssembly`。

让我们深入看 `Hooks.addAssemblyInfo()`：

源码文件：`reactor/core/publisher/Hooks.java`

```java
@SuppressWarnings("unchecked")
static <T, P extends Publisher<T>> Publisher<T> addAssemblyInfo(P publisher, AssemblySnapshot stacktrace) {
    if (publisher instanceof Callable) {
        if (publisher instanceof Mono) {
            return new MonoCallableOnAssembly<>((Mono<T>) publisher, stacktrace);
        }
        return new FluxCallableOnAssembly<>((Flux<T>) publisher, stacktrace);
    }
    if (publisher instanceof Mono) {
        return new MonoOnAssembly<>((Mono<T>) publisher, stacktrace);
    }
    if (publisher instanceof ParallelFlux) {
        return new ParallelFluxOnAssembly<>((ParallelFlux<T>) publisher, stacktrace);
    }
    if (publisher instanceof ConnectableFlux) {
        return new ConnectableFluxOnAssembly<>((ConnectableFlux<T>) publisher, stacktrace);
    }
    return new FluxOnAssembly<>((Flux<T>) publisher, stacktrace);
}
```

这个方法根据 Publisher 的具体类型（`Callable`、`Mono`、`ParallelFlux`、`ConnectableFlux`、普通 `Flux`）选择对应的 OnAssembly 包装器。所有这些包装器都持有 `AssemblySnapshot`——一个在装配时创建的堆栈快照。

### 2.3 Hooks.onEachOperator：装配时的全局拦截器

`Hooks.onEachOperator` 是 Reactor 提供的全局装配时拦截机制。其注册方式如下：

源码文件：`reactor/core/publisher/Hooks.java`

```java
public static void onEachOperator(String key, Function<? super Publisher<Object>, ? extends Publisher<Object>> onEachOperator) {
    Objects.requireNonNull(key, "key");
    Objects.requireNonNull(onEachOperator, "onEachOperator");
    log.debug("Hooking onEachOperator: {}", key);

    synchronized (log) {
        onEachOperatorHooks.put(key, onEachOperator);
        onEachOperatorHook = createOrUpdateOpHook(onEachOperatorHooks.values());
    }
}
```

可以看到，多个 sub-hook 被存储在 `LinkedHashMap<String, Function>` 中（保持插入顺序），然后通过 `createOrUpdateOpHook` 组合成一个串联的复合函数：

```java
@SuppressWarnings({"unchecked", "rawtypes"})
static @Nullable Function<Publisher, Publisher> createOrUpdateOpHook(
        Collection<Function<? super Publisher<Object>, ? extends Publisher<Object>>> hooks) {
    Function<Publisher, Publisher> composite = null;
    for (Function<? super Publisher<Object>, ? extends Publisher<Object>> function : hooks) {
        Function<? super Publisher, ? extends Publisher> op = (Function<? super Publisher, ? extends Publisher>) function;
        if (composite != null) {
            composite = composite.andThen(op);
        }
        else {
            composite = (Function<Publisher, Publisher>) op;
        }
    }
    return composite;
}
```

这意味着如果有多个 hook，它们会按顺序串联执行：`hook1.andThen(hook2).andThen(hook3)`。每次装配一个新操作符时，这个复合函数都会被调用一次。

**为什么不在执行时触发 Hooks？** 因为 `onEachOperator` 的语义是"每个操作符被创建时"拦截，而不是"每次订阅时"拦截。如果把拦截放在 subscribe 时，那么同一个 Publisher 被多次 subscribe 时，hook 会被重复执行——而装配时只执行一次，无论后续被 subscribe 多少次。这既保证了语义正确性，又保证了性能。

### 2.4 checkpoint()：装配时插入 FluxOnAssembly

`checkpoint()` 是 Reactor 提供的调试辅助方法，它在装配时将一个 `FluxOnAssembly` 操作符插入到操作符链中：

源码文件：`reactor/core/publisher/Flux.java`

```java
public final Flux<T> checkpoint() {
    return checkpoint(null, true);
}

public final Flux<T> checkpoint(String description) {
    return checkpoint(Objects.requireNonNull(description), false);
}

public final Flux<T> checkpoint(@Nullable String description, boolean forceStackTrace) {
    final AssemblySnapshot stacktrace;
    if (!forceStackTrace) {
        stacktrace = new CheckpointLightSnapshot(description);
    }
    else {
        stacktrace = new CheckpointHeavySnapshot(description, Traces.callSiteSupplierFactory.get());
    }

    return new FluxOnAssembly<>(this, stacktrace);
}
```

注意，`checkpoint()` 方法直接返回 `new FluxOnAssembly<>(this, stacktrace)`，**没有经过 `onAssembly()` 方法**。这是因为 `checkpoint` 本身就是手动插入装配跟踪，不需要再被 `onEachOperator` hook 拦截。

三种 checkpoint 模式：

| 方法 | snapshot 类型 | 是否捕获堆栈 | 开销 |
|------|-------------|------------|------|
| `checkpoint()` | `CheckpointHeavySnapshot` | 是 | 高 |
| `checkpoint("desc")` | `CheckpointLightSnapshot` | 否 | 低 |
| `checkpoint("desc", true)` | `CheckpointHeavySnapshot` | 是 | 高 |
| `checkpoint("desc", false)` | `CheckpointLightSnapshot` | 否 | 低 |

`CheckpointLightSnapshot` 的构造非常轻量：

源码文件：`reactor/core/publisher/FluxOnAssembly.java`

```java
static final class CheckpointLightSnapshot extends AssemblySnapshot {

    CheckpointLightSnapshot(@Nullable String description) {
        super(true, description, null);
        this.cached = "checkpoint(\"" + (description == null ? "" : description) + "\")";
    }

    @Override
    public boolean isLight() {
        return true;
    }

    @Override
    public String lightPrefix() {
        return "checkpoint";
    }

    @Override
    String operatorAssemblyInformation() {
        assert this.cached != null;
        return this.cached;
    }
}
```

Light checkpoint 不捕获堆栈（`assemblyInformationSupplier` 为 null），只保存一个描述字符串。这使得它的运行时开销几乎为零，但仍然能在错误发生时提供定位信息。

## 三、执行时发生了什么

### 3.1 InternalFluxOperator.subscribe()：优化循环的核心

当用户调用 `flux.subscribe(subscriber)` 时，执行时阶段正式开始。`InternalFluxOperator` 是绝大多数 Reactor 内建操作符的基类，其 `subscribe()` 方法是实现优化循环的关键：

源码文件：`reactor/core/publisher/InternalFluxOperator.java`

```java
@Override
@SuppressWarnings("unchecked")
public final void subscribe(CoreSubscriber<? super O> subscriber) {
    OptimizableOperator operator = this;
    try {
        while (true) {
            subscriber = operator.subscribeOrReturn(subscriber);
            if (subscriber == null) {
                // null means "I will subscribe myself", returning...
                return;
            }
            OptimizableOperator newSource = operator.nextOptimizableSource();
            if (newSource == null) {
                CorePublisher operatorSource = operator.source();
                subscriber = Operators.restoreContextOnSubscriberIfPublisherNonInternal(operatorSource, subscriber);
                operatorSource.subscribe(subscriber);
                return;
            }
            operator = newSource;
        }
    }
    catch (Throwable e) {
        Operators.reportThrowInSubscribe(subscriber, e);
        return;
    }
}
```

这段代码是整个 Reactor 执行时最精妙的设计之一。让我们逐行分析：

**第一步**：`operator = this`，从当前操作符开始（即用户直接 subscribe 的那个操作符，通常是链中最下游的操作符）。

**第二步**：进入 `while(true)` 循环。每次迭代：
- 调用 `operator.subscribeOrReturn(subscriber)`。这个方法由具体操作符实现，负责创建对应的 `Subscriber` 对象并返回。如果返回 null，表示该操作符自行处理了订阅（如某些优化场景），直接 return。
- 调用 `operator.nextOptimizableSource()` 获取链中的上一个 `OptimizableOperator`。如果返回 null，表示上游已经不是 `OptimizableOperator`（可能是原始数据源如 `FluxRange`），此时调用 `operator.source().subscribe(subscriber)` 真正订阅数据源，然后 return。
- 如果 `nextOptimizableSource()` 返回非 null，则 `operator = newSource`，继续循环，向上游走。

### 3.2 subscribeOrReturn：创建 Subscriber 而非递归 subscribe

`subscribeOrReturn` 是 `OptimizableOperator` 接口定义的核心方法：

源码文件：`reactor/core/publisher/OptimizableOperator.java`

```java
interface OptimizableOperator<IN, OUT> extends CorePublisher<IN> {

    /**
     * Allow delegation of the subscription by returning a {@link CoreSubscriber},
     * or force subscription encapsulation by returning null.
     */
    @Nullable CoreSubscriber<? super OUT> subscribeOrReturn(CoreSubscriber<? super IN> actual) throws Throwable;

    /**
     * @return {@link CorePublisher} to call subscribe on if nextOptimizableSource() returns null
     */
    CorePublisher<? extends OUT> source();

    /**
     * Allow delegation of the subscription by returning the next {@link OptimizableOperator} UP in the chain.
     */
    @Nullable OptimizableOperator<?, ? extends OUT> nextOptimizableSource();
}
```

传统方式下，每个操作符的 `subscribe` 方法会这样写：

```java
// 传统递归方式（伪代码）
public void subscribe(Subscriber subscriber) {
    Subscriber inner = new MapSubscriber(subscriber, mapper);
    source.subscribe(inner);  // 递归调用上游的 subscribe
}
```

这种方式的问题是：每次 `source.subscribe(inner)` 都是一次方法调用嵌套，操作符链越长，调用栈越深。对于 100 个操作符的链，栈深度就是 100 层。

而 Reactor 的优化循环方式：

```java
// Reactor 的循环方式
while (true) {
    subscriber = operator.subscribeOrReturn(subscriber);  // 只创建 Subscriber，不调用 subscribe
    // ...
    operator = newSource;  // 继续向上游走
}
// 到达源头后才调用 source.subscribe(subscriber)
```

整个链路只有一个 `source.subscribe(subscriber)` 调用，无论链有多长，调用栈深度始终为 1（在 subscribe 方法内部）。

### 3.3 nextOptimizableSource：链式遍历的纽带

`InternalFluxOperator` 的构造器在创建时就预先检查了上游 source 是否也是 `OptimizableOperator`：

源码文件：`reactor/core/publisher/InternalFluxOperator.java`

```java
protected InternalFluxOperator(Flux<? extends I> source) {
    super(source);
    if (source instanceof OptimizableOperator) {
        @SuppressWarnings("unchecked")
        OptimizableOperator<?, I> optimSource = (OptimizableOperator<?, I>) source;
        this.optimizableOperator = optimSource;
    }
    else {
        this.optimizableOperator = null;
    }
}
```

这个检查在装配时完成（构造器中），结果存储在 `final` 字段 `optimizableOperator` 中。执行时只需要直接读取这个字段，无需任何运行时类型检查：

```java
@Override
public final @Nullable OptimizableOperator<?, ? extends I> nextOptimizableSource() {
    return optimizableOperator;
}
```

`InternalMonoOperator` 的实现完全一致：

源码文件：`reactor/core/publisher/InternalMonoOperator.java`

```java
protected InternalMonoOperator(Mono<? extends I> source) {
    super(source);
    if (source instanceof OptimizableOperator) {
        @SuppressWarnings("unchecked")
        OptimizableOperator<?, I> optimSource = (OptimizableOperator<?, I>) source;
        this.optimizableOperator = optimSource;
    }
    else {
        this.optimizableOperator = null;
    }
}
```

### 3.4 restoreContextOnSubscriberIfPublisherNonInternal：Context 保护

在优化循环到达链的顶端、即将调用 `source.subscribe()` 之前，有一个关键步骤：

```java
if (newSource == null) {
    CorePublisher operatorSource = operator.source();
    subscriber = Operators.restoreContextOnSubscriberIfPublisherNonInternal(operatorSource, subscriber);
    operatorSource.subscribe(subscriber);
    return;
}
```

源码文件：`reactor/core/publisher/Operators.java`

```java
static <T> CoreSubscriber<T> restoreContextOnSubscriberIfPublisherNonInternal(
        Publisher<?> publisher, CoreSubscriber<T> subscriber) {
    if (ContextPropagationSupport.shouldWrapPublisher(publisher)) {
        return restoreContextOnSubscriber(publisher, subscriber);
    }
    return subscriber;
}
```

当上游 Publisher 不是 Reactor 内部类型（即非 `InternalFluxOperator`/`InternalMonoOperator`），而是用户自定义的 Publisher 时，Reactor 需要确保 Context 不会被丢失。这个方法检查是否需要为 subscriber 包装一层 Context 恢复逻辑。这是 Reactor 3.5+ 引入的 Context 传播机制的一部分。

### 3.5 信号传播方向

订阅建立后，信号的传播严格遵循 Reactive Streams 规范：

- **onSubscribe**：从上游向下游传播。Source 调用 `MapSubscriber.onSubscribe()`，`MapSubscriber` 调用 `FilterSubscriber.onSubscribe()`，以此类推。
- **request**：从下游向上游传播。用户 subscriber 调用 `request(n)`，经过各层 Subscriber 的 `request()` 方法，最终到达 Source。
- **onNext/onError/onComplete**：从上游向下游传播。Source 产出数据，经过各层 Subscriber 的处理，最终到达用户 subscriber。

这种双向传播模型确保了背压的正确传递——消费者通过 `request` 控制生产者速率，生产者通过 `onNext` 推送数据。

## 四、OptimizableOperator 如何用循环替代递归

### 4.1 设计动机

**如果去掉 OptimizableOperator 会怎样？**

假设 Reactor 不使用优化循环，而是传统的递归 subscribe。考虑一个有 50 个操作符的链：

```
flux.map(f1).filter(p1).map(f2).flatMap(g).map(f3)...subscribe(sub)
```

每次 `subscribe` 都会递归调用上游的 `subscribe`，导致调用栈深度达到 50 层。这在正常情况下可能不是大问题，但在以下场景中会变得严重：

1. **深层嵌套的 flatMap**：`flatMap` 内部会订阅新的 Publisher，如果内部也有长操作符链，栈深度会叠加。
2. **调试模式**：开启 `Hooks.onOperatorDebug()` 后，`FluxOnAssembly` 也会参与链路，增加额外深度。
3. **某些 JVM 优化限制**：过深的递归可能阻止 JIT 内联优化。

### 4.2 循环的核心逻辑

OptimizableOperator 的循环逻辑可以简化为以下伪代码：

```
operator = 最下游操作符
subscriber = 用户 subscriber

while (true) {
    // 1. 当前操作符创建对应的 Subscriber（包装下游 subscriber）
    newSubscriber = operator.subscribeOrReturn(subscriber)
    
    if (newSubscriber == null) return  // 操作符自行处理了订阅
    
    subscriber = newSubscriber
    
    // 2. 获取链中的上一个 OptimizableOperator
    nextOperator = operator.nextOptimizableSource()
    
    if (nextOperator == null) {
        // 3. 上游不是 OptimizableOperator，调用其 subscribe
        source = operator.source()
        source.subscribe(subscriber)
        return
    }
    
    operator = nextOperator  // 4. 继续向上游走
}
```

关键在于：**循环过程中不调用任何 `subscribe` 方法**，只是不断创建新的 Subscriber 包装器。只有当遍历到链的顶端（非 OptimizableOperator 的 Source），才执行唯一一次 `source.subscribe(subscriber)`。

### 4.3 subscribeOrReturn 返回 null 的场景

某些操作符的 `subscribeOrReturn` 可能返回 null，表示"我自己处理了订阅，不需要继续向上游走"。例如，`FluxOnAssembly` 的 `subscribeOrReturn` 总是返回非 null（它只是包装 subscriber），但某些特殊操作符可能在内部直接订阅上游。

当返回 null 时，循环直接 return，不再继续遍历。这种设计允许操作符"短路"优化循环，在需要时接管整个订阅流程。

## 五、FluxLift：自定义操作符机制

### 5.1 Lift 的设计

`FluxLift` 是 Reactor 提供的自定义操作符机制。当用户通过 `Operators.lift()` 创建一个 lift 函数并应用到 Publisher 时，最终会创建 `FluxLift`：

源码文件：`reactor/core/publisher/FluxLift.java`

```java
final class FluxLift<I, O> extends InternalFluxOperator<I, O> {

    final Operators.LiftFunction<I, O> liftFunction;

    FluxLift(Publisher<I> p,
             Operators.LiftFunction<I, O> liftFunction) {
        super(Flux.from(p));
        this.liftFunction = liftFunction;
    }

    @Override
    public CoreSubscriber<? super I> subscribeOrReturn(CoreSubscriber<? super O> actual) {
        // No need to wrap actual for CP, the Operators$LiftFunction handles it.
        CoreSubscriber<? super I> input = liftFunction.lifter.apply(source, actual);

        Objects.requireNonNull(input, "Lifted subscriber MUST NOT be null");

        return input;
    }
}
```

`FluxLift` 继承自 `InternalFluxOperator`，因此它也参与优化循环。它的 `subscribeOrReturn` 调用 `liftFunction.lifter.apply(source, actual)`——这是一个用户提供的 `BiFunction<Publisher, CoreSubscriber, CoreSubscriber>`，接收上游 Publisher 和下游 Subscriber，返回一个新的 Subscriber。

### 5.2 LiftFunction 的 apply 方法

`LiftFunction` 是 `Operators` 的内部类，其 `apply` 方法负责根据 Publisher 类型创建对应的 Lift 操作符：

源码文件：`reactor/core/publisher/Operators.java`

```java
final static class LiftFunction<I, O>
        implements Function<Publisher<I>, Publisher<O>> {

    final @Nullable Predicate<Publisher> filter;
    final String name;
    final BiFunction<Publisher, ? super CoreSubscriber<? super O>,
            ? extends CoreSubscriber<? super I>> lifter;

    @Override
    public Publisher<O> apply(Publisher<I> publisher) {
        if (filter != null && !filter.test(publisher)) {
            @SuppressWarnings("unchecked")
            Publisher<O> _publisher = (Publisher<O>) publisher;
            return _publisher;
        }

        if (publisher instanceof Fuseable) {
            if (publisher instanceof Mono) {
                return new MonoLiftFuseable<>(publisher, this);
            }
            if (publisher instanceof ParallelFlux) {
                return new ParallelLiftFuseable<>((ParallelFlux<I>)publisher, this);
            }
            if (publisher instanceof ConnectableFlux) {
                return new ConnectableLiftFuseable<>((ConnectableFlux<I>) publisher, this);
            }
            if (publisher instanceof GroupedFlux) {
                return new GroupedLiftFuseable<>((GroupedFlux<?, I>) publisher, this);
            }
            return new FluxLiftFuseable<>(publisher, this);
        }
        else {
            if (publisher instanceof Mono) {
                return new MonoLift<>(publisher, this);
            }
            if (publisher instanceof ParallelFlux) {
                return new ParallelLift<>((ParallelFlux<I>)publisher, this);
            }
            if (publisher instanceof ConnectableFlux) {
                return new ConnectableLift<>((ConnectableFlux<I>) publisher, this);
            }
            if (publisher instanceof GroupedFlux) {
                return new GroupedLift<>((GroupedFlux<?, I>) publisher, this);
            }
            return new FluxLift<>(publisher, this);
        }
    }
}
```

这个方法展示了 Reactor 对不同 Publisher 类型的精细处理：

- **Fuseable vs 非 Fuseable**：如果上游实现了 `Fuseable` 接口，使用 `FluxLiftFuseable`（支持队列融合）；否则使用 `FluxLift`。
- **Mono vs Flux vs ParallelFlux vs ConnectableFlux vs GroupedFlux**：每种类型都有对应的 Lift 变体，确保类型安全。
- **filter 过滤**：如果提供了 `Predicate<Publisher>` 过滤器且不匹配，直接返回原始 Publisher，不应用 lift。

### 5.3 Lift 中的 Context 保护

`LiftFunction` 的构造过程中，lifter 函数被包装了一层以确保 Context 传播：

源码文件：`reactor/core/publisher/Operators.java`

```java
BiFunction<Publisher, ? super CoreSubscriber<? super O>, ? extends CoreSubscriber<? super I>>
effectiveLifter =
        (pub, sub) -> {
            CoreSubscriber<? super I> userLiftedSub =
                    lifter.apply(Scannable.from(pub),
                            restoreContextOnSubscriberIfAutoCPEnabled(pub, sub));
            return restoreContextOnSubscriberIfPublisherNonInternal(pub, userLiftedSub);
        };
```

这里有两层 Context 保护：
1. **入口保护**：`restoreContextOnSubscriberIfAutoCPEnabled(pub, sub)` 确保在调用用户 lifter 之前，如果自动 Context 传播已开启，subscriber 的 Context 被正确恢复到 ThreadLocal。
2. **出口保护**：`restoreContextOnSubscriberIfPublisherNonInternal(pub, userLiftedSub)` 确保 lifter 返回的 subscriber 在传给非内部 Publisher 时，Context 不会丢失。

## 六、FluxOnAssembly：装配跟踪的运行时行为

### 6.1 subscribeOrReturn 的包装逻辑

`FluxOnAssembly` 在装配时创建，保存了 `AssemblySnapshot`。在执行时（subscribe 时），它的 `subscribeOrReturn` 方法负责将下游 subscriber 包装为 `OnAssemblySubscriber`：

源码文件：`reactor/core/publisher/FluxOnAssembly.java`

```java
@Override
@SuppressWarnings("unchecked")
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    return wrapSubscriber(actual, source, this, snapshotStack);
}

@SuppressWarnings("unchecked")
static <T> CoreSubscriber<? super T> wrapSubscriber(CoreSubscriber<? super T> actual,
                                                    Flux<? extends T> source,
                                                    Publisher<?> current,
                                                    @Nullable AssemblySnapshot snapshotStack) {
    if(snapshotStack != null) {
        if (actual instanceof ConditionalSubscriber) {
            ConditionalSubscriber<? super T> cs = (ConditionalSubscriber<? super T>) actual;
            return new OnAssemblyConditionalSubscriber<>(cs, snapshotStack, source, current);
        }
        else {
            return new OnAssemblySubscriber<>(actual, snapshotStack, source, current);
        }
    }
    else {
        return actual;
    }
}
```

注意这里对 `ConditionalSubscriber` 的特殊处理——如果下游是条件订阅者，则创建 `OnAssemblyConditionalSubscriber` 以保持 `tryOnNext` 优化路径。这体现了 Reactor 在功能增强和性能优化之间的精细平衡。

### 6.2 OnAssemblySubscriber：错误时附加堆栈

`OnAssemblySubscriber` 的核心逻辑在 `onError` 时触发：

源码文件：`reactor/core/publisher/FluxOnAssembly.java`

```java
@Override
final public void onError(Throwable t) {
    actual.onError(fail(t));
}

final Throwable fail(Throwable t) {
    boolean lightCheckpoint = snapshotStack.isLight();

    OnAssemblyException onAssemblyException = null;
    for (Throwable e : t.getSuppressed()) {
        if (e instanceof OnAssemblyException) {
            onAssemblyException = (OnAssemblyException) e;
            break;
        }
    }

    if (onAssemblyException == null) {
        if (lightCheckpoint) {
            onAssemblyException = new OnAssemblyException("");
        }
        else {
            StringBuilder sb = new StringBuilder();
            fillStacktraceHeader(sb, parent.getClass(), snapshotStack.getDescription());
            sb.append(snapshotStack.toAssemblyInformation().replaceFirst("\\n$", ""));
            String description = sb.toString();
            onAssemblyException = new OnAssemblyException(description);
        }

        t = Exceptions.addSuppressed(t, onAssemblyException);
        // ... 清理堆栈中的 OnAssembly 噪声行 ...
    }

    onAssemblyException.add(parent, current, snapshotStack);

    return t;
}
```

这段代码的关键逻辑：

1. **延迟到错误时才生成堆栈信息**：虽然 `AssemblySnapshot` 在装配时创建，但实际的堆栈格式化和 `OnAssemblyException` 创建是在 `onError` 时才发生的。对于 light checkpoint，连堆栈都不需要格式化。
2. **复用已有的 OnAssemblyException**：如果异常已经被之前的 OnAssemblySubscriber 附加过 `OnAssemblyException`，则直接复用，在其上追加当前节点的信息。
3. **构建调用链树**：`OnAssemblyException` 内部维护了一个 `ObservedAtInformationNode` 树结构，记录了错误经过的所有操作符节点及其调用位置。

### 6.3 OnAssemblyException.getMessage()：格式化调用链

当最终异常被打印时，`OnAssemblyException.getMessage()` 会格式化整个调用链：

```java
@Override
public @Nullable String getMessage() {
    synchronized (nodesPerId) {
        if (root.children.isEmpty()) {
            return super.getMessage();
        }

        StringBuilder sb = new StringBuilder(super.getMessage())
            .append(System.lineSeparator())
            .append("Error has been observed at the following site(s):")
            .append(System.lineSeparator());

        List<List<ObservedAtInformationNode>> rootPaths = new ArrayList<>();
        root.children.forEach(actualRoot -> findPathToLeaves(actualRoot, rootPaths));

        rootPaths.forEach(path -> path.forEach(node -> {
            boolean isRoot = node.parent == null || node.parent == root;
            sb.append("\t");
            String connector = "|_";
            if (isRoot) {
                connector = "*_";
            }
            sb.append(connector);
            // ... 格式化每个节点 ...
        }));

        sb.append("Original Stack Trace:");
        return sb.toString();
    }
}
```

输出类似：
```

    *__FluxOnAssembly.flatten ⇢ at com.example.MyClass.myMethod(MyClass.java:42)
    |_FluxMap.map ⇢ at com.example.MyClass.myMethod(MyClass.java:43)
    |_FluxFilter.filter ⇢ at com.example.MyClass.myMethod(MyClass.java:44)
Original Stack Trace:
```

## 七、Hooks.onLastOperator：最终 subscribe 前的触发

除了 `onEachOperator`（每个操作符创建时触发），Reactor 还提供了 `onLastOperator`——它在链的最后一个操作符（即用户直接 subscribe 的那个操作符）被创建时触发。

源码文件：`reactor/core/publisher/Hooks.java`

```java
public static void onLastOperator(String key, Function<? super Publisher<Object>, ? extends Publisher<Object>> onLastOperator) {
    Objects.requireNonNull(key, "key");
    Objects.requireNonNull(onLastOperator, "onLastOperator");
    log.debug("Hooking onLastOperator: {}", key);

    synchronized (log) {
        onLastOperatorHooks.put(key, onLastOperator);
        onLastOperatorHook = createOrUpdateOpHook(onLastOperatorHooks.values());
    }
}
```

`onLastOperator` 的典型用途是在 subscribe 之前插入全局的监控或日志操作符。与 `onEachOperator` 不同，`onLastOperator` 只对链的最后一个操作符生效。

**为什么需要区分 onEachOperator 和 onLastOperator？** 如果你想在每个操作符上都插入某种横切逻辑（如装配跟踪），用 `onEachOperator`。如果你只想在最外层（subscribe 入口处）插入一次（如 metrics 指标收集），用 `onLastOperator`。后者避免了在链中插入 N 个监控操作符的开销。

## 八、反例：如果不区分装配时和执行时

### 8.1 假设场景

假设 Reactor 不区分装配时和执行时，而是在 `map(fn)` 方法内部就执行 `fn`：

```java
// 假设的错误设计
public <V> Flux<V> map(Function<T, V> mapper) {
    V result = mapper.apply(this.lastValue);  // 在装配时就执行 mapper！
    return new FluxJust<>(result);
}
```

这会导致以下严重问题：

1. **副作用过早执行**：如果 mapper 有副作用（如打印日志、修改外部状态），这些副作用会在 `map()` 被调用时立即执行，而不是在 subscribe 时才执行。这破坏了声明式编程的语义。

2. **无法处理异步源**：如果上游是 `Flux.fromIterable(items).map(fn)`，在装配时 `items` 可能还没有准备好（例如来自异步 HTTP 响应），`mapper.apply()` 无从执行。

3. **每次 subscribe 重复执行**：如果链被多次 subscribe，mapper 应该对每次订阅的数据都执行一次。如果在装配时执行，就只能执行一次，后续 subscribe 时使用的是固定结果。

4. **背压失效**：如果装配时就执行了 mapper，那么 request(n) 控制的就是已经映射后的结果，而不是原始数据。生产者-消费者之间的背压关系被打破。

5. **错误处理混乱**：如果 mapper 抛出异常，在装配时抛出和执行时抛出的处理方式完全不同。装配时抛出是普通 Java 异常，执行时抛出是 `onError` 信号。

### 8.2 正确设计的优势

Reactor 的正确设计确保了：

- **纯声明**：`flux.map(fn).filter(pred)` 只是构建了一个 `FluxFilter -> FluxMap -> Source` 的链，不执行任何用户代码。
- **延迟执行**：只有 `subscribe()` 才触发数据流动，mapper 和 predicate 在此时才开始被调用。
- **多次订阅**：同一个 Flux 链可以被 subscribe 多次，每次订阅都会从头开始执行所有操作符逻辑。
- **背压正确**：request 从下游向上游传播，确保消费者控制生产者速率。

## 九、多角度交叉验证

### 9.1 从内存模型角度

装配时创建的操作符链是一个不可变的单向链表：每个操作符持有上游 source 的引用。这个链表在构造完成后不会被修改（`final` 字段），因此对多线程可见性是安全的。多个线程可以同时 subscribe 同一个 Flux 链，每次 subscribe 都会创建独立的 Subscriber 链。

### 9.2 从性能角度

优化循环避免了递归调用栈的深度问题。对于一个 N 个操作符的链，传统递归的栈深度是 O(N)，而循环方式的栈深度是 O(1)。这在操作符链较长时（如复杂的 flatMap 嵌套场景）可以显著减少栈帧开销。

### 9.3 从调试角度

装配时捕获的 `AssemblySnapshot` 在执行时才被使用（在 `onError` 时附加到异常）。这种延迟使用设计确保了：
- 正常路径零开销（不捕获堆栈时）
- 错误路径才付出格式化代价
- 堆栈信息在多次 subscribe 间共享（因为 AssemblySnapshot 是 final 字段，在装配时创建一次）

### 9.4 从 Reactive Streams 规范角度

Reactive Streams 规范规定 `Publisher.subscribe()` 的调用不应阻塞。Reactor 的优化循环完全在 subscribe 方法内部完成（创建 Subscriber 链 + 调用 source.subscribe），不涉及任何阻塞操作。唯一可能阻塞的是 source.subscribe 内部的 onSubscribe 调用链，但规范允许这一步同步执行。

## 十、归纳表格

### 装配时 vs 执行时对比表

| 维度 | 装配时 (Assembly Time) | 执行时 (Execution Time) |
|------|----------------------|------------------------|
| **触发时机** | 调用 `map()`、`filter()` 等操作符方法时 | 调用 `subscribe()` 时 |
| **执行内容** | 创建操作符对象，存 source 引用和参数 | 创建 Subscriber 链，接通数据管道 |
| **数据流动** | 无，纯粹是声明式构建 | 有，onNext/onError/onComplete 信号传播 |
| **副作用** | 无用户代码执行（Hooks 除外） | 执行 mapper、predicate、consumer 等用户代码 |
| **调用栈深度** | O(1)（每个操作符独立构造） | O(1)（OptimizableOperator 循环优化） |
| **Hooks 触发** | `onEachOperator`、`onLastOperator` | 无（Hooks 在装配时已应用） |
| **堆栈捕获** | `FluxOnAssembly` 构造时捕获 `AssemblySnapshot` | `OnAssemblySubscriber.fail()` 时格式化堆栈 |
| **可重复性** | 只执行一次（操作符链不可变） | 每次 subscribe 都重新执行 |
| **线程安全** | 构造后不可变，天然线程安全 | 每次 subscribe 创建独立 Subscriber 链 |
| **核心方法** | `Flux.onAssembly()`、构造器 | `InternalFluxOperator.subscribe()`、`subscribeOrReturn()` |
| **优化机制** | `nextOptimizableSource()` 在构造时预计算 | `while(true)` 循环替代递归 |
| **Context 处理** | 不涉及 | `restoreContextOnSubscriberIfPublisherNonInternal()` |
| **错误处理** | 构造异常直接抛出 | `Operators.reportThrowInSubscribe()` 转为 onError |
| **典型类** | `FluxOperator`、`FluxMap`、`FluxOnAssembly` | `InternalFluxOperator`、`OptimizableOperator`、`OnAssemblySubscriber` |
| **checkpoint 行为** | 创建 `FluxOnAssembly` 插入链中 | 包装 Subscriber，在 onError 时附加调用链 |

### 核心源码类职责表

| 类名 | 职责 | 阶段 |
|------|------|------|
| `FluxOperator` | 操作符基类，持有 source 引用 | 装配时 |
| `InternalFluxOperator` | 内建 Flux 操作符基类，实现优化循环 | 执行时 |
| `InternalMonoOperator` | 内建 Mono 操作符基类，实现优化循环 | 执行时 |
| `OptimizableOperator` | 接口，定义循环优化的三个核心方法 | 执行时 |
| `FluxOnAssembly` | 装配跟踪操作符，保存堆栈快照 | 装配时+执行时 |
| `FluxLift` | 自定义操作符包装器，委托给 LiftFunction | 执行时 |
| `Hooks` | 全局钩子管理，装配时拦截入口 | 装配时 |
| `Operators.LiftFunction` | lift 函数实现，根据类型创建对应 Lift 变体 | 装配时 |
| `OnAssemblySubscriber` | 装配跟踪 Subscriber，错误时附加调用链 | 执行时 |

## 十一、总结

Reactor Core 的装配时与执行时分离是其最核心的架构设计之一。这一设计带来了三个关键优势：

1. **声明式语义**：用户代码构建的是数据处理管道的"蓝图"，而非立即执行的命令。这与 Java Stream API 的设计理念一致，但 Reactor 将其扩展到了异步、背压驱动的场景。

2. **优化空间**：装配时构建的不可变操作符链为执行时优化提供了基础。`OptimizableOperator` 的循环替代递归正是利用了装配时预先建立的 `optimizableOperator` 链表，在执行时以 O(1) 栈深度完成整个订阅过程。

3. **可观测性**：装配时捕获的信息（如 `AssemblySnapshot`）为执行时的错误诊断提供了丰富的上下文。`checkpoint()` 和 `Hooks.onOperatorDebug()` 在装配时插入跟踪节点，但实际的堆栈格式化延迟到 `onError` 时才执行，实现了零开销观测。

理解这一分离机制，是理解 Reactor 所有其他机制（操作符融合、背压传播、线程调度、Context 传播）的基础。后续篇章中讨论的所有执行时行为，都建立在装配时构建的操作符链之上。
