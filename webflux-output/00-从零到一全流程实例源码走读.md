## 示例一：最简链路 —— `Flux.just(1,2,3).map(n -> n*10).subscribe()`

这是能写出的最简单的 Reactor 链。我们用它来追踪"从用户代码到数据发射"的完整路径。

### 1.1 装配时：创建操作符链

**第一步：`Flux.just(1, 2, 3)`**

源码位置：`reactor/core/publisher/Flux.java` 中的静态工厂方法

```java
// Flux.java（简化展示关键逻辑）
public static <T> Flux<T> just(T... data) {
    return fromArray(data);
}

public static <T> Flux<T> fromArray(T... array) {
    // ...
    return new FluxArray<>(array);
}
```

这行代码创建了 `FluxArray` 对象。来看 `FluxArray` 的构造器：

源码位置：`reactor/core/publisher/FluxArray.java`

```java
final class FluxArray<T> extends Flux<T> implements Fuseable, SourceProducer<T> {

    final T[] array;

    @SafeVarargs
    public FluxArray(T... array) {
        this.array = Objects.requireNonNull(array, "array");
    }
    // ...
}
```

注意 `FluxArray` 实现了两个关键接口：`Fuseable`（标记可熔合）和 `SourceProducer<T>`（标记为链的起点）。此时 `array = [1, 2, 3]` 被存在 final 字段里，没有任何数据流动。

**第二步：`.map(n -> n * 10)`**

源码位置：`reactor/core/publisher/Flux.java` 中的实例方法

```java
// Flux.java（简化）
public final <V> Flux<V> map(Function<? super T, ? extends V> mapper) {
    if (this instanceof Fuseable) {
        return new FluxMapFuseable<>(this, mapper);
    }
    return new FluxMap<>(this, mapper);
}
```

这里有一个关键分支：如果 source 实现了 `Fuseable`（`FluxArray` 确实实现了），就用 `FluxMapFuseable` 而不是 `FluxMap`。这是熔合优化的入口。

由于 `FluxArray` 实现了 `Fuseable`，实际创建的是 `FluxMapFuseable`：

源码位置：`reactor/core/publisher/FluxMapFuseable.java`

```java
final class FluxMapFuseable<T, R> extends InternalFluxOperator<T, R> implements Fuseable {

    final Function<? super T, ? extends R> mapper;

    FluxMapFuseable(Flux<? extends T> source,
            Function<? super T, ? extends R> mapper) {
        super(source);
        this.mapper = Objects.requireNonNull(mapper, "mapper");
    }
    // ...
}
```

构造器调用 `super(source)`，将 `FluxArray` 存入父类 `FluxOperator` 的 `source` 字段：

源码位置：`reactor/core/publisher/FluxOperator.java`

```java
public abstract class FluxOperator<I, O> extends Flux<O> implements Scannable {
    protected final Flux<? extends I> source;

    protected FluxOperator(Flux<? extends I> source) {
        this.source = Objects.requireNonNull(source, "source");
    }
}
```

同时 `InternalFluxOperator` 构造器还会检查 source 是否是 `OptimizableOperator`，以构建优化链：

源码位置：`reactor/core/publisher/InternalFluxOperator.java`

```java
abstract class InternalFluxOperator<I, O> extends FluxOperator<I, O> implements Scannable,
                                                                                OptimizableOperator<O, I> {

    final @Nullable OptimizableOperator<?, I> optimizableOperator;

    protected InternalFluxOperator(Flux<? extends I> source) {
        super(source);
        if (source instanceof OptimizableOperator) {
            @SuppressWarnings("unchecked")
            OptimizableOperator<?, I> optimSource = (OptimizableOperator<?, I>) source;
            this.optimizableOperator = optimSource;
        }
        else {
            this.optimizableOperator = null;  // FluxArray 不是 OptimizableOperator，所以这里是 null
        }
    }
}
```

此时装配后的对象图：

```
FluxMapFuseable
  ├ source = FluxArray(array=[1,2,3])
  ├ mapper = n -> n * 10
  ├ optimizableOperator = null  (FluxArray不是OptimizableOperator)
  └ implements Fuseable
```

**第三步：`.subscribe()`**

用户调用无参 `subscribe()`，实际调用的是 `Flux.subscribe(Consumer)` 的简化版：

源码位置：`reactor/core/publisher/Flux.java`

```java
// 最终调用到这个方法
public final Disposable subscribe(
        @Nullable Consumer<? super T> consumer,
        @Nullable Consumer<? super Throwable> errorConsumer,
        @Nullable Runnable completeConsumer) {
    return subscribe(consumer, errorConsumer, completeConsumer,
            (Consumer<? super Subscription>) null, Context.empty());
}
```

这个方法内部创建了一个 `LambdaSubscriber`：

源码位置：`reactor/core/publisher/LambdaSubscriber.java`

```java
final class LambdaSubscriber<T>
        implements InnerConsumer<T>, Disposable {

    final @Nullable Consumer<? super T>            consumer;
    final @Nullable Consumer<? super Throwable>    errorConsumer;
    final @Nullable Runnable                       completeConsumer;
    final @Nullable Consumer<? super Subscription> subscriptionConsumer;

    final Context initialContext;

    volatile Subscription subscription;

    LambdaSubscriber(
            @Nullable Consumer<? super T> consumer,
            @Nullable Consumer<? super Throwable> errorConsumer,
            @Nullable Runnable completeConsumer,
            @Nullable Consumer<? super Subscription> subscriptionConsumer,
            @Nullable Context initialContext) {
        this.consumer = consumer;
        this.errorConsumer = errorConsumer;
        this.completeConsumer = completeConsumer;
        this.subscriptionConsumer = subscriptionConsumer;
        this.initialContext = initialContext == null ? Context.empty() : initialContext;
    }
    // ...
}
```

由于 `subscriptionConsumer` 为 null，`LambdaSubscriber` 在 `onSubscribe` 中会自动请求 `Long.MAX_VALUE`：

```java
@Override
public void onSubscribe(Subscription s) {
    if (Operators.validate(subscription, s)) {
        this.subscription = s;
        if (subscriptionConsumer != null) {
            try {
                subscriptionConsumer.accept(s);
            }
            catch (Throwable t) {
                Exceptions.throwIfFatal(t);
                s.cancel();
                onError(t);
            }
        }
        else {
            s.request(Long.MAX_VALUE);  // ← 自动请求无界
        }
    }
}
```

### 1.2 订阅时：优化循环

`subscribe(LambdaSubscriber)` 最终调用 `FluxMapFuseable` 继承自 `InternalFluxOperator` 的 `subscribe` 方法：

源码位置：`reactor/core/publisher/InternalFluxOperator.java`

```java
@Override
@SuppressWarnings("unchecked")
public final void subscribe(CoreSubscriber<? super O> subscriber) {
    OptimizableOperator operator = this;
    try {
        while (true) {
            subscriber = operator.subscribeOrReturn(subscriber);
            if (subscriber == null) {
                // "I will subscribe myself", returning...
                return;
            }
            OptimizableOperator newSource = operator.nextOptimizableSource();
            if (newSource == null) {
                CorePublisher operatorSource = operator.source();
                subscriber = Operators.restoreContextOnSubscriberIfPublisherNonInternal(operatorSource, subscriber);
                operatorSource.subscribe(subscriber);
                return;
            }
            operator = newSource;
        }
    }
    catch (Throwable e) {
        Operators.reportThrowInSubscribe(subscriber, e);
        return;
    }
}
```

逐步执行：

**迭代 1：operator = FluxMapFuseable**

调用 `FluxMapFuseable.subscribeOrReturn(actual)`：

源码位置：`reactor/core/publisher/FluxMapFuseable.java`

```java
@Override
@SuppressWarnings("unchecked")
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
    if (actual instanceof ConditionalSubscriber) {
        ConditionalSubscriber<? super R> cs = (ConditionalSubscriber<? super R>) actual;
        return new MapFuseableConditionalSubscriber<>(cs, mapper);
    }
    return new MapFuseableSubscriber<>(actual, mapper);
}
```

`LambdaSubscriber` 不是 `ConditionalSubscriber`，所以创建 `MapFuseableSubscriber`：

```java
static final class MapFuseableSubscriber<T, R>
        implements InnerOperator<T, R>,
                   QueueSubscription<R> {

    final CoreSubscriber<? super R>        actual;
    final Function<? super T, ? extends R> mapper;

    boolean done;

    QueueSubscription<T> s;
    int sourceMode;

    MapFuseableSubscriber(CoreSubscriber<? super R> actual,
            Function<? super T, ? extends R> mapper) {
        this.actual = actual;
        this.mapper = mapper;
    }
    // ...
}
```

`subscribeOrReturn` 返回了 `MapFuseableSubscriber(actual=LambdaSubscriber, mapper=n->n*10)`，不是 null，循环继续。

调用 `nextOptimizableSource()` 返回 `optimizableOperator` 字段，即 `null`（因为 `FluxArray` 不是 `OptimizableOperator`）。

`newSource == null`，所以执行：

```java
CorePublisher operatorSource = operator.source();  // = FluxArray
operatorSource.subscribe(subscriber);               // FluxArray.subscribe(MapFuseableSubscriber)
```

### 1.3 源的订阅：FluxArray.subscribe

源码位置：`reactor/core/publisher/FluxArray.java`

```java
@Override
public void subscribe(CoreSubscriber<? super T> actual) {
    subscribe(actual, array);
}

@SuppressWarnings("unchecked")
public static <T> void subscribe(CoreSubscriber<? super T> s, T[] array) {
    if (array.length == 0) {
        Operators.complete(s);
        return;
    }
    if (s instanceof ConditionalSubscriber) {
        s.onSubscribe(new ArrayConditionalSubscription<>((ConditionalSubscriber<? super T>) s, array));
    }
    else {
        s.onSubscribe(new ArraySubscription<>(s, array));
    }
}
```

`MapFuseableSubscriber` 不是 `ConditionalSubscriber`，所以创建 `ArraySubscription`：

```java
static final class ArraySubscription<T>
        implements InnerProducer<T>, SynchronousSubscription<T> {

    final CoreSubscriber<? super T> actual;
    final T[] array;

    int index;
    volatile boolean cancelled;

    volatile long requested;
    static final AtomicLongFieldUpdater<ArraySubscription> REQUESTED =
            AtomicLongFieldUpdater.newUpdater(ArraySubscription.class, "requested");

    ArraySubscription(CoreSubscriber<? super T> actual, T[] array) {
        this.actual = actual;
        this.array = array;
    }
    // ...
}
```

然后调用 `MapFuseableSubscriber.onSubscribe(ArraySubscription)`。

### 1.4 onSubscribe 传播 + 熔合协商

源码位置：`reactor/core/publisher/FluxMapFuseable.java`

```java
@SuppressWarnings("unchecked")
@Override
public void onSubscribe(Subscription s) {
    if (Operators.validate(this.s, s)) {
        this.s = (QueueSubscription<T>) s;  // ArraySubscription 实现了 SynchronousSubscription
        actual.onSubscribe(this);           // 调用 LambdaSubscriber.onSubscribe(this)
    }
}
```

注意这里 `this.s` 被赋为 `ArraySubscription`。因为 `ArraySubscription` 实现了 `SynchronousSubscription`（它继承自 `QueueSubscription`），所以强转成功。

然后 `actual.onSubscribe(this)` 调用 `LambdaSubscriber.onSubscribe(MapFuseableSubscriber)`：

```java
// LambdaSubscriber.onSubscribe
@Override
public void onSubscribe(Subscription s) {
    if (Operators.validate(subscription, s)) {
        this.subscription = s;
        // subscriptionConsumer 为 null
        s.request(Long.MAX_VALUE);  // ← 请求无界
    }
}
```

### 1.5 request 传播

`LambdaSubscriber` 调用 `MapFuseableSubscriber.request(Long.MAX_VALUE)`：

```java
// FluxMapFuseable.MapFuseableSubscriber
@Override
public void request(long n) {
    s.request(n);  // 转发给 ArraySubscription
}
```

`ArraySubscription.request(Long.MAX_VALUE)`：

源码位置：`reactor/core/publisher/FluxArray.java`

```java
@Override
public void request(long n) {
    if (Operators.validate(n)) {
        if (Operators.addCap(REQUESTED, this, n) == 0) {
            if (n == Long.MAX_VALUE) {
                fastPath();       // ← n == Long.MAX_VALUE 走 fastPath
            }
            else {
                slowPath(n);
            }
        }
    }
}
```

`Operators.addCap` 返回的是修改前的值（0），所以进入 fastPath。

### 1.6 数据发射：fastPath

```java
void fastPath() {
    final T[] a = array;
    final int len = a.length;
    final Subscriber<? super T> s = actual;  // = MapFuseableSubscriber

    for (int i = index; i != len; i++) {
        if (cancelled) {
            return;
        }

        T t = a[i];

        if (t == null) {
            s.onError(new NullPointerException("The " + i + "th array element was null"));
            return;
        }

        s.onNext(t);  // ← 发射数据
    }
    if (cancelled) {
        return;
    }
    s.onComplete();  // ← 发射完成信号
}
```

逐次循环，`ArraySubscription` 调用 `MapFuseableSubscriber.onNext(1)`、`onNext(2)`、`onNext(3)`：

```java
// FluxMapFuseable.MapFuseableSubscriber.onNext
@Override
public void onNext(T t) {
    if (sourceMode == ASYNC) {
        actual.onNext(null);
    }
    else {
        if (done) {
            Operators.onNextDropped(t, actual.currentContext());
            return;
        }
        R v;
        try {
            v = mapper.apply(t);       // ← 1 * 10 = 10, 2 * 10 = 20, 3 * 10 = 30
            if (v == null) {
                throw new NullPointerException("...");
            }
        }
        catch (Throwable e) {
            Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
            if (e_ != null) {
                onError(e_);
            }
            else {
                s.request(1);
            }
            return;
        }

        actual.onNext(v);  // ← 转发给 LambdaSubscriber
    }
}
```

`sourceMode` 默认是 0（`NONE`），不是 `ASYNC`，所以走 else 分支。mapper 把 1 变成 10、2 变成 20、3 变成 30。

`LambdaSubscriber.onNext(10)`：

```java
@Override
public void onNext(T x) {
    try {
        if (consumer != null) {
            consumer.accept(x);  // ← 打印 10, 20, 30
        }
    }
    catch (Throwable t) {
        Exceptions.throwIfFatal(t);
        this.subscription.cancel();
        onError(t);
    }
}
```

最后 `MapFuseableSubscriber.onComplete()` → `LambdaSubscriber.onComplete()`。

## 示例二：加入 filter —— `Flux.just(1,2,3,4,5).map(n->n*10).filter(n->n>=30).subscribe()`

这个示例展示当链中有多个操作符时，优化循环如何依次创建 Subscriber 链，以及 filter 丢弃元素时的 `request(1)` 补偿机制。

### 2.1 装配时的对象链

```
FluxFilterFuseable
  ├ source = FluxMapFuseable
  │    ├ source = FluxArray([1,2,3,4,5])
  │    └ mapper = n -> n * 10
  ├ predicate = n -> n >= 30
  └ optimizableOperator = FluxMapFuseable  ← 关键！source 是 OptimizableOperator
```

`FluxFilterFuseable` 的 `optimizableOperator` 字段指向 `FluxMapFuseable`，因为后者实现了 `OptimizableOperator`。这就构成了优化链。

### 2.2 订阅时的优化循环

```
InternalFluxOperator.subscribe(LambdaSubscriber)
  │
  ├ 迭代1: operator = FluxFilterFuseable
  │   subscribeOrReturn(LambdaSubscriber) → 创建 FilterFuseableSubscriber
  │   nextOptimizableSource() → FluxMapFuseable
  │
  ├ 迭代2: operator = FluxMapFuseable
  │   subscribeOrReturn(FilterFuseableSubscriber) → 创建 MapFuseableSubscriber
  │   nextOptimizableSource() → null (FluxArray 不是 OptimizableOperator)
  │
  └ operatorSource = FluxArray
    FluxArray.subscribe(MapFuseableSubscriber)
```

注意优化循环是 `while(true)` 结构，不是递归。这个设计避免了深链时的栈溢出。如果用递归实现，一个有 100 个操作符的链在 subscribe 时需要 100 层栈帧；而用 while 循环，只需要常量级别的栈深度。

### 2.3 onSubscribe 传播链

```
FluxArray.subscribe(MapFuseableSubscriber)
  └ MapFuseableSubscriber.onSubscribe(ArraySubscription)
      └ FilterFuseableSubscriber.onSubscribe(MapFuseableSubscriber)
          └ LambdaSubscriber.onSubscribe(FilterFuseableSubscriber)
              └ FilterFuseableSubscriber.request(Long.MAX_VALUE)
                  └ MapFuseableSubscriber.request(Long.MAX_VALUE)
                      └ ArraySubscription.request(Long.MAX_VALUE)
                          └ fastPath()
```

### 2.4 数据流动：filter 丢弃与补偿

当 `fastPath` 发射数据时：

```
ArraySubscription.fastPath() → MapFuseableSubscriber.onNext(1)
  mapper.apply(1) = 10
  → FilterFuseableSubscriber.onNext(10)
      predicate.test(10) = false (10 < 30)
      → s.request(1)  ← 补偿请求！因为元素被丢弃了，需要向源头再要一个
      → Operators.onDiscard(10, ctx)  ← 通知丢弃钩子

ArraySubscription.fastPath() → MapFuseableSubscriber.onNext(2)
  mapper.apply(2) = 20
  → FilterFuseableSubscriber.onNext(20)
      predicate.test(20) = false (20 < 30)
      → s.request(1)  ← 再次补偿
      → Operators.onDiscard(20, ctx)

ArraySubscription.fastPath() → MapFuseableSubscriber.onNext(3)
  mapper.apply(3) = 30
  → FilterFuseableSubscriber.onNext(30)
      predicate.test(30) = true (30 >= 30)
      → actual.onNext(30)  ← 通过！转发给 LambdaSubscriber → 打印 30

ArraySubscription.fastPath() → MapFuseableSubscriber.onNext(4)
  mapper.apply(4) = 40
  → FilterFuseableSubscriber.onNext(40)
      predicate.test(40) = true
      → actual.onNext(40)  ← 打印 40

ArraySubscription.fastPath() → MapFuseableSubscriber.onNext(5)
  mapper.apply(5) = 50
  → FilterFuseableSubscriber.onNext(50)
      predicate.test(50) = true
      → actual.onNext(50)  ← 打印 50

→ MapFuseableSubscriber.onComplete()
  → FilterFuseableSubscriber.onComplete()
    → LambdaSubscriber.onComplete()
```

为什么 filter 丢弃时需要 `request(1)`？因为下游请求了 1 个数据，filter 吃掉了一个不满足条件的元素，如果不补偿请求，上游就少发一个元素，下游永远收不到它该收的数量。这个 `s.request(1)` 告诉上游"刚才那个不算，再给我一个"。

### 2.5 SYNC 熔合路径

上面的分析假设没有熔合。但实际上 `FluxArray` 实现了 `SynchronousSubscription`，`FluxMapFuseable` 和 `FluxFilterFuseable` 也实现了 `Fuseable`，所以可能触发 SYNC 熔合。

在熔合模式下，`onSubscribe` 中的协商过程：

```
ArraySubscription (SynchronousSubscription)
  └ MapFuseableSubscriber.onSubscribe(ArraySubscription)
      ├ this.s = (QueueSubscription) ArraySubscription
      ├ actual.onSubscribe(this)  // this 是 MapFuseableSubscriber
      │   └ FilterFuseableSubscriber.onSubscribe(MapFuseableSubscriber)
      │       ├ this.s = (QueueSubscription) MapFuseableSubscriber
      │       └ actual.onSubscribe(this)
      │           └ LambdaSubscriber.onSubscribe(FilterFuseableSubscriber)
      │               └ request(Long.MAX_VALUE)
```

在熔合模式下，数据流动变成 `poll()` 拉取而不是 `onNext` 推送：

```
LambdaSubscriber.request(MAX) → FilterFuseableSubscriber.request(MAX) → MapFuseableSubscriber.request(MAX) → ArraySubscription.request(MAX)

但 fastPath 不会执行，因为熔合后不需要 request 来驱动数据。
取而代之的是 LambdaSubscriber 的消费循环通过 poll() 拉取：

FilterFuseableSubscriber.poll():
  for(;;) {
    T v = s.poll();  // = MapFuseableSubscriber.poll()
    if (v != null) {
      if (predicate.test(v)) return v;  // 通过
      // 不通过，继续循环拉取下一个
    }
    return null;
  }

MapFuseableSubscriber.poll():
  T v = s.poll();  // = ArraySubscription.poll()
  if (v != null) {
    return mapper.apply(v);  // 直接应用 mapper
  }
  return null;

ArraySubscription.poll():
  if (index < array.length) {
    T t = array[index];
    index++;
    return t;
  }
  return null;
```

SYNC 熔合省去了所有 `request(1)` 补偿调用。filter 丢弃元素时不需要补偿请求，直接在 `poll()` 循环中跳过。这就是熔合优化的核心价值：用同步拉取替代异步推送+请求补偿。

## 示例三：线程切换 —— `Flux.range(1, 5).map(n -> n*2).publishOn(Schedulers.parallel()).subscribe()`

这个示例展示 `publishOn` 如何切换数据发射线程，以及 prefetch 队列的工作机制。

### 3.1 装配时

```
FluxPublishOn
  ├ source = FluxMap (source = FluxRange(1, 5), mapper = n -> n*2)
  │    注意：FluxRange 实现了 Fuseable，但 FluxMap（非 Fuseable 版）不实现
  │    所以这里用的是 FluxMap 而不是 FluxMapFuseable
  │    原因：map() 检查的是 this（即 FluxRange），FluxRange 是 Fuseable
  │    但... 实际上 map 在 FluxRange 上调用，FluxRange 实现了 Fuseable
  │    所以创建的是 FluxMapFuseable
  │
  ├ scheduler = ParallelScheduler (N = CPU核心数)
  ├ delayError = false
  ├ prefetch = 256 (默认值，来自 Queues.SMALL_BUFFER_SIZE)
  ├ lowTide = 256
  └ queueSupplier = Queues::get
```

### 3.2 订阅时

`FluxPublishOn.subscribeOrReturn` 返回 `PublishOnSubscriber`（不是 null），所以优化循环继续向上游走。

但 `FluxPublishOn` 的 `subscribeOrReturn` 有个特殊之处——它返回的 `PublishOnSubscriber` 会直接被上游 `source.subscribe()` 消费：

源码位置：`reactor/core/publisher/FluxPublishOn.java`

```java
@Override
@SuppressWarnings("unchecked")
public @Nullable CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    Worker worker = Objects.requireNonNull(scheduler.createWorker(),
            "The scheduler returned a null worker");

    if (actual instanceof ConditionalSubscriber) {
        ConditionalSubscriber<? super T> cs = (ConditionalSubscriber<? super T>) actual;
        source.subscribe(new PublishOnConditionalSubscriber<>(cs,
                scheduler, worker, delayError, prefetch, lowTide, queueSupplier));
        return null;  // ← 返回 null！自己处理订阅
    }
    return new PublishOnSubscriber<>(actual,
            scheduler, worker, delayError, prefetch, lowTide, queueSupplier);
}
```

对于普通 `LambdaSubscriber`，返回 `PublishOnSubscriber`（非 null），优化循环继续向上。

### 3.3 PublishOnSubscriber 的 onSubscribe：队列与 prefetch

源码位置：`reactor/core/publisher/FluxPublishOn.java`

```java
static final class PublishOnSubscriber<T>
        implements QueueSubscription<T>, Runnable, InnerOperator<T, T> {

    final CoreSubscriber<? super T> actual;
    final Worker worker;
    final int prefetch;
    final int limit;
    final Supplier<? extends Queue<T>> queueSupplier;

    Subscription s;
    Queue<T> queue;

    volatile boolean cancelled;
    volatile boolean done;
    @Nullable Throwable error;

    volatile int wip;
    static final AtomicIntegerFieldUpdater<PublishOnSubscriber> WIP =
            AtomicIntegerFieldUpdater.newUpdater(PublishOnSubscriber.class, "wip");

    volatile long requested;
    static final AtomicLongFieldUpdater<PublishOnSubscriber> REQUESTED =
            AtomicLongFieldUpdater.newUpdater(PublishOnSubscriber.class, "requested");

    int sourceMode;
    long produced;
    boolean outputFused;

    // ...

    @Override
    public void onSubscribe(Subscription s) {
        if (Operators.validate(this.s, s)) {
            this.s = s;

            // 尝试熔合
            if (s instanceof QueueSubscription) {
                @SuppressWarnings("unchecked") QueueSubscription<T> f =
                        (QueueSubscription<T>) s;

                int m = f.requestFusion(Fuseable.ANY | Fuseable.THREAD_BARRIER);

                if (m == Fuseable.SYNC) {
                    sourceMode = Fuseable.SYNC;
                    queue = f;
                    done = true;
                    actual.onSubscribe(this);
                    return;
                }
                if (m == Fuseable.ASYNC) {
                    sourceMode = Fuseable.ASYNC;
                    queue = f;
                    actual.onSubscribe(this);
                    s.request(Operators.unboundedOrPrefetch(prefetch));
                    return;
                }
            }

            // 不熔合，创建独立队列
            queue = queueSupplier.get();
            actual.onSubscribe(this);
            s.request(Operators.unboundedOrPrefetch(prefetch));  // ← 向上游请求 prefetch 个数据
        }
    }
```

这里的关键设计：

`prefetch` 默认是 `Queues.SMALL_BUFFER_SIZE`（即 `Math.max(16, Integer.parseInt(System.getProperty("reactor.bufferSize.small", "256")))`，默认 256）。`limit` = `Operators.unboundedOrLimit(prefetch, lowTide)`，当 prefetch 不是 `Integer.MAX_VALUE` 时，`limit` = `prefetch - (prefetch >> 2)`，即 75% 的 prefetch。这个 75% 是补货阈值——当消耗了 75% 的预取量时，向上游再请求一批。

### 3.4 数据流：跨线程

```
当前线程（main）：
  LambdaSubscriber.request(MAX)
    → PublishOnSubscriber.request(MAX)
        → Operators.addCap(REQUESTED, this, MAX)  // 记录下游需求
        → trySchedule(this, null, null)            // 触发 worker 调度

  上游也在当前线程开始发射（假设 FluxRange 是同步源）：
  FluxRange.subscribe(PublishOnSubscriber)
    → PublishOnSubscriber.onSubscribe(RangeSubscription)
        → queue = queueSupplier.get()  // 创建队列
        → actual.onSubscribe(this)
        → s.request(prefetch)          // 向上游请求 256 个

  RangeSubscription 开始发射（在当前线程！）：
    → PublishOnSubscriber.onNext(1)     // 当前线程 = main
        → queue.offer(1)
        → trySchedule(this, null, 1)    // 通过 worker.schedule(this) 切到 parallel 线程
    → PublishOnSubscriber.onNext(2)
        → queue.offer(2)
        → trySchedule  // WIP CAS 失败（已经有一次调度了），直接返回
    → ... 同理 3, 4, 5
    → PublishOnSubscriber.onComplete()
        → done = true
        → trySchedule

parallel 线程（Worker 线程）：
  PublishOnSubscriber.run()  // Worker 执行的 Runnable
    → runAsync() 或 runSync() 或 runBackfused()（取决于 sourceMode）

  假设非熔合模式，走 runAsync():
    while (e != r) {       // e = produced, r = requested
        v = queue.poll();
        if (v == null) break;  // 队列空了
        actual.onNext(v);      // ← 在 parallel 线程上调用 LambdaSubscriber.onNext
        e++;
    }
    // 补货逻辑
    if (e == limit) {      // 消耗了 75% 的预取量
        s.request(e);      // 向上游再请求一批
        e = 0;
    }
```

这就是 `publishOn` 的本质：上游在调用线程（main）上把数据放入队列，下游在 Worker 线程（parallel-1）上从队列中取出数据。线程切换发生在 `trySchedule` → `worker.schedule(this)` 这一步。

### 3.5 WIP（work-in-progress）的 CAS 保护

```java
void trySchedule(
        @Nullable Subscription subscription,
        @Nullable Throwable suppressed,
        @Nullable Object dataSignal) {
    if (WIP.getAndIncrement(this) != 0) {  // ← CAS 递增
        // 已经有线程在 drain 了
        if (cancelled) {
            // 处理取消时的队列清理
        }
        return;  // ← 直接返回，不重复调度
    }

    try {
        worker.schedule(this);  // ← 只有一个线程能到这里
    }
    catch (RejectedExecutionException ree) {
        // 处理拒绝执行
    }
}
```

`WIP.getAndIncrement(this) != 0` 的含义：如果之前 WIP 不是 0，说明已经有线程在 drain 队列了（或者已经调度了），不需要重复调度。只有从 0 变成 1 的那个线程才有资格调用 `worker.schedule(this)`。

## 示例四：subscribeOn —— `Mono.fromCallable(() -> blockingDbCall()).subscribeOn(Schedulers.boundedElastic()).subscribe()`

这个示例展示 `subscribeOn` 如何将整个订阅过程移到另一个线程上执行，以及它和 `publishOn` 的本质区别。

### 4.1 装配时

```
MonoSubscribeOn
  ├ source = MonoCallable(callable = () -> blockingDbCall())
  ├ scheduler = BoundedElasticScheduler
  └ requestOnSeparateThread = true
```

### 4.2 订阅时：subscribeOn 的特殊性

源码位置：`reactor/core/publisher/FluxSubscribeOn.java`（Mono 版逻辑相同）

```java
@Override
public @Nullable CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    Worker worker = Objects.requireNonNull(scheduler.createWorker(),
            "The scheduler returned a null Function");

    SubscribeOnSubscriber<T> parent = new SubscribeOnSubscriber<>(source,
            actual, worker, requestOnSeparateThread);
    actual.onSubscribe(parent);  // ← 在当前线程调用 onSubscribe！

    try {
        worker.schedule(parent);  // ← 在 Worker 线程上执行 parent.run()
    }
    catch (RejectedExecutionException ree) {
        // ...
    }
    return null;  // ← 返回 null，自己处理订阅
}
```

注意 `subscribeOrReturn` 返回 `null`！这意味着优化循环在这里停止——`subscribeOn` 自己负责订阅上游。

`actual.onSubscribe(parent)` 在当前线程（main）上调用，此时 `LambdaSubscriber` 收到了 Subscription 但上游还没有真正订阅。

然后 `worker.schedule(parent)` 在 `boundedElastic` 线程上执行 `SubscribeOnSubscriber.run()`：

```java
@Override
public void run() {
    THREAD.lazySet(this, Thread.currentThread());  // 记住当前线程
    source.subscribe(this);  // ← 在 Worker 线程上订阅上游！
}
```

这就是 `subscribeOn` 和 `publishOn` 的根本区别：

`publishOn` 影响的是数据流线程——上游在调用线程上 push 数据到队列，下游在 Worker 线程上从队列 poll 数据。

`subscribeOn` 影响的是订阅线程——整个 `source.subscribe()` 调用都在 Worker 线程上执行，因此上游的 `onSubscribe`、`request`、`onNext` 都在 Worker 线程上。如果源是同步的（如 `MonoCallable`），那么 `onNext` 也在这个 Worker 线程上。

### 4.3 request 的线程感知

```java
void requestUpstream(final long n, final Subscription s) {
    if (!requestOnSeparateThread || Thread.currentThread() == THREAD.get(this)) {
        s.request(n);  // ← 如果当前线程就是订阅线程，直接请求
    }
    else {
        try {
            worker.schedule(() -> s.request(n));  // ← 否则切到 Worker 线程请求
        }
        catch (RejectedExecutionException ree) {
            // ...
        }
    }
}
```

`SubscribeOnSubscriber` 记住了订阅时的线程（`THREAD` 字段）。当下游调用 `request(n)` 时，如果当前线程不是订阅线程，就通过 `worker.schedule()` 切到订阅线程上执行。这保证了上游的所有方法调用都在同一个线程上。

### 4.4 为什么多个 subscribeOn 只有最上游的生效

考虑 `flux.subscribeOn(A).subscribeOn(B).subscribe()`：

```
subscribe(B):
  SubscribeOnSubscriber_B.subscribeOrReturn(actual)
    actual.onSubscribe(parent_B)
    worker_B.schedule(parent_B)
    return null

  在 worker_B 线程上：
    parent_B.run()
      source.subscribe(parent_B)  // source = subscribeOn(A)
      
      subscribeOn(A) 的 InternalFluxOperator.subscribe(parent_B)
        SubscribeOnSubscriber_A.subscribeOrReturn(parent_B)
          actual.onSubscribe(parent_A)  // actual = parent_B
          worker_A.schedule(parent_A)
          return null

        在 worker_A 线程上：
          parent_A.run()
            source.subscribe(parent_A)  // ← 真正的源在这里订阅
```

所以最终的源订阅发生在 `worker_A` 线程上。`subscribeOn(B)` 影响的是 `subscribeOn(A)` 的订阅线程，但 `subscribeOn(A)` 又把线程切换到了 A。只有最上游（离源最近的）`subscribeOn` 决定了源的订阅线程。

## 示例五：错误处理 —— `Flux.range(1, 5).map(n -> { if (n==3) throw new RuntimeException("boom"); return n; }).onErrorResume(e -> Flux.just(99)).subscribe()`

这个示例展示 `onErrorResume` 如何在运行时捕获错误并切换到备用 Publisher。

### 5.1 装配时

```
FluxOnErrorResume
  ├ source = FluxMapFuseable
  │    ├ source = FluxRange(1, 5)
  │    └ mapper = n -> { if (n==3) throw... ; return n; }
  ├ nextFactory = e -> Flux.just(99)
  └ extends InternalFluxOperator
```

### 5.2 订阅时的 Subscriber 链

```
FluxOnErrorResume.subscribeOrReturn(LambdaSubscriber)
  → 创建 ResumeSubscriber(actual=LambdaSubscriber, nextFactory=e->Flux.just(99))
  → 返回 ResumeSubscriber
```

`ResumeSubscriber` 继承 `Operators.MultiSubscriptionSubscriber`，这意味着它可以管理多个 Subscription（原始的和备用 Publisher 的）。

### 5.3 数据流与错误恢复

源码位置：`reactor/core/publisher/FluxOnErrorResume.java`

```java
static final class ResumeSubscriber<T>
        extends Operators.MultiSubscriptionSubscriber<T, T> {

    final Function<? super Throwable, ? extends Publisher<? extends T>> nextFactory;

    boolean second;  // ← 标记是否已经切换到备用 Publisher

    ResumeSubscriber(CoreSubscriber<? super T> actual,
            Function<? super Throwable, ? extends Publisher<? extends T>> nextFactory) {
        super(actual);
        this.nextFactory = nextFactory;
    }

    @Override
    public void onSubscribe(Subscription s) {
        if (!second) {
            actual.onSubscribe(this);  // 第一次：通知下游
        }
        set(s);  // 设置/替换 Subscription
    }

    @Override
    public void onNext(T t) {
        actual.onNext(t);
        if (!second) {
            producedOne();  // 记录已消费（用于 request 管理）
        }
    }

    @Override
    public void onError(Throwable t) {
        if (!second) {
            second = true;  // ← 切换到第二次模式

            Publisher<? extends T> p;
            try {
                p = Operators.toFluxOrMono(Objects.requireNonNull(nextFactory.apply(t),
                "The nextFactory returned a null Publisher"));
            }
            catch (Throwable e) {
                Throwable _e = Operators.onOperatorError(e, actual.currentContext());
                _e = Exceptions.addSuppressed(_e, t);
                actual.onError(_e);
                return;
            }
            p.subscribe(this);  // ← 用同一个 ResumeSubscriber 订阅备用 Publisher！
        }
        else {
            actual.onError(t);  // 第二次也出错了，直接传给下游
        }
    }
}
```

执行流程：

```
FluxRange 发射 1 → MapFuseableSubscriber.onNext(1) → mapper(1)=1 → ResumeSubscriber.onNext(1) → LambdaSubscriber.onNext(1) → 打印 1

FluxRange 发射 2 → MapFuseableSubscriber.onNext(2) → mapper(2)=2 → ResumeSubscriber.onNext(2) → LambdaSubscriber.onNext(2) → 打印 2

FluxRange 发射 3 → MapFuseableSubscriber.onNext(3)
  mapper.apply(3) → 抛出 RuntimeException("boom")
  catch: Operators.onNextError(3, e, ctx, s)
    → 返回非 null（默认策略 STOP）
    → MapFuseableSubscriber.onError(e)
      → done = true
      → ResumeSubscriber.onError(e)
        → second == false → second = true
        → nextFactory.apply(e) → Flux.just(99)
        → Flux.just(99).subscribe(this)  ← 用同一个 ResumeSubscriber 订阅备用源
          
          FluxJust.subscribe(ResumeSubscriber)
            → ResumeSubscriber.onSubscribe(ScalarSubscription(99))
              → second == true，所以不再调用 actual.onSubscribe
              → set(ScalarSubscription)  ← 替换 Subscription
            → ScalarSubscription.request(MAX) 触发...
              实际上 FluxJust 的 subscribe 直接调用：
              Operators.scalarSubscription(actual, value)
              
              ResumeSubscriber.onNext(99)
                → actual.onNext(99) → LambdaSubscriber.onNext(99) → 打印 99
              
              ResumeSubscriber.onComplete()
                → actual.onComplete() → LambdaSubscriber.onComplete() → 打印 "done"
```

### 5.4 关键设计：为什么用 `second` 布尔值

`second` 字段确保 `onErrorResume` 只恢复一次。如果备用 Publisher 也出错，`onError` 被再次调用，但此时 `second == true`，直接将错误传给下游。如果允许无限恢复，一个持续出错的链可能导致无限循环。

## 示例六：flatMap 并发 —— `Flux.range(1, 3).flatMap(n -> Flux.range(n*10, 2)).subscribe()`

这个示例展示 `flatMap` 如何同时管理多个内部 Publisher 的订阅。

### 6.1 装配时

```
FluxFlatMap
  ├ source = FluxRange(1, 3)
  ├ mapper = n -> Flux.range(n*10, 2)
  ├ delayError = false
  ├ maxConcurrency = 256 (默认，来自 Queues.SMALL_BUFFER_SIZE)
  ├ prefetch = 32 (默认 inner prefetch)
  ├ mainQueueSupplier = 队列工厂（当 inner 数量超过 maxConcurrency 时缓存）
  └ innerQueueSupplier = 每个 inner 的队列工厂
```

### 6.2 订阅时：FlatMapMain

```java
// FluxFlatMap.subscribeOrReturn
@Override
public @Nullable CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
    if (trySubscribeScalarMap(source, actual, mapper, false, true)) {
        return null;  // 标量优化成功（source 是 Callable 且 mapper 返回 Callable）
    }

    return new FlatMapMain<>(actual,
            mapper, delayError, maxConcurrency,
            mainQueueSupplier, prefetch, innerQueueSupplier);
}
```

`FluxRange` 不是 `Callable`（它不是 `ScalarCallable`），所以标量优化失败，创建 `FlatMapMain`。

### 6.3 数据流：多路并发

```
FluxRange 发射 1 → FlatMapMain.onNext(1)
  → mapper.apply(1) = Flux.range(10, 2)
  → 创建 FlatMapInner(FluxRange(10,2), prefetch=32)
  → inner.subscribe(FlatMapInner)
  
  FluxRange(10,2).subscribe(FlatMapInner)
    → FlatMapInner.onSubscribe(RangeSubscription)
    → FlatMapInner.request(32)
    → RangeSubscription 发射 10, 11
      → FlatMapInner.onNext(10) → FlatMapMain.tryEmit(inner, 10)
          → mainQueue.offer(10) 或直接 actual.onNext(10)
      → FlatMapInner.onNext(11) → FlatMapMain.tryEmit(inner, 11)
      → FlatMapInner.onComplete() → FlatMapMain.innerComplete(inner)

FluxRange 发射 2 → FlatMapMain.onNext(2)
  → mapper.apply(2) = Flux.range(20, 2)
  → 创建新的 FlatMapInner...
  → 可能与上面的 10, 11 交错！这就是 "interleaving"

FluxRange 发射 3 → FlatMapMain.onNext(3)
  → mapper.apply(3) = Flux.range(30, 2)
  → 又一个 FlatMapInner...
```

`flatMap` 的核心特征是交错（interleaving）：三个 inner Publisher 的数据可能以任意顺序到达下游。如果需要保证顺序，应该用 `concatMap` 而不是 `flatMap`。

### 6.4 maxConcurrency 的限制

`FlatMapMain` 维护一个 inner 订阅数组。当活跃的 inner 数量达到 `maxConcurrency` 时，上游的 `onNext` 会被暂停（不再 `request`），直到某个 inner 完成并释放一个槽位。这就是为什么 `flatMap` 可以处理大量并发但不会失控——`maxConcurrency` 是一个安全阀。

## 示例七：Flux.create + 背压 —— `Flux.create(sink -> { for(int i=0; i<1000; i++) sink.next(i); }, FluxSink.OverflowStrategy.BUFFER).subscribe()`

这个示例展示 `Flux.create` 的编程式 API 和不同背压策略的实现。

### 7.1 装配时

```
FluxCreate
  ├ source = sink -> { for(int i=0; i<1000; i++) sink.next(i); }
  ├ backpressure = OverflowStrategy.BUFFER
  └ createMode = PUSH_PULL (默认)
```

### 7.2 订阅时：创建 Sink

源码位置：`reactor/core/publisher/FluxCreate.java`

```java
@Override
public void subscribe(CoreSubscriber<? super T> actual) {
    CoreSubscriber<? super T> wrapped =
            Operators.restoreContextOnSubscriberIfAutoCPEnabled(this, actual);
    BaseSink<T> sink = createSink(wrapped, backpressure);

    wrapped.onSubscribe(sink);
    try {
        source.accept(
                createMode == CreateMode.PUSH_PULL ? new SerializedFluxSink<>(sink) :
                        sink);
    }
    catch (Throwable ex) {
        Exceptions.throwIfFatal(ex);
        sink.error(Operators.onOperatorError(ex, wrapped.currentContext()));
    }
}
```

`createSink` 根据 `OverflowStrategy` 创建不同的 Sink：

```java
static <T> BaseSink<T> createSink(CoreSubscriber<? super T> t,
        OverflowStrategy backpressure) {
    switch (backpressure) {
        case IGNORE: {
            return new IgnoreSink<>(t);        // 忽略背压，直接推送
        }
        case ERROR: {
            return new ErrorAsyncSink<>(t);    // 超出需求时报错
        }
        case DROP: {
            return new DropAsyncSink<>(t);     // 超出需求时丢弃
        }
        case LATEST: {
            return new LatestAsyncSink<>(t);   // 只保留最新的一个
        }
        default: {
            return new BufferAsyncSink<>(t, Queues.SMALL_BUFFER_SIZE);  // 缓冲到队列
        }
    }
}
```

### 7.3 BUFFER 策略下的数据流

`BufferAsyncSink` 内部维护一个无界队列。当 `sink.next(i)` 被调用时：

```
sink.next(0) → queue.offer(0) → drain()
sink.next(1) → queue.offer(1) → drain()
...
sink.next(999) → queue.offer(999) → drain()
```

`drain()` 会检查下游的 `requested`，如果有需求就从队列中 poll 数据转发给下游。

### 7.4 SerializedFluxSink 的 MPSC 序列化

由于 `createMode` 是 `PUSH_PULL`，用户拿到的 sink 被包装成 `SerializedFluxSink`：

源码位置：`reactor/core/publisher/FluxCreate.java`

```java
static final class SerializedFluxSink<T> implements FluxSink<T>, Scannable {

    final BaseSink<T> sink;

    volatile int wip;
    static final AtomicIntegerFieldUpdater<SerializedFluxSink> WIP =
            AtomicIntegerFieldUpdater.newUpdater(SerializedFluxSink.class, "wip");

    final Queue<T> mpscQueue;

    @Override
    public FluxSink<T> next(T t) {
        Objects.requireNonNull(t, "t is null in sink.next(t)");
        if (sink.isTerminated() || done) {
            Operators.onNextDropped(t, sink.currentContext());
            return this;
        }
        if (WIP.get(this) == 0 && WIP.compareAndSet(this, 0, 1)) {
            // 没有其他线程在写，直接推送
            try {
                sink.next(t);
            }
            catch (Throwable ex) {
                Operators.onOperatorError(sink, ex, t, sink.currentContext());
            }
            if (WIP.decrementAndGet(this) == 0) {
                return this;  // 没有排队的写操作，直接返回
            }
        }
        else {
            // 有其他线程在写，放入 MPSC 队列
            this.mpscQueue.offer(t);
            if (WIP.getAndIncrement(this) != 0) {
                return this;  // 已经有线程在 drain，直接返回
            }
        }
        drainLoop();  // 当前线程负责排空队列
        return this;
    }
```

这是一个经典的 MPSC（Multi-Producer Single-Consumer）模式：

第一个获得 `WIP` CAS（从 0 到 1）的线程成为"drainer"，它先直接调用 `sink.next(t)`，如果在它执行期间其他线程也调用了 `next()`，那些数据被放入 `mpscQueue`，然后 `WIP` 递增。当第一个线程完成直接调用后，检查 `WIP.decrementAndGet`，如果结果不为 0，说明队列里有数据，进入 `drainLoop()` 排空队列。

这种设计保证了即使多个线程同时调用 `sink.next()`，`BaseSink` 的 `onNext` 也不会并发执行——Reactive Streams 规范要求 `onNext` 是串行的。

### 7.5 五种 OverflowStrategy 的对比

用同一个 `Flux.create` 但不同的策略，行为截然不同：

假设下游请求了 3 个数据，但上游推送了 10 个：

**IGNORE**：忽略背压，全部 10 个直接推给下游。可能导致 `MissingBackpressureException` 如果下游不支持无界接收。实际上 `IgnoreSink` 的 `request` 是无操作的——它总是直接 `actual.onNext(t)`。

**ERROR**：当下游没有足够需求时，调用 `actual.onError(new OverflowException())`。流终止。

**DROP**：超出需求的数据直接丢弃，不报错。`Operators.onNextDropped` 会被调用（默认打 DEBUG 日志）。

**LATEST**：只保留最新的一未消费的数据。当下游来请求时，收到的是最新的而不是最早的。

**BUFFER**：所有数据放入无界队列，等下游来请求时按 FIFO 发放。风险是内存可能溢出。

这 7 个示例覆盖了 Reactor Core 的核心运行机制：操作符链装配、优化循环订阅、背压协议、线程切换、错误恢复、并发扁平化、编程式数据源。每一步都指向真实的源码类和方法，没有概念层面的空谈。
