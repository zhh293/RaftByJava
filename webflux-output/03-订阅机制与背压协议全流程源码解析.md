## 一、Reactive Streams 协议交互总览

## 二、Operators 工具类：背压协议的基础设施

`Operators` 类是 Reactor Core 中最重要的工具类之一。它提供了背压管理、信号验证、错误处理等基础设施。本节重点分析与背压直接相关的几个核心方法。

### 2.1 Operators.validate(long n)：请求量验证

源码位置：`reactor/core/publisher/Operators.java`（第 1358-1364 行）

```java
/**
 * Evaluate if a request is strictly positive otherwise {@link #reportBadRequest(long)}
 */
public static boolean validate(long n) {
    if (n <= 0) {
        reportBadRequest(n);
        return false;
    }
    return true;
}
```

Reactive Streams 规范 §3.9 要求 `request(n)` 中的 `n` 必须大于 0。这个方法做了这个检查。注意它只是调用 `reportBadRequest` 打印日志然后返回 `false`——**不会抛异常**。这是 `CoreSubscriber` 对规范的放宽：无效请求被静默忽略，而不是触发 `onError`。

**为什么不抛异常？** 在异步流中，一个负数请求可能是由竞态条件引起的（例如一个线程正在 cancel 的同时另一个线程发出了 request），抛异常可能导致不可预期的级联错误。静默忽略 + 日志是更安全的策略。

### 2.2 Operators.validate(Subscription current, Subscription next)：重复订阅检查

源码位置：`reactor/core/publisher/Operators.java`（第 1342-1351 行）

```java
public static boolean validate(@Nullable Subscription current, Subscription next) {
    Objects.requireNonNull(next, "Subscription cannot be null");
    if (current != null) {
        next.cancel();
        //reportSubscriptionSet();
        return false;
    }

    return true;
}
```

这个方法检查一个 Subscriber 是否已经被订阅过。如果 `current` 不为 null（已有 Subscription），它会取消新的 Subscription 并返回 false。

**应用场景：** 每个操作符的内部 Subscriber（如 `MapSubscriber`）在 `onSubscribe` 中调用这个方法：

```java
// MapSubscriber.onSubscribe
public void onSubscribe(Subscription s) {
    if (Operators.validate(this.s, s)) {
        this.s = s;
        actual.onSubscribe(this);
    }
}
```

第一次调用时 `this.s` 是 null（未初始化），所以验证通过。如果错误地被二次订阅，`this.s` 不为 null，新的 Subscription 被取消。

### 2.3 Operators.addCap(long a, long b)：溢出安全的加法

源码位置：`reactor/core/publisher/Operators.java`（第 70-76 行）

```java
/**
 * Cap an addition to Long.MAX_VALUE
 */
public static long addCap(long a, long b) {
    long res = a + b;
    if (res < 0L) {
        return Long.MAX_VALUE;
    }
    return res;
}
```

这是一个简单但关键的方法。`Long.MAX_VALUE + 1` 在 Java 中会溢出变成负数。在背压场景中，两次 `request(Long.MAX_VALUE)` 的累加不应该变成负数——它应该维持在 `Long.MAX_VALUE`。这个方法通过检查 `res < 0L` 来捕获溢出，并钳位到 `Long.MAX_VALUE`。

**为什么不用 `Math.addExact` 捕获异常？** 因为异常处理的开销远大于一个条件判断。在高频调用路径上（每个 `request` 都可能触发），异常处理是不可接受的。

### 2.4 Operators.addCap(AtomicLongFieldUpdater, instance, toAdd)：CAS 无锁累加

源码位置：`reactor/core/publisher/Operators.java`（第 88-100 行）

```java
/**
 * Concurrent addition bound to Long.MAX_VALUE.
 * Any concurrent write will "happen before" this operation.
 *
 * @return value before addition or Long.MAX_VALUE
 */
public static <T> long addCap(AtomicLongFieldUpdater<T> updater, T instance, long toAdd) {
    long r, u;
    for (;;) {
        r = updater.get(instance);
        if (r == Long.MAX_VALUE) {
            return Long.MAX_VALUE;
        }
        u = addCap(r, toAdd);
        if (updater.compareAndSet(instance, r, u)) {
            return r;
        }
    }
}
```

这是背压管理中最核心的并发原语。让我们逐行分析：

1. **`for (;;)` 无限循环**——这是经典的 CAS 自旋循环模式。循环会持续直到 CAS 操作成功。

2. **`r = updater.get(instance)`**——读取当前的 requested 值。`AtomicLongFieldUpdater` 保证了 volatile 语义的读取。

3. **`if (r == Long.MAX_VALUE) return Long.MAX_VALUE`**——如果已经是无界请求，无需再累加。直接返回 `Long.MAX_VALUE` 作为旧值。这是一个重要的优化：一旦请求量达到无界，后续所有 `addCap` 调用都是 O(1) 的。

4. **`u = addCap(r, toAdd)`**——调用前面分析的溢出安全加法。

5. **`updater.compareAndSet(instance, r, u)`**——原子地将 `requested` 从 `r` 更新为 `u`。如果另一个线程在此期间修改了 `requested`，CAS 失败，循环重试。

6. **`return r`**——返回的是 CAS 成功前的**旧值**。调用方通过检查旧值是否为 0 来判断是否需要启动数据发射（drain）。

**为什么返回旧值而不是新值？** 因为调用方的关键决策是"之前有没有未完成的请求"。如果旧值为 0（之前没有请求），说明没有正在进行的 drain 循环，当前线程需要启动一个。如果旧值大于 0，说明已经有 drain 循环在运行，新的请求量会被当前运行的 drain 循环发现并处理。

**这个方法为什么不用 `synchronized`？** 在高并发场景下（例如多个线程同时 `request`），`synchronized` 会导致线程阻塞和上下文切换。CAS 循环是无锁的——竞争失败的线程只是重试，不会被挂起。对于低竞争场景（大多数 Reactor 应用），CAS 通常第一次就成功。

### 2.5 Operators.complete(Subscriber)：空序列的快速完成

源码位置：`reactor/core/publisher/Operators.java`（第 135-138 行）

```java
public static void complete(Subscriber<?> s) {
    s.onSubscribe(EmptySubscription.INSTANCE);
    s.onComplete();
}
```

当一个 Publisher 没有元素时（例如 `Flux.empty()`、长度为 0 的 `FluxArray`），它使用这个方法一步完成订阅：先发送一个空的 Subscription（不能 request 任何东西），然后立即发送 `onComplete`。

**为什么不直接调用 `onComplete` 跳过 `onSubscribe`？** 因为 Reactive Streams 规范 §1.9 要求 `onSubscribe` 必须在 `onNext`/`onError`/`onComplete` 之前被调用。即使序列为空，也必须先建立订阅关系。

### 2.6 Operators.error(Subscriber, Throwable)：错误的快速传递

源码位置：`reactor/core/publisher/Operators.java`（第 196-199 行）

```java
public static void error(Subscriber<?> s, Throwable e) {
    s.onSubscribe(EmptySubscription.INSTANCE);
    s.onError(e);
}
```

与 `complete` 对称，用于在订阅时就已知会失败的场景。

## 三、FluxArray：源头 Publisher 的背压实现

`FluxArray` 是最简单的有界源头 Publisher——它将一个 Java 数组包装成响应式流。尽管简单，它的 `ArraySubscription` 完美展示了背压协议的所有关键模式。

### 3.1 FluxArray 类结构

源码位置：`reactor/core/publisher/FluxArray.java`

```java
final class FluxArray<T> extends Flux<T> implements Fuseable, SourceProducer<T> {

    final T[] array;

    @SafeVarargs
    public FluxArray(T... array) {
        this.array = Objects.requireNonNull(array, "array");
    }

    @SuppressWarnings("unchecked")
    public static <T> void subscribe(CoreSubscriber<? super T> s, T[] array) {
        if (array.length == 0) {
            Operators.complete(s);
            return;
        }
        if (s instanceof ConditionalSubscriber) {
            s.onSubscribe(new ArrayConditionalSubscription<>(
                (ConditionalSubscriber<? super T>) s, array));
        }
        else {
            s.onSubscribe(new ArraySubscription<>(s, array));
        }
    }

    @Override
    public void subscribe(CoreSubscriber<? super T> actual) {
        subscribe(actual, array);
    }
}
```

`subscribe` 方法的逻辑：
1. 空数组 → 快速完成（`Operators.complete`）。
2. 否则创建 `ArraySubscription`（或 `ArrayConditionalSubscription`），通过 `onSubscribe` 传给 Subscriber。

### 3.2 ArraySubscription 的字段布局

源码位置：`reactor/core/publisher/FluxArray.java`（第 70-89 行）

```java
static final class ArraySubscription<T>
        implements InnerProducer<T>, SynchronousSubscription<T> {

    final CoreSubscriber<? super T> actual;
    final T[] array;
    int index;
    volatile boolean cancelled;
    
    volatile long requested;
    @SuppressWarnings("rawtypes")
    static final AtomicLongFieldUpdater<ArraySubscription> REQUESTED =
            AtomicLongFieldUpdater.newUpdater(ArraySubscription.class, "requested");
```

| 字段 | 类型 | 可变性 | 用途 |
|-----|------|-------|------|
| `actual` | `CoreSubscriber<? super T>` | final | 下游 Subscriber 引用 |
| `array` | `T[]` | final | 数据源 |
| `index` | `int` | 可变（非 volatile） | 当前发射位置 |
| `cancelled` | `volatile boolean` | volatile | 取消标记 |
| `requested` | `volatile long` | volatile (通过 AtomicLongFieldUpdater) | 累积请求量 |
| `REQUESTED` | `AtomicLongFieldUpdater` | static final | CAS 操作句柄 |

**为什么 `index` 不是 `volatile`？** 因为 `index` 只在 drain 循环内部读写，而 drain 循环通过 `REQUESTED` 的 CAS 操作保证了只有一个线程在执行——这是一种隐式的互斥。多个线程可以并发调用 `request(n)`，但只有一个线程会"赢得"启动 drain 循环的权利（`addCap` 返回 0 的那个）。

**为什么 `cancelled` 是 `volatile`？** 因为 `cancel()` 可能从任意线程调用（例如用户在主线程 cancel，而数据发射在 Scheduler 线程）。`volatile` 保证了 drain 循环能看到最新的 `cancelled` 状态。

**为什么用 `AtomicLongFieldUpdater` 而不是 `AtomicLong`？** 内存优化。`AtomicLong` 是一个独立的对象，每个实例额外消耗 ~16 字节的对象头。`AtomicLongFieldUpdater` 是一个共享的静态工具，通过反射直接操作 `volatile long` 字段，不增加对象开销。在大量 Subscription 实例的场景下（例如 `flatMap` 中的内部流），这个优化很有价值。

### 3.3 request(n) 方法：drain 循环的入口

源码位置：`reactor/core/publisher/FluxArray.java`（第 92-103 行）

```java
@Override
public void request(long n) {
    if (Operators.validate(n)) {
        if (Operators.addCap(REQUESTED, this, n) == 0) {
            if (n == Long.MAX_VALUE) {
                fastPath();
            }
            else {
                slowPath(n);
            }
        }
    }
}
```

这段代码的控制流：

```
request(n)
    │
    ├─ validate(n) → n <= 0? → 忽略，返回
    │
    ├─ addCap(REQUESTED, this, n)
    │   ├─ 返回值 > 0 → 已有 drain 在运行，返回（新请求量已累加到 requested）
    │   └─ 返回值 == 0 → 之前无请求，当前线程负责启动 drain
    │       │
    │       ├─ n == Long.MAX_VALUE → fastPath()
    │       └─ otherwise → slowPath(n)
    │
    └── 结束
```

**关键洞见：`addCap` 返回旧值。** 旧值为 0 意味着"之前没有人在 drain"，当前线程获得了 drain 的所有权。旧值大于 0 意味着已经有线程在 drain，新的请求量已经原子地加到了 `requested` 字段，运行中的 drain 循环会在适当时候看到它。

### 3.4 fastPath：无界请求的极简路径

源码位置：`reactor/core/publisher/FluxArray.java`（第 154-177 行）

```java
void fastPath() {
    final T[] a = array;
    final int len = a.length;
    final Subscriber<? super T> s = actual;

    for (int i = index; i != len; i++) {
        if (cancelled) {
            return;
        }

        T t = a[i];

        if (t == null) {
            s.onError(new NullPointerException("The " + i + "th array element was null"));
            return;
        }

        s.onNext(t);
    }
    if (cancelled) {
        return;
    }
    s.onComplete();
}
```

当 `n == Long.MAX_VALUE` 时进入 fastPath。这是一个"一路到底"的循环——不检查 `requested` 计数器，不做 CAS 操作，直接把所有元素发射完毕，然后 `onComplete`。

**为什么 `Long.MAX_VALUE` 可以特殊处理？** 因为 `Long.MAX_VALUE` 意味着"无界请求"——下游声明它可以处理任意数量的元素。既然不需要限流，就不需要计数和暂停的开销。

**循环中的 `cancelled` 检查**：虽然是无界请求，下游仍然可以 `cancel`。`cancelled` 是 `volatile` 的，所以每次循环迭代都能看到最新值。但注意检查频率是"每个元素一次"——如果 `onNext` 的处理很耗时，cancel 的响应可能有延迟。

**null 元素检查**：Reactive Streams 规范不允许 null 元素。如果数组中有 null，发送 `onError(NullPointerException)` 并终止。

**fastPath 的性能优势**：
- 没有 CAS 操作（`addCap` 只在 `request` 方法中调用一次）。
- 没有 `requested` 字段的读写。
- 局部变量 `a`、`len`、`s` 避免了每次循环访问 `this.array`、`this.actual` 的间接寻址。
- 整个循环的热路径只有：数组读取 → null 检查 → `onNext` 调用。

### 3.5 slowPath：精确计量的背压路径

源码位置：`reactor/core/publisher/FluxArray.java`（第 105-152 行）

```java
void slowPath(long n) {
    final T[] a = array;
    final int len = a.length;
    final Subscriber<? super T> s = actual;

    int i = index;
    int e = 0;

    for (; ; ) {
        if (cancelled) {
            return;
        }

        while (i != len && e != n) {
            T t = a[i];

            if (t == null) {
                s.onError(new NullPointerException("The " + i + "th array element was null"));
                return;
            }

            s.onNext(t);

            if (cancelled) {
                return;
            }

            i++;
            e++;
        }

        if (i == len) {
            s.onComplete();
            return;
        }

        n = requested;

        if (n == e) {
            index = i;
            n = REQUESTED.addAndGet(this, -e);
            if (n == 0) {
                return;
            }
            e = 0;
        }
    }
}
```

这段代码是背压协议实现的精华。让我们分层分析。

#### 3.5.1 外层无限循环 `for (;;)`

slowPath 使用了一个永不结束的外层循环。这个循环的退出条件分散在循环体内部：
- `cancelled` 为 true → 返回。
- `i == len` → 发完所有元素，`onComplete` 后返回。
- `n == 0`（在 CAS 减少后）→ 无更多请求，暂停并返回。

#### 3.5.2 内层 while 循环

```java
while (i != len && e != n) {
    // ... 发射元素 ...
    i++;
    e++;
}
```

内层循环在"还有数据 (`i != len`)"和"还有配额 (`e != n`)"两个条件同时满足时发射元素。`e` 是已发射计数器，`n` 是当前批次的请求量。

#### 3.5.3 配额耗尽后的 CAS 回退

当内层循环退出时（要么数据用完，要么配额用完），进入关键的 CAS 操作：

```java
n = requested;

if (n == e) {
    index = i;
    n = REQUESTED.addAndGet(this, -e);
    if (n == 0) {
        return;
    }
    e = 0;
}
```

逐行解析：

1. **`n = requested`**——重新读取 `requested` 的最新值。在内层循环运行期间，其他线程可能调用了 `request(m)` 增加了 `requested`。

2. **`if (n == e)`**——如果请求量恰好等于已发射量，说明没有新请求到来。
   - 保存当前位置 `index = i`。
   - `REQUESTED.addAndGet(this, -e)` 原子地减去已消费的配额。这个 CAS 操作是关键的同步点。
   - 如果减完后 `n == 0`——没有新的请求，drain 循环暂停返回。下次 `request(n)` 调用时会重新启动。
   - 如果减完后 `n > 0`——在减的过程中有新请求到来，重置 `e = 0` 继续循环。

3. **如果 `n != e`**——说明在内层循环运行期间有新请求到来（`requested` 被增大了）。外层循环直接带着更大的 `n` 继续，不需要 CAS 操作。

**这个设计的巧妙之处**：drain 循环和 `request` 调用之间通过 `requested` 字段做了一个隐式的"握手"。drain 循环尝试减少 `requested`，如果发现有新请求就继续；`request` 增加 `requested`，如果发现 drain 循环不在运行就启动一个。这保证了：
- 不会有两个 drain 循环同时运行。
- 不会遗漏任何 `request` 调用。
- 没有锁。

### 3.6 cancel 的实现

```java
@Override
public void cancel() {
    cancelled = true;
}
```

极其简单——只是设置一个 `volatile boolean` 标记。drain 循环在每次发射元素前后都会检查这个标记。

**为什么 cancel 不需要更复杂的清理逻辑？** 因为 `FluxArray` 的数据源是一个静态数组，没有需要释放的资源。对于更复杂的源头（如网络连接、文件句柄），`cancel` 通常需要做更多清理。

**cancel 后还会收到 onNext 吗？** 可能会。在 cancel 标记设置后、drain 循环检查到标记之前的窗口期内，可能会有一个 `onNext` 被发出。Reactive Streams 规范允许这种行为——§3.7 规定 cancel 后可能仍会收到信号。

## 四、FluxRange：另一个源头的背压实现

### 4.1 RangeSubscription 的请求处理

`FluxRange` 的 `RangeSubscription` 与 `FluxArray.ArraySubscription` 结构几乎相同，但数据源是整数范围而不是数组。

源码位置：`reactor/core/publisher/FluxRange.java`（第 78-121 行）

```java
static final class RangeSubscription implements InnerProducer<Integer>,
                                                SynchronousSubscription<Integer> {

    final CoreSubscriber<? super Integer> actual;
    final long end;
    volatile boolean cancelled;
    long index;
    
    volatile long requested;
    static final AtomicLongFieldUpdater<RangeSubscription> REQUESTED =
      AtomicLongFieldUpdater.newUpdater(RangeSubscription.class, "requested");

    @Override
    public void request(long n) {
        if (Operators.validate(n)) {
            if (Operators.addCap(REQUESTED, this, n) == 0) {
                if (n == Long.MAX_VALUE) {
                    fastPath();
                } else {
                    slowPath(n);
                }
            }
        }
    }
}
```

**request 方法与 ArraySubscription 完全一致**——这是一个通用的背压管理模式。

### 4.2 RangeSubscription 的 fastPath

源码位置：`reactor/core/publisher/FluxRange.java`（第 122-139 行）

```java
void fastPath() {
    final long e = end;
    final Subscriber<? super Integer> a = actual;

    for (long i = index; i != e; i++) {
        if (cancelled) {
            return;
        }

        a.onNext((int) i);
    }

    if (cancelled) {
        return;
    }

    a.onComplete();
}
```

与 `ArraySubscription.fastPath` 的区别：
1. 没有 null 检查——整数不可能为 null。
2. 使用 `(int) i` 强制转换——`index` 和 `end` 是 `long`，但发射的元素是 `Integer`。

### 4.3 RangeSubscription 的 slowPath

源码位置：`reactor/core/publisher/FluxRange.java`（第 141-185 行）

```java
void slowPath(long n) {
    final Subscriber<? super Integer> a = actual;

    long f = end;
    long e = 0;
    long i = index;

    for (; ; ) {

        if (cancelled) {
            return;
        }

        while (e != n && i != f) {

            a.onNext((int) i);

            if (cancelled) {
                return;
            }

            e++;
            i++;
        }

        if (cancelled) {
            return;
        }

        if (i == f) {
            a.onComplete();
            return;
        }

        n = requested;
        if (n == e) {
            index = i;
            n = REQUESTED.addAndGet(this, -e);
            if (n == 0) {
                return;
            }
            e = 0;
        }
    }
}
```

**与 ArraySubscription.slowPath 几乎完全一致**。唯一区别是数据来源——数组下标访问 vs 整数递增。这种模式的高度一致性说明 Reactor 团队对 drain 循环进行了标准化。

### 4.4 FluxRange.subscribe 中的特殊优化

源码位置：`reactor/core/publisher/FluxRange.java`（第 53-70 行）

```java
@Override
@SuppressWarnings("unchecked")
public void subscribe(CoreSubscriber<? super Integer> actual) {
    long st = start;
    long en = end;
    if (st == en) {
        Operators.complete(actual);
        return;
    } else
    if (st + 1 == en) {
        actual.onSubscribe(Operators.scalarSubscription(actual, (int)st));
        return;
    }
    
    if (actual instanceof ConditionalSubscriber) {
        actual.onSubscribe(new RangeSubscriptionConditional(
            (ConditionalSubscriber<? super Integer>) actual, st, en));
        return;
    }
    actual.onSubscribe(new RangeSubscription(actual, st, en));
}
```

两个特殊情况优化：
1. **空范围 (`st == en`)**：直接调用 `Operators.complete`。
2. **单元素范围 (`st + 1 == en`)**：使用 `Operators.scalarSubscription` 返回一个极简的 Subscription——不需要 drain 循环、CAS、volatile 等开销。

**为什么单元素要特殊处理？** 因为单元素的 Subscription 只需要处理一次 `request`，之后就 `onComplete`。用通用的 `RangeSubscription` 处理单元素虽然正确，但白白创建了 `AtomicLongFieldUpdater`、volatile 字段等基础设施，浪费资源。

## 五、LambdaSubscriber：自动请求 Long.MAX_VALUE

### 5.1 LambdaSubscriber 的设计定位

`LambdaSubscriber` 是 Reactor 中最常见的终端 Subscriber——当用户调用 `flux.subscribe(consumer)` 时，Reactor 内部会创建一个 `LambdaSubscriber` 来包装用户提供的 lambda。

源码位置：`reactor/core/publisher/LambdaSubscriber.java`

```java
final class LambdaSubscriber<T>
        implements InnerConsumer<T>, Disposable {

    final @Nullable Consumer<? super T>            consumer;
    final @Nullable Consumer<? super Throwable>    errorConsumer;
    final @Nullable Runnable                       completeConsumer;
    final @Nullable Consumer<? super Subscription> subscriptionConsumer;

    final Context initialContext;

    volatile Subscription subscription;

    static final AtomicReferenceFieldUpdater<LambdaSubscriber, @Nullable Subscription> S =
            AtomicReferenceFieldUpdater.newUpdater(LambdaSubscriber.class,
                    Subscription.class,
                    "subscription");
```

### 5.2 onSubscribe：自动请求无界

源码位置：`reactor/core/publisher/LambdaSubscriber.java`（第 109-126 行）

```java
@Override
public void onSubscribe(Subscription s) {
    if (Operators.validate(subscription, s)) {
        this.subscription = s;
        if (subscriptionConsumer != null) {
            try {
                subscriptionConsumer.accept(s);
            }
            catch (Throwable t) {
                Exceptions.throwIfFatal(t);
                s.cancel();
                onError(t);
            }
        }
        else {
            s.request(Long.MAX_VALUE);
        }
    }
}
```

**关键逻辑：如果用户没有提供 `subscriptionConsumer`，自动请求 `Long.MAX_VALUE`。**

这意味着 `flux.subscribe(x -> System.out.println(x))` 默认是无界消费——不做背压控制。这对大多数场景是合理的：用户想处理所有元素，不想手动管理 request。

**如果用户需要背压控制怎么办？** 使用带 `subscriptionConsumer` 的重载：
```java
flux.subscribe(
    value -> process(value),          // onNext
    error -> handleError(error),      // onError
    () -> complete(),                 // onComplete
    sub -> sub.request(10)            // 自定义初始请求
);
```

或者使用 `BaseSubscriber`（下一节详述）。

### 5.3 onNext/onError/onComplete 的实现

```java
@Override
public void onNext(T x) {
    try {
        if (consumer != null) {
            consumer.accept(x);
        }
    }
    catch (Throwable t) {
        Exceptions.throwIfFatal(t);
        this.subscription.cancel();
        onError(t);
    }
}
```

`onNext` 将元素传给用户的 `consumer`。如果 consumer 抛异常，cancel 上游并触发 `onError`。

```java
@Override
public void onError(Throwable t) {
    Subscription s = S.getAndSet(this, Operators.cancelledSubscription());
    if (s == Operators.cancelledSubscription()) {
        Operators.onErrorDropped(t, this.initialContext);
        return;
    }
    if (errorConsumer != null) {
        errorConsumer.accept(t);
    }
    else {
        Operators.onErrorDropped(
            Exceptions.errorCallbackNotImplemented(t), this.initialContext);
    }
}
```

`onError` 中的 CAS 操作（`S.getAndSet(this, Operators.cancelledSubscription())`）保证了终止信号的幂等性——即使 `onError` 被多次调用，只有第一次会执行用户的 `errorConsumer`，后续调用会将错误丢到 `Operators.onErrorDropped`。

**注意：如果用户没有提供 `errorConsumer`，错误会被包装成 `ErrorCallbackNotImplemented` 丢到全局的 `onErrorDropped` hook。** 这是 Reactor 的一个重要设计决策——不静默吞掉错误，而是通过 hook 机制让用户有机会感知到。

### 5.4 dispose 和 isDisposed：Disposable 接口实现

```java
@Override
public boolean isDisposed() {
    return subscription == Operators.cancelledSubscription();
}

@Override
public void dispose() {
    Subscription s = S.getAndSet(this, Operators.cancelledSubscription());
    if (s != null && s != Operators.cancelledSubscription()) {
        s.cancel();
    }
}
```

`LambdaSubscriber` 实现了 `Disposable` 接口，所以 `flux.subscribe(consumer)` 返回的 `Disposable` 就是这个 `LambdaSubscriber` 本身。用户可以调用 `disposable.dispose()` 来取消订阅。

`dispose` 使用 CAS 操作原子地将 subscription 替换为 `cancelledSubscription` 哨兵，然后 cancel 旧的 subscription。CAS 保证了即使多线程同时 dispose，cancel 只被调用一次。

## 六、BaseSubscriber：Hook 模式的手动背压控制

### 6.1 设计定位

`BaseSubscriber` 是 Reactor 提供给用户的"高级消费者"基类。与 `LambdaSubscriber` 不同，它提供了细粒度的生命周期 hook，让用户可以手动控制背压。

源码位置：`reactor/core/publisher/BaseSubscriber.java`

```java
public abstract class BaseSubscriber<T> implements CoreSubscriber<T>, Subscription,
                                                   Disposable {

    volatile Subscription subscription;

    static AtomicReferenceFieldUpdater<BaseSubscriber, @Nullable Subscription> S =
            AtomicReferenceFieldUpdater.newUpdater(
                BaseSubscriber.class, Subscription.class, "subscription");
```

### 6.2 Hook 方法一览

```java
protected void hookOnSubscribe(Subscription subscription){
    subscription.request(Long.MAX_VALUE);
}

protected void hookOnNext(T value){
    // NO-OP
}

protected void hookOnComplete() {
    // NO-OP
}

protected void hookOnError(Throwable throwable) {
    throw Exceptions.errorCallbackNotImplemented(throwable);
}

protected void hookOnCancel() {
    //NO-OP
}

protected void hookFinally(SignalType type) {
    //NO-OP
}
```

**注意 `hookOnSubscribe` 的默认实现是 `subscription.request(Long.MAX_VALUE)`**——与 `LambdaSubscriber` 相同，默认无界请求。用户需要覆盖此方法来实现自定义背压策略。

**为什么 `hookOnError` 的默认实现抛异常而不是静默忽略？** 这是"fail loudly"原则。如果用户忘记处理错误，应该立即报错而不是静默继续运行——后者可能导致数据不一致。

### 6.3 onSubscribe：setOnce 语义

源码位置：`reactor/core/publisher/BaseSubscriber.java`（第 148-157 行）

```java
@Override
public final void onSubscribe(Subscription s) {
    if (Operators.setOnce(S, this, s)) {
        try {
            hookOnSubscribe(s);
        }
        catch (Throwable throwable) {
            onError(Operators.onOperatorError(s, throwable, currentContext()));
        }
    }
}
```

`Operators.setOnce` 使用 CAS 原子地设置 subscription，保证只设置一次。如果重复订阅，CAS 失败，`hookOnSubscribe` 不会被调用。

`onSubscribe` 是 `final` 的——用户不能覆盖。模板方法模式：框架代码（CAS 设置、异常处理）在 `onSubscribe` 中，用户逻辑在 `hookOnSubscribe` 中。

### 6.4 onNext、onError、onComplete：统一的模板

```java
@Override
public final void onNext(T value) {
    Objects.requireNonNull(value, "onNext");
    try {
        hookOnNext(value);
    }
    catch (Throwable throwable) {
        onError(Operators.onOperatorError(subscription, throwable, value, currentContext()));
    }
}

@Override
public final void onError(Throwable t) {
    Objects.requireNonNull(t, "onError");

    if (S.getAndSet(this, Operators.cancelledSubscription()) == Operators
            .cancelledSubscription()) {
        Operators.onErrorDropped(t, currentContext());
        return;
    }

    try {
        hookOnError(t);
    }
    catch (Throwable e) {
        e = Exceptions.addSuppressed(e, t);
        Operators.onErrorDropped(e, currentContext());
    }
    finally {
        safeHookFinally(SignalType.ON_ERROR);
    }
}

@Override
public final void onComplete() {
    if (S.getAndSet(this, Operators.cancelledSubscription()) != Operators
            .cancelledSubscription()) {
        try {
            hookOnComplete();
        }
        catch (Throwable throwable) {
            hookOnError(Operators.onOperatorError(throwable, currentContext()));
        }
        finally {
            safeHookFinally(SignalType.ON_COMPLETE);
        }
    }
}
```

所有 `on*` 方法都是 `final` 的，遵循模板方法模式。关键特征：

1. **CAS 终止保护**：`onError` 和 `onComplete` 都通过 `S.getAndSet(this, cancelledSubscription)` 实现幂等终止——只有第一次调用有效。

2. **hookFinally 保证执行**：无论终止原因是什么（error、complete、cancel），`hookFinally` 都会在 `finally` 块中执行。这类似于 try-with-resources 模式，确保资源清理。

3. **hookOnError 异常处理**：如果 `hookOnError` 本身抛出异常，两个异常会通过 `Exceptions.addSuppressed` 合并后丢到 `onErrorDropped`，不会丢失任何错误信息。

### 6.5 request 和 cancel：公开的控制方法

```java
@Override
public final void request(long n) {
    if (Operators.validate(n)) {
        Subscription s = this.subscription;
        if (s != null) {
            s.request(n);
        }
    }
}

@Override
public final void cancel() {
    if (Operators.terminate(S, this)) {
        try {
            hookOnCancel();
        }
        catch (Throwable throwable) {
            hookOnError(Operators.onOperatorError(
                subscription, throwable, currentContext()));
        }
        finally {
            safeHookFinally(SignalType.CANCEL);
        }
    }
}
```

`request` 将请求委托给上游 subscription。`cancel` 使用 `Operators.terminate` 原子地取消 subscription，然后调用 `hookOnCancel` 和 `hookFinally`。

**`Operators.terminate` 的实现逻辑**：原子地将 subscription 替换为 `cancelledSubscription`，如果替换成功则 cancel 旧的 subscription 并返回 true；如果已经是 `cancelledSubscription`（已取消），返回 false。

### 6.6 BaseSubscriber vs LambdaSubscriber 对比

| 特性 | LambdaSubscriber | BaseSubscriber |
|------|-----------------|----------------|
| 创建方式 | `flux.subscribe(consumer, error, complete)` | 子类化 `BaseSubscriber` |
| 接口实现 | `InnerConsumer<T>`, `Disposable` | `CoreSubscriber<T>`, `Subscription`, `Disposable` |
| 默认请求策略 | 无 subscriptionConsumer 时自动 `request(Long.MAX_VALUE)` | `hookOnSubscribe` 默认 `request(Long.MAX_VALUE)` |
| 手动背压控制 | 通过 subscriptionConsumer | 覆盖 `hookOnSubscribe`，在 `hookOnNext` 中 `request(1)` |
| 终止保护 | CAS + `cancelledSubscription` 哨兵 | CAS + `cancelledSubscription` 哨兵 |
| 生命周期 hook | 无 | `hookOnSubscribe`, `hookOnNext`, `hookOnComplete`, `hookOnError`, `hookOnCancel`, `hookFinally` |
| 模板方法 | `on*` 方法不是 final | `on*` 方法是 final，用户只能覆盖 `hook*` |
| Context 支持 | 通过构造器传入 `initialContext` | 覆盖 `currentContext()` |

## 七、Queues.SMALL_BUFFER_SIZE 和 XS_BUFFER_SIZE

虽然本篇主要讨论的是简单源头的背压实现，但 Reactor 的异步操作符（如 `flatMap`、`publishOn`）依赖内部队列来缓冲元素，队列大小由 `Queues` 类定义。

源码位置：`reactor/util/concurrent/Queues.java`

```java
/**
 * An allocation friendly default of available slots in a given container, e.g. slow 
 * publishers and or fast/few subscribers
 */
public static final int XS_BUFFER_SIZE = Math.max(8,
    Integer.parseInt(System.getProperty("reactor.bufferSize.x", "32")));

/**
 * A small default of available slots in a given container, compromise between 
 * intensive pipelines, small subscribers numbers and memory use.
 */
public static final int SMALL_BUFFER_SIZE = Math.max(16,
    Integer.parseInt(System.getProperty("reactor.bufferSize.small", "256")));
```

| 常量 | 默认值 | 最小值 | 系统属性 | 用途 |
|------|-------|-------|---------|------|
| `XS_BUFFER_SIZE` | 32 | 8 | `reactor.bufferSize.x` | 超小缓冲，用于低吞吐场景 |
| `SMALL_BUFFER_SIZE` | 256 | 16 | `reactor.bufferSize.small` | 标准缓冲，用于 `flatMap`、`publishOn` 等 |

**为什么要有最小值限制？** 防止用户通过系统属性设置过小的值。缓冲区太小会导致频繁的 request/drain 切换，性能急剧下降。`Math.max(8, ...)` 和 `Math.max(16, ...)` 是性能的安全下限。

**为什么通过系统属性而不是 API 参数配置？** 因为这些缓冲区大小影响的是框架的全局行为——大多数用户不需要调整它们。系统属性提供了一个不侵入 API 的调优入口。

| `cancel()` | `BaseSubscriber` | `void cancel()` | Operators.terminate + hookOnCancel + hookFinally | terminate 的 CAS 保证幂等 | 用户取消订阅 |

## 九、总结：背压协议的三层架构

从本篇的源码分析中，可以归纳出 Reactor 背压协议的三层架构：

**第一层：验证与安全**
- `Operators.validate(n)` 确保请求量合法。
- `Operators.validate(current, next)` 防止重复订阅。
- `Operators.addCap` 防止 long 溢出。
- `cancelled` / `done` / `cancelledSubscription` 防止终止后继续操作。

**第二层：drain 循环核心**
- `request(n)` 是 drain 循环的入口。
- `addCap` 的 CAS 返回值 (== 0) 决定是否启动新的 drain。
- `fastPath` 和 `slowPath` 是 drain 的两条路径，前者追求极致性能，后者精确计量。
- `slowPath` 的外层 `for(;;)` + 内层 `while` + CAS 减量构成了完整的 drain-check-resume 循环。

**第三层：终端消费者**
- `LambdaSubscriber` 面向简单场景，默认无界请求。
- `BaseSubscriber` 面向高级场景，提供 hook 模式实现手动背压控制。
- 两者都通过 CAS + 哨兵对象（`cancelledSubscription`）实现线程安全的终止语义。

这三层的协作保证了 Reactor 的背压机制既安全又高效——在无背压场景下接近零开销（fastPath），在需要精确控制时又能精确到每一个元素（slowPath + BaseSubscriber）。
