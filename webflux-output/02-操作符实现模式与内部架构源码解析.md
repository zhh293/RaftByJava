# 操作符实现模式与内部架构源码解析

> **Reactor Core 源码深度研究系列 · 第 02 篇**

## 一、全局架构总览

### 1.1 操作符链装配时序图

当用户编写 `Flux.just(1,2,3).map(x -> x * 2).filter(x -> x > 2)` 时，装配阶段只创建操作符对象，不触发任何数据流动：

```
装配阶段（调用操作符方法时）：
═══════════════════════════

   Flux.just(1,2,3)          .map(x -> x*2)           .filter(x -> x > 2)
         │                        │                          │
         ▼                        ▼                          ▼
    ┌──────────┐           ┌──────────┐              ┌────────────┐
    │ FluxArray│◄──source──│ FluxMap  │◄──source─────│ FluxFilter │
    │ array=[1,│           │mapper=   │              │predicate=  │
    │  2, 3]   │           │ x->x*2   │              │  x->x>2   │
    └──────────┘           └──────────┘              └────────────┘

    数据流方向 ──────────────────────────────────────────────────►
    source 指针方向 ◄──────────────────────────────────────────────
```

### 1.2 订阅时优化循环展开图

当用户调用 `.subscribe(System.out::println)` 时，优化循环沿着 source 指针链迭代展开：

```
订阅阶段（while(true) 循环）：
═══════════════════════════════

  起点：FluxFilter.subscribe(LambdaSubscriber)
    │
    │  ① operator = FluxFilter
    │     subscriber = FluxFilter.subscribeOrReturn(LambdaSubscriber)
    │                = FilterSubscriber(actual=LambdaSubscriber, predicate)
    │     operator = FluxFilter.nextOptimizableSource() → FluxMap
    │
    │  ② operator = FluxMap
    │     subscriber = FluxMap.subscribeOrReturn(FilterSubscriber)
    │                = MapSubscriber(actual=FilterSubscriber, mapper)
    │     operator = FluxMap.nextOptimizableSource() → null (FluxArray不是OptimizableOperator)
    │
    │  ③ nextOptimizableSource == null → 退出循环
    │     FluxArray.subscribe(MapSubscriber)
    │
    ▼

  最终的 Subscriber 嵌套结构（由内而外）：

  ┌─────────────────────────────────────────────────────────┐
  │  FluxArray                                              │
  │   └─→ onSubscribe(ArraySubscription)                    │
  │        └─→ MapSubscriber                                │
  │             ├─ actual = FilterSubscriber                 │
  │             │   ├─ actual = LambdaSubscriber             │
  │             │   │   └─ consumer = System.out::println    │
  │             │   └─ predicate = x -> x > 2               │
  │             └─ mapper = x -> x * 2                      │
  └─────────────────────────────────────────────────────────┘
```

## 二、OptimizableOperator 接口深度解析

### 2.1 接口定义回顾

源码位置：`reactor/core/publisher/OptimizableOperator.java`

```java
interface OptimizableOperator<IN, OUT> extends CorePublisher<IN> {

    @Nullable CoreSubscriber<? super OUT> subscribeOrReturn(
        CoreSubscriber<? super IN> actual) throws Throwable;

    CorePublisher<? extends OUT> source();

    @Nullable OptimizableOperator<?, ? extends OUT> nextOptimizableSource();
}
```

### 2.2 三方法的协作逻辑

这三个方法的交互关系可以用一个状态机来理解：

```
                    ┌─────────────────────────────────┐
                    │  while(true) 循环入口             │
                    └──────────────┬──────────────────┘
                                   │
                    ┌──────────────▼──────────────────┐
                    │ subscriber = operator            │
                    │   .subscribeOrReturn(subscriber) │
                    └──────────────┬──────────────────┘
                                   │
                          ┌────────┴────────┐
                          │ subscriber null?│
                          └────────┬────────┘
                         Yes ┌─────┴─────┐ No
                             │           │
                    ┌────────▼────┐ ┌────▼───────────────────┐
                    │ return;     │ │ newSource = operator     │
                    │(已自行订阅)│ │   .nextOptimizableSource()│
                    └─────────────┘ └────┬───────────────────┘
                                         │
                                ┌────────┴────────┐
                                │ newSource null? │
                                └────────┬────────┘
                               Yes ┌─────┴─────┐ No
                                   │           │
                    ┌──────────────▼──┐  ┌─────▼──────────┐
                    │ source =         │  │ operator =      │
                    │  operator.source()│  │  newSource      │
                    │ source.subscribe │  │ continue while  │
                    │  (subscriber)    │  └─────────────────┘
                    └──────────────────┘
```

### 2.3 优化循环如何避免递归

**传统递归方式（假设没有优化循环）：**

```java
// 伪代码：FluxFilter 的传统 subscribe
public void subscribe(CoreSubscriber<? super T> actual) {
    CoreSubscriber<? super T> filterSub = new FilterSubscriber(actual, predicate);
    source.subscribe(filterSub);  // 递归调用 FluxMap.subscribe()
}

// 伪代码：FluxMap 的传统 subscribe  
public void subscribe(CoreSubscriber<? super T> actual) {
    CoreSubscriber<? super T> mapSub = new MapSubscriber(actual, mapper);
    source.subscribe(mapSub);  // 递归调用 FluxArray.subscribe()
}
```

每一层操作符的 `subscribe` 调用都会在栈上留下一个栈帧。100 层操作符 = 100 个栈帧。如果每个栈帧消耗 ~200 字节，100 层就是 ~20KB——在默认 512KB 或 1MB 的栈空间下似乎没问题，但在某些极端场景（例如动态构建的操作符链、嵌套的 `flatMap` 中的内部流）下，栈深度可能远超 100 层。

**优化循环方式（实际实现）：**

```java
// InternalFluxOperator.subscribe 中的 while(true)
while (true) {
    subscriber = operator.subscribeOrReturn(subscriber);  // 不递归，只创建包装
    // ...检查和推进...
    operator = newSource;  // 移动到上一层，但仍在同一个栈帧
}
```

所有操作符的 `subscribeOrReturn` 调用都在**同一个栈帧**内完成。不管链多深，栈深度恒定为 O(1)。

**关键洞见：`subscribeOrReturn` 做了 `subscribe` 的一半工作。** 传统的 `subscribe` = 创建内部 Subscriber + 递归订阅上游。`subscribeOrReturn` 只做了"创建内部 Subscriber"这一步，把"递归订阅上游"这一步留给了 while 循环的下一轮迭代。

## 三、FluxMap：典范操作符的完整解剖

`FluxMap` 是理解 Reactor 操作符实现模式的最佳入口——它足够简单（一对一映射），却包含了所有核心要素。

### 3.1 操作符四大要素

在分析代码之前，先定义操作符实现的四大要素：

| 要素 | 职责 | FluxMap 中的对应 |
|-----|------|----------------|
| **构造器** | 存储 `source` 和业务参数 | `FluxMap(Flux source, Function mapper)` |
| **subscribeOrReturn** | 创建内部 Subscriber 包装下游 | 返回 `MapSubscriber` 或 `MapConditionalSubscriber` |
| **内部 Subscriber** | 实现 `InnerOperator`，持有 `actual`（下游引用）和 `Subscription`（上游引用） | `MapSubscriber<T, R>` |
| **request/cancel 委托** | 将背压信号透传给上游 | `s.request(n)` / `s.cancel()` |

### 3.2 构造器与 mapper 字段

源码位置：`reactor/core/publisher/FluxMap.java`（第 35-51 行）

```java
final class FluxMap<T, R> extends InternalFluxOperator<T, R> {

    final Function<? super T, ? extends R> mapper;

    FluxMap(Flux<? extends T> source,
            Function<? super T, ? extends R> mapper) {
        super(source);
        this.mapper = Objects.requireNonNull(mapper, "mapper");
    }
```

注意几个设计细节：

1. **类是 `final` 的。** 所有内部操作符类都是 `final`——禁止继承意味着 JVM 可以更积极地做方法内联。
2. **`mapper` 字段是 `final` 的。** 不可变性保证了线程安全——多个订阅者共享同一个 `FluxMap` 实例时，不需要同步。
3. **`mapper` 的类型是 `Function<? super T, ? extends R>`。** 使用了 PECS 原则（Producer Extends, Consumer Super），最大化泛型兼容性。
4. **`Objects.requireNonNull` 的错误消息是 `"mapper"`。** 提供了足够的调试信息，同时避免了冗长的错误描述。

### 3.3 subscribeOrReturn：创建内部 Subscriber

源码位置：`reactor/core/publisher/FluxMap.java`（第 53-62 行）

```java
@Override
@SuppressWarnings("unchecked")
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
    if (actual instanceof Fuseable.ConditionalSubscriber) {
        Fuseable.ConditionalSubscriber<? super R> cs =
                (Fuseable.ConditionalSubscriber<? super R>) actual;
        return new MapConditionalSubscriber<>(cs, mapper);
    }
    return new MapSubscriber<>(actual, mapper);
}
```

这段代码包含一个关键的分支判断：如果下游 `actual` 实现了 `Fuseable.ConditionalSubscriber` 接口，就创建 `MapConditionalSubscriber`；否则创建普通的 `MapSubscriber`。

**为什么要区分 ConditionalSubscriber？** 这个问题我们在第五节详细讨论。先来看标准的 `MapSubscriber`。

### 3.4 MapSubscriber：内部 Subscriber 的完整实现

源码位置：`reactor/core/publisher/FluxMap.java`（第 70-170 行）

```java
static final class MapSubscriber<T, R>
        implements InnerOperator<T, R> {

    final CoreSubscriber<? super R>        actual;
    final Function<? super T, ? extends R> mapper;

    boolean done;

    Subscription s;

    MapSubscriber(CoreSubscriber<? super R> actual,
            Function<? super T, ? extends R> mapper) {
        this.actual = actual;
        this.mapper = mapper;
    }

    @Override
    public void onSubscribe(Subscription s) {
        if (Operators.validate(this.s, s)) {
            this.s = s;
            actual.onSubscribe(this);
        }
    }

    @Override
    public void onNext(T t) {
        if (done) {
            Operators.onNextDropped(t, actual.currentContext());
            return;
        }

        R v;

        try {
            v = mapper.apply(t);
            if (v == null) {
                throw new NullPointerException("The mapper [" + mapper.getClass().getName() 
                    + "] returned a null value.");
            }
        }
        catch (Throwable e) {
            Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
            if (e_ != null) {
                onError(e_);
            }
            else {
                s.request(1);
            }
            return;
        }

        actual.onNext(v);
    }

    @Override
    public void onError(Throwable t) {
        if (done) {
            Operators.onErrorDropped(t, actual.currentContext());
            return;
        }
        done = true;
        actual.onError(t);
    }

    @Override
    public void onComplete() {
        if (done) {
            return;
        }
        done = true;
        actual.onComplete();
    }

    @Override
    public CoreSubscriber<? super R> actual() {
        return actual;
    }

    @Override
    public void request(long n) {
        s.request(n);
    }

    @Override
    public void cancel() {
        s.cancel();
    }
}
```

让我们逐块分析这个类。

#### 3.4.1 类签名与接口实现

`MapSubscriber` 实现了 `InnerOperator<T, R>`。这个接口的继承链是：

源码位置：`reactor/core/publisher/InnerOperator.java`

```java
interface InnerOperator<I, O>
        extends InnerConsumer<I>, InnerProducer<O> {

    @Override
    default Context currentContext() {
        CoreSubscriber<? super O> actual = actual();
        assert actual != null : "actual subscriber can not be null in inner operator";
        return actual.currentContext();
    }
}
```

源码位置：`reactor/core/publisher/InnerConsumer.java`

```java
interface InnerConsumer<I>
        extends CoreSubscriber<I>, Scannable {
}
```

源码位置：`reactor/core/publisher/InnerProducer.java`

```java
interface InnerProducer<O>
        extends Scannable, Subscription {

    @Nullable CoreSubscriber<? super O> actual();

    @Override
    default @Nullable Object scanUnsafe(Attr key) {
        if (key == Attr.ACTUAL) {
            return actual();
        }
        if (key == InternalProducerAttr.INSTANCE) return true;
        return null;
    }
}
```

把这三个接口展开后，`InnerOperator` = `CoreSubscriber<I>` + `Subscription` + `Scannable`。也就是说，`MapSubscriber` 同时扮演了两个角色：

1. **作为上游的 Subscriber**（`CoreSubscriber<T>` 方面）：接收上游的 `onSubscribe`、`onNext`、`onError`、`onComplete` 信号。
2. **作为下游的 Subscription**（`Subscription` 方面）：接收下游的 `request(n)` 和 `cancel()` 调用。

这是典型的"中间人"模式。`InnerOperator` 的 `currentContext()` 默认实现是委托给 `actual().currentContext()`——即 Context 从下游向上游传播。

**为什么不直接实现 `CoreSubscriber` 和 `Subscription` 这两个接口，而要通过 InnerOperator 间接实现？**

因为 `InnerOperator` 提供了：
- `currentContext()` 的默认委托实现（避免每个操作符都写一遍）。
- `scanUnsafe` 中 `Attr.ACTUAL` 的默认实现（用于调试链的扫描）。
- `InternalProducerAttr.INSTANCE` 标记（表示这是内部组件）。

#### 3.4.2 actual 和 s 字段：双向引用

```java
final CoreSubscriber<? super R> actual;  // 下游 Subscriber
Subscription s;                          // 上游 Subscription
```

`actual` 指向下游，`s` 指向上游。这两个引用构成了操作符在数据流中的双向连接：

```
上游 ──onNext──► MapSubscriber ──onNext──► actual (下游)
上游 ◄──request── MapSubscriber ◄──request── actual (下游)
```

`actual` 是 `final` 的——一旦创建就不会改变。`s` 不是 `final`——它在 `onSubscribe` 时被设置。

#### 3.4.3 onSubscribe：建立上游连接

```java
@Override
public void onSubscribe(Subscription s) {
    if (Operators.validate(this.s, s)) {
        this.s = s;
        actual.onSubscribe(this);
    }
}
```

`Operators.validate(this.s, s)` 检查是否重复订阅（§2.5 规范要求一个 Subscriber 只能被订阅一次）。如果验证通过：
1. 保存上游 Subscription 到 `this.s`。
2. 将自身（`this`）作为 Subscription 传递给下游的 `actual.onSubscribe(this)`。

**为什么传 `this` 而不是直接传 `s`？** 因为 `MapSubscriber` 需要拦截下游的 `request`/`cancel` 调用。虽然在 `FluxMap` 这个简单场景中，`request` 和 `cancel` 只是透传给 `s`，但更复杂的操作符（如 `FluxBuffer`）需要在 `request` 中做额外逻辑。统一用 `this` 作为 Subscription 是保持一致性的设计选择。

#### 3.4.4 onNext：核心转换逻辑

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    R v;

    try {
        v = mapper.apply(t);
        if (v == null) {
            throw new NullPointerException("The mapper [" + mapper.getClass().getName() 
                + "] returned a null value.");
        }
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            onError(e_);
        }
        else {
            s.request(1);
        }
        return;
    }

    actual.onNext(v);
}
```

逐行分析：

1. **`done` 检查**：如果已经收到过终止信号（`onError` 或 `onComplete`），后续的 `onNext` 被丢弃到 `Operators.onNextDropped`。这是防御性编程——规范不允许终止后再发信号，但上游可能有 bug。

2. **`mapper.apply(t)` 调用**：核心业务逻辑。注意结果 `v` 不允许为 `null`——Reactive Streams 规范禁止 `null` 元素，Reactor 在这里强制执行。

3. **异常处理**：`mapper.apply` 可能抛出异常。`Operators.onNextError` 负责决定如何处理：
   - 返回非 null 的 `Throwable` 时，表示应该调用 `onError` 终止流。
   - 返回 `null` 时，表示错误被 `onErrorContinue` 等策略消化了，`s.request(1)` 请求下一个元素继续。

4. **`actual.onNext(v)` 传播**：将转换后的值传给下游。

#### 3.4.5 done 标记的设计考量

`done` 是一个普通的 `boolean`（不是 `volatile`）。**为什么不需要 `volatile`？**

因为 Reactive Streams 规范保证了 `onNext`、`onError`、`onComplete` 之间的先行发生（happens-before）关系——它们不会被并发调用。同一时刻最多只有一个线程在调用这些方法。所以 `done` 的可见性由规范的串行化保证来保障，不需要额外的内存屏障。

**去掉 `done` 检查会怎样？** 如果上游在发出 `onError` 后又错误地发出 `onNext`，`mapper.apply` 可能抛出异常，`onError` 会被二次调用，下游可能收到两个终止信号——违反规范。`done` 是一道防火墙。

#### 3.4.6 request 和 cancel：透传

```java
@Override
public void request(long n) {
    s.request(n);
}

@Override
public void cancel() {
    s.cancel();
}
```

`FluxMap` 是一个一对一的操作符——每消费一个输入元素恰好产生一个输出元素。所以 `request(n)` 可以原封不动地传给上游：下游请求 N 个，上游就需要产生 N 个。

**什么操作符不能直接透传 `request`？** `FluxFilter` 就不行。当 filter 丢弃了一个不满足条件的元素时，它需要自己再向上游额外 `request(1)` 来补偿——否则下游请求的 N 个元素可能永远凑不齐。

## 四、FluxFilter：与 FluxMap 的对比

### 4.1 subscribeOrReturn 的对比

源码位置：`reactor/core/publisher/FluxFilter.java`（第 46-54 行）

```java
@Override
@SuppressWarnings("unchecked")
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    if (actual instanceof ConditionalSubscriber) {
        return new FilterConditionalSubscriber<>((ConditionalSubscriber<? super T>) actual,
                predicate);
    }
    return new FilterSubscriber<>(actual, predicate);
}
```

结构与 `FluxMap.subscribeOrReturn` 完全相同——都是检查 `ConditionalSubscriber` 后选择创建哪种内部 Subscriber。

### 4.2 FilterSubscriber.onNext 的关键差异

源码位置：`reactor/core/publisher/FluxFilter.java`（第 90-120 行）

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t,  this.ctx);
        return;
    }

    boolean b;

    try {
        b = predicate.test(t);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e,  this.ctx, s);
        if (e_ != null) {
            onError(e_);
        }
        else {
            s.request(1);
        }
        Operators.onDiscard(t,  this.ctx);
        return;
    }
    if (b) {
        actual.onNext(t);
    }
    else {
        Operators.onDiscard(t,  this.ctx);
        s.request(1);
    }
}
```

**与 MapSubscriber.onNext 的核心区别：**

1. **条件分支**：filter 不是无条件转发，而是根据 `predicate.test(t)` 的结果决定是否传递给下游。
2. **背压补偿**：当元素被过滤掉时（`b == false`），filter 主动调用 `s.request(1)` 向上游请求补偿。这是因为下游请求了 N 个元素，但 filter 消耗了一个不转发给下游，所以需要再从上游多拿一个。
3. **Discard 处理**：被丢弃的元素通过 `Operators.onDiscard(t, ctx)` 通知——如果用户注册了 discard hook（比如用于释放 pooled buffer），这里会触发资源回收。
4. **Context 缓存**：`FilterSubscriber` 在构造时就缓存了 `this.ctx = actual.currentContext()`，而 `MapSubscriber` 每次调用 `actual.currentContext()`。这是因为 filter 的 `onNext` 中多处需要 Context（discard、onNextError），缓存避免了重复调用。

### 4.3 FilterSubscriber 额外实现了 ConditionalSubscriber

一个值得注意的细节——`FilterSubscriber` 不仅实现了 `InnerOperator`，还实现了 `Fuseable.ConditionalSubscriber`：

```java
static final class FilterSubscriber<T>
        implements InnerOperator<T, T>,
                   Fuseable.ConditionalSubscriber<T> {
```

这意味着 `FilterSubscriber` 本身也是一个 `ConditionalSubscriber`。为什么？因为如果 filter 的上游也是一个支持 `tryOnNext` 的操作符，filter 可以利用 `tryOnNext` 来避免不必要的 `request(1)` 补偿调用。

## 五、ConditionalSubscriber 与 tryOnNext 优化

### 5.1 问题引出

考虑操作符链 `source.filter(p1).filter(p2).filter(p3)`。当一个元素通过了 p1 但被 p2 拒绝时：

**没有 tryOnNext 优化：**
```
source 发出元素 x
  → FilterSubscriber1.onNext(x)
    → predicate1.test(x) = true → actual.onNext(x)
      → FilterSubscriber2.onNext(x)
        → predicate2.test(x) = false
        → s.request(1)  // 向 FilterSubscriber1 请求补偿
          → FilterSubscriber1 → source.request(1)
            // 一个额外的 request(1) 调用穿越了整个链
```

每次过滤掉一个元素都会触发一次 `request(1)` 调用，这个调用需要穿越所有中间操作符到达源头。对于连续多个 filter 的场景，开销显著。

**有 tryOnNext 优化：**
```
source 发出元素 x
  → FilterSubscriber1.tryOnNext(x)  // 注意是 tryOnNext
    → predicate1.test(x) = true → actual.tryOnNext(x)
      → FilterSubscriber2.tryOnNext(x)
        → predicate2.test(x) = false
        → return false  // 告诉上游：我没消费这个元素
      ← FilterSubscriber1 收到 false → 不计入已消费数
    // 不需要额外的 request(1)！上游自己处理补偿
```

`tryOnNext` 返回 `boolean`——`true` 表示元素被消费了（计入请求配额），`false` 表示没消费（不计入）。这让源头的 `slowPath` 循环可以在不触发额外 `request` 调用的情况下自动补偿。

### 5.2 MapConditionalSubscriber 的 tryOnNext

源码位置：`reactor/core/publisher/FluxMap.java`（第 228-254 行）

```java
@Override
public boolean tryOnNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return true;
    }

    R v;

    try {
        v = mapper.apply(t);
        if (v == null) {
            throw new NullPointerException("The mapper [" + mapper.getClass().getName() 
                + "] returned a null value.");
        }
        return actual.tryOnNext(v);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            done = true;
            actual.onError(e_);
            return true;
        }
        else {
            return false;
        }
    }
}
```

`MapConditionalSubscriber` 的 `tryOnNext` 将 mapper 应用后，委托给下游的 `actual.tryOnNext(v)`——布尔返回值原样透传。

**对比普通的 `onNext`：** `onNext` 没有返回值，一旦调用了 `actual.onNext(v)`，map 就无法知道下游是否真的"消费"了这个元素。`tryOnNext` 通过返回值传递了这个信息。

### 5.3 FilterSubscriber.tryOnNext

源码位置：`reactor/core/publisher/FluxFilter.java`（第 122-149 行）

```java
@Override
public boolean tryOnNext(T t) {
    if (done) {
        Operators.onNextDropped(t,  this.ctx);
        return false;
    }

    boolean b;

    try {
        b = predicate.test(t);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e,  this.ctx, s);
        if (e_ != null) {
            onError(e_);
        }
        Operators.onDiscard(t,  this.ctx);
        return false;
    }
    if (b) {
        actual.onNext(t);
    }
    else {
        Operators.onDiscard(t,  this.ctx);
    }
    return b;
}
```

**关键区别：在 `tryOnNext` 中，当 predicate 返回 `false` 时，filter 不调用 `s.request(1)`。** 它只是返回 `false`，让上游知道这个元素没有被消费。上游（例如 `FluxArray.ArrayConditionalSubscription.slowPath`）会根据 `tryOnNext` 的返回值自行决定是否递减请求计数器。

## 六、MonoMap：Flux 与 Mono 之间的 Subscriber 复用

### 6.1 MonoMap 的完整源码

源码位置：`reactor/core/publisher/MonoMap.java`

```java
final class MonoMap<T, R> extends InternalMonoOperator<T, R> {

    final Function<? super T, ? extends R> mapper;

    MonoMap(Mono<? extends T> source, Function<? super T, ? extends R> mapper) {
        super(source);
        this.mapper = Objects.requireNonNull(mapper, "mapper");
    }

    @Override
    @SuppressWarnings("unchecked")
    public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
        if (actual instanceof Fuseable.ConditionalSubscriber) {
            Fuseable.ConditionalSubscriber<? super R> cs = 
                (Fuseable.ConditionalSubscriber<? super R>) actual;
            return new FluxMap.MapConditionalSubscriber<>(cs, mapper);
        }
        return new FluxMap.MapSubscriber<>(actual, mapper);
    }

    @Override
    public @Nullable Object scanUnsafe(Attr key) {
        if (key == Attr.RUN_STYLE) return Attr.RunStyle.SYNC;
        return super.scanUnsafe(key);
    }
}
```

### 6.2 直接复用 FluxMap 的 Subscriber

`MonoMap.subscribeOrReturn` 的实现直接使用了 `FluxMap.MapSubscriber` 和 `FluxMap.MapConditionalSubscriber`——没有创建任何新的内部类。

**为什么可以这样复用？** 因为 `MapSubscriber` 的逻辑是"接收 T，用 mapper 转换成 R，传给下游"——这个逻辑不关心上游是 `Flux` 还是 `Mono`。Subscriber 只关心信号（`onNext`、`onError`、`onComplete`），不关心源的基数约束。

**这种复用的好处：**
1. **减少类的数量。** 如果 `MonoMap` 定义自己的 `MonoMapSubscriber`，代码几乎完全一样，只是增加了维护负担。
2. **保持行为一致性。** 使用同一个 Subscriber 类保证了 `Mono.map` 和 `Flux.map` 在 `onNext` 处理、错误处理、null 检查等方面的行为完全一致。

**什么时候不能复用？** 当 Mono 的操作符语义与 Flux 不同时。例如 `Mono.flatMap` 返回 `Mono`（因为 1->1 映射），而 `Flux.flatMap` 返回 `Flux`（因为 N->M 映射）——它们的内部 Subscriber 有本质不同的并发控制逻辑，无法复用。

## 七、InnerOperator / InnerProducer / InnerConsumer 三接口的设计

### 7.1 三接口的关系

```
          Scannable    CoreSubscriber<I>
              │              │
              ▼              ▼
     ┌────────────────────────────┐
     │    InnerConsumer<I>        │   = Scannable + CoreSubscriber<I>
     └────────────┬───────────────┘
                  │
                  │    Scannable    Subscription
                  │        │            │
                  │        ▼            ▼
                  │   ┌──────────────────────┐
                  │   │  InnerProducer<O>     │   = Scannable + Subscription + actual()
                  │   └──────────┬───────────┘
                  │              │
                  ▼              ▼
          ┌──────────────────────────────┐
          │     InnerOperator<I, O>      │   = InnerConsumer<I> + InnerProducer<O>
          │                              │     + currentContext() 委托
          └──────────────────────────────┘
```

### 7.2 为什么分成三个接口

**InnerConsumer** 代表"消费上游数据"的角色——纯粹的 Subscriber。适用于链的末端消费者，如 `LambdaSubscriber`。

**InnerProducer** 代表"产生数据给下游"的角色——纯粹的 Subscription。适用于链的源头，如 `FluxArray.ArraySubscription`。它提供了 `actual()` 方法，返回它服务的下游 Subscriber。

**InnerOperator** 代表"既消费又产生"的中间角色——同时是 Subscriber 和 Subscription。绝大多数操作符的内部 Subscriber 都实现这个接口。

**为什么不只定义一个 InnerOperator？** 因为不是所有参与者都需要同时扮演两个角色。`FluxArray.ArraySubscription` 只是一个 Subscription（没有上游需要消费），强迫它实现 `CoreSubscriber` 的所有方法（`onNext`、`onError`、`onComplete`、`onSubscribe`）是不合理的。

### 7.3 InnerOperator 的 currentContext() 默认实现

源码位置：`reactor/core/publisher/InnerOperator.java`

```java
interface InnerOperator<I, O>
        extends InnerConsumer<I>, InnerProducer<O> {

    @Override
    default Context currentContext() {
        CoreSubscriber<? super O> actual = actual();
        assert actual != null : "actual subscriber can not be null in inner operator";
        return actual.currentContext();
    }
}
```

这个默认实现将 `currentContext()` 委托给了 `actual()`（下游 Subscriber）的 `currentContext()`。这是 Context 沿着 Subscriber 链向上传播的关键——当上游操作符需要 Context 时（比如获取 trace ID），它调用 `currentContext()`，这个调用沿着 `actual` 引用链一路传到最终的消费者。

## 八、操作符生命周期全景图

把装配和订阅两个阶段结合起来，一个操作符的完整生命周期如下：

```
阶段1: 装配（用户调用操作符方法时）
  flux.map(mapper)
    → new FluxMap(flux, mapper)
    → 返回 FluxMap 实例
    → 此时无任何数据流动

阶段2: 订阅（用户调用 subscribe 时）
  fluxMap.subscribe(lambdaSubscriber)
    → while(true) 循环中调用 FluxMap.subscribeOrReturn(lambdaSubscriber)
    → 创建 MapSubscriber(actual=lambdaSubscriber, mapper)
    → 循环继续到 source（FluxArray）
    → FluxArray.subscribe(mapSubscriber)

阶段3: 连接（源头调用 onSubscribe 时）
  FluxArray → mapSubscriber.onSubscribe(arraySubscription)
    → mapSubscriber 保存 this.s = arraySubscription
    → mapSubscriber 调用 actual.onSubscribe(this)
      → lambdaSubscriber.onSubscribe(mapSubscriber作为Subscription)

阶段4: 请求（onSubscribe 中或之后触发 request）
  lambdaSubscriber → mapSubscriber.request(Long.MAX_VALUE)
    → arraySubscription.request(Long.MAX_VALUE)
      → fastPath() 开始发射数据

阶段5: 数据流动
  arraySubscription → mapSubscriber.onNext(element)
    → mapper.apply(element) → mappedElement
    → actual.onNext(mappedElement)
      → lambdaSubscriber.onNext(mappedElement)
        → consumer.accept(mappedElement)

阶段6: 终止
  arraySubscription → mapSubscriber.onComplete()
    → done = true
    → actual.onComplete()
      → lambdaSubscriber.onComplete()
```

| **scanUnsafe RUN_STYLE** | `SYNC` | `SYNC` | `SYNC` |

## 十、设计模式总结

### 10.1 装饰器模式

每个操作符都是一个装饰器——它包装了上游的 Publisher（通过 `source` 字段），并在订阅时创建一个内部 Subscriber 来包装下游的 Subscriber（通过 `actual` 字段）。操作符本身不持有任何订阅状态——状态在内部 Subscriber 中。

### 10.2 中间人模式

内部 Subscriber（如 `MapSubscriber`）同时实现了 `CoreSubscriber` 和 `Subscription`，充当上游和下游之间的中间人。上游通过 `onNext` 等方法向它推送数据，下游通过 `request`/`cancel` 向它发出背压信号。

### 10.3 策略模式

操作符的业务逻辑（`mapper`、`predicate` 等）通过构造器注入，以函数式接口的形式存在。操作符框架代码（错误处理、done 检查、背压管理）是固定的模板，业务逻辑是可替换的策略。

### 10.4 类型安全的泛型链

操作符通过泛型参数 `<I, O>` 严格约束输入/输出类型。`FluxMap<T, R>` 消费 `T` 产出 `R`，`FluxFilter<T>` 消费 `T` 产出 `T`。编译器在装配阶段就能发现类型不匹配的错误，而不是推迟到运行时。

### 10.5 两阶段初始化

操作符对象在装配阶段创建（不可变），内部 Subscriber 在订阅阶段创建（持有可变状态）。这种分离让同一个操作符对象可以被多次订阅——每次订阅创建新的内部 Subscriber，互不干扰。
