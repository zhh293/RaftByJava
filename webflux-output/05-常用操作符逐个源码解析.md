### 1.2 操作符的统一模式

所有操作符都继承 `InternalFluxOperator<T, R>`（或 `InternalMonoOperator<T, R>`），实现 `subscribeOrReturn` 方法返回一个 `InnerOperator`：

```
              subscribe(Subscriber)
                      │
                      ▼
          ┌───────────────────────┐
          │ InternalFluxOperator  │
          │  subscribeOrReturn()  │
          └───────────┬───────────┘
                      │ 返回 InnerOperator
                      ▼
          ┌───────────────────────┐
          │   source.subscribe    │
          │     (innerOperator)   │
          └───────────┬───────────┘
                      │
                      ▼
          ┌───────────────────────┐
          │     InnerOperator     │
          │  onSubscribe(request) │
          │  onNext(item)         │
          │  onError(error)       │
          │  onComplete()         │
          │  request(n) → 上游    │
          │  cancel()  → 上游     │
          └───────────────────────┘
```

## 二、转换类操作符

### 2.1 FluxMap——一对一转换

源码文件：`reactor/core/publisher/FluxMap.java`

`FluxMap` 是最简单的操作符，它对每个上游值应用 `mapper` 函数，将结果传递给下游。

#### 2.1.1 类声明

```java
final class FluxMap<T, R> extends InternalFluxOperator<T, R> {
    final Function<? super T, ? extends R> mapper;

    @Override
    @SuppressWarnings("unchecked")
    public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
        if (actual instanceof Fuseable.ConditionalSubscriber) {
            Fuseable.ConditionalSubscriber<? super R> cs =
                    (Fuseable.ConditionalSubscriber<? super R>) actual;
            return new MapConditionalSubscriber<>(cs, mapper);
        }
        return new MapSubscriber<>(actual, mapper);
    }
}
```

与数据源一样，`FluxMap` 也区分 `ConditionalSubscriber` 和普通 Subscriber，提供 `MapSubscriber` 和 `MapConditionalSubscriber` 两个实现。

#### 2.1.2 MapSubscriber 的 onNext

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    R v;
    try {
        v = mapper.apply(t);
        if (v == null) {
            throw new NullPointerException("The mapper [" + mapper.getClass().getName() +
                    "] returned a null value.");
        }
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            onError(e_);
        }
        else {
            s.request(1);
        }
        return;
    }

    actual.onNext(v);
}
```

关键设计点：

1. **null 检查**：mapper 返回 null 会抛出 `NullPointerException`。Reactor 不允许 null 值流经管道。
2. **错误恢复**：`Operators.onNextError` 检查是否有 `onErrorResume` 策略。如果返回 null（表示错误被恢复），则 `s.request(1)` 补偿这一条被丢弃的数据，继续处理下一个值。
3. **done 标志**：一旦 `onError` 或 `onComplete` 被调用，`done` 设为 true，后续的 `onNext` 会被丢弃。

#### 2.1.3 MapConditionalSubscriber 的 tryOnNext

```java
@Override
public boolean tryOnNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return true;
    }
    R v;
    try {
        v = mapper.apply(t);
        if (v == null) {
            throw new NullPointerException("The mapper [" + mapper.getClass().getName() +
                    "] returned a null value.");
        }
        return actual.tryOnNext(v);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            done = true;
            actual.onError(e_);
            return true;
        }
        else {
            return false;  // 错误被恢复，值未消费
        }
    }
}
```

**与 MapSubscriber 的关键区别：** `tryOnNext` 返回 boolean 表示值是否被下游消费。如果 mapper 抛异常但错误被恢复，返回 `false` 表示"这个值没被消费"，上游（如 `FluxFilter`）知道需要继续提供值。这比普通 `onNext` 路径的 `s.request(1)` 补偿更高效——不需要额外的 request 往返。

#### 2.1.4 背压传递

```java
@Override
public void request(long n) {
    s.request(n);
}

@Override
public void cancel() {
    s.cancel();
}
```

`FluxMap` 是 1:1 转换，直接将下游的 request 量传递给上游。这是最理想的背压模式——每个下游请求对应一个上游发射。

### 2.2 FluxFilter——过滤

源码文件：`reactor/core/publisher/FluxFilter.java`

```java
final class FluxFilter<T> extends InternalFluxOperator<T, T> {
    final Predicate<? super T> predicate;
}
```

#### 2.2.1 FilterSubscriber 的 onNext

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, this.ctx);
        return;
    }

    boolean b;
    try {
        b = predicate.test(t);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, this.ctx, s);
        if (e_ != null) {
            onError(e_);
        }
        else {
            s.request(1);
        }
        Operators.onDiscard(t, this.ctx);
        return;
    }
    if (b) {
        actual.onNext(t);
    }
    else {
        Operators.onDiscard(t, this.ctx);
        s.request(1);
    }
}
```

**被过滤掉的值需要 `s.request(1)` 补偿：** filter 是 N:1 操作符——上游的 N 个值可能只产生 1 个下游值。当 predicate 返回 false 时，下游请求的 1 个配额被"消耗"在上游，需要向上游再 request(1) 来满足下游的需求。

**FilterSubscriber 同时实现 ConditionalSubscriber：** 注意类声明 `implements InnerOperator<T, T>, Fuseable.ConditionalSubscriber<T>`。即使下游不是 ConditionalSubscriber，FilterSubscriber 仍实现了 `tryOnNext`。这让上游（如 `FluxArray`）可以通过 `tryOnNext` 路径优化——上游调用 `tryOnNext`，filter 内部执行 predicate，如果不匹配返回 false，上游知道值未被消费，不需要额外 request 补偿。

**去掉 ConditionalSubscriber 优化会怎样？** 如果上游是 `FluxArray`，下游是 `Flux.filter`。不使用 `tryOnNext` 时：array 发射值 → filter 的 onNext → predicate false → filter request(1) → array 继续发射。每个被过滤的值需要 3 次方法调用 + 1 次 request。使用 `tryOnNext` 时：array.tryOnNext → filter.tryOnNext → predicate false → return false。只需要 2 次方法调用，无 request 往返。

### 2.3 FluxFlatMap——一对多扁平化（核心操作符）

源码文件：`reactor/core/publisher/FluxFlatMap.java`

`FluxFlatMap` 是 Reactor 中最复杂的操作符之一。它将上游的每个值映射为一个内部 Publisher，然后并发订阅这些内部 Publisher，将其发射的值"扁平化"传递给下游。

#### 2.3.1 类声明与核心参数

```java
final class FluxFlatMap<T, R> extends InternalFluxOperator<T, R> {
    final Function<? super T, ? extends Publisher<? extends R>> mapper;
    final boolean delayError;
    final int maxConcurrency;        // 最大并发内部订阅数
    final Supplier<? extends Queue<R>> mainQueueSupplier;
    final int prefetch;              // 每个内部 Publisher 的预取量
    final Supplier<? extends Queue<R>> innerQueueSupplier;
}
```

**maxConcurrency vs prefetch：**
- `maxConcurrency`：同时订阅多少个内部 Publisher。例如 `flatMap(mapper, 4)` 最多同时订阅 4 个内部 Publisher。
- `prefetch`：每个内部 Publisher 预取多少个值。例如 `prefetch=32` 表示每个内部 Publisher 初始请求 32 个值。

**去掉 maxConcurrency 限制会怎样？** 如果上游快速发射 10000 个值，每个值映射为一个 HTTP 请求 Publisher，无限制并发会导致 10000 个同时进行的 HTTP 请求——可能耗尽连接池、内存和 CPU。`maxConcurrency` 通过限制并发订阅数实现背压保护。

#### 2.3.2 FlatMapMain——并发管理核心

```java
static final class FlatMapMain<T, R> extends FlatMapTracker<FlatMapInner<R>>
        implements InnerOperator<T, R> {

    final boolean delayError;
    final int maxConcurrency;
    final int prefetch;
    final int limit;
    final CoreSubscriber<? super R> actual;

    volatile @Nullable Queue<R> scalarQueue;   // 标量值队列
    volatile @Nullable Throwable error;
    volatile boolean done;
    volatile boolean cancelled;
    volatile long requested;
    volatile int wip;
}
```

`FlatMapMain` 继承 `FlatMapTracker<FlatMapInner<R>>`——一个自定义的数组追踪器，用于管理活跃的 `FlatMapInner` 实例。

#### 2.3.3 onSubscribe 与初始请求

```java
@Override
public void onSubscribe(Subscription s) {
    if (Operators.validate(this.s, s)) {
        this.s = s;
        actual.onSubscribe(this);
        s.request(Operators.unboundedOrPrefetch(maxConcurrency));
    }
}
```

初始请求量为 `unboundedOrPrefetch(maxConcurrency)`。如果 `maxConcurrency == Integer.MAX_VALUE`，请求 `Long.MAX_VALUE`（无界）；否则请求 `maxConcurrency`。

#### 2.3.4 onNext——处理上游值

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    Publisher<? extends R> p;
    try {
        p = Objects.requireNonNull(mapper.apply(t),
                "The mapper returned a null Publisher");
    }
    catch (Throwable e) {
        // 错误处理...
        return;
    }

    if (p instanceof Callable) {
        // 标量优化：如果内部 Publisher 是 Callable，直接 call() 获取值
        R v;
        try {
            v = ((Callable<R>) p).call();
        }
        catch (Throwable e) {
            // 错误处理...
            return;
        }
        tryEmitScalar(v);
    }
    else {
        // 创建 FlatMapInner 并订阅
        FlatMapInner<R> inner = new FlatMapInner<>(this, prefetch);
        if (add(inner)) {
            p = Operators.toFluxOrMono(p);
            p.subscribe(inner);
        } else {
            Operators.onDiscard(t, actual.currentContext());
        }
    }
}
```

**标量优化（Callable 检查）：** 如果 mapper 返回的 Publisher 实现了 `Callable`（如 `MonoJust`），直接调用 `call()` 获取值，跳过整个订阅流程。`tryEmitScalar(v)` 将值放入 `scalarQueue` 或直接发射给下游。

**去掉标量优化会怎样？** `Flux.range(1, 1000).flatMap(x -> Mono.just(x * 2))` 中的每个 `Mono.just(x*2)` 都会创建 `FlatMapInner`、执行 `subscribe`、`onSubscribe`、`request`、`onNext`、`onComplete` 等完整链路。标量优化直接在 `tryEmitScalar` 中处理，省去了这些开销。

#### 2.3.5 FlatMapInner——内部订阅者

```java
static final class FlatMapInner<R>
        implements InnerConsumer<R>, Subscription {

    final FlatMapMain<?, R> parent;
    final int prefetch;
    final int limit;
    volatile Subscription s;
    long produced;
    volatile @Nullable Queue<R> queue;
    volatile boolean done;
    int sourceMode;

    @Override
    public void onSubscribe(Subscription s) {
        if (Operators.setOnce(S, this, s)) {
            if (s instanceof Fuseable.QueueSubscription) {
                @SuppressWarnings("unchecked") Fuseable.QueueSubscription<R> f =
                        (Fuseable.QueueSubscription<R>) s;
                int m = f.requestFusion(Fuseable.ANY | Fuseable.THREAD_BARRIER);
                if (m == Fuseable.SYNC) {
                    sourceMode = Fuseable.SYNC;
                    queue = f;
                    done = true;
                    parent.drain(null);
                    return;
                }
                if (m == Fuseable.ASYNC) {
                    sourceMode = Fuseable.ASYNC;
                    queue = f;
                }
            }
            s.request(Operators.unboundedOrPrefetch(prefetch));
        }
    }

    @Override
    public void onNext(R t) {
        if (sourceMode == Fuseable.ASYNC) {
            parent.drain(t);
        }
        else {
            if (done) {
                Operators.onNextDropped(t, parent.currentContext());
                return;
            }
            parent.tryEmit(this, t);
        }
    }

    @Override
    public void request(long n) {
        if (sourceMode == Fuseable.SYNC) {
            return;
        }
        long p = produced + n;
        if (p >= limit) {
            produced = 0L;
            s.request(p);
        }
        else {
            produced = p;
        }
    }
}
```

**prefetch 补充策略（request 方法）：** `FlatMapInner.request` 不是每次都向上游 request。它累积 `produced`，当达到 `limit`（`Operators.unboundedOrLimit(prefetch)`）时才批量 request。这是典型的"补满"策略——减少 request 往返次数。

**融合支持：** `FlatMapInner.onSubscribe` 检查上游是否支持融合。如果 SYNC 融合，直接将 queue 设为上游的 QueueSubscription，`done=true`，然后触发 `parent.drain`。如果 ASYNC 融合，设置 queue 但不标记 done——后续通过 `onNext(null)` 触发 drain。

#### 2.3.6 drainLoop——核心排空循环

`FlatMapMain.drainLoop()` 是 flatMap 最复杂的方法，负责将 scalarQueue 和各 inner 的 queue 中的值按下游请求量发射：

```java
void drainLoop() {
    int missed = 1;
    final Subscriber<? super R> a = actual;

    for (;;) {
        boolean d = done;
        @Nullable FlatMapInner<R>[] as = get();
        int n = as.length;
        Queue<R> sq = scalarQueue;
        boolean noSources = isEmpty();

        if (checkTerminated(d, noSources && (sq == null || sq.isEmpty()), a, null)) {
            return;
        }

        // 1. 先排空 scalarQueue
        // 2. 再轮询所有 inner 的 queue（round-robin）
        // 3. 补充上游 request（replenishMain）
        // 4. 如果有进展（again=true），继续循环
    }
}
```

**轮询策略（round-robin）：** drainLoop 使用 `lastIndex` 记录上次轮询到哪个 inner，下次从下一个开始。这保证了各 inner 的公平性——避免某个 inner 的队列被排空而其他 inner 饥饿。

#### 2.3.7 FlatMapTracker——内部订阅者的数组管理

```java
abstract class FlatMapTracker<T> {
    volatile @Nullable T[] array = empty();
    int[] free = FREE_EMPTY;
    long producerIndex;
    long consumerIndex;
    volatile int size;
}
```

`FlatMapTracker` 使用一个数组 + 空闲索引栈管理 `FlatMapInner` 实例。`add` 方法优先复用已移除的槽位，不够时扩容（`n << 1`）。`remove` 方法将槽位置 null 并回收索引。

**为什么不用 ConcurrentHashMap？** FlatMapInner 的添加和移除发生在 drainLoop 中（单线程），不需要并发安全。`array` 的 volatile 保证了其他线程能读到最新的数组引用。用 synchronized 保护 add/remove 中的数组操作，足够保证正确性且开销远低于 CHM。

### 2.4 FluxConcatMap——顺序扁平化

源码文件：`reactor/core/publisher/FluxConcatMap.java`

```java
final class FluxConcatMap<T, R> extends InternalFluxOperator<T, R> {
    final Function<? super T, ? extends Publisher<? extends R>> mapper;
    final Supplier<? extends Queue<T>> queueSupplier;
    final int prefetch;
    final ErrorMode errorMode;

    enum ErrorMode {
        IMMEDIATE,  // 立即报告错误，取消当前内部源
        BOUNDARY,   // 当前内部源终止后报告错误
        END         // 所有源终止后报告错误
    }
}
```

#### 2.4.1 FlatMap vs ConcatMap 的核心区别

| 特性 | FluxFlatMap | FluxConcatMap |
|---|---|---|
| 并发订阅 | 多个内部 Publisher 同时订阅 | 同时只订阅一个内部 Publisher |
| 顺序保证 | 交错（interleaving） | 严格顺序 |
| 核心参数 | maxConcurrency, prefetch | prefetch |
| 内部结构 | FlatMapTracker 数组管理多个 Inner | 单个 ConcatMapInner，active 标志控制 |
| drain 逻辑 | 轮询所有 inner 的 queue | 只在 active=false 时取下一个值 |

**ConcatMapImmediate 的 drain 方法：**

```java
void drain() {
    if (WIP.getAndIncrement(this) == 0) {
        for (;;) {
            if (cancelled) return;

            if (!active) {
                boolean d = done;
                T v;
                try {
                    v = queue.poll();
                }
                catch (Throwable e) {
                    actual.onError(Operators.onOperatorError(s, e, this.ctx));
                    return;
                }

                boolean empty = v == null;
                if (d && empty) {
                    actual.onComplete();
                    return;
                }

                if (!empty) {
                    Publisher<? extends R> p = mapper.apply(v);
                    // ...
                    if (p instanceof Callable) {
                        // 标量优化
                    }
                    else {
                        active = true;
                        p.subscribe(inner);
                    }
                }
            }
            if (WIP.decrementAndGet(this) == 0) break;
        }
    }
}
```

**关键设计：`active` 标志。** 当 `active=true` 时，drain 不取新值——当前内部 Publisher 的值必须全部发射完毕（`innerComplete` 将 `active` 设为 `false`），才能取下一个上游值并订阅新的内部 Publisher。

**去掉 active 控制会怎样？** 如果在内部 Publisher 未完成时就取下一个值并订阅，多个内部 Publisher 的值会交错——这就是 flatMap 的行为。concatMap 的语义是"顺序连接"，必须保证前一个完成后再开始下一个。

#### 2.4.2 ConcatMapImmediate 的 guard 机制

`ConcatMapImmediate` 使用一个 `guard` 原子整数保护 `innerNext` 和 `onError` 之间的竞争：

```java
@Override
public void innerNext(R value) {
    if (guard == 0 && GUARD.compareAndSet(this, 0, 1)) {
        actual.onNext(value);
        if (GUARD.compareAndSet(this, 1, 0)) {
            return;
        }
        // guard 未能重置回 0，说明 onError 在等待
        Throwable e = Exceptions.terminate(ERROR, this);
        if (e != TERMINATED) {
            actual.onError(e);
        }
    }
}
```

**为什么需要 guard？** 在 `IMMEDIATE` 模式下，如果上游 `onError` 和内部 `onNext` 并发发生，直接调用 `actual.onNext` 和 `actual.onError` 会违反 Reactive Streams 规范（不允许并发调用）。`guard` 通过 CAS 确保同一时间只有一个信号传递给下游。如果 `onError` 在 `onNext` 期间到达（CAS 1→0 失败），则在 `onNext` 完成后立即传递 error。

## 三、截取类操作符：FluxTake

源码文件：`reactor/core/publisher/FluxTake.java`

```java
final class FluxTake<T> extends InternalFluxOperator<T, T> {
    final long n;
}
```

### 3.1 TakeSubscriber 的 onNext 取消逻辑

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    long r = remaining;
    if (r == 0) {
        s.cancel();
        onComplete();
        return;
    }

    remaining = --r;
    boolean stop = r == 0L;

    actual.onNext(t);

    if (stop) {
        s.cancel();
        onComplete();
    }
}
```

**关键设计：先 `actual.onNext(t)` 再 `cancel()`。** 如果反过来先 cancel 再 onNext，在 SYNC 融合模式下可能导致问题——cancel 后上游可能已经释放了资源。先 onNext 确保下游收到值后再取消。

**`remaining == 0` 的防御性检查：** 如果上游在 cancel 生效前又发射了值（这在异步源中可能发生），`remaining` 已经是 0，直接 cancel 并 complete，不再向下游传递。

### 3.2 TakeSubscriber 的 request 优化

```java
@Override
public void request(long n) {
    if (wip == 0 && WIP.compareAndSet(this, 0, 1)) {
        if (n >= this.n) {
            s.request(Long.MAX_VALUE);
        } else {
            s.request(n);
        }
        return;
    }
    s.request(n);
}
```

**如果下游请求量 >= take 的数量，直接请求 Long.MAX_VALUE。** 这让上游进入 fastPath，避免逐个 request 的开销。例如 `Flux.range(1, 1000000).take(10)`，下游 request(10) 时，n >= this.n（10 >= 10），上游直接 fastPath 遍历，take 在第 10 个值时 cancel。

### 3.3 TakeFuseableSubscriber——融合支持

`FluxTake` 还提供了 `TakeFuseableSubscriber`，支持 SYNC/ASYNC 融合：

```java
@Override
public @Nullable T poll() {
    if (done) return null;
    long r = remaining;
    T v = qs.poll();
    if (r == 0L) {
        done = true;
        if (inputMode == Fuseable.ASYNC) {
            qs.cancel();
            actual.onComplete();
        }
        return null;
    }
    if (v != null) {
        remaining = --r;
        if (r == 0L) {
            if (!done) {
                done = true;
                if (inputMode == Fuseable.ASYNC) {
                    qs.cancel();
                    actual.onComplete();
                }
            }
        }
    }
    return v;
}
```

在 SYNC 融合模式下，下游直接通过 `poll()` 拉取值。`poll()` 内部检查 `remaining`，到 0 时标记 done 并返回 null（表示没有更多值）。这比 `onNext` 路径更高效——不需要 `cancel()` 调用，因为融合模式下 `poll()` 返回 null 就自动终止。

## 四、聚合类操作符

### 4.1 FluxScan——带中间结果的累加

源码文件：`reactor/core/publisher/FluxScan.java`

```java
final class FluxScan<T> extends InternalFluxOperator<T, T> {
    final BiFunction<T, ? super T, T> accumulator;
}
```

#### 4.1.1 ScanSubscriber 的 onNext

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    T v = value;
    if (v != null) {
        try {
            t = Objects.requireNonNull(accumulator.apply(v, t),
                    "The accumulator returned a null value");
        }
        catch (Throwable e) {
            onError(Operators.onOperatorError(s, e, t, actual.currentContext()));
            return;
        }
    }
    value = t;
    actual.onNext(t);
}
```

**设计要点：**
1. 第一个值不经过 accumulator——直接作为初始值存储并发射。
2. 后续值与上一次的累加结果 `value` 通过 `accumulator.apply(v, t)` 计算。
3. accumulator 返回 null 会抛出 NPE。
4. `value` 字段在 `onError`/`onComplete`/`cancel` 时被置 null（cancel 除外，因注释说明了竞争问题）。

**ScanSubscriber.cancel 中的特殊注释：**

```java
@Override
public void cancel() {
    s.cancel();
    //unless we want to pay a volatile, cancel() nulling out might race with onNext
    //and result in re-setting value, retaining it. So we don't null out, nor discard.
}
```

**为什么不在 cancel 时清理 value？** cancel 和 onNext 可能并发执行（来自不同线程）。如果 cancel 将 value 置 null，而 onNext 正在读取 value，可能导致 NPE 或数据不一致。即使加了 volatile，onNext 可能在 cancel 之后仍然设置 value（因为上游 cancel 生效前的 in-flight onNext），导致 value 被重新设置，内存泄漏。因此 Reactor 选择不清理——接受潜在的一次值保留，换取正确性。

### 4.2 关于 FluxReduce 和 FluxCollect

在此版本的 Reactor Core 源码中，`FluxReduce.java` 和 `FluxCollect.java` 未找到独立文件。在 Reactor 的实现中：

- **FluxReduce** 通常基于 `FluxScan` 实现：`reduce` 等价于 `scan` + 只取最后一个值。scan 在每次累加后发射中间结果，reduce 只在完成时发射最终结果。
- **FluxCollect** 通常基于 `reduce` 实现：`collect(supplier, accumulator)` 等价于 `reduce` 时用 supplier 创建初始容器，accumulator 将每个值加入容器。

这种"操作符组合"的设计避免了重复实现累加逻辑。`FluxScan` 提供了完整的累加机制，`reduce` 和 `collect` 只是不同的封装方式。

## 五、容错类操作符

### 5.1 FluxOnErrorResume——错误恢复

源码文件：`reactor/core/publisher/FluxOnErrorResume.java`

```java
final class FluxOnErrorResume<T> extends InternalFluxOperator<T, T> {
    final Function<? super Throwable, ? extends Publisher<? extends T>> nextFactory;
}
```

#### 5.1.1 ResumeSubscriber 的错误恢复机制

```java
static final class ResumeSubscriber<T>
        extends Operators.MultiSubscriptionSubscriber<T, T> {

    final Function<? super Throwable, ? extends Publisher<? extends T>> nextFactory;
    boolean second;

    @Override
    public void onSubscribe(Subscription s) {
        if (!second) {
            actual.onSubscribe(this);
        }
        set(s);
    }

    @Override
    public void onNext(T t) {
        actual.onNext(t);
        if (!second) {
            producedOne();
        }
    }

    @Override
    public void onError(Throwable t) {
        if (!second) {
            second = true;
            Publisher<? extends T> p;
            try {
                p = Operators.toFluxOrMono(Objects.requireNonNull(nextFactory.apply(t),
                        "The nextFactory returned a null Publisher"));
            }
            catch (Throwable e) {
                Throwable _e = Operators.onOperatorError(e, actual.currentContext());
                _e = Exceptions.addSuppressed(_e, t);
                actual.onError(_e);
                return;
            }
            p.subscribe(this);
        }
        else {
            actual.onError(t);
        }
    }
}
```

**核心设计：`second` 标志 + 自订阅。**

1. 第一次 `onError` 时，`second` 为 false。设置 `second = true`，调用 `nextFactory.apply(t)` 获取恢复 Publisher，然后 **用 this 订阅恢复 Publisher**。
2. 恢复 Publisher 的 `onSubscribe` 中，因为 `second` 为 true，不再调用 `actual.onSubscribe(this)`（已经调过了），只调用 `set(s)` 替换当前 Subscription。
3. 如果恢复 Publisher 也出错（第二次 `onError`），`second` 为 true，直接传递给下游——不支持二次恢复。

**为什么继承 MultiSubscriptionSubscriber？** `MultiSubscriptionSubscriber` 支持在运行时替换内部的 Subscription——从原始 Publisher 切换到恢复 Publisher。它还管理 `produced` 计数，在切换 Subscription 时补偿已消费的量。

**去掉 second 标志会怎样？** 如果没有 second 标志，恢复 Publisher 出错时又会触发 `onError`，导致无限递归订阅。`second` 确保最多只恢复一次，第二次错误直接传递给下游。

#### 5.1.2 onSubscribe 中的条件逻辑

```java
@Override
public void onSubscribe(Subscription s) {
    if (!second) {
        actual.onSubscribe(this);
    }
    set(s);
}
```

第一次订阅时，需要通知下游 `onSubscribe`。恢复订阅时，下游已经有了 Subscription（就是 this），不需要再次通知——只需要替换内部的上游 Subscription。

### 5.2 FluxRetry——重订阅

源码文件：`reactor/core/publisher/FluxRetry.java`

```java
final class FluxRetry<T> extends InternalFluxOperator<T, T> {
    final long times;

    @Override
    public @Nullable CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
        RetrySubscriber<T> parent = new RetrySubscriber<>(source, actual, times);
        actual.onSubscribe(parent);
        if (!parent.isCancelled()) {
            parent.resubscribe();
        }
        return null;
    }
}
```

**注意 `subscribeOrReturn` 返回 null！** 这意味着 `FluxRetry` 不会在 `InternalFluxOperator.subscribe` 的标准流程中订阅上游。它自己控制订阅时机——在 `subscribeOrReturn` 中直接创建 `RetrySubscriber` 并调用 `resubscribe()`。

#### 5.2.1 RetrySubscriber 的重订阅机制

```java
static final class RetrySubscriber<T>
        extends Operators.MultiSubscriptionSubscriber<T, T> {

    final CorePublisher<? extends T> source;
    long remaining;
    volatile int wip;

    @Override
    public void onNext(T t) {
        produced++;
        actual.onNext(t);
    }

    @Override
    public void onError(Throwable t) {
        long r = remaining;
        if (r != Long.MAX_VALUE) {
            if (r == 0) {
                actual.onError(t);
                return;
            }
            remaining = r - 1;
        }
        resubscribe();
    }

    void resubscribe() {
        if (WIP.getAndIncrement(this) == 0) {
            do {
                if (isCancelled()) return;

                long c = produced;
                if (c != 0L) {
                    produced = 0L;
                    produced(c);
                }

                source.subscribe(Operators.restoreContextOnSubscriberIfPublisherNonInternal(source, this));
            } while (WIP.decrementAndGet(this) != 0);
        }
    }
}
```

**关键设计点：**

1. **WIP 保证串行重订阅：** `resubscribe` 通过 WIP CAS 保证同一时间只有一个线程在执行重订阅。如果 `onError` 在前一次 `source.subscribe` 完成前到达，WIP 递增但不执行，由当前循环的 `decrementAndGet` 检测到非 0 后继续。

2. **produced 补偿：** 每次 `onNext` 递增 `produced`。重订阅前，通过 `produced(c)` 将已消费量报告给 `MultiSubscriptionSubscriber`，后者在下次 `request` 时补偿。这保证了重试后的 request 量正确——不会因为重试而多请求或少请求。

3. **times == Long.MAX_VALUE 表示无限重试：** `remaining` 初始为 `times`，每次 `onError` 递减。当 `remaining == Long.MAX_VALUE` 时跳过递减，永远重试。

**去掉 WIP 会怎样？** 假设 `source.subscribe(this)` 内部同步触发了 `onError`（如 `Flux.error(e).retry(3)`），`onError` 调用 `resubscribe`，`resubscribe` 再次调用 `source.subscribe`。如果没有 WIP 保护，这会变成无限递归调用栈，最终 StackOverflow。WIP 的 CAS 将递归转为循环——第一次 `getAndIncrement` 返回 0 进入循环，同步触发的 `resubscribe` 的 `getAndIncrement` 返回 1 不进入循环，外层循环的 `decrementAndGet` 返回 1（非 0），继续下一轮。

## 六、副作用类操作符

### 6.1 FluxDoOnEach——生命周期窥探

源码文件：`reactor/core/publisher/FluxDoOnEach.java`

```java
final class FluxDoOnEach<T> extends InternalFluxOperator<T, T> {
    final Consumer<? super Signal<T>> onSignal;
}
```

`FluxDoOnEach` 在每个信号（onNext/onError/onComplete）到达时，先调用 `onSignal` 回调，再将信号传递给下游。它不修改数据流，只产生副作用。

#### 6.1.1 DoOnEachSubscriber 的状态机

```java
static class DoOnEachSubscriber<T> implements InnerOperator<T, T>, Signal<T> {
    static final short STATE_FLUX_START   = (short) 0;
    static final short STATE_MONO_START   = (short) 1;
    static final short STATE_SKIP_HANDLER = (short) 2;
    static final short STATE_DONE         = (short) 3;

    short state;

    DoOnEachSubscriber(CoreSubscriber<? super T> actual,
            Consumer<? super Signal<T>> onSignal,
            boolean monoFlavor) {
        this.state = monoFlavor ? STATE_MONO_START : STATE_FLUX_START;
    }
}
```

**状态机的意义：**
- `STATE_FLUX_START`：Flux 模式初始状态。onNext 时触发 onSignal，onComplete 时触发 onSignal。
- `STATE_MONO_START`：Mono 模式初始状态。onNext 时触发 onSignal **并且** 立即触发 onComplete 的 onSignal（因为 Mono 语义上 onNext 后必然 onComplete）。
- `STATE_SKIP_HANDLER`：已触发过 onComplete 的 onSignal，后续的 onComplete 不再触发。
- `STATE_DONE`：已终止，所有后续信号被丢弃。

**为什么 Mono 需要特殊处理？** 在 Mono 语义中，`onNext` 后紧跟 `onComplete` 是隐含的。`doOnEach` 的用户期望在 Mono 中 onNext 回调后也会收到 onComplete 回调。但某些 Mono 实现（如 `MonoJust`）只调用 `onSubscribe` + `onNext`，不显式调用 `onComplete`。`STATE_MONO_START` 状态在 onNext 后自动触发 onComplete 回调，弥补了这一差异。

#### 6.1.2 DoOnEachSubscriber 实现 Signal<T> 接口

```java
static class DoOnEachSubscriber<T> implements InnerOperator<T, T>, Signal<T> {
    @Nullable T t;

    @Override
    public @Nullable T get() { return t; }

    @Override
    public SignalType getType() { return SignalType.ON_NEXT; }

    @Override
    public @Nullable Throwable getThrowable() { return null; }
}
```

**DoOnEachSubscriber 自身实现了 `Signal<T>` 接口！** 在 `onNext` 中，它将当前值存入 `this.t`，然后将自己作为 Signal 传给 `onSignal.accept(this)`：

```java
@Override
public void onNext(T t) {
    if (state == STATE_DONE) {
        Operators.onNextDropped(t, cachedContext);
        return;
    }
    try {
        this.t = t;
        onSignal.accept(this);  // this 就是 Signal<T>
    }
    catch (Throwable e) {
        onError(Operators.onOperatorError(s, e, t, cachedContext));
        return;
    }
    // ...
    actual.onNext(t);
}
```

**为什么这样设计？** 避免为每个 onNext 创建新的 Signal 对象。如果用 `Signal.next(t)` 工厂方法，每次 onNext 都会分配一个 Signal 实例。在百万级数据流中，这会产生大量短命对象，增加 GC 压力。通过复用 `this` 作为 Signal，实现了零分配的副作用通知。

**去掉这个优化会怎样？** `Flux.range(1, 1000000).doOnEach(s -> ...).subscribe()` 中，每个值都会创建一个 Signal 对象。100 万个 Signal 对象的分配和回收会显著增加 GC 时间。

#### 6.1.3 DoOnEachFuseableSubscriber 的融合支持

```java
@Override
public @Nullable T poll() {
    if (qs == null) return null;
    T v = qs.poll();
    if (v == null && this.fusionMode == SYNC) {
        state = STATE_DONE;
        onSignal.accept(Signal.complete(cachedContext));
    } else if (v != null) {
        this.t = v;
        onSignal.accept(this);  // 在 poll 路径中也触发回调
    }
    return v;
}
```

在 SYNC 融合模式下，下游通过 `poll()` 拉取值。`DoOnEachFuseableSubscriber.poll()` 在拉取到值后触发 onSignal 回调，在拉取到 null（表示完成）时触发 complete 回调。这确保了融合模式下副作用回调不会丢失。

## 七、分批类操作符

### 7.1 FluxBuffer——缓冲分组

源码文件：`reactor/core/publisher/FluxBuffer.java`

```java
final class FluxBuffer<T, C extends Collection<? super T>> extends InternalFluxOperator<T, C> {
    final int size;
    final int skip;
    final Supplier<C> bufferSupplier;
}
```

`FluxBuffer` 有三种模式，通过 `size` 和 `skip` 的关系决定：

```java
@Override
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super C> actual) {
    if (size == skip) {
        return new BufferExactSubscriber<>(actual, size, bufferSupplier);
    }
    else if (skip > size) {
        return new BufferSkipSubscriber<>(actual, size, skip, bufferSupplier);
    }
    else {
        return new BufferOverlappingSubscriber<>(actual, size, skip, bufferSupplier);
    }
}
```

| 模式 | 条件 | 行为 |
|---|---|---|
| Exact | size == skip | 每 size 个值组成一个 buffer |
| Skip | skip > size | 每 skip 个值取 size 个组成 buffer，跳过中间的 |
| Overlapping | skip < size | 每 skip 个值开始新 buffer，buffer 大小为 size（有重叠） |

#### 7.1.1 BufferExactSubscriber 的 request 优化

```java
@Override
public void request(long n) {
    if (Operators.validate(n)) {
        s.request(Operators.multiplyCap(n, size));
    }
}
```

**下游请求 n 个 buffer，上游请求 n * size 个值。** `multiplyCap` 防止溢出。这是 1:N 操作符的标准背压转换——下游的 1 个请求对应上游的 N 个值。

#### 7.1.2 BufferExactSubscriber 的 onNext

```java
@Override
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    C b = buffer;
    if (b == null) {
        try {
            b = Objects.requireNonNull(bufferSupplier.get(),
                    "The bufferSupplier returned a null buffer");
        }
        catch (Throwable e) {
            // 错误处理...
            return;
        }
        buffer = b;
    }

    if (b.add(t)) {
        if (b.size() == size) {
            buffer = null;
            actual.onNext(b);
        }
    }
    else {
        Operators.onDiscard(t, actual.currentContext());
        s.request(1);
    }
}
```

**`b.add(t)` 返回 false 的处理：** 某些 Collection（如定长队列）的 `add` 可能返回 false 表示添加失败。Reactor 在此情况下 discard 该值并 request(1) 补偿，保证背压正确。

### 7.2 FluxDistinct——去重

源码文件：`reactor/core/publisher/FluxDistinct.java`

```java
final class FluxDistinct<T, K, C> extends InternalFluxOperator<T, T> {
    final Function<? super T, ? extends K> keyExtractor;
    final Supplier<C> collectionSupplier;
    final BiPredicate<C, K> distinctPredicate;
    final Consumer<C> cleanupCallback;
}
```

`FluxDistinct` 的设计比一般实现更灵活——它不硬编码 HashSet，而是通过三个函数式接口让用户自定义去重逻辑：

- `keyExtractor`：从值中提取去重 key
- `collectionSupplier`：创建去重容器（如 `HashSet::new`）
- `distinctPredicate`：测试 key 是否首次出现（如 `(set, k) -> set.add(k)`）
- `cleanupCallback`：清理容器（如 `set -> set.clear()`）

#### 7.2.1 DistinctSubscriber 的 tryOnNext

```java
@Override
public boolean tryOnNext(T t) {
    if (done) {
        Operators.onNextDropped(t, this.ctx);
        return true;
    }

    K k;
    try {
        k = Objects.requireNonNull(keyExtractor.apply(t),
                "The distinct extractor returned a null value.");
    }
    catch (Throwable e) {
        onError(Operators.onOperatorError(s, e, t, this.ctx));
        Operators.onDiscard(t, this.ctx);
        return true;
    }

    boolean b;
    try {
        b = distinctPredicate.test(collection, k);
    }
    catch (Throwable e) {
        onError(Operators.onOperatorError(s, e, t, ctx));
        Operators.onDiscard(t, this.ctx);
        return true;
    }

    if (b) {
        actual.onNext(t);
        return true;
    }
    Operators.onDiscard(t, ctx);
    return false;
}
```

**DistinctSubscriber 总是实现 ConditionalSubscriber。** 即使下游不是 ConditionalSubscriber，`onNext` 内部调用 `tryOnNext`，如果返回 false（重复值），则 `s.request(1)` 补偿：

```java
@Override
public void onNext(T t) {
    if (!tryOnNext(t)) {
        s.request(1);
    }
}
```

#### 7.2.2 DistinctFuseableSubscriber 的 poll 循环

在 SYNC 融合模式下，`DistinctFuseableSubscriber.poll()` 需要跳过重复值：

```java
@Override
public @Nullable T poll() {
    if (sourceMode == Fuseable.ASYNC) {
        long dropped = 0;
        for (;;) {
            T v = qs.poll();
            if (v == null) {
                return null;
            }
            try {
                K r = Objects.requireNonNull(keyExtractor.apply(v),
                        "The keyExtractor returned a null collection");
                if (distinctPredicate.test(collection, r)) {
                    if (dropped != 0) {
                        request(dropped);
                    }
                    return v;
                }
                Operators.onDiscard(v, ctx);
                dropped++;
            }
            catch (Throwable error) {
                Operators.onDiscard(v, this.ctx);
                throw error;
            }
        }
    }
    else {
        // SYNC 模式类似，但不需要 request 补偿
    }
}
```

**ASYNC 融合模式下的 request 补偿：** 在 ASYNC 模式中，poll 可能返回重复值（被丢弃），这些值消耗了上游的配额。`poll()` 内部累积 `dropped` 计数，在找到非重复值时通过 `request(dropped)` 补偿。

## 八、操作符分类对照表

| 操作符 | 类名 | 类型 | 背压模型 | ConditionalSubscriber | Fuseable | 关键设计 |
|---|---|---|---|---|---|---|
| map | FluxMap | 转换 | 1:1 透传 | 是 | 否 | mapper null 检查 + 错误恢复 |
| filter | FluxFilter | 转换 | N:1（补偿） | 是 | 否 | tryOnNext 避免 request 往返 |
| flatMap | FluxFlatMap | 转换 | M:N（并发） | 否 | 内部支持 | maxConcurrency + prefetch + 标量优化 |
| concatMap | FluxConcatMap | 转换 | M:1（顺序） | 否 | 内部支持 | active 标志 + guard 保护 |
| take | FluxTake | 截取 | N:M（有限） | 是 | 是 | 先 onNext 再 cancel |
| scan | FluxScan | 聚合 | 1:1 透传 | 否 | 否 | value 状态 + cancel 不清理 |
| onErrorResume | FluxOnErrorResume | 容错 | 切换源 | 否 | 否 | second 标志 + 自订阅 |
| retry | FluxRetry | 容错 | 重订阅 | 否 | 否 | WIP 防递归 + produced 补偿 |
| doOnEach | FluxDoOnEach | 副作用 | 1:1 透传 | 是 | 是 | 自实现 Signal 零分配 + Mono 状态机 |
| buffer | FluxBuffer | 分批 | 1:N 转换 | 否 | 否 | size/skip 三模式 + multiplyCap |
| distinct | FluxDistinct | 分批 | N:1（补偿） | 是 | 是 | 自定义去重逻辑 + poll 循环 |

### 关键设计模式总结

| 设计模式 | 使用者 | 动机 |
