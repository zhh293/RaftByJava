# 编解码器框架全流程源码解析

## 一、核心问题引入：TCP 粘包/拆包

### 1.1 什么是 TCP 粘包/拆包？

TCP 是一个"流"协议，它不像 UDP 那样保留消息边界。当应用层向 TCP 发送数据时，TCP 会根据缓冲区大小、MSS、Nagle 算法等因素，将数据切分或合并成若干个 TCP 段进行传输。这意味着**发送方写入的消息边界，在接收方是完全不可见的**。

假设客户端连续发送两条消息 `MSG1` 和 `MSG2`：

```
发送方视角（两次 write）：
+----------+  +----------+
|   MSG1   |  |   MSG2   |
+----------+  +----------+

接收方视角（可能的三种情况）：
```

**情况一：正常接收（理想，但不保证）**
```
+----------+  +----------+
|   MSG1   |  |   MSG2   |
+----------+  +----------+
```

**情况二：粘包（两条消息合并到一次读取中）**
```
+----------------------+
|   MSG1   |   MSG2    |
+----------------------+
```

**情况三：拆包（一条消息被分散到多次读取中）**
```
+-------+  +----------------+  +------+
| MSG1前 |  | MSG1后 | MSG2前 |  | MSG2后|
+-------+  +----------------+  +------+
```

**情况四：粘包与拆包同时发生**
```
+----------------+  +--------------+
| MSG1 | MSG2前半 |  | MSG2后半      |
+----------------+  +--------------+
```

### 1.2 为什么需要编解码器？

面对上述问题，Netty 的 `ChannelPipeline` 需要一个专门的层来完成**"字节流到结构化消息"**的转换。这就是编解码器存在的意义：

- **解码器（Decoder）**：在 Inbound 方向，从原始字节流中识别消息边界，将连续的 ByteBuf 拆分/拼装为完整的业务消息对象
- **编码器（Encoder）**：在 Outbound 方向，将业务消息对象序列化为字节流，并按照协议格式添加边界标识

整个编解码框架的核心设计目标是：**在流式数据到达时增量解码，而不是等待所有数据到齐后一次性处理**。这种"累积器"模式是 Netty 高性能的关键之一。

## 二、编解码器的类层次结构

Netty 的编解码器框架构建了一个清晰的类层次，每个类解决特定的转换场景：

```
                        ChannelInboundHandlerAdapter
                                   |
                    +--------------+------------------+
                    |                                 |
         ByteToMessageDecoder          MessageToMessageDecoder<I>
                    |                                 |
        +-----------+-----------+          (String -> Integer 等)
        |           |           |
  FixedLength  LineBased  LengthFieldBased
  FrameDecoder FrameDecoder FrameDecoder


                       ChannelOutboundHandlerAdapter
                                   |
                    +--------------+------------------+
                    |                                 |
         MessageToByteEncoder<I>       MessageToMessageEncoder<I>
                                                     |
                                           LengthFieldPrepender


                        ChannelDuplexHandler
                                |
                 +--------------+------------------+
                 |                                 |
      ByteToMessageCodec<I>    CombinedChannelDuplexHandler<I,O>
```

各类的职责定位：

| 类名 | 方向 | 输入 | 输出 | 核心特征 |
|------|------|------|------|----------|
| ByteToMessageDecoder | Inbound | ByteBuf（流） | Object | 带累积器，解决粘包拆包 |
| MessageToMessageDecoder | Inbound | Object | Object | 无累积器，消息级转换 |
| MessageToByteEncoder | Outbound | Object | ByteBuf | 分配 buffer - 编码 - 写出 |
| MessageToMessageEncoder | Outbound | Object | Object | PromiseCombiner 聚合多产出 |
| ByteToMessageCodec | 双向 | 委托模式 | 委托模式 | 内部组合 decoder + encoder |
| CombinedChannelDuplexHandler | 双向 | 代理上下文 | 代理上下文 | 组合任意 inbound + outbound |

## 三、ByteToMessageDecoder 源码深度解析

`ByteToMessageDecoder` 是整个编解码框架中最重要的类——所有处理字节流的解码器都继承自它。它解决的核心问题是：**如何在异步、分片到达的字节流上，持续尝试解码出完整消息**。

### 3.1 累积器（Cumulator）

累积器是 ByteToMessageDecoder 的灵魂。它负责将每次 `channelRead` 收到的新数据与之前未解码完的数据进行合并。

#### 3.1.1 Cumulator 接口定义

```java
public interface Cumulator {
    ByteBuf cumulate(ByteBufAllocator alloc, ByteBuf cumulation, ByteBuf in);
}
```

接口非常简洁：接收旧的累积缓冲区 `cumulation` 和新到达的数据 `in`，返回合并后的 ByteBuf。

#### 3.1.2 MERGE_CUMULATOR（默认策略——内存拷贝合并）

```java
public static final Cumulator MERGE_CUMULATOR = new Cumulator() {
    @Override
    public ByteBuf cumulate(ByteBufAllocator alloc, ByteBuf cumulation, ByteBuf in) {
        if (cumulation == in) {
            // 防止同一个 buffer 被重复计数
            in.release();
            return cumulation;
        }
        if (!cumulation.isReadable() && in.isContiguous()) {
            // 优化：如果累积缓冲区为空且 in 是连续的，直接用 in 替代
            cumulation.release();
            return in;
        }
        try {
            final int required = in.readableBytes();
            if (required > cumulation.maxWritableBytes() ||
                required > cumulation.maxFastWritableBytes() && cumulation.refCnt() > 1 ||
                cumulation.isReadOnly()) {
                // 需要扩容：容量不够 / 共享中不安全 / 只读
                return expandCumulation(alloc, cumulation, in);
            }
            cumulation.writeBytes(in, in.readerIndex(), required);
            in.readerIndex(in.writerIndex());
            return cumulation;
        } finally {
            in.release(); // 无论如何都要释放 in
        }
    }
};
```

**设计要点解读**：

为什么采用内存拷贝作为默认策略？因为绝大多数协议场景下，每次到达的数据量不大，一次 `System.arraycopy` 的开销远小于维护 CompositeByteBuf 复杂索引结构的开销。同时，连续内存对 CPU 缓存更友好，后续解码时的顺序读取性能更高。

特别注意 `cumulation.refCnt() > 1` 的检查——如果引用计数大于 1，说明有外部代码持有了这个 buffer 的引用（可能通过 `slice().retain()` 或 `duplicate().retain()`），此时直接扩容写入可能破坏外部持有者看到的数据，必须创建新的 buffer。

#### 3.1.3 COMPOSITE_CUMULATOR（零拷贝策略）

```java
public static final Cumulator COMPOSITE_CUMULATOR = new Cumulator() {
    @Override
    public ByteBuf cumulate(ByteBufAllocator alloc, ByteBuf cumulation, ByteBuf in) {
        if (cumulation == in) {
            in.release();
            return cumulation;
        }
        if (!cumulation.isReadable()) {
            cumulation.release();
            return in;
        }
        CompositeByteBuf composite = null;
        try {
            if (cumulation instanceof CompositeByteBuf && cumulation.refCnt() == 1) {
                composite = (CompositeByteBuf) cumulation;
                if (composite.writerIndex() != composite.capacity()) {
                    composite.capacity(composite.writerIndex());
                }
            } else {
                composite = alloc.compositeBuffer(Integer.MAX_VALUE)
                        .addFlattenedComponents(true, cumulation);
            }
            composite.addFlattenedComponents(true, in);
            in = null;
            return composite;
        } finally {
            if (in != null) {
                in.release();
                if (composite != null && composite != cumulation) {
                    composite.release();
                }
            }
        }
    }
};
```

**设计要点解读**：

`COMPOSITE_CUMULATOR` 通过 `CompositeByteBuf` 将多个 ByteBuf 逻辑上拼接在一起，**不发生任何内存拷贝**。这在每次收到的数据块较大时非常有优势。但代价是 `CompositeByteBuf` 的随机访问需要先定位到对应的 component，索引计算更复杂。

`addFlattenedComponents(true, in)` 中的 `true` 表示同时增加 `writerIndex`，确保新添加的数据立即可读。`Flattened` 意味着如果 `in` 本身也是 CompositeByteBuf，则展平其内部 components，避免嵌套。

#### 3.1.4 expandCumulation 辅助方法

```java
static ByteBuf expandCumulation(ByteBufAllocator alloc, ByteBuf oldCumulation, ByteBuf in) {
    int oldBytes = oldCumulation.readableBytes();
    int newBytes = in.readableBytes();
    int totalBytes = oldBytes + newBytes;
    ByteBuf newCumulation = alloc.buffer(alloc.calculateNewCapacity(totalBytes, Integer.MAX_VALUE));
    ByteBuf toRelease = newCumulation;
    try {
        // 使用 setBytes 而不是 writeBytes，避免冗余的边界检查和栈深度
        newCumulation.setBytes(0, oldCumulation, oldCumulation.readerIndex(), oldBytes)
            .setBytes(oldBytes, in, in.readerIndex(), newBytes)
            .writerIndex(totalBytes);
        in.readerIndex(in.writerIndex());
        toRelease = oldCumulation;
        return newCumulation;
    } finally {
        toRelease.release();
    }
}
```

为什么用 `setBytes` + 手动设置 `writerIndex` 而不是直接用 `writeBytes`？因为 `writeBytes` 内部会做 `ensureWritable` 检查（我们已经确保了容量足够），还会逐步推进 writerIndex（多一次方法调用的栈深度）。`setBytes` 是更底层的操作，在已知安全的情况下性能更好。

### 3.2 channelRead() 核心流程

```java
@Override
public void channelRead(ChannelHandlerContext ctx, Object input) throws Exception {
    if (decodeState == STATE_INIT) {
        do {
            if (input instanceof ByteBuf) {
                selfFiredChannelRead = true;
                CodecOutputList out = CodecOutputList.newInstance();
                try {
                    first = cumulation == null;
                    cumulation = cumulator.cumulate(ctx.alloc(),
                            first ? EMPTY_BUFFER : cumulation, (ByteBuf) input);
                    callDecode(ctx, cumulation, out);
                } catch (DecoderException e) {
                    throw e;
                } catch (Exception e) {
                    throw new DecoderException(e);
                } finally {
                    try {
                        if (cumulation != null && !cumulation.isReadable()) {
                            numReads = 0;
                            try {
                                cumulation.release();
                            } catch (IllegalReferenceCountException e) {
                                throw new IllegalReferenceCountException(
                                        getClass().getSimpleName() +
                                        "#decode() might have released its input buffer...", e);
                            }
                            cumulation = null;
                        } else if (++numReads >= discardAfterReads) {
                            numReads = 0;
                            discardSomeReadBytes();
                        }

                        int size = out.size();
                        firedChannelRead |= out.insertSinceRecycled();
                        fireChannelRead(ctx, out, size);
                    } finally {
                        out.recycle();
                    }
                }
            } else {
                ctx.fireChannelRead(input);
            }
        } while (inputMessages != null && (input = inputMessages.poll()) != null);
    } else {
        // 重入调用：将消息入队，由外层循环统一处理
        if (inputMessages == null) {
            inputMessages = new ArrayDeque<>(2);
        }
        inputMessages.offer(input);
    }
}
```

**完整调用流程图示**：

```
channelRead(ctx, msg)
     |
     +-- msg 不是 ByteBuf？--> ctx.fireChannelRead(msg) 直接透传
     |
     +-- 处于重入状态？--> inputMessages.offer(msg) 入队等待
     |
     +-- 正常状态 (STATE_INIT)
           |
           +-- 1. first = (cumulation == null)
           |
           +-- 2. cumulation = cumulator.cumulate(alloc, cumulation, input)
           |      将新数据合并到累积缓冲区
           |
           +-- 3. callDecode(ctx, cumulation, out)
           |      循环调用 decode() 解码
           |
           +-- 4. finally 清理
                  |
                  +-- cumulation 无可读数据？
                  |     -> release + 置 null（全部数据已解码完毕）
                  |
                  +-- numReads >= 16？
                  |     -> discardSomeReadBytes()（防止 OOM）
                  |
                  +-- fireChannelRead(ctx, out, size)
                        遍历 out 列表向下游传播
```

**重入保护机制**：为什么需要 `inputMessages` 队列？

考虑这样的场景：在 `decode()` 中，子类可能调用了 `ctx.fireChannelRead(msg)`，而下游的某个 handler 又触发了数据写入，写入完成后可能触发新的 `channelRead` 回调（自读取场景）。此时如果不做保护，就会在同一个累积器上并发操作，导致数据错乱。Netty 通过 `decodeState` 标志检测到重入，将新消息暂存到 `inputMessages` 队列中，等外层 `do-while` 循环统一处理。

**discardAfterReads=16 的设计**：每次 channelRead 后，如果累积缓冲区还有剩余未解码数据，就递增计数器。当连续 16 次 channelRead 都没能清空累积缓冲区时，说明数据可能在持续堆积（可能是半包等待），此时调用 `discardSomeReadBytes()` 压缩已读区域，释放内存前端空间，防止 OOM。

### 3.3 callDecode() 循环解码逻辑

```java
protected void callDecode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    try {
        while (in.isReadable()) {
            final int outSize = out.size();

            if (outSize > 0) {
                fireChannelRead(ctx, out, outSize);
                out.clear();
                if (ctx.isRemoved()) {
                    break;
                }
            }

            int oldInputLength = in.readableBytes();
            decodeRemovalReentryProtection(ctx, in, out);

            if (ctx.isRemoved()) {
                break;
            }

            if (out.isEmpty()) {
                if (oldInputLength == in.readableBytes()) {
                    break;  // 退出条件1：没有产出且没消费数据
                } else {
                    continue; // 消费了数据但没产出，继续尝试
                }
            }

            if (oldInputLength == in.readableBytes()) {
                // 退出条件2：有产出但没消费数据——这是 BUG！
                throw new DecoderException(
                    StringUtil.simpleClassName(getClass()) +
                    ".decode() did not read anything but decoded a message.");
            }

            if (isSingleDecode()) {
                break; // 退出条件3：单次解码模式
            }
        }
    } catch (DecoderException e) {
        throw e;
    } catch (Exception cause) {
        throw new DecoderException(cause);
    }
}
```

**四种退出条件的详细分析**：

```
+------------------+-------------------+------------------------------+
|  out 列表状态     |  readerIndex 状态  |  行为                         |
+------------------+-------------------+------------------------------+
|  为空(无产出)     |  未前进(没消费)     |  break：数据不够，等更多数据    |
|  为空(无产出)     |  前进了(消费了)     |  continue：跳过了无效数据      |
|  非空(有产出)     |  未前进(没消费)     |  throw：BUG！凭空产出消息      |
|  非空(有产出)     |  前进了(消费了)     |  继续循环/singleDecode退出    |
+------------------+-------------------+------------------------------+
```

**防止死循环的检测机制**：

这套判断逻辑确保了 `callDecode()` 不会陷入无限循环：

1. 如果 `decode()` 什么都没做（不消费数据、不产出消息），循环必然退出
2. 如果 `decode()` 产出了消息但没消费数据，直接抛异常——这是子类实现的 BUG（凭空创造数据）
3. 如果 `decode()` 消费了数据但没产出（比如跳过了损坏的帧头），允许继续尝试——因为 buffer 中数据在减少，终会触发条件 1 退出
4. `ctx.isRemoved()` 检查确保 handler 被动态移除时安全退出

### 3.4 decodeRemovalReentryProtection

```java
final void decodeRemovalReentryProtection(ChannelHandlerContext ctx, ByteBuf in, List<Object> out)
        throws Exception {
    decodeState = STATE_CALLING_CHILD_DECODE;
    try {
        decode(ctx, in, out);
    } finally {
        if (inputMessages == null || inputMessages.isEmpty()) {
            boolean removePending = decodeState == STATE_HANDLER_REMOVED_PENDING;
            decodeState = STATE_INIT;
            if (removePending) {
                fireChannelRead(ctx, out, out.size());
                out.clear();
                handlerRemoved(ctx);
            }
        }
    }
}
```

这个方法解决了一个微妙的并发问题：如果在 `decode()` 执行期间，Pipeline 收到了 `handlerRemoved` 事件（比如协议升级场景），不能立即移除 handler（因为 decode 还在操作 cumulation），所以先标记为 `STATE_HANDLER_REMOVED_PENDING`，等 decode 返回后再安全地执行移除操作。

### 3.5 channelReadComplete() 时的内存整理

```java
@Override
public void channelReadComplete(ChannelHandlerContext ctx) throws Exception {
    numReads = 0;
    discardSomeReadBytes();
    if (selfFiredChannelRead && !firedChannelRead && !ctx.channel().config().isAutoRead()) {
        ctx.read();
    }
    firedChannelRead = false;
    selfFiredChannelRead = false;
    ctx.fireChannelReadComplete();
}

protected final void discardSomeReadBytes() {
    if (cumulation != null && !first && cumulation.refCnt() == 1) {
        cumulation.discardSomeReadBytes();
    }
}
```

`channelReadComplete()` 在一轮读取周期结束时被调用。此时做两件事：

1. **内存压缩**：`discardSomeReadBytes()` 将累积缓冲区中已读的数据丢弃，把未读数据移到 buffer 开头。条件 `!first` 确保第一次调用不做无用功（first 表示 cumulation 是新创建的），`refCnt() == 1` 确保没有外部引用持有这个 buffer 的 slice。

2. **自动触发读取**：如果 `autoRead=false` 且本轮没有产出任何消息（`!firedChannelRead`），说明数据还不够解码一条完整消息，需要主动调用 `ctx.read()` 触发下一轮读取。

## 四、MessageToByteEncoder 源码解析

`MessageToByteEncoder` 是 Outbound 方向的核心编码器基类，将 Java 对象编码为字节流。

```java
public abstract class MessageToByteEncoder<I> extends ChannelOutboundHandlerAdapter {

    private final TypeParameterMatcher matcher;
    private final boolean preferDirect;

    @Override
    public void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise) throws Exception {
        ByteBuf buf = null;
        try {
            if (acceptOutboundMessage(msg)) {
                @SuppressWarnings("unchecked")
                I cast = (I) msg;
                buf = allocateBuffer(ctx, cast, preferDirect);
                try {
                    encode(ctx, cast, buf);
                } finally {
                    ReferenceCountUtil.release(cast); // 编码完成，释放原始消息
                }

                if (buf.isReadable()) {
                    ctx.write(buf, promise);
                } else {
                    buf.release();
                    ctx.write(Unpooled.EMPTY_BUFFER, promise);
                }
                buf = null;
            } else {
                ctx.write(msg, promise); // 不匹配的消息直接透传
            }
        } catch (EncoderException e) {
            throw e;
        } catch (Throwable e) {
            throw new EncoderException(e);
        } finally {
            if (buf != null) {
                buf.release(); // 异常时释放 buffer
            }
        }
    }

    protected ByteBuf allocateBuffer(ChannelHandlerContext ctx, I msg,
                                     boolean preferDirect) throws Exception {
        if (preferDirect) {
            return ctx.alloc().ioBuffer();  // 直接内存，适合网络 IO
        } else {
            return ctx.alloc().heapBuffer(); // 堆内存
        }
    }

    protected abstract void encode(ChannelHandlerContext ctx, I msg, ByteBuf out) throws Exception;
}
```

**设计要点**：

1. **TypeParameterMatcher**：通过泛型参数 `I` 自动推断要处理的消息类型，`acceptOutboundMessage()` 在运行时做类型检查。不匹配的消息直接透传给下一个 handler，实现了"责任链"模式的选择性处理。

2. **preferDirect=true 的默认选择**：编码后的数据最终要通过 Socket 发送，使用直接内存（off-heap）可以避免 JVM 堆内存到内核缓冲区的一次额外拷贝。

3. **引用计数管理**：`ReferenceCountUtil.release(cast)` 在 `encode()` 之后立即释放原始消息——因为编码器已经将消息内容写入了 `buf`，原始消息不再需要。如果 `encode()` 抛异常，finally 块中的 `buf.release()` 确保不会泄漏分配的 buffer。

## 五、MessageToMessageDecoder 与 MessageToMessageEncoder

### 5.1 MessageToMessageDecoder

```java
public abstract class MessageToMessageDecoder<I> extends ChannelInboundHandlerAdapter {

    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
        CodecOutputList out = CodecOutputList.newInstance();
        try {
            if (acceptInboundMessage(msg)) {
                @SuppressWarnings("unchecked")
                I cast = (I) msg;
                try {
                    decode(ctx, cast, out);
                } finally {
                    ReferenceCountUtil.release(cast);
                }
            } else {
                out.add(msg); // 不匹配的消息加入 out，后续会 fireChannelRead
            }
        } catch (DecoderException e) {
            throw e;
        } catch (Exception e) {
            throw new DecoderException(e);
        } finally {
            try {
                int size = out.size();
                for (int i = 0; i < size; i++) {
                    ctx.fireChannelRead(out.getUnsafe(i));
                }
            } finally {
                out.recycle();
            }
        }
    }

    protected abstract void decode(ChannelHandlerContext ctx, I msg, List<Object> out)
            throws Exception;
}
```

**与 ByteToMessageDecoder 的核心区别**：没有累积器！每条入站消息独立处理，不存在"半包等待"的问题。典型使用场景是将已经被帧解码器处理过的 ByteBuf 进一步转换为业务对象（如 `ByteBuf -> HttpRequest`）。

### 5.2 MessageToMessageEncoder

```java
public abstract class MessageToMessageEncoder<I> extends ChannelOutboundHandlerAdapter {

    @Override
    public void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise)
            throws Exception {
        CodecOutputList out = null;
        try {
            if (acceptOutboundMessage(msg)) {
                out = CodecOutputList.newInstance();
                I cast = (I) msg;
                try {
                    encode(ctx, cast, out);
                } catch (Throwable th) {
                    ReferenceCountUtil.safeRelease(cast);
                    PlatformDependent.throwException(th);
                }
                ReferenceCountUtil.release(cast);

                if (out.isEmpty()) {
                    throw new EncoderException(
                        StringUtil.simpleClassName(this) + " must produce at least one message.");
                }
            } else {
                ctx.write(msg, promise);
            }
        } finally {
            if (out != null) {
                try {
                    final int sizeMinusOne = out.size() - 1;
                    if (sizeMinusOne == 0) {
                        ctx.write(out.getUnsafe(0), promise);
                    } else if (sizeMinusOne > 0) {
                        if (promise == ctx.voidPromise()) {
                            writeVoidPromise(ctx, out);
                        } else {
                            writePromiseCombiner(ctx, out, promise);
                        }
                    }
                } finally {
                    out.recycle();
                }
            }
        }
    }
}
```

**多产出时的 PromiseCombiner**：当 `encode()` 产出多个对象时（如 LengthFieldPrepender 产出"长度字段 ByteBuf + 消息体 ByteBuf"），一个 `write` 操作对应一个 `promise`。PromiseCombiner 将多个写操作的结果聚合：只有当所有产出都写入成功时，原始 promise 才标记为成功。如果 promise 是 `voidPromise()`（表示调用者不关心结果），则跳过聚合逻辑以减少 GC 压力。

## 六、ByteToMessageCodec 与 CombinedChannelDuplexHandler

### 6.1 ByteToMessageCodec——委托模式

```java
public abstract class ByteToMessageCodec<I> extends ChannelDuplexHandler {

    private final MessageToByteEncoder<I> encoder;

    private final ByteToMessageDecoder decoder = new ByteToMessageDecoder() {
        @Override
        public void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out)
                throws Exception {
            ByteToMessageCodec.this.decode(ctx, in, out);
        }

        @Override
        protected void decodeLast(ChannelHandlerContext ctx, ByteBuf in, List<Object> out)
                throws Exception {
            ByteToMessageCodec.this.decodeLast(ctx, in, out);
        }
    };

    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
        decoder.channelRead(ctx, msg); // 委托给内部 decoder
    }

    @Override
    public void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise)
            throws Exception {
        encoder.write(ctx, msg, promise); // 委托给内部 encoder
    }
}
```

ByteToMessageCodec 采用**委托模式**：内部持有一个匿名的 `ByteToMessageDecoder` 实例和一个 `MessageToByteEncoder` 实例，将 inbound 事件委托给 decoder，outbound 事件委托给 encoder。这样用户只需要继承一个类就能同时实现编解码，而不用在 pipeline 中添加两个 handler。

**为什么不能标记 @Sharable**？因为内部的 `ByteToMessageDecoder` 维护了 `cumulation` 状态，这是 per-channel 的，不能跨 channel 共享。

### 6.2 CombinedChannelDuplexHandler——代理上下文

```java
public class CombinedChannelDuplexHandler<I extends ChannelInboundHandler,
                                          O extends ChannelOutboundHandler>
        extends ChannelDuplexHandler {

    private DelegatingChannelHandlerContext inboundCtx;
    private DelegatingChannelHandlerContext outboundCtx;
    private I inboundHandler;
    private O outboundHandler;
}
```

与 ByteToMessageCodec 不同，CombinedChannelDuplexHandler 可以组合**任意已存在的** inbound handler 和 outbound handler，无需它们有继承关系。它通过 `DelegatingChannelHandlerContext` 为内部的两个 handler 各自创建代理上下文，确保事件正确路由。

典型使用场景：将一个现成的解码器和编码器组合为一个 handler，减少 pipeline 中的 handler 数量。

## 七、内置解码器详解

### 7.1 FixedLengthFrameDecoder——固定长度解码器

#### 解决什么问题

当协议规定每条消息的长度固定时（如金融行情推送、传感器数据采集），使用固定长度解码器是最简单高效的方案。

```
输入（粘包的字节流）：
+---+----+------+----+
| A | BC | DEFG | HI |
+---+----+------+----+

FixedLengthFrameDecoder(3) 输出：
+-----+-----+-----+
| ABC | DEF | GHI |
+-----+-----+-----+
```

#### 核心源码

```java
public class FixedLengthFrameDecoder extends ByteToMessageDecoder {

    private final int frameLength;

    public FixedLengthFrameDecoder(int frameLength) {
        checkPositive(frameLength, "frameLength");
        this.frameLength = frameLength;
    }

    @Override
    protected final void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out)
            throws Exception {
        Object decoded = decode(ctx, in);
        if (decoded != null) {
            out.add(decoded);
        }
    }

    protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
        if (in.readableBytes() < frameLength) {
            return null; // 数据不够一帧，等待更多数据
        } else {
            return in.readRetainedSlice(frameLength); // 零拷贝切片
        }
    }
}
```

**极致简洁的设计**：整个类不到 30 行有效代码。`readRetainedSlice` 返回一个共享底层内存的切片并增加引用计数，避免了数据拷贝。当 `callDecode()` 循环调用时，只要 buffer 中有 >= frameLength 的数据，就会持续产出帧。

#### 使用示例

```java
// 每条消息固定 20 字节
ch.pipeline().addLast(new FixedLengthFrameDecoder(20));
ch.pipeline().addLast(new StringDecoder());
ch.pipeline().addLast(new BusinessHandler());
```

### 7.2 LineBasedFrameDecoder——行解码器

#### 解决什么问题

文本协议（SMTP、FTP、Redis 的 RESP 文本部分）通常以 `\n` 或 `\r\n` 作为消息分隔符。LineBasedFrameDecoder 按行分割字节流。

```
输入：
+----------------------------------+
| "Hello\r\nWorld\nFoo\r\nBar\n"   |
+----------------------------------+

输出（stripDelimiter=true）：
+-------+-------+-----+-----+
| Hello | World | Foo | Bar |
+-------+-------+-----+-----+
```

#### 核心源码

```java
public class LineBasedFrameDecoder extends ByteToMessageDecoder {

    private final int maxLength;
    private final boolean failFast;
    private final boolean stripDelimiter;
    private boolean discarding;  // 状态机：正常模式 / 丢弃模式
    private int discardedBytes;
    private int offset;          // 搜索优化：记录上次搜索到的位置

    protected Object decode(ChannelHandlerContext ctx, ByteBuf buffer) throws Exception {
        final int eol = findEndOfLine(buffer);
        if (!discarding) {
            if (eol >= 0) {
                // 找到行尾：正常解码
                final ByteBuf frame;
                final int length = eol - buffer.readerIndex();
                final int delimLength = buffer.getByte(eol) == '\r' ? 2 : 1;

                if (length > maxLength) {
                    buffer.readerIndex(eol + delimLength);
                    fail(ctx, length);
                    return null;
                }

                if (stripDelimiter) {
                    frame = buffer.readRetainedSlice(length);
                    buffer.skipBytes(delimLength);
                } else {
                    frame = buffer.readRetainedSlice(length + delimLength);
                }
                return frame;
            } else {
                // 没找到行尾：检查是否超长
                final int length = buffer.readableBytes();
                if (length > maxLength) {
                    discardedBytes = length;
                    buffer.readerIndex(buffer.writerIndex());
                    discarding = true; // 切换到丢弃模式
                    offset = 0;
                    if (failFast) {
                        fail(ctx, "over " + discardedBytes);
                    }
                }
                return null;
            }
        } else {
            // 丢弃模式：已经超长，等找到行尾后丢弃整行
            if (eol >= 0) {
                final int length = discardedBytes + eol - buffer.readerIndex();
                final int delimLength = buffer.getByte(eol) == '\r' ? 2 : 1;
                buffer.readerIndex(eol + delimLength);
                discardedBytes = 0;
                discarding = false; // 恢复正常模式
                if (!failFast) {
                    fail(ctx, length);
                }
            } else {
                discardedBytes += buffer.readableBytes();
                buffer.readerIndex(buffer.writerIndex());
                offset = 0;
            }
            return null;
        }
    }

    private int findEndOfLine(final ByteBuf buffer) {
        int totalLength = buffer.readableBytes();
        // 关键优化：从 offset 位置开始搜索，避免重复扫描
        int i = buffer.indexOf(buffer.readerIndex() + offset,
                               buffer.readerIndex() + totalLength, (byte) '\n');
        if (i >= 0) {
            offset = 0;
            if (i > 0 && buffer.getByte(i - 1) == '\r') {
                i--; // \r\n 的情况，返回 \r 的位置
            }
        } else {
            offset = totalLength; // 记录已搜索过的范围
        }
        return i;
    }
}
```

**设计亮点**：

1. **offset 优化**：如果本次没找到换行符，记录已经搜索过的字节数。下次有新数据到来时，`findEndOfLine` 从 `offset` 位置开始搜索，避免对已扫描过的数据重复搜索。这将时间复杂度从 O(n^2)（每次重头扫描）降低到 O(n)（每个字节只被扫描一次）。

2. **两种模式的状态机**：当发现当前行超过 `maxLength` 时，切换到"丢弃模式"。在丢弃模式下，所有到来的数据直接跳过，直到找到行尾后恢复正常模式。这是一种防御性设计——防止恶意客户端发送超长行导致内存耗尽。

3. **failFast 策略选择**：`failFast=true` 在检测到超长时立即抛异常通知应用层；`failFast=false` 等整行丢弃完毕后再报错——后者适合需要精确统计丢弃字节数的场景。

#### 使用示例

```java
// 每行最多 1024 字节，去除分隔符
ch.pipeline().addLast(new LineBasedFrameDecoder(1024, true, false));
ch.pipeline().addLast(new StringDecoder(CharsetUtil.UTF_8));
ch.pipeline().addLast(new MyTextProtocolHandler());
```

### 7.3 DelimiterBasedFrameDecoder——自定义分隔符解码器

#### 解决什么问题

当分隔符不是简单的换行符，而是自定义的字节序列（如 NUL 字符、`$$`、`##END##` 等）时使用。支持指定多个分隔符，选择产出最短帧的那个。

```
输入（分隔符为 \n 和 \r\n）：
+--------------+
| ABC\nDEF\r\n |
+--------------+

选择 \n（产出更短帧 "ABC"）：
+-----+-----+
| ABC | DEF |
+-----+-----+
```

#### 核心源码

```java
public class DelimiterBasedFrameDecoder extends ByteToMessageDecoder {

    private final ByteBuf[] delimiters;
    private final LineBasedFrameDecoder lineBasedDecoder; // 特例优化

    public DelimiterBasedFrameDecoder(int maxFrameLength, boolean stripDelimiter,
                                       boolean failFast, ByteBuf... delimiters) {
        // 关键优化：如果分隔符恰好是 \n 和 \r\n，委托给更高效的 LineBasedFrameDecoder
        if (isLineBased(delimiters) && !isSubclass()) {
            lineBasedDecoder = new LineBasedFrameDecoder(maxFrameLength, stripDelimiter, failFast);
            this.delimiters = null;
        } else {
            this.delimiters = new ByteBuf[delimiters.length];
            for (int i = 0; i < delimiters.length; i++) {
                ByteBuf d = delimiters[i];
                this.delimiters[i] = d.slice(d.readerIndex(), d.readableBytes());
            }
            lineBasedDecoder = null;
        }
    }

    protected Object decode(ChannelHandlerContext ctx, ByteBuf buffer) throws Exception {
        if (lineBasedDecoder != null) {
            return lineBasedDecoder.decode(ctx, buffer); // 快速路径
        }
        // 尝试所有分隔符，选择产出最短帧的
        int minFrameLength = Integer.MAX_VALUE;
        ByteBuf minDelim = null;
        for (ByteBuf delim : delimiters) {
            int frameLength = indexOf(buffer, delim);
            if (frameLength >= 0 && frameLength < minFrameLength) {
                minFrameLength = frameLength;
                minDelim = delim;
            }
        }

        if (minDelim != null) {
            int minDelimLength = minDelim.capacity();

            if (discardingTooLongFrame) {
                discardingTooLongFrame = false;
                buffer.skipBytes(minFrameLength + minDelimLength);
                return null;
            }

            if (minFrameLength > maxFrameLength) {
                buffer.skipBytes(minFrameLength + minDelimLength);
                fail(minFrameLength);
                return null;
            }

            if (stripDelimiter) {
                frame = buffer.readRetainedSlice(minFrameLength);
                buffer.skipBytes(minDelimLength);
            } else {
                frame = buffer.readRetainedSlice(minFrameLength + minDelimLength);
            }
            return frame;
        } else {
            // 未找到任何分隔符
            if (!discardingTooLongFrame) {
                if (buffer.readableBytes() > maxFrameLength) {
                    tooLongFrameLength = buffer.readableBytes();
                    buffer.skipBytes(buffer.readableBytes());
                    discardingTooLongFrame = true;
                    if (failFast) { fail(tooLongFrameLength); }
                }
            } else {
                tooLongFrameLength += buffer.readableBytes();
                buffer.skipBytes(buffer.readableBytes());
            }
            return null;
        }
    }

    private static boolean isLineBased(final ByteBuf[] delimiters) {
        if (delimiters.length != 2) {
            return false;
        }
        ByteBuf a = delimiters[0];
        ByteBuf b = delimiters[1];
        if (a.capacity() < b.capacity()) { a = delimiters[1]; b = delimiters[0]; }
        return a.capacity() == 2 && b.capacity() == 1
                && a.getByte(0) == '\r' && a.getByte(1) == '\n'
                && b.getByte(0) == '\n';
    }
}
```

**设计亮点**：

1. **isLineBased 特例优化**：当检测到分隔符恰好是 `\n` 和 `\r\n` 时，直接委托给 `LineBasedFrameDecoder`。为什么？因为 LineBasedFrameDecoder 有 offset 搜索优化，性能更好。这是一种"特例快速路径"的常见优化手法。

2. **最短帧选择策略**：当存在多个分隔符时，选择使得帧最短的那个。为什么？因为如果选择了产出更长帧的分隔符，可能会把"不属于这一帧的数据"错误地包含在帧内。

#### 使用示例

```java
// 以 "$_" 作为分隔符
ByteBuf delimiter = Unpooled.copiedBuffer("$_", CharsetUtil.UTF_8);
ch.pipeline().addLast(new DelimiterBasedFrameDecoder(1024, delimiter));
ch.pipeline().addLast(new StringDecoder());
ch.pipeline().addLast(new MyHandler());
```

### 7.4 LengthFieldBasedFrameDecoder——长度字段解码器（最通用！）

#### 解决什么问题

大量私有协议采用"TLV"（Type-Length-Value）或"LV"（Length-Value）格式：在消息头中用固定字节数表示后续消息体的长度。LengthFieldBasedFrameDecoder 是 Netty 提供的**最通用的帧解码器**，通过四个参数组合，可以适配几乎所有基于长度字段的二进制协议。

#### 四个核心参数详解

```
+------+--------------+----------+--------------+
| HDR1 | Length Field  |   HDR2   |   Payload    |
|      |              |          |              |
|<---->|<------------>|<-------->|<------------>|
|offset|  fieldLen    |adjustment|              |
+------+--------------+----------+--------------+
```

| 参数 | 含义 | 默认值 |
|------|------|--------|
| `lengthFieldOffset` | 长度字段相对于帧起始位置的偏移量 | 0 |
| `lengthFieldLength` | 长度字段本身占用的字节数（1/2/3/4/8） | - |
| `lengthAdjustment` | 对长度字段值的补偿值 | 0 |
| `initialBytesToStrip` | 解码后从帧前部剥离的字节数 | 0 |

**帧长度计算公式**：

```
实际帧长度 = lengthFieldValue + lengthAdjustment + lengthFieldEndOffset
其中 lengthFieldEndOffset = lengthFieldOffset + lengthFieldLength
```

#### 参数组合示例

**示例 1：最简单的 Length + Body**
```

lengthFieldLength   = 2
lengthAdjustment    = 0
initialBytesToStrip = 0

BEFORE DECODE (14 bytes)         AFTER DECODE (14 bytes)
+--------+----------------+      +--------+----------------+
| Length | Actual Content |----->| Length | Actual Content |
| 0x000C | "HELLO, WORLD" |      | 0x000C | "HELLO, WORLD" |
+--------+----------------+      +--------+----------------+
```

**示例 2：Length + Body，剥离长度头**
```

lengthFieldLength   = 2
lengthAdjustment    = 0
initialBytesToStrip = 2 (剥离 Length 字段)

BEFORE DECODE (14 bytes)         AFTER DECODE (12 bytes)
+--------+----------------+      +----------------+
| Length | Actual Content |----->| Actual Content |
| 0x000C | "HELLO, WORLD" |      | "HELLO, WORLD" |
+--------+----------------+      +----------------+
```

**示例 3：Length 表示整包长度（包含自身）**
```

lengthFieldLength   =  2

BEFORE DECODE (14 bytes)         AFTER DECODE (14 bytes)
+--------+----------------+      +--------+----------------+
| Length | Actual Content |----->| Length | Actual Content |
```

```
BEFORE DECODE (17 bytes)                      AFTER DECODE (17 bytes)
```

```
+------+--------+------+----------------+      +------+----------------+
```

#### 核心源码

```java
protected Object decode(ChannelHandlerContext ctx, ByteBuf in) throws Exception {
    long frameLength = 0;
    if (frameLengthInt == -1) { // ===== 第一阶段：读取长度字段 =====

        if (discardingTooLongFrame) {
            discardingTooLongFrame(in);
        }

        // 数据不够连长度字段都读不出来
        if (in.readableBytes() < lengthFieldEndOffset) {
            return null;
        }

        // 从指定偏移位置读取长度值
        int actualLengthFieldOffset = in.readerIndex() + lengthFieldOffset;
        frameLength = getUnadjustedFrameLength(in, actualLengthFieldOffset,
                lengthFieldLength, byteOrder);

        if (frameLength < 0) {
            failOnNegativeLengthField(in, frameLength, lengthFieldEndOffset);
        }

        // 应用帧长公式
        frameLength += lengthAdjustment + lengthFieldEndOffset;

        if (frameLength < lengthFieldEndOffset) {
            failOnFrameLengthLessThanLengthFieldEndOffset(in, frameLength, lengthFieldEndOffset);
        }

        if (frameLength > maxFrameLength) {
            exceededFrameLength(in, frameLength);
            return null;
        }

        frameLengthInt = (int) frameLength; // 缓存计算结果
    }

    // ===== 第二阶段：等待完整帧数据 =====
    if (in.readableBytes() < frameLengthInt) {
        return null; // 数据还不够，等待更多
    }

    // 剥离前部字节
    if (initialBytesToStrip > frameLengthInt) {
        failOnFrameLengthLessThanInitialBytesToStrip(in, frameLength, initialBytesToStrip);
    }
    in.skipBytes(initialBytesToStrip);

    // 提取帧
    int readerIndex = in.readerIndex();
    int actualFrameLength = frameLengthInt - initialBytesToStrip;
    ByteBuf frame = extractFrame(ctx, in, readerIndex, actualFrameLength);
    in.readerIndex(readerIndex + actualFrameLength);
    frameLengthInt = -1; // 重置状态，准备解码下一帧
    return frame;
}

protected long getUnadjustedFrameLength(ByteBuf buf, int offset, int length, ByteOrder order) {
    buf = buf.order(order);
    long frameLength;
    switch (length) {
        case 1: frameLength = buf.getUnsignedByte(offset);   break;
        case 2: frameLength = buf.getUnsignedShort(offset);  break;
        case 3: frameLength = buf.getUnsignedMedium(offset); break;
        case 4: frameLength = buf.getUnsignedInt(offset);    break;
        case 8: frameLength = buf.getLong(offset);            break;
        default: throw new DecoderException(
                "unsupported lengthFieldLength: " + lengthFieldLength);
    }
    return frameLength;
}
```

**两阶段解码设计**：

为什么要分两个阶段？`frameLengthInt` 作为缓存字段起了关键作用：

```
第一阶段：                        第二阶段：
+------------------------+        +------------------------+
| 够读长度字段吗？         |        | 够读完整帧吗？          |
|   否 -> return null    |        |   否 -> return null    |
|   是 -> 读取并缓存到    |        |   是 -> 提取帧返回      |
|        frameLengthInt  |        |                        |
+------------------------+        +------------------------+
```

当第一阶段完成但数据不够整帧时（`readableBytes < frameLengthInt`），直接返回 null。下次 channelRead 进入时，`frameLengthInt != -1`，跳过第一阶段直接进入第二阶段。这避免了重复计算帧长度。

#### 使用示例

```java
// 典型的 Header(2) + Length(4) + Body 协议
// Length 字段值表示 Body 长度
ch.pipeline().addLast(new LengthFieldBasedFrameDecoder(
    65535,   // maxFrameLength
    2,       // lengthFieldOffset（跳过 2 字节 Header）
    4,       // lengthFieldLength
    0,       // lengthAdjustment
    6        // initialBytesToStrip（剥离 Header + Length）
));
ch.pipeline().addLast(new MyProtocolDecoder());
```

## 八、LengthFieldPrepender 编码器

LengthFieldPrepender 是 LengthFieldBasedFrameDecoder 的"镜像"——它在发送时为消息添加长度前缀。

### 8.1 源码解析

```java
@Sharable
public class LengthFieldPrepender extends MessageToMessageEncoder<ByteBuf> {

    private final ByteOrder byteOrder;
    private final int lengthFieldLength;
    private final boolean lengthIncludesLengthFieldLength;
    private final int lengthAdjustment;

    @Override
    protected void encode(ChannelHandlerContext ctx, ByteBuf msg, List<Object> out)
            throws Exception {
        int length = msg.readableBytes() + lengthAdjustment;
        if (lengthIncludesLengthFieldLength) {
            length += lengthFieldLength; // 长度值是否包含长度字段本身
        }

        checkPositiveOrZero(length, "length");

        switch (lengthFieldLength) {
            case 1:
                if (length >= 256) {
                    throw new IllegalArgumentException(
                            "length does not fit into a byte: " + length);
                }
                out.add(ctx.alloc().buffer(1).order(byteOrder).writeByte((byte) length));
                break;
            case 2:
                if (length >= 65536) {
                    throw new IllegalArgumentException(
                            "length does not fit into a short integer: " + length);
                }
                out.add(ctx.alloc().buffer(2).order(byteOrder).writeShort((short) length));
                break;
            case 3:
                if (length >= 16777216) {
                    throw new IllegalArgumentException(
                            "length does not fit into a medium integer: " + length);
                }
                out.add(ctx.alloc().buffer(3).order(byteOrder).writeMedium(length));
                break;
            case 4:
                out.add(ctx.alloc().buffer(4).order(byteOrder).writeInt(length));
                break;
            case 8:
                out.add(ctx.alloc().buffer(8).order(byteOrder).writeLong(length));
                break;
            default:
                throw new Error("Unexpected length field length: " + lengthFieldLength);
        }
        out.add(msg.retain()); // 保留原始消息的引用
    }
}
```

### 8.2 关键设计点

1. **产出两个对象**：encode 方法向 `out` 中添加了两个 ByteBuf——长度字段和原始消息体。这就是 `MessageToMessageEncoder` 支持多产出的典型场景。底层会用 `PromiseCombiner` 将两次写入聚合为一次 promise 回调。

2. **msg.retain()**：原始消息会被 `MessageToMessageEncoder` 的框架代码 release，所以这里必须 `retain()` 一次来保持消息有效。

3. **@Sharable**：LengthFieldPrepender 没有任何可变实例状态（所有字段都是 final 的），因此可以安全地在多个 Channel 之间共享。

4. **lengthIncludesLengthFieldLength**：某些协议的 Length 字段表示"包含自身在内的总长度"，设置此标志后会自动加上 lengthFieldLength 的字节数。

```
不包含时（默认）：Length = body.readableBytes() + lengthAdjustment
+--------+----------------+
| 0x000C | "HELLO, WORLD" |  <-- Length=12 只算 Body
+--------+----------------+

包含时：Length = body.readableBytes() + lengthAdjustment + lengthFieldLength
+--------+----------------+
| 0x000E | "HELLO, WORLD" |  <-- Length=14 算上自身2字节
+--------+----------------+
```

### 8.3 与 LengthFieldBasedFrameDecoder 的配合

```
编码方向（出站）：                        解码方向（入站）：
LengthFieldPrepender                   LengthFieldBasedFrameDecoder

原始消息                                收到的字节流
+----------------+                     +--------+----------------+
| "HELLO, WORLD" |                     | 0x000C | "HELLO, WORLD" |
+----------------+                     +--------+----------------+
        |                                        |
        v encode()                               v decode()
+--------+----------------+            +----------------+
| 0x000C | "HELLO, WORLD" |            | "HELLO, WORLD" |
+--------+----------------+            +----------------+
```

典型配置：

```java
// 服务端/客户端通用 Pipeline 配置
pipeline.addLast(new LengthFieldBasedFrameDecoder(65535, 0, 4, 0, 4));
pipeline.addLast(new LengthFieldPrepender(4));
pipeline.addLast(new BusinessHandler());
```

## 九、设计哲学：累积器模式的优越性

### 9.1 为什么不"等数据齐了再通知"？

一种看似更简单的设计是：底层 NIO 收到数据后，先不通知上层，等凑够一个完整帧再回调。这种方式存在严重问题：

**问题一：底层无法知道"多少数据才够"**。帧的边界信息（固定长度、分隔符、长度字段）是应用层协议的语义，NIO 层无从知晓。如果让 NIO 层来判断，就会导致传输层和应用层的耦合。

**问题二：数据在内核缓冲区堆积**。如果不及时从 Socket 读取数据，内核的 TCP 接收缓冲区会被填满，导致 TCP 窗口缩小，甚至触发零窗口探测，严重影响网络吞吐量。

**问题三：无法支持多种协议共存**。同一个 EventLoop 管理着多种协议的 Channel，不可能为每种协议定制不同的"等待策略"。

### 9.2 累积器模式的优势

Netty 的累积器模式遵循"尽快读取、逐步解码"的原则：

```
时刻 T1: 内核有数据 -> channelRead -> cumulate 累积 -> callDecode 尝试解码
                                                    -> 数据不够，返回
时刻 T2: 内核有数据 -> channelRead -> cumulate 追加 -> callDecode 再次尝试
                                                    -> 数据够了，产出帧
                                                    -> 继续循环，看剩余数据能否再产出
```

这种设计的优势：

1. **解耦彻底**：传输层只负责"读数据"，协议层只负责"判边界"，职责清晰。
2. **内存可控**：cumulation 是用户态的 ByteBuf，其生命周期完全由框架管理，可以选择合适时机 discard 已读数据。
3. **吞吐量最优**：尽快从内核读取数据，保持 TCP 接收窗口大小，不会反压对端。
4. **灵活组合**：同一套机制支持所有拆包策略（定长、分隔符、长度字段），只需替换 decode() 实现。
5. **零拷贝可选**：通过 COMPOSITE_CUMULATOR 可以避免数据拷贝，对大包场景特别友好。

### 9.3 discardAfterReads 的平衡之道

累积器模式的一个潜在问题是 cumulation 不断增长导致 OOM。Netty 通过 `discardAfterReads=16` 的阈值策略来平衡：

- **不是每次都 discard**：频繁的 `discardSomeReadBytes()` 会导致内存拷贝（把未读数据往前移动），影响性能。
- **不是永不 discard**：如果一直不释放已读空间，cumulation 会无限增长。
- **选择 16 次**：经验值，既不会太频繁拷贝，又能及时回收内存。
- **只在 refCnt==1 时才 discard**：如果用户通过 slice/retain 持有了 cumulation 的引用，discard 会破坏那些引用。

## 十、本篇涉及的设计模式

**模板方法模式（Template Method）**：ByteToMessageDecoder 定义了完整的解码算法骨架（channelRead -> cumulate -> callDecode -> 循环调用 decode），子类只需实现 `decode()` 方法。这是整个编解码器框架最核心的设计模式，将"如何管理累积缓冲区"的复杂性封装在父类中，子类只关注"如何识别帧边界"的纯业务逻辑。

**策略模式（Strategy）**：Cumulator 接口抽象了"如何合并新数据到累积缓冲区"的策略。MERGE_CUMULATOR 使用内存拷贝，COMPOSITE_CUMULATOR 使用零拷贝的 CompositeByteBuf。用户可以通过 `setCumulator()` 在运行时切换策略，无需修改解码逻辑。

**委托模式（Delegation）**：ByteToMessageCodec 内部持有一个匿名的 ByteToMessageDecoder 实例和一个 Encoder 实例，将 channelRead 委托给 decoder，将 write 委托给 encoder。CombinedChannelDuplexHandler 更进一步，通过 DelegatingChannelHandlerContext 代理上下文，使得任意 InboundHandler 和 OutboundHandler 可以组合成一个 DuplexHandler。

**状态模式（State）**：LineBasedFrameDecoder 和 LengthFieldBasedFrameDecoder 都采用了显式的状态机设计。LineBasedFrameDecoder 有 `discarding` 标志区分正常模式和丢弃模式；LengthFieldBasedFrameDecoder 有 `discardingTooLongFrame` 和 `frameLengthInt` 实现两阶段解码（解析长度字段 -> 等待完整帧体）。

**享元模式（Flyweight）**：CodecOutputList 使用 ThreadLocal 的 recycler 池化，避免每次 channelRead 都创建新的 List 对象。EMPTY_BUFFER 作为全局共享的空缓冲区，避免重复分配。

**组合模式（Composite）**：COMPOSITE_CUMULATOR 利用 CompositeByteBuf 将多个 ByteBuf 组合成逻辑上的单一缓冲区，对外提供统一的 ByteBuf 接口，内部避免数据拷贝。

## 十一、本篇涉及的高性能并发技术

**无锁单线程模型**：ByteToMessageDecoder 的所有状态（cumulation、numReads、decodeState、discarding 等）都是非 volatile 的普通字段。这是因为 Netty 保证同一个 Channel 的所有 I/O 事件在同一个 EventLoop 线程中执行，无需同步。这种设计将线程安全的保证从"锁/CAS"提升到了"架构层面的线程隔离"，性能开销为零。

**重入检测与防护**：channelRead 中通过 `decodeState` 状态字段和 `inputMessages` 队列实现重入保护。当 decode() 内部触发了新的 channelRead（例如通过 fireChannelRead 传播后又回到同一个 handler），新消息不会立即处理，而是入队等待当前循环结束后处理。这避免了栈溢出和状态混乱，同时不需要任何锁机制。

**内存拷贝最小化**：MERGE_CUMULATOR 在 cumulation 有足够 writable 空间时直接 writeBytes 追加（无需分配新 buffer）；cumulation 不可读时直接替换为 in（零分配）；expandCumulation 使用 setBytes 而非 writeBytes 避免额外的边界检查。COMPOSITE_CUMULATOR 通过 addFlattenedComponents 实现完全零拷贝。

**对象池化与回收**：CodecOutputList 是线程本地缓存的列表对象，通过 `newInstance()` 从池中获取，通过 `recycle()` 归还。这种 ThreadLocal recycler 模式避免了 GC 压力，对于每次 channelRead 都需要创建临时列表的场景效果显著。

**延迟内存回收（discardSomeReadBytes）**：不在每次解码后立即压缩 cumulation，而是累积 16 次读取后才执行一次 discardSomeReadBytes。这是典型的"批量化"优化思想——用少量的内存浪费换取显著的 CPU 时间节省（减少 memmove 调用）。

**引用计数精确管理**：整个编解码流程中严格遵循"谁创建谁释放"原则。MERGE_CUMULATOR 在 finally 中释放 in；decode 产出的帧 retain 后加入 out；channelRead finally 中检查 cumulation 是否可读来决定释放或保留。每个分支都有明确的释放路径，既避免内存泄漏又避免 use-after-free。

**选择性零拷贝**：readRetainedSlice 而非 readBytes 来产出帧，产生的是 cumulation 的切片视图（共享底层内存），避免了帧数据的拷贝。只有当帧数据需要跨越 cumulation 的 discard 周期存活时，上层业务才需要额外 copy。

**两阶段解码优化（LengthFieldBasedFrameDecoder）**：通过 `frameLengthInt` 字段缓存已解析的帧长度，当一次 channelRead 收到的数据不足以构成完整帧时，下次进入 decode 无需重新解析长度字段，直接比较 readableBytes() 与 frameLengthInt。这对高频小包场景能减少重复的字节序转换开销。
