# 操作符实现模式：Reactor 的操作符到底是怎么工作的？

> **Reactor Core 源码解析 · 易懂版 02**
>
> 本篇用"流水线"类比，从你最常用的 `map` 和 `filter` 操作符入手，拆解 Reactor 操作符的内部实现模式。看完这篇，你会知道每个操作符都是由哪些"零件"组成的，以及为什么 Reactor 的操作符能做到既高性能又线程安全。

---

## 开场：把操作符想象成流水线上的工位

假设你在 WebFlux 项目中写了这样一段代码：

```java
@GetMapping("/products")
public Flux<ProductVO> getProducts() {
    return productRepository.findAll()          // 从数据库查出所有商品
        .map(product -> convertToVO(product))    // 转成 VO 对象
        .filter(vo -> vo.getPrice() > 0)         // 过滤掉价格为 0 的
        .take(10);                               // 只取前 10 个
}
```

这条链上有三个操作符：`map`、`filter`、`take`。每一个操作符就像流水线上的一个工位：

```
[数据库查询] ──→ [map 工位：转 VO] ──→ [filter 工位：检查价格] ──→ [take 工位：限制数量] ──→ [最终消费者]
```

**关键认知：每个工位不改变"原材料"，而是把原材料包装一层再传给下一个工位。**

什么意思？当你调用 `.map(product -> convertToVO(product))` 时，原来的 `Flux<Product>` 没有被修改——Reactor 创建了一个新的 `FluxMap` 对象，它里面有一个 `source` 指针指向原来的 Flux。就像工厂不会改造已有的传送带，而是在后面接一段新的传送带。

**你可能会问：那什么时候数据才真正开始流动？这些工位什么时候"通电"？**

答案是：调用 `subscribe()` 的时候（在 WebFlux 中，框架帮你调了）。在此之前，你只是在搭建流水线而已。

---

## 操作符的四大要素：每个工位都由什么组成？

不管是 `map`、`filter`、`flatMap` 还是 `publishOn`，Reactor 的每个操作符都遵循同一套"四大要素"模板：

| 要素 | 做什么 | 流水线类比 |
|------|--------|-----------|
| **构造器** | 保存上游引用（source）和业务参数（mapper/predicate 等） | 搭建工位、安装工具 |
| **subscribeOrReturn** | 创建"内部 Subscriber"来包装下游 | 给这个工位分配工人 |
| **内部 Subscriber** | 持有上下游的双向引用，处理数据的核心逻辑 | 工人本人——既从上一个工位接活，也把成品传给下一个工位 |
| **request/cancel 委托** | 将背压信号传给上游 | 工人跟上一个工位沟通"再给我几个零件"或"停工" |

下面我们以 `FluxMap` 为典范，把这四大要素逐一拆解。

---

## FluxMap：用最简单的操作符看懂全部模式

为什么选 `FluxMap`？因为它足够简单（一个输入对应一个输出），却包含了操作符实现的所有核心要素。看懂了它，你就能看懂 Reactor 里 90% 的操作符。

### 要素一：构造器 —— "搭工位"

当你写 `flux.map(product -> convertToVO(product))` 时，Reactor 内部创建了一个 `FluxMap` 对象：

```java
final class FluxMap<T, R> extends InternalFluxOperator<T, R> {

    final Function<? super T, ? extends R> mapper;

    FluxMap(Flux<? extends T> source, Function<? super T, ? extends R> mapper) {
        super(source);                                       // 保存上游引用
        this.mapper = Objects.requireNonNull(mapper, "mapper"); // 保存转换函数
    }
}
```

几个设计细节值得注意：

1. **类是 `final` 的** —— 禁止继承，这让 JVM 可以更积极地内联方法，提升性能。
2. **`mapper` 是 `final` 的** —— 不可变意味着线程安全。多个线程可以安全地共享同一个 `FluxMap` 实例。
3. **`mapper` 的泛型用了 PECS 原则** —— `Function<? super T, ? extends R>`，最大化泛型兼容性。

> 流水线类比：你在传送带后面接了一个新工位，工位上安装了一台"转换机器"（mapper）。但此时机器还没通电，没有工人，只是把设备安装好了。

### 要素二：subscribeOrReturn —— "分配工人"

当 `subscribe()` 触发时，优化循环会调用 `FluxMap.subscribeOrReturn`：

```java
@Override
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
    if (actual instanceof Fuseable.ConditionalSubscriber) {
        // 下游是 ConditionalSubscriber，创建优化版工人
        ConditionalSubscriber<? super R> cs = (ConditionalSubscriber<? super R>) actual;
        return new MapConditionalSubscriber<>(cs, mapper);
    }
    // 普通情况，创建标准版工人
    return new MapSubscriber<>(actual, mapper);
}
```

这里有一个分支判断：如果下游实现了 `ConditionalSubscriber` 接口，就创建优化版的 `MapConditionalSubscriber`。这个优化我们后面在讲 `filter` 时会详细讨论。

> 流水线类比：工头检查下一个工位的工人是什么类型。如果下一个工位的工人支持"试处理"（tryOnNext），就派一个能配合试处理的工人过来。否则派标准工人。

### 要素三：MapSubscriber —— "工人"的全部逻辑

这是操作符的核心——`MapSubscriber` 负责接收上游数据、执行转换、传给下游。它同时扮演了两个角色：

```
        上游的 Subscriber（接收数据）
              ▲
              │
        MapSubscriber
              │
              ▼
        下游的 Subscription（响应背压）
```

让我们看完整的简化源码，然后逐块分析：

```java
static final class MapSubscriber<T, R> implements InnerOperator<T, R> {

    final CoreSubscriber<? super R> actual;     // 下游 Subscriber
    final Function<? super T, ? extends R> mapper; // 转换函数

    boolean done;          // 终止标记
    Subscription s;        // 上游 Subscription

    MapSubscriber(CoreSubscriber<? super R> actual,
                  Function<? super T, ? extends R> mapper) {
        this.actual = actual;
        this.mapper = mapper;
    }

    @Override
    public void onSubscribe(Subscription s) {
        if (Operators.validate(this.s, s)) {
            this.s = s;
            actual.onSubscribe(this);  // 把自己作为 Subscription 传给下游
        }
    }

    @Override
    public void onNext(T t) {
        if (done) {
            Operators.onNextDropped(t, actual.currentContext());
            return;
        }

        R v;
        try {
            v = mapper.apply(t);
            if (v == null) {
                throw new NullPointerException("The mapper returned a null value.");
            }
        } catch (Throwable e) {
            Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
            if (e_ != null) {
                onError(e_);
            } else {
                s.request(1);  // 错误被消化了（如 onErrorContinue），继续请求下一个
            }
            return;
        }

        actual.onNext(v);  // 把转换后的值传给下游
    }

    @Override
    public void onError(Throwable t) {
        if (done) {
            Operators.onErrorDropped(t, actual.currentContext());
            return;
        }
        done = true;
        actual.onError(t);
    }

    @Override
    public void onComplete() {
        if (done) return;
        done = true;
        actual.onComplete();
    }

    @Override
    public void request(long n) {
        s.request(n);  // 直接透传给上游
    }

    @Override
    public void cancel() {
        s.cancel();    // 直接透传给上游
    }

    @Override
    public CoreSubscriber<? super R> actual() {
        return actual;
    }
}
```

下面我们逐块深入分析。

#### actual 和 s：双向引用

```java
final CoreSubscriber<? super R> actual;  // 指向下游
Subscription s;                          // 指向上游
```

`actual` 是 `final` 的——创建后不变。`s` 不是 `final`——它在 `onSubscribe` 时才被赋值。

这两个引用构成了 MapSubscriber 在操作符链中的"位置"：

```
上游 ──onNext──→ MapSubscriber ──onNext──→ actual（下游）
上游 ←──request── MapSubscriber ←──request── actual（下游）
```

数据从左往右流，背压信号从右往左传。MapSubscriber 就是中间的"中间人"。

#### onSubscribe：建立连接

```java
public void onSubscribe(Subscription s) {
    if (Operators.validate(this.s, s)) {  // 检查是否重复订阅
        this.s = s;                        // 记住上游 Subscription
        actual.onSubscribe(this);          // 把自己作为 Subscription 传给下游
    }
}
```

**为什么把 `this` 传给下游，而不是直接传 `s`（上游的 Subscription）？**

因为 MapSubscriber 需要拦截下游的 `request`/`cancel` 调用。虽然在 `FluxMap` 这个简单场景中，`request` 和 `cancel` 只是原样透传，但更复杂的操作符（如 `FluxBuffer`、`FluxPublishOn`）需要在 `request` 中做额外逻辑。统一用 `this` 是保持一致性的设计选择。

#### onNext：核心转换逻辑

```java
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    R v;
    try {
        v = mapper.apply(t);     // 执行你写的转换函数
        if (v == null) {
            throw new NullPointerException("...");
        }
    } catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            onError(e_);         // 终止流
        } else {
            s.request(1);        // 错误被消化，继续处理下一个
        }
        return;
    }

    actual.onNext(v);            // 传给下游
}
```

这段代码有几个重要的设计：

**1. done 检查** —— 如果流已经终止（收到过 onError 或 onComplete），后续的 onNext 被丢弃。这是防御性编程——规范不允许终止后再发数据，但万一上游有 bug 呢？

**2. null 检查** —— Reactive Streams 规范禁止 null 元素，Reactor 在这里强制执行。如果你的 mapper 返回了 null，直接抛 NPE。

⚠️ **踩坑提醒**：很多新手会在 `map` 里不小心返回 null（比如从 Map 中 get 一个不存在的 key），导致流意外终止。如果你的转换可能返回 null，应该用 `flatMap` + `Mono.justOrEmpty()` 来安全处理。

**3. Operators.onNextError** —— 当 mapper 抛异常时，这个方法决定如何处理：
- 返回非 null 的 Throwable → 调用 `onError` 终止流
- 返回 null → 错误被 `onErrorContinue` 等策略消化了，`s.request(1)` 请求下一个元素继续

**4. actual.onNext(v)** —— 把转换后的值传给下游。

#### done 标记为什么不是 volatile？

`done` 是一个普通的 `boolean`，没有 `volatile` 修饰。

**你可能会问：这不会有线程安全问题吗？**

不会。因为 Reactive Streams 规范保证了 `onNext`、`onError`、`onComplete` 之间的串行化——同一时刻最多只有一个线程调用这些方法。`done` 的可见性由规范的串行化保证来保障，不需要额外的内存屏障。

**去掉 done 检查会怎样？** 如果上游在发出 onError 后又错误地发出 onNext，mapper 可能抛异常，onError 被二次调用，下游收到两个终止信号——违反规范。done 是一道防火墙。

### 要素四：request 和 cancel —— "跟上游沟通"

```java
public void request(long n) {
    s.request(n);   // 原样透传
}

public void cancel() {
    s.cancel();     // 原样透传
}
```

`FluxMap` 是一对一的操作符——每消费一个输入恰好产生一个输出。所以下游请求 N 个，上游也恰好需要产生 N 个，直接透传就好。

**你可能会问：什么操作符不能直接透传 request？**

`FluxFilter` 就不行！当 filter 丢弃了一个不满足条件的元素时，它需要自己向上游额外 `request(1)` 来补偿。下面我们就来对比看看。

## InnerOperator 接口：为什么不直接实现 CoreSubscriber + Subscription？

上面的 `MapSubscriber` 实现了 `InnerOperator<T, R>` 接口。这个接口的继承链是：

```
         CoreSubscriber<I>    Subscription    Scannable
              │                    │              │
              ▼                    ▼              │
        InnerConsumer<I>    InnerProducer<O>      │
              │                    │              │
              └────────┬───────────┘              │
                       ▼                          │
              InnerOperator<I, O> ←───────────────┘
```

展开后，`InnerOperator` = `CoreSubscriber<I>` + `Subscription` + `Scannable`。也就是说 MapSubscriber 同时是：
- **上游的 Subscriber**：接收 onSubscribe、onNext、onError、onComplete
- **下游的 Subscription**：响应 request(n) 和 cancel()

**你可能会问：为什么不直接实现 CoreSubscriber 和 Subscription 两个接口，要搞这么多层？**

因为 `InnerOperator` 提供了几个有用的默认实现：

**1. currentContext() 的自动委托：**

```java
// InnerOperator.java
default Context currentContext() {
    CoreSubscriber<? super O> actual = actual();
    return actual.currentContext();  // 自动委托给下游
}
```

这就是 Context 沿着订阅链向上传播的机制——当上游需要 Context（比如获取 Trace ID）时，调用 `currentContext()`，这个调用沿着 `actual` 引用链一路传到最终消费者。

如果没有这个默认实现，每个操作符的内部 Subscriber 都得手写一遍 `currentContext()` 的委托逻辑。

**2. scanUnsafe 中的默认实现：**

```java
// InnerProducer.java
default Object scanUnsafe(Attr key) {
    if (key == Attr.ACTUAL) return actual();  // 用于调试链的扫描
    if (key == InternalProducerAttr.INSTANCE) return true;
    return null;
}
```

**3. 角色分离：** `InnerConsumer`（纯消费者）、`InnerProducer`（纯生产者）、`InnerOperator`（既消费又生产）——不是所有参与者都需要同时扮演两个角色。比如 `FluxArray.ArraySubscription` 只是一个生产者（Subscription），不需要实现 onNext/onError 等消费方法。

## FluxFilter：对比看"不能透传 request"的操作符

### subscribeOrReturn 几乎一样

```java
// FluxFilter.subscribeOrReturn
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    if (actual instanceof ConditionalSubscriber) {
        return new FilterConditionalSubscriber<>((ConditionalSubscriber<? super T>) actual, predicate);
    }
    return new FilterSubscriber<>(actual, predicate);
}
```

结构与 `FluxMap.subscribeOrReturn` 完全相同——检查 `ConditionalSubscriber`，然后选择创建哪种内部 Subscriber。这就是"四大要素"模式的一致性。

### onNext 的关键差异

```java
// FilterSubscriber.onNext
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, this.ctx);
        return;
    }

    boolean b;
    try {
        b = predicate.test(t);  // 执行你写的过滤条件
    } catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, this.ctx, s);
        if (e_ != null) onError(e_);
        else s.request(1);
        Operators.onDiscard(t, this.ctx);  // 通知丢弃钩子
        return;
    }

    if (b) {
        actual.onNext(t);              // 通过！传给下游
    } else {
        Operators.onDiscard(t, this.ctx); // 不通过，通知丢弃
        s.request(1);                    // 向上游补偿请求
    }
}
```

与 MapSubscriber.onNext 相比，有四个核心差异：

**差异一：条件分支。** map 无条件转发（输入一个必定输出一个），filter 根据 predicate 的结果决定是否转发。

**差异二：背压补偿。** 当元素被过滤掉时（`b == false`），filter 调用 `s.request(1)` 向上游补偿。

> 为什么要补偿？下游说"给我 10 个"，filter 收到第一个发现不满足条件，丢掉了。如果不补偿，上游以为已经"消耗"了一个配额，最终下游只能收到 9 个。`request(1)` 就是告诉上游"刚才那个不算，再给我一个"。

**差异三：Discard 处理。** 被丢弃的元素通过 `Operators.onDiscard(t, ctx)` 通知。如果你注册了 discard hook（比如用于释放 pooled ByteBuf），这里会触发资源回收。

⚠️ **踩坑提醒**：在使用 Netty 的 ByteBuf 时，如果 filter 过滤掉了某些数据包，没有 discard hook 来释放 ByteBuf 就会导致内存泄漏。Reactor 的 discard 机制就是为了解决这个问题。

**差异四：Context 缓存。** FilterSubscriber 在构造时缓存了 `this.ctx = actual.currentContext()`，而 MapSubscriber 每次调用 `actual.currentContext()`。因为 filter 的 onNext 中多处需要 Context（discard、onNextError），缓存避免了重复调用。

### FilterSubscriber 还额外实现了 ConditionalSubscriber

```java
static final class FilterSubscriber<T>
        implements InnerOperator<T, T>,
                   Fuseable.ConditionalSubscriber<T> {
    // ...
}
```

FilterSubscriber 不仅是 InnerOperator，还是 ConditionalSubscriber。这为 `tryOnNext` 优化铺平了道路——接下来我们详细讲这个。

---

## ConditionalSubscriber 和 tryOnNext：连续多个 filter 的性能优化

### 问题场景

考虑连续三个 filter：

```java
source.filter(p1).filter(p2).filter(p3)
```

当一个元素通过了 p1 但被 p2 拒绝时：

**没有 tryOnNext 优化时：**
```
source 发出元素 x
  → FilterSubscriber1.onNext(x)
    → p1.test(x) = true → 通过！
    → actual.onNext(x)
      → FilterSubscriber2.onNext(x)
        → p2.test(x) = false → 不通过！
        → s.request(1)        ← 补偿请求穿越整条链回到源头
          → FilterSubscriber1.request(1) → source.request(1)
```

每次 filter 丢弃一个元素，都会触发一次 `request(1)`，这个调用需要穿越所有中间操作符。对于连续多个 filter，开销不小。

**有 tryOnNext 优化时：**
```
source 发出元素 x
  → FilterSubscriber1.tryOnNext(x)    // 注意是 tryOnNext！
    → p1.test(x) = true → 通过！
    → actual.tryOnNext(x)              // 继续用 tryOnNext
      → FilterSubscriber2.tryOnNext(x)
        → p2.test(x) = false → 不通过！
        → return false                 // 只返回 false，不调用 request(1)
      ← FilterSubscriber1 收到 false
    // 上游自己处理补偿，不需要额外的 request(1)！
```

`tryOnNext` 返回 `boolean`——`true` 表示"这个元素我消费了"，`false` 表示"我没消费"。源头的循环可以根据返回值自动调整计数器，不需要额外的 `request` 调用。

> 流水线类比：原来的方式是"质检员发现不合格品，打电话通知仓库再送一个过来"。tryOnNext 方式是"质检员在传送带边上站着，不合格品直接推到一边，传送带不停，下一个自动来了"。不需要打电话（request 调用），效率更高。

### MapConditionalSubscriber 的 tryOnNext

```java
// FluxMap.MapConditionalSubscriber.tryOnNext
public boolean tryOnNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return true;   // done 状态下返回 true（算作消费了）
    }

    R v;
    try {
        v = mapper.apply(t);
        if (v == null) throw new NullPointerException("...");
        return actual.tryOnNext(v);  // 委托给下游的 tryOnNext，布尔值原样返回
    } catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            done = true;
            actual.onError(e_);
            return true;   // 错误终止，算作消费了
        } else {
            return false;  // 错误被消化，没有消费
        }
    }
}
```

map 的 `tryOnNext` 只是在普通 `onNext` 的基础上加了返回值——把下游 `actual.tryOnNext(v)` 的布尔结果原样返回。

### FilterSubscriber 的 tryOnNext

```java
// FluxFilter.FilterSubscriber.tryOnNext
public boolean tryOnNext(T t) {
    if (done) {
        Operators.onNextDropped(t, this.ctx);
        return false;
    }

    boolean b;
    try {
        b = predicate.test(t);
    } catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, this.ctx, s);
        if (e_ != null) onError(e_);
        Operators.onDiscard(t, this.ctx);
        return false;
    }

    if (b) {
        actual.onNext(t);  // 通过，传给下游
    } else {
        Operators.onDiscard(t, this.ctx);
        // 注意：这里没有 s.request(1)！
    }
    return b;  // 通过返回 true，不通过返回 false
}
```

**关键区别**：在 `tryOnNext` 中，当 predicate 返回 false 时，filter **不调用 `s.request(1)`**。它只是返回 `false`，让上游知道"这个元素我没消费"。上游（比如 `ArrayConditionalSubscription.slowPath`）会根据返回值自动决定是否递减请求计数器。

这就是 `tryOnNext` 优化的本质：**把"补偿请求"的职责从 filter 转移给了源头，避免了中间操作符之间的 request 穿透。**

## MonoMap：Flux 和 Mono 之间的 Subscriber 复用

### 一个精巧的设计

来看 `MonoMap` 的完整源码：

```java
final class MonoMap<T, R> extends InternalMonoOperator<T, R> {

    final Function<? super T, ? extends R> mapper;

    MonoMap(Mono<? extends T> source, Function<? super T, ? extends R> mapper) {
        super(source);
        this.mapper = Objects.requireNonNull(mapper, "mapper");
    }

    @Override
    public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
        if (actual instanceof Fuseable.ConditionalSubscriber) {
            return new FluxMap.MapConditionalSubscriber<>(...);  // 复用 FluxMap 的！
        }
        return new FluxMap.MapSubscriber<>(actual, mapper);      // 复用 FluxMap 的！
    }
}
```

注意到了吗？`MonoMap.subscribeOrReturn` 直接复用了 `FluxMap.MapSubscriber` 和 `FluxMap.MapConditionalSubscriber`——没有创建任何新的内部类。

**你可能会问：Mono 和 Flux 不是两种不同的流吗？怎么能共用同一个 Subscriber？**

因为 `MapSubscriber` 的逻辑是"接收 T，用 mapper 转成 R，传给下游"——这个逻辑不关心上游是 Flux 还是 Mono。Subscriber 只关心信号（onNext、onError、onComplete），不关心源的基数约束。

**复用的好处：**
1. 减少类数量——少维护一个类就少一处潜在 bug。
2. 保证行为一致性——`Mono.map` 和 `Flux.map` 在 onNext 处理、错误处理、null 检查方面完全一样。

**什么时候不能复用？** 当 Mono 和 Flux 的操作符语义不同时。比如 `Mono.flatMap` 返回 `Mono`（1 → 1），`Flux.flatMap` 返回 `Flux`（N → M），它们的内部 Subscriber 有本质不同的并发控制逻辑，无法复用。

## 操作符的完整生命周期

把前面讲的内容串起来，一个操作符从创建到销毁的完整生命周期如下：

```
阶段 1：装配（你调用操作符方法时）
  flux.map(mapper)
    → 创建 FluxMap(source=flux, mapper=mapper)
    → 返回 FluxMap 实例
    → 此时无任何数据流动

阶段 2：订阅（subscribe 被调用时）
  while(true) 循环调用 FluxMap.subscribeOrReturn(下游Subscriber)
    → 创建 MapSubscriber(actual=下游Subscriber, mapper)
    → 循环继续到源头

阶段 3：连接（源头调用 onSubscribe 时）
  源头 → MapSubscriber.onSubscribe(上游Subscription)
    → 保存 this.s = 上游Subscription
    → 调用 actual.onSubscribe(this)  ← 把自己作为 Subscription 传给下游

阶段 4：请求（onSubscribe 之后触发）
  下游 → MapSubscriber.request(n) → 上游Subscription.request(n)
    → 上游开始发射数据

阶段 5：数据流动
  上游 → MapSubscriber.onNext(element)
    → mapper.apply(element) = mappedElement
    → actual.onNext(mappedElement) → 下游收到转换后的数据

阶段 6：终止
  上游 → MapSubscriber.onComplete()
    → done = true
    → actual.onComplete() → 下游收到完成信号
```

**一个关键洞察：操作符对象（FluxMap）是在装配阶段创建的，是不可变的；内部 Subscriber（MapSubscriber）是在订阅阶段创建的，持有可变状态。** 这种分离让同一个操作符对象可以被多次订阅——每次订阅创建新的内部 Subscriber，互不干扰。

> 流水线类比：工位（FluxMap）只需搭建一次，但每次生产新批次的产品时，都会安排新的工人（MapSubscriber）上岗。工位是固定资产，工人是按需分配的。

## 设计模式总结

回顾全文，Reactor 操作符的实现用到了几种经典的设计模式：

### 装饰器模式

每个操作符包装上游 Publisher（通过 source 字段），在订阅时创建内部 Subscriber 来包装下游 Subscriber（通过 actual 字段）。操作符本身不持有订阅状态——状态在内部 Subscriber 中。

### 中间人模式

内部 Subscriber（如 MapSubscriber）同时实现 CoreSubscriber 和 Subscription，充当上下游之间的中间人。上游通过 onNext 等方法推送数据，下游通过 request/cancel 发出背压信号。

### 策略模式

业务逻辑（mapper、predicate 等）通过构造器注入，以函数式接口的形式存在。框架代码（错误处理、done 检查、背压管理）是固定的模板，业务逻辑是可替换的策略。

### 类型安全的泛型链

操作符通过泛型参数 `<I, O>` 约束输入/输出类型。`FluxMap<T, R>` 消费 T 产出 R，`FluxFilter<T>` 消费 T 产出 T。编译器在装配阶段就能发现类型不匹配，不用等到运行时。

### 两阶段初始化

操作符对象在装配阶段创建（不可变），内部 Subscriber 在订阅阶段创建（可变状态）。分离让同一个操作符可被多次订阅——每次创建独立的 Subscriber。

## 归纳表格

### FluxMap vs FluxFilter vs MonoMap 对照表

| 维度 | FluxMap | FluxFilter | MonoMap |
|------|---------|-----------|---------|
| **继承基类** | InternalFluxOperator<T, R> | InternalFluxOperator<T, T> | InternalMonoOperator<T, R> |
| **业务参数** | `Function<? super T, ? extends R> mapper` | `Predicate<? super T> predicate` | `Function<? super T, ? extends R> mapper` |
| **内部 Subscriber** | MapSubscriber / MapConditionalSubscriber | FilterSubscriber / FilterConditionalSubscriber | 直接复用 FluxMap 的 |
| **onNext 行为** | 应用 mapper，null 检查，传给 actual | 应用 predicate，通过则传给 actual，不通过则 discard + request(1) | 同 FluxMap |
| **tryOnNext 行为** | 应用 mapper，委托 actual.tryOnNext，返回其结果 | 应用 predicate，通过返回 true，不通过返回 false（不 request） | 同 FluxMap |
| **request 行为** | 透传 s.request(n) | 透传 s.request(n) | 透传 s.request(n) |
| **背压补偿** | 不需要（一对一映射） | 需要（过滤掉元素时 request(1)） | 不需要 |
| **Discard 支持** | 不支持（mapper 总是产出） | 支持（过滤掉的元素触发 onDiscard） | 不支持 |
| **done 标记类型** | boolean（非 volatile） | boolean（非 volatile） | 复用 FluxMap 的 |
| **Context 获取** | 每次调 actual.currentContext() | 构造时缓存 this.ctx | 同 FluxMap |
| **额外实现的接口** | InnerOperator | InnerOperator + ConditionalSubscriber | 同 FluxMap |

### 操作符四大要素速查表

| 要素 | 职责 | 对应真实源码 | 生命阶段 |
|------|------|------------|---------|
| 构造器 | 存 source + 业务参数 | `FluxMap(Flux source, Function mapper)` | 装配时 |
| subscribeOrReturn | 创建内部 Subscriber | `new MapSubscriber(actual, mapper)` | 订阅时 |
| 内部 Subscriber | 双向中间人：接收上游数据 + 响应下游背压 | `MapSubscriber implements InnerOperator` | 订阅时创建，数据流动时工作 |
| request/cancel | 背压信号传递 | `s.request(n)` / `s.cancel()` | 运行时 |

理解了这四大要素的模式，你就掌握了阅读 Reactor 任何操作符源码的通用框架。不管是 `flatMap`、`publishOn`、`buffer` 还是 `window`，它们的骨架都是一样的——区别只在于 onNext 里的业务逻辑和 request 里的背压策略。
