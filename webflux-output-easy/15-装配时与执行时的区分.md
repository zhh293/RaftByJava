# 装配时与执行时的区分——Reactor 最关键的概念之一

> **Reactor Core 源码解析系列 · 第 15 篇（易懂版）**
>
> 用最通俗的方式理解 Reactor 的"画图纸"与"施工"——为什么你写的操作符链在定义时不执行，在 subscribe 时才执行？这个区分到底带来了什么好处？

---

## 一、从一个真实的"踩坑"说起

先看一段代码：

```java
// 同事写的"查询用户"逻辑
public Flux<User> getUsers() {
    return Flux.just(queryDb())
        .map(user -> user.toUpperCase());
}

private User queryDb() {
    System.out.println("正在查库...");
    return userRepository.findByName("张三");
}
```

你觉得这段代码什么时候会打印"正在查库..."？

很多人的第一反应是："当然是 subscribe 之后啊，Reactor 不是声明式的吗？"

但答案是：**在 `Flux.just(queryDb())` 这行被执行的时候，`queryDb()` 就已经被调用了。** 即使你根本没有 subscribe。

为什么？因为 `just()` 的参数是 Java 方法参数——在调用 `just()` 之前，Java 会先对 `queryDb()` 求值，把结果传给 `just()`。这跟 Reactor 的声明式没有关系，是 Java 语言本身的求值规则。

那怎么解决？用 `defer`：

```java
// 正确写法：用 defer 把查库推迟到 subscribe 时
public Flux<User> getUsers() {
    return Flux.defer(() -> Flux.just(queryDb()))
        .map(user -> user.toUpperCase());
}
```

`Flux.defer()` 接收的是一个 `Supplier`——一个 lambda 表达式。这个 lambda 不会在装配时执行，而是在 subscribe 时才被调用。这就是装配时与执行时区分的核心价值。

⚠️ **踩坑提醒**：这不是 Reactor 的 bug，而是 Java 方法参数的求值机制。凡是接受具体值（而非 Supplier）的工厂方法（如 `just`、`error`），都会在装配时求值。需要延迟求值时，用 `defer`、`fromCallable`、`fromSupplier` 等。

这个例子引出了本文要讲的核心主题：**装配时（Assembly Time）和执行时（Execution Time）的严格分离。** 这是理解 Reactor 的一切机制的基石。

## 二、画图纸 vs 施工：装配时和执行时到底在干什么

### 2.1 日常生活类比

想象你要建一条工厂流水线。你会分两步走：

1. **画图纸（装配时）**：你在图纸上画出"原材料进来 → 工位A加工 → 工位B筛选 → 工位C包装 → 成品出去"。这个阶段你只画图纸，不生产任何产品。图纸画完后可以复印多份，每份都可以拿去施工。
2. **施工（执行时）**：按图纸真正搭建流水线，接通电源，原材料开始流动，产品开始产出。

Reactor 的设计完全一样：

- **装配时**：你写 `flux.map(fn).filter(pred).flatMap(g)`，这就像画图纸——定义了一条数据处理流水线，但不生产任何数据。
- **执行时**：你调用 `flux.subscribe(subscriber)`，这就像按图纸施工——流水线通电，数据开始流动。

### 2.2 装配时具体发生了什么

当你写下面这行代码时：

```java
Flux<String> pipeline = Flux.range(1, 100)
    .map(i -> "item-" + i)
    .filter(s -> s.length() > 5);
```

装配时发生了什么？三件事：

1. `Flux.range(1, 100)` 创建了一个 `FluxRange` 对象——记住，此时没有任何数字被产出。
2. `.map(i -> "item-" + i)` 创建了一个 `FluxMap` 对象，它的构造器做了两件事：存上游 source 引用（FluxRange），存 mapper 函数（`i -> "item-" + i`）。
3. `.filter(s -> s.length() > 5)` 创建了一个 `FluxFilter` 对象，同样存了上游 source 引用（FluxMap）和 predicate 函数。

最终你得到一条链：`FluxFilter → FluxMap → FluxRange`。但整个过程中，**没有任何数据流动，没有任何 mapper 被调用，没有任何 predicate 被求值。**

对应到源码，每个操作符的基类 `FluxOperator` 非常简单：

```java
public abstract class FluxOperator<I, O> extends Flux<O> implements Scannable {
    protected final Flux<? extends I> source;

    protected FluxOperator(Flux<? extends I> source) {
        this.source = Objects.requireNonNull(source);
    }
}
```

构造器只做一件事：保存上游 source 的引用。具体的子类（如 `FluxMap`）会额外保存操作参数（如 mapper 函数）。仅此而已。

### 2.3 onAssembly：装配时的统一入口

每个内建操作符在构造完成后，都会经过 `Flux.onAssembly()` 方法。这个方法做两件事：

1. **检查全局 Hooks**：如果用户通过 `Hooks.onEachOperator()` 注册了全局拦截器，就对这个新创建的操作符应用拦截。这就像图纸审批——每画完一个工位，审批人员检查一下。
2. **检查调试模式**：如果开启了全局堆栈跟踪（`Hooks.onOperatorDebug()`），就创建一个 `AssemblySnapshot`（堆栈快照）并包装为 `FluxOnAssembly`。这就像在图纸上标注"这个工位是在哪个办公室、哪张桌子上画的"。

源码如下：

```java
protected static <T> Flux<T> onAssembly(Flux<T> source) {
    Function<Publisher, Publisher> hook = Hooks.onEachOperatorHook;
    if(hook != null) {
        source = (Flux<T>) hook.apply(source);
    }
    if (Hooks.GLOBAL_TRACE) {
        AssemblySnapshot stacktrace = new AssemblySnapshot(null, Traces.callSiteSupplierFactory.get());
        source = (Flux<T>) Hooks.addAssemblyInfo(source, stacktrace);
    }
    return source;
}
```

⚠️ **踩坑提醒**：`Hooks.onOperatorDebug()` 会在每次装配操作符时捕获堆栈，开销很大。生产环境不要开启，只在开发/调试时使用。如果只需要局部调试，用 `checkpoint()` 代替。

### 2.4 执行时具体发生了什么

当你调用 `pipeline.subscribe(System.out::println)` 时，执行时正式开始。

这一步就像施工队按图纸从最下游的工位（FluxFilter）开始，逐个向上游走，每到一個工位就创建对应的"操作工人"（Subscriber），走到最上游的原料仓库（FluxRange）时，按下启动按钮（`source.subscribe(subscriber)`）。

这个过程是本文的重点，我们稍后在第四、五节详细展开。

## 三、Hooks 和 checkpoint：装配时的"审批"和"标注"

### 3.1 Hooks.onEachOperator：全局装配拦截器

Reactor 允许你注册全局钩子，在每个操作符被创建（装配）时拦截：

```java
// 注册一个全局钩子：在每个操作符创建时打印日志
Hooks.onEachOperator("myLogger", publisher -> {
    System.out.println("操作符被创建: " + publisher.getClass().getSimpleName());
    return publisher;
});
```

如果你注册了多个钩子，它们会按注册顺序串联执行：`hook1.andThen(hook2).andThen(hook3)`。源码中 `createOrUpdateOpHook` 方法负责把多个 Function 组合成一个复合函数：

```java
static Function<Publisher, Publisher> createOrUpdateOpHook(
        Collection<Function<? super Publisher<Object>, ? extends Publisher<Object>>> hooks) {
    Function<Publisher, Publisher> composite = null;
    for (Function<? super Publisher<Object>, ? extends Publisher<Object>> function : hooks) {
        if (composite != null) {
            composite = composite.andThen(op);
        } else {
            composite = op;
        }
    }
    return composite;
}
```

**为什么在装配时触发，而不是在 subscribe 时触发？** 因为 `onEachOperator` 的语义是"每个操作符被创建时"拦截一次。如果放在 subscribe 时，同一个 Publisher 被 subscribe 10 次，hook 就会被执行 10 次——而装配时只执行 1 次，无论后续被 subscribe 多少次。这既保证了语义正确性，又保证了性能。

### 3.2 Hooks.onLastOperator：只拦截最外层

`onLastOperator` 与 `onEachOperator` 类似，但只对链的最后一个操作符（即用户直接 subscribe 的那个）生效。

**什么时候用 onEachOperator，什么时候用 onLastOperator？**

- 如果你想在每个操作符上都插入某种横切逻辑（如装配跟踪），用 `onEachOperator`。
- 如果你只想在最外层 subscribe 入口处插入一次（如 metrics 指标收集），用 `onLastOperator`。后者避免了在链中插入 N 个监控操作符的开销。

### 3.3 checkpoint()：手动插入调试标注

`checkpoint()` 是 Reactor 提供的调试辅助方法，它在装配时将一个 `FluxOnAssembly` 操作符插入到链中：

```java
// 完整堆栈 checkpoint（开销大）
flux.checkpoint();

// 轻量 checkpoint（只保存描述字符串，不捕获堆栈）
flux.checkpoint("查询用户列表");

// 带描述的完整堆栈 checkpoint
flux.checkpoint("查询用户列表", true);
```

三种模式的开销对比：

| 方法 | 是否捕获堆栈 | 开销 | 适用场景 |
|------|------------|------|---------|
| `checkpoint()` | 是 | 高 | 开发调试，定位问题 |
| `checkpoint("desc")` | 否 | 低 | 生产环境，轻量标注 |
| `checkpoint("desc", true)` | 是 | 高 | 精确调试特定节点 |

轻量 checkpoint 的 `CheckpointLightSnapshot` 构造极其简单，只保存一个字符串：

```java
static final class CheckpointLightSnapshot extends AssemblySnapshot {
    CheckpointLightSnapshot(@Nullable String description) {
        super(true, description, null);  // null 表示不捕获堆栈
        this.cached = "checkpoint(\"" + (description == null ? "" : description) + "\")";
    }
}
```

⚠️ **踩坑提醒**：`checkpoint()` 和 `Hooks.onOperatorDebug()` 的区别——前者是局部调试，只标注你指定的那一个节点；后者是全局调试，标注所有节点。生产环境用 `checkpoint("desc")` 轻量版即可，不要全局开启 `onOperatorDebug()`。

### 3.4 堆栈信息什么时候用？——延迟到 onError 时

一个精妙的设计：虽然 `AssemblySnapshot` 在装配时创建，但堆栈格式化和 `OnAssemblyException` 的创建是在执行时的 `onError` 才发生的。

也就是说，正常流程（没有错误）时，checkpoint 几乎零开销。只有出错时才付出格式化代价。错误输出类似：

```
Error has been observed at the following site(s):
    *__FluxOnAssembly.flatten ⇢ at com.example.MyClass.myMethod(MyClass.java:42)
    |_FluxMap.map ⇢ at com.example.MyClass.myMethod(MyClass.java:43)
    |_FluxFilter.filter ⇢ at com.example.MyClass.myMethod(MyClass.java:44)
Original Stack Trace:
```

这个设计体现了"正常路径零开销，错误路径才付出代价"的原则。

## 四、执行时的核心：优化循环替代递归

### 4.1 传统方式的问题：递归导致栈太深

假设有 50 个操作符的链：

```java
flux.map(f1).filter(p1).map(f2).flatMap(g).map(f3)...subscribe(sub);
```

传统方式下，每个操作符的 subscribe 方法会递归调用上游的 subscribe：

```java
// 传统递归方式（伪代码）
public void subscribe(Subscriber subscriber) {
    Subscriber inner = new MapSubscriber(subscriber, mapper);
    source.subscribe(inner);  // 递归调用上游的 subscribe！
}
```

50 个操作符 = 50 层递归 = 50 层调用栈。这在正常情况可能没问题，但在以下场景中会变严重：

1. **深层嵌套的 flatMap**：`flatMap` 内部会订阅新的 Publisher，如果内部也有长操作符链，栈深度叠加。
2. **调试模式**：开启 `Hooks.onOperatorDebug()` 后，每个 `FluxOnAssembly` 也参与链路，增加额外深度。
3. **JIT 优化限制**：过深的递归可能阻止 JIT 内联优化。

### 4.2 Reactor 的解决方案：while 循环

Reactor 用 `InternalFluxOperator.subscribe()` 中的 `while(true)` 循环替代递归：

```java
public final void subscribe(CoreSubscriber<? super O> subscriber) {
    OptimizableOperator operator = this;
    try {
        while (true) {
            // 1. 当前操作符创建对应的 Subscriber（包装下游 subscriber）
            subscriber = operator.subscribeOrReturn(subscriber);
            if (subscriber == null) {
                return;  // 操作符自行处理了订阅
            }
            // 2. 获取链中的上一个 OptimizableOperator
            OptimizableOperator newSource = operator.nextOptimizableSource();
            if (newSource == null) {
                // 3. 上游不是 OptimizableOperator，真正订阅数据源
                CorePublisher operatorSource = operator.source();
                subscriber = Operators.restoreContextOnSubscriberIfPublisherNonInternal(
                    operatorSource, subscriber);
                operatorSource.subscribe(subscriber);
                return;
            }
            // 4. 继续向上游走
            operator = newSource;
        }
    } catch (Throwable e) {
        Operators.reportThrowInSubscribe(subscriber, e);
    }
}
```

用日常生活类比：传统方式是"我把图纸交给下游工位，下游工位自己去找上游工位"——每个人都在等上游回应，调用栈越叠越深。Reactor 的循环方式是"一个人拿着图纸从下游往上游走，每到一個工位就创建好操作工人，走到原料仓库时一次性启动"——全程只有一个人在走，不产生嵌套。

关键在于：**循环过程中不调用任何 `subscribe` 方法**，只是不断创建新的 Subscriber 包装器。只有当遍历到链的顶端（数据源），才执行唯一一次 `source.subscribe(subscriber)`。无论链有多长，调用栈深度始终为 O(1)。

### 4.3 subscribeOrReturn：创建工人而非递归调用

`subscribeOrReturn` 是 `OptimizableOperator` 接口定义的核心方法：

```java
interface OptimizableOperator<IN, OUT> extends CorePublisher<IN> {
    // 创建对应的 Subscriber，返回 null 表示"我自己处理了订阅"
    @Nullable CoreSubscriber<? super OUT> subscribeOrReturn(CoreSubscriber<? super IN> actual) throws Throwable;
    
    // 获取上游数据源
    CorePublisher<? extends OUT> source();
    
    // 获取链中的上一个 OptimizableOperator
    @Nullable OptimizableOperator<?, ? extends OUT> nextOptimizableSource();
}
```

对比传统方式：

| 维度 | 传统递归方式 | Reactor 循环方式 |
|------|------------|----------------|
| 每个操作符做什么 | 创建 Subscriber + 递归调用 source.subscribe | 只创建 Subscriber，不调用 subscribe |
| 谁调用 source.subscribe | 每个操作符都调用上游的 subscribe | 只有循环到顶端时才调用一次 |
| 栈深度 | O(N)（N = 操作符数量） | O(1) |

### 4.4 nextOptimizableSource：装配时预计算

这个"向上游走"的逻辑怎么知道上游是不是 `OptimizableOperator`？答案是在装配时就预计算好了：

```java
protected InternalFluxOperator(Flux<? extends I> source) {
    super(source);
    if (source instanceof OptimizableOperator) {
        this.optimizableOperator = (OptimizableOperator<?, I>) source;
    } else {
        this.optimizableOperator = null;
    }
}
```

这个检查在构造器中完成，结果存在 `final` 字段 `optimizableOperator` 中。执行时直接读取，无需运行时类型检查。这就是"装配时预计算、执行时直接用"的又一体现。

## 五、自定义操作符：FluxLift

### 5.1 什么是 Lift

`FluxLift` 是 Reactor 提供的自定义操作符机制。当你通过 `Operators.lift()` 创建一个 lift 函数并应用到 Publisher 时，就创建了一个 `FluxLift`：

```java
// 自定义操作符示例：给每个操作符加上耗时统计
Hooks.onEachOperator(Operators.lift((source, subscriber) -> {
    return new TimingSubscriber(subscriber, source.getClass().getSimpleName());
}));
```

`FluxLift` 的 `subscribeOrReturn` 非常简单——调用用户提供的 lifter 函数：

```java
public CoreSubscriber<? super I> subscribeOrReturn(CoreSubscriber<? super O> actual) {
    CoreSubscriber<? super I> input = liftFunction.lifter.apply(source, actual);
    Objects.requireNonNull(input, "Lifted subscriber MUST NOT be null");
    return input;
}
```

### 5.2 LiftFunction 的类型适配

`LiftFunction.apply()` 根据 Publisher 的具体类型选择对应的 Lift 变体：

- **Fuseable vs 非 Fuseable**：如果上游实现了 `Fuseable` 接口，用 `FluxLiftFuseable`（支持队列融合）；否则用 `FluxLift`。
- **Mono vs Flux vs ParallelFlux vs ConnectableFlux vs GroupedFlux**：每种类型都有对应的 Lift 变体。

这就像工厂里不同的流水线类型需要不同的适配器——有自动传送带的用一种适配器，没有传送带的用另一种。

### 5.3 Lift 中的 Context 保护

Lift 的 lifter 函数被包装了两层 Context 保护：

1. **入口保护**：调用用户 lifter 之前，确保 subscriber 的 Context 被正确恢复到 ThreadLocal。
2. **出口保护**：lifter 返回的 subscriber 传给非内部 Publisher 时，确保 Context 不会丢失。

这确保了即使自定义操作符不感知 Context，Context 传播也不会中断。

## 六、FluxOnAssembly：装配跟踪的运行时行为

### 6.1 执行时包装 Subscriber

`FluxOnAssembly` 在装配时创建，保存了 `AssemblySnapshot`。执行时（subscribe 时），它的 `subscribeOrReturn` 负责将下游 subscriber 包装为 `OnAssemblySubscriber`：

```java
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    return wrapSubscriber(actual, source, this, snapshotStack);
}
```

注意对 `ConditionalSubscriber` 的特殊处理——如果下游是条件订阅者，创建 `OnAssemblyConditionalSubscriber` 以保持 `tryOnNext` 优化路径。这体现了 Reactor 在功能增强和性能优化之间的精细平衡：加了调试功能，但不牺牲已有的优化。

### 6.2 onError 时附加调用链

`OnAssemblySubscriber` 的核心逻辑在 `onError` 时触发：

```java
final public void onError(Throwable t) {
    actual.onError(fail(t));
}
```

`fail()` 方法的关键逻辑：

1. 检查异常是否已附加过 `OnAssemblyException`，有则复用。
2. 没有则创建新的 `OnAssemblyException`，格式化堆栈信息。
3. 在 `OnAssemblyException` 上追加当前操作符节点的信息。

最终 `OnAssemblyException.getMessage()` 会格式化整个调用链，输出前面看到的"Error has been observed at the following site(s)"信息。

## 七、反例：如果不区分装配时和执行时会怎样

### 7.1 假设的错误设计

假设 Reactor 不区分装配时和执行时，在 `map(fn)` 方法内部就执行 `fn`：

```java
// 假设的错误设计
public <V> Flux<V> map(Function<T, V> mapper) {
    V result = mapper.apply(this.lastValue);  // 装配时就执行 mapper！
    return new FluxJust<>(result);
}
```

### 7.2 五个致命问题

1. **副作用过早执行**：如果 mapper 有副作用（打印日志、修改外部状态），在 `map()` 被调用时就执行了，而不是在 subscribe 时。

2. **无法处理异步源**：如果上游是异步的（如 HTTP 响应），装配时数据还没到，mapper 无从执行。

3. **多次订阅结果不一致**：一个 Flux 链可以被 subscribe 多次，每次应该重新执行所有逻辑。如果装配时就执行了，后续 subscribe 只会拿到固定结果。

4. **背压失效**：request(n) 控制的是原始数据的流动。如果装配时就映射完了，request 控制的就是已映射结果，背压关系被打破。

5. **错误处理混乱**：装配时抛异常是普通 Java 异常，执行时抛异常是 `onError` 信号。如果不区分两个阶段，错误处理逻辑会混乱。

### 7.3 正确设计的优势

Reactor 的正确设计确保了：

- **纯声明**：`flux.map(fn).filter(pred)` 只是构建了链，不执行任何用户代码。
- **延迟执行**：只有 `subscribe()` 才触发数据流动。
- **多次订阅**：同一个 Flux 可以被 subscribe 多次，每次从头执行。
- **背压正确**：request 从下游向上游传播，消费者控制生产者。

## 八、信号传播方向

订阅建立后，信号的传播遵循 Reactive Streams 规范的双向模型：

```
onSubscribe:  Source ──► MapSubscriber ──► FilterSubscriber ──► 用户Subscriber
request:      用户Subscriber ──► FilterSubscriber ──► MapSubscriber ──► Source
onNext:       Source ──► MapSubscriber ──► FilterSubscriber ──► 用户Subscriber
onComplete:   Source ──► MapSubscriber ──► FilterSubscriber ──► 用户Subscriber
onError:      Source ──► MapSubscriber ──► FilterSubscriber ──► 用户Subscriber
```

用工厂类比：
- **onSubscribe** 是"流水线接通通知"，从原料仓库向下游传递。
- **request** 是"订单"，从下游（客户）向上游（原料仓库）传递——"我要 10 个产品"。
- **onNext** 是"产品交付"，从上游向下游传递。
- **onComplete** 是"原料用完了"，从上游向下游传递。
- **onError** 是"出故障了"，从上游向下游传递。

这种双向传播确保了背压的正确传递——消费者通过 request 控制生产者速率。

## 九、多角度交叉验证

### 9.1 从内存模型角度

装配时创建的操作符链是一个不可变的单向链表：每个操作符持有上游 source 的 `final` 引用。构造完成后不会被修改，因此对多线程可见性是安全的。多个线程可以同时 subscribe 同一个 Flux 链，每次 subscribe 创建独立的 Subscriber 链。

### 9.2 从性能角度

优化循环避免了递归栈深度问题。N 个操作符的链，传统递归栈深度 O(N)，循环方式栈深度 O(1)。在操作符链较长时（如复杂 flatMap 嵌套）可以显著减少栈帧开销。

### 9.3 从调试角度

装配时捕获的 `AssemblySnapshot` 在执行时 `onError` 时才使用。这种延迟使用设计确保了：
- 正常路径零开销（不捕获堆栈时）
- 错误路径才付出格式化代价
- 堆栈信息在多次 subscribe 间共享（AssemblySnapshot 是 final 字段，装配时创建一次）

### 9.4 从 Reactive Streams 规范角度

规范规定 `Publisher.subscribe()` 的调用不应阻塞。Reactor 的优化循环完全在 subscribe 方法内部完成（创建 Subscriber 链 + 调用 source.subscribe），不涉及任何阻塞操作。

## 十、归纳表格

### 装配时 vs 执行时对比表

| 维度 | 装配时（画图纸） | 执行时（施工） |
|------|----------------|--------------|
| **触发时机** | 调用 `map()`、`filter()` 等操作符方法时 | 调用 `subscribe()` 时 |
| **执行内容** | 创建操作符对象，存 source 引用和参数 | 创建 Subscriber 链，接通数据管道 |
| **数据流动** | 无，纯声明式构建 | 有，onNext/onError/onComplete 信号传播 |
| **副作用** | 无用户代码执行（Hooks 除外） | 执行 mapper、predicate、consumer 等用户代码 |
| **调用栈深度** | O(1) | O(1)（OptimizableOperator 循环优化） |
| **Hooks 触发** | `onEachOperator`、`onLastOperator` | 无（Hooks 在装配时已应用） |
| **堆栈捕获** | `FluxOnAssembly` 构造时捕获 `AssemblySnapshot` | `OnAssemblySubscriber.fail()` 时格式化 |
| **可重复性** | 只执行一次（操作符链不可变） | 每次 subscribe 都重新执行 |
| **线程安全** | 构造后不可变，天然线程安全 | 每次 subscribe 创建独立 Subscriber 链 |
| **核心方法** | `Flux.onAssembly()`、构造器 | `InternalFluxOperator.subscribe()`、`subscribeOrReturn()` |
| **优化机制** | `nextOptimizableSource()` 预计算 | `while(true)` 循环替代递归 |
| **Context 处理** | 不涉及 | `restoreContextOnSubscriberIfPublisherNonInternal()` |
| **错误处理** | 构造异常直接抛出 | `Operators.reportThrowInSubscribe()` 转为 onError |
| **典型类** | `FluxOperator`、`FluxMap`、`FluxOnAssembly` | `InternalFluxOperator`、`OptimizableOperator` |
| **checkpoint** | 创建 `FluxOnAssembly` 插入链中 | 包装 Subscriber，onError 时附加调用链 |

### 核心源码类职责表

| 类名 | 职责 | 阶段 | 通俗解释 |
|------|------|------|---------|
| `FluxOperator` | 操作符基类，持有 source 引用 | 装配时 | 工位的基础设施 |
| `InternalFluxOperator` | 内建操作符基类，实现优化循环 | 执行时 | 流水线启动器 |
| `OptimizableOperator` | 接口，定义循环优化的三个核心方法 | 执行时 | 工位之间的连接协议 |
| `FluxOnAssembly` | 装配跟踪操作符，保存堆栈快照 | 装配时+执行时 | 图纸上的标注 |
| `FluxLift` | 自定义操作符包装器 | 执行时 | 自定义工位适配器 |
| `Hooks` | 全局钩子管理 | 装配时 | 图纸审批流程 |
| `Operators.LiftFunction` | lift 函数实现，按类型创建 Lift 变体 | 装配时 | 适配器选择器 |
| `OnAssemblySubscriber` | 装配跟踪 Subscriber，错误时附加调用链 | 执行时 | 标注的运行时体现 |

### 常见踩坑总结表

| 踩坑场景 | 错误写法 | 正确写法 | 原因 |
|---------|---------|---------|------|
| 参数过早求值 | `Flux.just(queryDb())` | `Flux.defer(() -> Flux.just(queryDb()))` | Java 方法参数在调用前求值 |
| 错误过早抛出 | `Flux.error(loadException())` | `Flux.defer(() -> Flux.error(loadException()))` | 同上 |
| 全局调试模式 | 生产环境开 `Hooks.onOperatorDebug()` | 用 `checkpoint("desc")` 局部调试 | 全局堆栈捕获开销大 |
| 递归栈过深 | 不使用 Reactor 内建操作符 | 使用内建操作符自动享受优化循环 | 内建操作符实现了 OptimizableOperator |

## 十一、总结

装配时与执行时的分离是 Reactor 最核心的架构设计之一。用一句话概括：

**装配时画图纸，执行时施工。图纸画完后可以复印多份、从不同角度施工，但画图纸本身不生产任何产品。**

这一设计带来三个关键优势：

1. **声明式语义**：用户代码构建的是数据处理管道的"蓝图"，而非立即执行的命令。`Flux.just(queryDb())` 之所以会提前查库，是因为 Java 参数求值机制，而非 Reactor 的设计缺陷——用 `defer` 可以把求值推迟到执行时。

2. **优化空间**：装配时构建的不可变操作符链为执行时优化提供了基础。`OptimizableOperator` 的 while 循环替代递归，正是利用了装配时预先建立的 `optimizableOperator` 链表，以 O(1) 栈深度完成整个订阅过程。

3. **可观测性**：装配时捕获的信息（如 `AssemblySnapshot`）为执行时的错误诊断提供了丰富上下文。`checkpoint()` 和 `Hooks.onOperatorDebug()` 在装配时插入跟踪节点，但堆栈格式化延迟到 `onError` 时才执行——正常路径零开销，错误路径才付出代价。

理解这一分离机制，是理解 Reactor 所有其他机制（操作符融合、背压传播、线程调度、Context 传播）的基础。后续篇章中讨论的所有执行时行为，都建立在装配时构建的操作符链之上。
