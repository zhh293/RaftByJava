## 一、先讲个场景：为什么会有背压这回事

假设你在一家很火的餐厅吃饭。服务员（生产者）如果一次性把菜单上所有 100 道菜都做好端上来，会发生什么？

- 桌子放不下（内存爆了，OOM）
- 你根本吃不过来，菜都凉了（数据积压、处理不过来）
- 后厨为了赶工可能手忙脚乱出错（系统过载崩溃）

正常的餐厅是怎么运作的？**你（消费者）先说"我要 3 个菜"，后厨（生产者）做好这 3 个就端上来，等你吃得差不多了，再点下一批。** 这就是背压（Backpressure）——消费者主动告诉生产者"我现在能处理多少"，生产者按需生产，而不是敞开了往外推。

这在响应式编程里对应着一个问题：**如果生产数据的速度比消费数据的速度快，多出来的数据该怎么办？** Reactive Streams 规范给出的答案是：让消费者说了算，消费者通过 `request(n)` 告诉生产者"给我 n 个"，生产者绝不能多给。

WebFlux 底层的 Reactor Core 完整实现了这套协议。这一篇我们就来看看，`Flux.just(1,2,3).subscribe(System.out::println)` 这行代码背后，"点菜"和"上菜"的每一步究竟是怎么发生的。

## 二、Reactive Streams 三方协议：点菜的三个角色

先明确三个角色，对应我们的餐厅比喻：

| Reactive Streams 角色 | 餐厅类比 | 职责 |
|---|---|---|
| `Publisher`（数据源） | 后厨 | 生产数据 |
| `Subscriber`（订阅者） | 顾客 | 消费数据，发起请求 |
| `Subscription`（订阅凭证） | 点菜单/服务员 | 承载 request/cancel 的"传菜通道" |

四个核心方法构成了完整的对话：

```
Subscriber.onSubscribe(Subscription s)   顾客拿到点菜单
Subscription.request(n)                  顾客说"先来3个"
Publisher通过Subscription把数据推给Subscriber.onNext(T)   上菜
Subscriber.onComplete() / onError(e)     "上完了" / "厨房失火了"
```

拿 `Flux.just(1,2,3).subscribe(System.out::println)` 举例，完整的时序是这样的（`FluxArray` 是 `just` 底层用的类）：

```
  LambdaSubscriber                  FluxArray                  ArraySubscription
  (顾客)                            (后厨)                      (点菜单)
       │                                │                           │
       │   Flux.subscribe(lambda)       │                           │
       │ ──────────────────────────►    │                           │
       │                                │  new ArraySubscription()  │
       │                                │ ─────────────────────────►│
       │     onSubscribe(subscription)  │                           │
       │ ◄──────────────────────────────│                           │
       │                                │                           │
       │  request(Long.MAX_VALUE)       │                           │
       │ ──────────────────────────────────────────────────────────►│
       │                                │    fastPath()             │
       │        onNext(1)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
       │        onNext(2)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
       │        onNext(3)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
       │        onComplete()            │                           │
       │ ◄──────────────────────────────────────────────────────────│
```

**注意关键的一步**：`subscribe(System.out::println)` 这种写法，底层默认会调用 `request(Long.MAX_VALUE)`——也就是"我不设限，管够上"。这是最常见但也最容易被忽视的一个细节：**默认情况下 WebFlux 是没有背压限流的**，除非你手动控制。

如果你想手动控制"点菜节奏"，画风就变成这样（用 `BaseSubscriber`，`FluxRange` 作为数据源）：

```
  BaseSubscriber                    FluxRange                  RangeSubscription
  (手动点菜的顾客)                   (后厨)                      (点菜单)
       │                                │                           │
       │   subscribe(baseSubscriber)    │                           │
       │ ──────────────────────────►    │                           │
       │                                │ new RangeSubscription()   │
       │                                │ ─────────────────────────►│
       │     onSubscribe(subscription)  │                           │
       │ ◄──────────────────────────────│                           │
       │                                │                           │
       │  hookOnSubscribe:              │                           │
       │    request(2)   "先来2个"       │                           │
       │ ──────────────────────────────────────────────────────────►│
       │                                │   slowPath(2)             │
       │        onNext(1)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
       │        onNext(2)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
       │                                │   配额用完，暂停等待       │
       │                                │                           │
       │  hookOnNext: request(2)  "再来2个" │                       │
       │ ──────────────────────────────────────────────────────────►│
       │                                │   slowPath 恢复            │
       │        onNext(3)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
       │        onNext(4)               │                           │
       │ ◄──────────────────────────────────────────────────────────│
```

这两个流程图的差别，就是"敞开供应"（fastPath）和"按需供应"（slowPath）的差别。后面我们会深入讲这两条路径。

⚠️ **踩坑提醒**：很多新人以为 WebFlux "自带流量控制"，实际上默认订阅方式（lambda 订阅）等于直接 `request(Long.MAX_VALUE)`，跟同步代码没有本质区别——真正的背压保护，需要你用 `BaseSubscriber` 手动控制，或者依赖中间操作符（比如 `flatMap` 的 `maxConcurrency`）间接限流。

## 三、Operators 工具类：这套协议靠什么保证不出错

`Operators` 是 Reactor Core 里的一个基础工具类，背压协议里所有"脏活累活"（校验、并发安全、边界处理）都在这里面。我们逐个看它是怎么把背压协议落到实处的。

### 3.1 请求量校验：不能点负数个菜

```java
public static boolean validate(long n) {
    if (n <= 0) {
        reportBadRequest(n);
        return false;
    }
    return true;
}
```

Reactive Streams 规范要求 `request(n)` 里的 `n` 必须大于 0——你总不能跟服务员说"给我上负 5 个菜"。这个方法做的就是这个校验。

**这里有个反直觉的设计**：校验失败后**不会抛异常**，只是打个日志然后默默返回 `false`。为什么这么"怂"？

因为在异步并发场景里，一个非法的 `request` 值很可能是竞态条件导致的（比如一个线程正在 `cancel`，另一个线程同时发出了 `request`）。如果贸然抛异常，可能引发级联错误，反而让问题更严重。**静默忽略 + 记录日志**，是更安全的策略——类似餐厅遇到奇怪的点菜要求，服务员选择礼貌无视，而不是当场跟顾客吵起来。

### 3.2 防止重复点菜：一个顾客不能同时拿两张点菜单

```java
public static boolean validate(@Nullable Subscription current, Subscription next) {
    Objects.requireNonNull(next, "Subscription cannot be null");
    if (current != null) {
        next.cancel();
        return false;
    }
    return true;
}
```

每个操作符内部的 Subscriber（比如后面会讲到的 `MapSubscriber`）在收到 `onSubscribe` 时都会调这个方法检查：**我是不是已经绑定过一张点菜单了？** 如果是，说明出现了重复订阅（可能是 bug 或者恶意的二次订阅），直接把新来的 Subscription 取消掉。这是防御性编程——保证一个 Subscriber 一辈子只认一个 Subscription。

### 3.3 溢出安全的加法：点菜数量算爆了怎么办

```java
public static long addCap(long a, long b) {
    long res = a + b;
    if (res < 0L) {
        return Long.MAX_VALUE;
    }
    return res;
}
```

这个方法很简单但很重要。Java 里 `Long.MAX_VALUE + 1` 会溢出变成负数。如果你分两次 `request(Long.MAX_VALUE)`，两次请求量加起来不应该变成一个负数（那就荒谬了——难道还能"要负数份菜"？），而应该保持在 `Long.MAX_VALUE`（无限量供应）。这个方法通过检测 `res < 0` 来发现溢出，然后把结果钳制在 `Long.MAX_VALUE`。

**为什么不用 `Math.addExact` 抛异常来处理溢出？** 因为异常处理的性能开销远比一次条件判断大。`request` 是高频调用路径，用异常处理溢出，性能上得不偿失。

### 3.4 CAS 无锁累加：多个人同时喊"加菜"怎么办

```java
public static <T> long addCap(AtomicLongFieldUpdater<T> updater, T instance, long toAdd) {
    long r, u;
    for (;;) {
        r = updater.get(instance);
        if (r == Long.MAX_VALUE) {
            return Long.MAX_VALUE;
        }
        u = addCap(r, toAdd);
        if (updater.compareAndSet(instance, r, u)) {
            return r;
        }
    }
}
```

这是整个背压机制里**最核心的并发原语**，值得逐行拆解：

1. `for (;;)`——一个死循环，这是经典的 CAS（比较并交换）自旋写法：不断尝试，直到成功为止。
2. `r = updater.get(instance)`——先读一下当前累计的请求量。
3. 如果已经是 `Long.MAX_VALUE`（已经无限量供应了），直接返回，不用再加了——这是一个重要优化：一旦进入"管够"状态，后续调用几乎零开销。
4. `u = addCap(r, toAdd)`——调用上面讲的溢出安全加法算出新值。
5. `compareAndSet(instance, r, u)`——尝试把值从 `r` 原子性地改成 `u`。如果这期间有别的线程改过这个值，CAS 会失败，回到循环开头重试。
6. **返回的是修改前的旧值**——这一点很关键。

**为什么要返回旧值而不是新值？** 因为调用方真正关心的问题是：**"在我之前，有没有正在进行的发菜流程？"** 如果旧值是 0，说明之前没人在发菜，当前线程需要亲自启动发菜流程；如果旧值大于 0，说明已经有人在发了，新加的量会被正在运行的那个流程自动看到并处理，当前线程什么都不用干，直接返回就行。

这就好比多个服务员同时往同一张点菜单上加菜——只有第一个动手写字的服务员需要去通知后厨"开始做菜"，后面的服务员只需要把菜名写上去就行，不用重复喊后厨。

**为什么不用 `synchronized` 加锁？** 加锁会导致线程阻塞、上下文切换，代价很高。而 CAS 是无锁的——抢不到的线程只是重试一下，不会被挂起。对于大多数低竞争场景（大部分应用不会疯狂并发调用 `request`），CAS 通常第一次尝试就能成功，性能非常好。

### 3.5 空序列和已知错误的快速处理

```java
public static void complete(Subscriber<?> s) {
    s.onSubscribe(EmptySubscription.INSTANCE);
    s.onComplete();
}

public static void error(Subscriber<?> s, Throwable e) {
    s.onSubscribe(EmptySubscription.INSTANCE);
    s.onError(e);
}
```

如果这家店压根没有这道菜（比如 `Flux.empty()`），或者一开始就知道做不出来（`Flux.error(e)`），Reactor 也**不会跳过点菜单这一步**，而是先给一个空的 Subscription，再立刻发 `onComplete` 或 `onError`。

**为什么不能省略 `onSubscribe` 直接报错/结束？** 因为 Reactive Streams 规范明确要求：`onSubscribe` 必须在 `onNext`/`onError`/`onComplete` 之前被调用，哪怕这次点菜从头到尾什么都不会发生，这个"建立关系"的礼节步骤也不能省。

## 四、FluxArray：一个"数组后厨"是怎么按需上菜的

`FluxArray` 是最简单的数据源之一——把一个 Java 数组包装成响应式流。它的内部类 `ArraySubscription` 完美展示了背压协议的所有关键套路。

### 4.1 字段设计：谁该加 volatile，谁不该

```java
static final class ArraySubscription<T>
        implements InnerProducer<T>, SynchronousSubscription<T> {

    final CoreSubscriber<? super T> actual;
    final T[] array;
    int index;                  // 当前发到第几个了，不是 volatile
    volatile boolean cancelled; // 取消标记，是 volatile
    volatile long requested;    // 累积请求量，是 volatile
    static final AtomicLongFieldUpdater<ArraySubscription> REQUESTED = ...;
}
```

这里有个很容易被问到的问题：**为什么 `index`（当前发射到哪个位置了）不是 `volatile`，而 `cancelled` 和 `requested` 是？**

- `index` 只在发菜的循环内部被读写，而这个循环通过 CAS 保证同一时刻只有一个线程在跑——这是一种"隐式互斥"。多个线程可以同时喊"加菜"，但只有一个线程能真正抢到"跑去后厨做菜"的资格（也就是前面讲的 `addCap` 返回 0 的那个线程）。既然只有一个线程会碰 `index`，就不需要额外的可见性保证。
- `cancelled` 可能从任意线程调用（比如用户在主线程点了"不要了"，而后厨正在另一个线程做菜），必须用 `volatile` 保证发菜的循环能第一时间看到这个取消信号。
- `requested` 需要被多个线程并发修改（多次调用 `request`），必须靠 `volatile` + CAS 保证并发安全。

**为什么用 `AtomicLongFieldUpdater` 而不是直接搞个 `AtomicLong` 字段？** 纯粹是内存优化——`AtomicLong` 是一个独立对象，每个实例都要多消耗十几个字节的对象头开销；而 `AtomicLongFieldUpdater` 是全类共享的一个静态工具，通过反射直接操作原始的 `volatile long` 字段，不会给每个 Subscription 实例增加额外负担。在 `flatMap` 这种会创建大量内部订阅的场景下，这个优化能省下不少内存。

### 4.2 request(n)：点菜请求走哪条路

```java
public void request(long n) {
    if (Operators.validate(n)) {
        if (Operators.addCap(REQUESTED, this, n) == 0) {
            if (n == Long.MAX_VALUE) {
                fastPath();
            } else {
                slowPath(n);
            }
        }
    }
}
```

翻译成人话：

1. 先检查这次点菜数量合不合法。
2. 用 CAS 把这次点的量累加到总请求量上。
3. 如果累加前的旧值是 0（说明之前没人在做菜），当前线程就负责去后厨"开火"：
   - 如果这次要的是"管够"（`Long.MAX_VALUE`），走 **fastPath**（敞开供应，全速上菜）。
   - 否则走 **slowPath**（精确计量，按需上菜）。
4. 如果旧值不是 0，说明已经有人在后厨忙活了，什么都不用干，新的请求量已经被记上了，正在运行的流程会看到。

### 4.3 fastPath：管够模式，怎么快怎么来

```java
void fastPath() {
    final T[] a = array;
    final int len = a.length;
    final Subscriber<? super T> s = actual;

    for (int i = index; i != len; i++) {
        if (cancelled) {
            return;
        }
        T t = a[i];
        if (t == null) {
            s.onError(new NullPointerException("The " + i + "th array element was null"));
            return;
        }
        s.onNext(t);
    }
    if (cancelled) {
        return;
    }
    s.onComplete();
}
```

当顾客说"随便上，管够"（`request(Long.MAX_VALUE)`）时，后厨就没必要精打细算了——直接从头做到尾，一路端上桌，中间不检查配额，也不用做任何 CAS 操作。

这里有几个细节：

- **每次循环都检查 `cancelled`**：虽然是敞开供应，顾客随时可能喊"不要了"（cancel）。因为 `cancelled` 是 `volatile` 的，每次循环都能看到最新状态。但注意，检查频率是"每上一道菜看一眼"——如果某道菜做得特别慢（`onNext` 处理耗时），取消的响应会有延迟。
- **null 检查**：数组里如果有 null 元素，直接报错终止——响应式流规范不允许 null 元素流过管道（就好比不能给顾客上一盘"空气"）。

**fastPath 快在哪？** 全程没有 CAS 操作（`addCap` 只在 `request` 入口调用一次），没有 `requested` 字段的反复读写，局部变量缓存了数组和 Subscriber 引用避免重复寻址。整个热路径极其精简：读数组、判空、发送。

### 4.4 slowPath：精确点菜模式，这才是背压协议的精华

```java
void slowPath(long n) {
    final T[] a = array;
    final int len = a.length;
    final Subscriber<? super T> s = actual;

    int i = index;
    int e = 0;

    for (; ; ) {
        if (cancelled) {
            return;
        }

        while (i != len && e != n) {
            T t = a[i];
            if (t == null) {
                s.onError(new NullPointerException("The " + i + "th array element was null"));
                return;
            }
            s.onNext(t);
            if (cancelled) {
                return;
            }
            i++;
            e++;
        }

        if (i == len) {
            s.onComplete();
            return;
        }

        n = requested;
        if (n == e) {
            index = i;
            n = REQUESTED.addAndGet(this, -e);
            if (n == 0) {
                return;
            }
            e = 0;
        }
    }
}
```

这是背压协议实现里最值得细品的一段代码。分层看：

**外层 `for(;;)` 死循环**——退出条件散落在循环体内部：取消了就退出、菜上完了就退出、配额用完且没有新请求就退出。

**内层 `while` 循环**——同时满足"还有菜没上"（`i != len`）和"配额没用完"（`e != n`）才继续上菜。`e` 是这一轮已经上了几道菜，`n` 是这一轮的配额。

**配额用完之后的 CAS 回退**——这是最精妙的部分：

```java
n = requested;
if (n == e) {
    index = i;
    n = REQUESTED.addAndGet(this, -e);
    if (n == 0) {
        return;
    }
    e = 0;
}
```

1. 重新读一次 `requested` 的最新值——因为在刚才发菜的过程中，顾客可能又喊了"再加点"（并发调用了 `request`）。
2. 如果 `n == e`（当前请求量和已上菜数量刚好相等），说明这段时间**没有新的加菜请求**，于是：
   - 保存当前上菜进度 `index = i`。
   - 用 CAS 从 `requested` 里扣掉已经上的这些菜的配额。
   - 如果扣完后变成 0，说明彻底没配额了，后厨暂停打烊，等下次顾客点菜再启动。
   - 如果扣完后还大于 0，说明扣的过程中又来了新请求，把已发数量 `e` 清零，继续循环干活。
3. 如果 `n != e`，说明发菜过程中确实有新请求进来了（`requested` 被增大了），外层循环直接带着更大的 `n` 继续跑，都不需要做 CAS。

**这个设计巧妙在哪？** 上菜循环和顾客的加菜请求之间，通过 `requested` 这个字段做了一次隐式的"对暗号"：上菜循环尝试把 `requested` 减掉自己已经上的量，减的过程中如果发现有人偷偷加了量，就继续干；顾客加菜时，如果发现后厨没在忙（旧值是 0），就亲自去喊后厨开工。这样保证了：

- 永远不会有两拨人同时在后厨做菜（不会有两个 drain 循环同时跑）。
- 顾客的每一次加菜请求都不会被遗漏。
- 全程没有用一把锁。

⚠️ **踩坑提醒**：如果你自己写自定义 Publisher，很容易忘记"重新读取 `requested` 最新值"这一步，直接用进入循环时的旧 `n` 做判断，这会导致背压请求丢失——顾客明明加了菜，后厨却因为读的是旧数据而没反应过来，导致数据卡住不动。这是手写背压逻辑最容易踩的坑。

### 4.5 cancel：说不要就不要，干脆利落

```java
public void cancel() {
    cancelled = true;
}
```

就是设置一个 `volatile boolean` 标记，没有更多逻辑。因为 `FluxArray` 的数据源是一个已经准备好的静态数组，没有什么额外资源需要释放（不像文件句柄、网络连接那样需要关闭）。

⚠️ **踩坑提醒**：`cancel()` 之后你**依然可能**收到一两个 `onNext`！因为从"设置取消标记"到"发菜循环检查到标记"之间有个窗口期。Reactive Streams 规范明确允许这种情况（§3.7）。所以在写 Subscriber 逻辑时，`onNext` 里不能假设"我已经 cancel 了就绝对不会再被调用"。

## 五、FluxRange：换个数据源，套路一模一样

`FluxRange`（对应 `Flux.range(1, 10)` 这种写法）内部的 `RangeSubscription`，跟 `ArraySubscription` 的结构几乎一模一样，唯一的区别是数据来源——一个是数组下标遍历，一个是整数递增。

```java
public void request(long n) {
    if (Operators.validate(n)) {
        if (Operators.addCap(REQUESTED, this, n) == 0) {
            if (n == Long.MAX_VALUE) {
                fastPath();
            } else {
                slowPath(n);
            }
        }
    }
}
```

这段代码跟 `ArraySubscription` 一字不差。这说明 Reactor 团队把"发菜循环"这套模式高度标准化了——不管数据从哪来，背压协议的处理套路都是统一的模板。

一个值得一提的细节：`FluxRange` 在 `subscribe` 时会做两个特殊优化：

```java
if (st == en) {
    Operators.complete(actual);       // 范围为空，直接完事
    return;
}
if (st + 1 == en) {
    actual.onSubscribe(Operators.scalarSubscription(actual, (int)st));  // 只有一个数，走极简通道
    return;
}
```

- 范围是空的（比如 `range(5, 0)`），直接完成，连 `RangeSubscription` 都不用创建。
- 范围里只有一个数字（比如 `range(5, 1)`），用一个专门的"单值 Subscription"，跳过整套 CAS、volatile 字段的重型基础设施。

**为什么单个元素也要特殊优化？** 因为通用的 `RangeSubscription` 只处理一次 `request` 就完事的场景时，白白创建了 `AtomicLongFieldUpdater` 这些用不上的基础设施，纯属浪费。这是一种"杀鸡不用牛刀"的性能优化思路，Reactor 源码里到处都是这类极致优化。

## 六、两种"顾客"：LambdaSubscriber 和 BaseSubscriber

到这里我们讲完了"后厨"（Publisher）怎么按背压协议做菜，接下来看"顾客"（Subscriber）这一端有哪两种典型实现。

### 6.1 LambdaSubscriber：图省事的散客，直接说"管够"

当你写 `flux.subscribe(x -> System.out.println(x))` 这种最常见的写法时，Reactor 内部会创建一个 `LambdaSubscriber` 来包装你的 lambda。

关键逻辑在 `onSubscribe` 里：

```java
public void onSubscribe(Subscription s) {
    if (Operators.validate(subscription, s)) {
        this.subscription = s;
        if (subscriptionConsumer != null) {
            // 用户自定义了怎么处理订阅，交给用户
            ...
        }
        else {
            s.request(Long.MAX_VALUE);   // 默认：管够
        }
    }
}
```

**只要你没有专门告诉它怎么控制请求量，它就默认帮你 `request(Long.MAX_VALUE)`。** 这就是为什么前面说"默认订阅方式没有真正的背压保护"——`LambdaSubscriber` 觉得，大多数人写 `subscribe(consumer)` 就是想处理全部数据，不想操心怎么手动控制节奏，索性直接敞开供应。

如果你确实需要控制初始请求量，可以用带 `subscriptionConsumer` 参数的重载：

```java
flux.subscribe(
    value -> process(value),          // onNext：怎么处理每个值
    error -> handleError(error),      // onError：出错了怎么办
    () -> complete(),                 // onComplete：正常结束怎么办
    sub -> sub.request(10)            // 自定义：一开始只要 10 个
);
```

`onError` 里还藏着一个重要的默认行为：

```java
public void onError(Throwable t) {
    Subscription s = S.getAndSet(this, Operators.cancelledSubscription());
    if (s == Operators.cancelledSubscription()) {
        Operators.onErrorDropped(t, this.initialContext);
        return;
    }
    if (errorConsumer != null) {
        errorConsumer.accept(t);
    }
    else {
        Operators.onErrorDropped(
            Exceptions.errorCallbackNotImplemented(t), this.initialContext);
    }
}
```

⚠️ **踩坑提醒**：如果你写 `flux.subscribe(x -> process(x))`，**没有传错误处理回调**，一旦流中发生错误，这个错误不会被静默吞掉，而是会被包装成 `ErrorCallbackNotImplemented` 异常，扔进全局的 `onErrorDropped` 钩子——很多新人上线后发现日志里冒出一堆"错误处理器未实现"的异常，都是这么来的。**生产代码里，永远建议传入错误处理回调。**

`onError` 和 `dispose` 里都用了同一个 CAS 套路——把 subscription 原子性地替换成一个"哨兵对象"（`cancelledSubscription()`），保证不管终止信号来多少次、或者多个线程同时调用 `dispose`，实际的取消动作只会执行一次。这跟前面讲的"点菜单不能被重复使用"是同一种思路的延伸——响应式流的终止语义必须是幂等的。

### 6.2 BaseSubscriber：讲究的老饕，自己精确点菜

如果你想手动控制背压节奏（比如实现"每次处理完 2 个再要 2 个"），就需要继承 `BaseSubscriber`。它提供了一套"钩子方法"（hook），让你只需要关心业务逻辑，底层的并发安全、幂等保护全部由框架处理。

```java
protected void hookOnSubscribe(Subscription subscription){
    subscription.request(Long.MAX_VALUE);  // 默认也是管够，除非你覆盖
}

protected void hookOnNext(T value){
    // 空实现，等你来写
}

protected void hookOnComplete() { }

protected void hookOnError(Throwable throwable) {
    throw Exceptions.errorCallbackNotImplemented(throwable);  // 默认直接抛异常！
}

protected void hookOnCancel() { }

protected void hookFinally(SignalType type) { }
```

一个典型的手动控制背压的写法：

```java
flux.subscribeWith(new BaseSubscriber<Integer>() {
    @Override
    protected void hookOnSubscribe(Subscription subscription) {
        request(2);   // 一开始只要 2 个
    }

    @Override
    protected void hookOnNext(Integer value) {
        process(value);
        request(1);   // 处理完一个，再要一个（"吃一个点一个"）
    }
});
```

**为什么 `hookOnError` 的默认实现是直接抛异常，而不是像 `LambdaSubscriber` 那样丢到全局钩子？** 这是"宁可吵闹地失败，也不要悄悄地出错"的设计哲学——如果你继承了 `BaseSubscriber` 却忘记覆盖错误处理逻辑，框架会立刻用异常提醒你"你漏处理错误了"，而不是让程序带着一个未处理的错误静默运行下去，导致更难排查的数据不一致问题。

`BaseSubscriber` 所有面向外部的方法（`onSubscribe`、`onNext`、`onError`、`onComplete`、`cancel`）都是 **`final` 的**，用户只能覆盖 `hookXxx` 方法。这是典型的"模板方法模式"——框架把 CAS 校验、幂等保护、异常兜底这些通用逻辑焊死在外层，你只需要专心写业务逻辑，不用担心并发安全这类细节被自己不小心写错。

比如 `onNext` 的模板：

```java
public final void onNext(T value) {
    Objects.requireNonNull(value, "onNext");
    try {
        hookOnNext(value);
    }
    catch (Throwable throwable) {
        onError(Operators.onOperatorError(subscription, throwable, value, currentContext()));
    }
}
```

即便你在 `hookOnNext` 里的业务代码抛了异常，框架也会自动帮你转换成规范的 `onError` 信号往下传，而不会让异常直接窜出去搞崩整个订阅链。

还有一个很实用的设计：无论最终是正常完成、出错还是被取消，`hookFinally` 都保证会被调用到——这跟 try-with-resources 的思路一样，专门用来做资源清理（比如关闭连接、释放锁），不用你在 `hookOnComplete`、`hookOnError`、`hookOnCancel` 里各写一遍清理逻辑。

### 6.3 两者对比一览

| 特性 | LambdaSubscriber | BaseSubscriber |
|------|-----------------|----------------|
| 怎么创建 | `flux.subscribe(consumer, error, complete)` | 继承 `BaseSubscriber` 后 `subscribeWith(...)` |
| 默认请求策略 | 没传自定义 subscriptionConsumer 时，自动 `request(Long.MAX_VALUE)` | `hookOnSubscribe` 默认也是 `request(Long.MAX_VALUE)`，但你可以随意覆盖 |
| 手动背压控制 | 只能通过 subscriptionConsumer 这个"小口子" | 直接在 `hookOnNext` 里精细控制每一次 `request` |
| 出错没处理时的行为 | 静默丢到全局 `onErrorDropped` 钩子 | 直接抛异常，逼你处理 |
| 生命周期钩子 | 无 | `hookOnSubscribe`、`hookOnNext`、`hookOnComplete`、`hookOnError`、`hookOnCancel`、`hookFinally` 一应俱全 |
| 典型使用场景 | 简单场景，"给我全部数据就行" | 需要精细控制消费节奏，或者需要生命周期钩子做资源管理 |

**该用哪个？** 日常业务代码 90% 场景用 `subscribe(consumer, error)` 这种简单写法就够了；只有当你确实需要"控制处理节奏"（比如对接一个处理能力有限的下游系统，需要严格限流）或者需要精细的生命周期管理时，才需要上 `BaseSubscriber`。

## 七、缓冲区大小：Queues 里的两个魔法数字

Reactor 内部的异步操作符（比如 `flatMap`、`publishOn`）在做流转的时候会用到队列，队列大小由 `Queues` 这个类统一定义：

```java
public static final int XS_BUFFER_SIZE = Math.max(8,
    Integer.parseInt(System.getProperty("reactor.bufferSize.x", "32")));

public static final int SMALL_BUFFER_SIZE = Math.max(16,
    Integer.parseInt(System.getProperty("reactor.bufferSize.small", "256")));
```

| 常量 | 默认值 | 最小值兜底 | 用途 |
|------|-------|-------|------|
| `XS_BUFFER_SIZE` | 32 | 8 | 低吞吐场景的小缓冲 |
| `SMALL_BUFFER_SIZE` | 256 | 16 | `flatMap`、`publishOn` 等常用操作符的标准缓冲 |

**为什么要有最小值兜底？** 防止有人通过系统属性把缓冲区调得过小。缓冲区太小会导致频繁的"要货-发货"切换（request/drain 反复触发），性能会急剧下降——就像餐厅如果每次只允许后厨备一份菜的库存，服务员就得不停地跑厨房催单，效率反而更低。这两个 `Math.max` 就是给性能设的安全下限。

## 八、归纳总结表

### 8.1 背压协议关键方法一览

| 方法 | 所在类 | 一句话功能 | 线程安全靠什么 |
|------|-------|------|------|
| `validate(long n)` | `Operators` | 检查点菜数量必须 > 0 | 无状态方法，天然安全 |
| `validate(Subscription, Subscription)` | `Operators` | 防止重复订阅 | 依赖调用时机保证单线程 |
| `addCap(long, long)` | `Operators` | 加法防溢出，封顶 Long.MAX_VALUE | 无状态，天然安全 |
| `addCap(AtomicLongFieldUpdater, T, long)` | `Operators` | CAS 循环累加请求量，返回旧值 | CAS 自旋无锁 |
| `complete(Subscriber)` | `Operators` | 空数据源的一步到位完成 | 订阅阶段调用，无并发问题 |
| `error(Subscriber, Throwable)` | `Operators` | 已知会失败时的一步到位报错 | 订阅阶段调用，无并发问题 |
| `request(n)` | `ArraySubscription` | 校验 → 累加 → 决定走哪条路径 | 依靠 addCap 的 CAS 保证只有一个人在发菜 |
| `fastPath()` | `ArraySubscription` | 无界请求下全速发射 | 靠 addCap==0 保证进入的是唯一线程 |
| `slowPath(n)` | `ArraySubscription` | 精确计量的背压发射循环 | CAS 扣减 requested + 外层循环重新检查 |
| `cancel()` | `ArraySubscription` | 设一个 volatile 标记 | volatile 写的可见性 |
| `onSubscribe` | `LambdaSubscriber` | 默认自动请求管够 | validate 保证只设置一次 |
| `hookOnSubscribe` | `BaseSubscriber` | 用户自定义初始请求策略 | onSubscribe 的 CAS 保证只调用一次 |

### 8.2 三层架构总结

| 层级 | 负责什么 | 关键机制 |
|---|---|---|
| 第一层：验证与安全 | 拦住非法调用、重复订阅、数值溢出、终止后的多余操作 | `validate`、`addCap`、哨兵对象 `cancelledSubscription` |
| 第二层：drain 循环核心 | 真正负责"发菜"的循环逻辑 | `request` 触发、`addCap` 决定谁去发菜、`fastPath`/`slowPath` 双路径 |
| 第三层：终端消费者 | 面向用户的两种订阅方式 | `LambdaSubscriber`（简单、默认管够）、`BaseSubscriber`（钩子式手动控制）|

一句话总结这一篇：**Reactor 的背压协议本质上是"生产者和消费者之间靠 CAS 完成的一场无锁对话"**——消费者通过 `request(n)` 表达需求，生产者通过 `fastPath`/`slowPath` 两种模式响应需求，全程没有用一把锁，却能在高并发下保证数据不多发、不少发、不乱序。这也是为什么响应式编程能在高吞吐场景下比传统阻塞式编程更省资源的核心原因之一。
