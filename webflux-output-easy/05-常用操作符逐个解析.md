## 一、从一段真实代码说起

你在 Controller 里大概率写过这样的代码：

```java
public Mono<UserVO> getUser(String userId) {
    return userRepository.findById(userId)
            .map(user -> toVO(user))                    // ① 转换
            .filter(vo -> vo != null)                    // ② 过滤
            .flatMap(vo -> enrichVO(vo));                // ③ 异步补充数据
}
```

这三行代码你可能天天在写，但有没有想过：

- `map` 和 `flatMap` 看起来都是"把一个值变成另一个值"，为什么要分成两个操作符？
- `filter` 把一个值判定为不通过之后，这个值凭空消失了，背压的"配额"怎么处理？
- 如果 `map` 里的转换函数抛了异常，流会立刻崩掉吗，还是有办法恢复？

这一篇我们就带着这些问题，把 Reactor Core 里最常用的一批操作符源码过一遍，搞清楚它们到底是怎么工作的。

先说一个贯穿全篇的核心设计：**几乎所有操作符都遵循同一套模板**——继承 `InternalFluxOperator<T, R>`，实现一个 `subscribeOrReturn` 方法，返回一个内部的 `InnerOperator`（相当于一个"承上启下"的中间商）：

```
              subscribe(Subscriber)
                      │
                      ▼
          ┌───────────────────────┐
          │ InternalFluxOperator  │
          │  subscribeOrReturn()  │
          └───────────┬───────────┘
                      │ 返回一个"中间商" InnerOperator
                      ▼
          ┌───────────────────────┐
          │   上游.subscribe      │
          │   (中间商)            │
          └───────────┬───────────┘
                      │
                      ▼
          ┌───────────────────────┐
          │     中间商做的事:      │
          │  onSubscribe(转发请求) │
          │  onNext(加工后转发)    │
          │  onError(转发)         │
          │  onComplete(转发)      │
          │  request(n) → 转给上游 │
          │  cancel()  → 转给上游  │
          └───────────────────────┘
```

理解了这个"中间商"模式，你就理解了 Reactor 里 90% 操作符的骨架——**每个操作符本质上都是一个既是 Subscriber（对上游而言）又是 Publisher（对下游而言）的双面角色**，它插在上下游之间，做一些加工，然后原样转发订阅协议里的其他部分（`request`、`cancel`）。

## 二、转换类操作符

### 2.1 map——同步的一对一"变身"

**先说结论：`map` 就是把苹果变成苹果汁——一个进，一个出，而且是当场、同步完成的，不涉及任何等待。**

```java
final class FluxMap<T, R> extends InternalFluxOperator<T, R> {
    final Function<? super T, ? extends R> mapper;

    public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
        if (actual instanceof Fuseable.ConditionalSubscriber) {
            return new MapConditionalSubscriber<>((ConditionalSubscriber<? super R>) actual, mapper);
        }
        return new MapSubscriber<>(actual, mapper);
    }
}
```

跟第 04 篇讲的数据源一样，这里也区分了 `ConditionalSubscriber` 和普通 Subscriber 两条路径，先看普通路径下 `MapSubscriber` 的 `onNext`：

```java
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, actual.currentContext());
        return;
    }

    R v;
    try {
        v = mapper.apply(t);
        if (v == null) {
            throw new NullPointerException("The mapper [...] returned a null value.");
        }
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            onError(e_);
        }
        else {
            s.request(1);   // 错误被"恢复"了，向上游补一个请求
        }
        return;
    }

    actual.onNext(v);
}
```

拆开看三个关键点：

**第一，null 检查很严格。** 如果 `mapper.apply(t)` 返回 null，会直接抛 `NullPointerException`。这跟第 04 篇提到的"Reactor 不允许 null 值流经管道"是同一套原则的延续——一旦你的 `map` 函数写成了 `user -> user.getNickname()`，而 `nickname` 恰好是 null，你的流会直接报错崩掉，而不是安静地把 null 传下去。

⚠️ **踩坑提醒**：这是新手最常踩的坑之一。写 `.map(user -> user.getEmail())` 之前一定要想清楚这个字段是否可能为 null。安全的写法是 `.map(user -> Optional.ofNullable(user.getEmail()).orElse(""))`，或者用 `.mapNotNull(...)`（较新版本 Reactor 提供）。

**第二，错误恢复机制。** `Operators.onNextError` 会检查当前链上有没有配置 `onErrorContinue` 这类"错误恢复策略"。如果配置了并且成功恢复（返回 null 表示"这个错误已经被消化掉了"），那么 `map` 会执行 `s.request(1)`——**向上游多要一个值，补偿刚才因为出错而没能正常往下传递的那一次配额**。这就好比质检员发现一件不合格产品，直接把它扔掉，然后立刻在生产订单上多批一件补上，保证最终交付数量不受影响。

**第三，`done` 标志防止"僵尸消息"。** 一旦 `onError` 或 `onComplete` 被调用过，`done` 就被设成 true，之后即使又收到一个 `onNext`（这在异步竞态下是可能发生的，参考第 03 篇讲的 cancel 窗口期问题），也会被直接丢弃而不是继续处理——这是响应式流规范里"终止信号具有排他性"原则的具体体现。

### 2.2 MapConditionalSubscriber：更聪明的一条路

```java
public boolean tryOnNext(T t) {
    ...
    try {
        v = mapper.apply(t);
        ...
        return actual.tryOnNext(v);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, actual.currentContext(), s);
        if (e_ != null) {
            done = true;
            actual.onError(e_);
            return true;
        }
        else {
            return false;   // 值没被消费，但不需要额外发一次 request
        }
    }
}
```

**跟普通路径的关键区别**：`tryOnNext` 直接返回一个 boolean 告诉上游"这个值到底有没有被消费"。如果转换过程中出错但被恢复了，直接返回 `false`——上游（比如 `FluxArray`）看到这个 `false`，自然知道"这次发送不算数，配额没扣，我继续发下一个"，**完全不需要走一次额外的 `request(1)` 往返**。

这跟第 04 篇讲的 filter 场景其实是同一个优化思路——**能用一次方法调用说清楚的事，就不要额外走一次网络往返式的协议交互**。

### 2.3 map 的背压转发：最理想的 1:1 模式

```java
public void request(long n) {
    s.request(n);
}

public void cancel() {
    s.cancel();
}
```

`map` 是严格的一对一转换——上游发一个，下游收一个，中间没有任何"增加"或"减少"。所以它的背压处理最简单：下游要多少，原样转发给上游多少，不需要做任何数量上的换算。这是所有操作符里背压逻辑最简单的一种。

## 三、filter——质检员，退货要在订单上补一笔

**类比：`filter` 就像一个质检员——检查每一件产品，不合格的直接退回，但退回之后必须马上在生产订单上补一件，不然最终交付的数量就凑不齐了。**

```java
final class FluxFilter<T> extends InternalFluxOperator<T, T> {
    final Predicate<? super T> predicate;
}
```

`FilterSubscriber` 的 `onNext`：

```java
public void onNext(T t) {
    if (done) {
        Operators.onNextDropped(t, this.ctx);
        return;
    }

    boolean b;
    try {
        b = predicate.test(t);
    }
    catch (Throwable e) {
        Throwable e_ = Operators.onNextError(t, e, this.ctx, s);
        if (e_ != null) {
            onError(e_);
        }
        else {
            s.request(1);
        }
        Operators.onDiscard(t, this.ctx);
        return;
    }
    if (b) {
        actual.onNext(t);
    }
    else {
        Operators.onDiscard(t, this.ctx);
        s.request(1);   // 关键一行：过滤掉了，向上游补一个请求
    }
}
```

**这就是本篇开头提到的"质检员补单"场景的源码原型**：当 `predicate.test(t)` 返回 `false`（不合格产品）时，`filter` 做两件事——第一，调用 `Operators.onDiscard` 把这个值标记为丢弃（如果值实现了某些资源接口，比如 `Disposable`，这一步还会顺便帮你释放资源，避免内存泄漏）；第二，`s.request(1)`——**向上游再要一个值来补偿刚才被过滤掉的这个名额**。

**为什么必须补偿？** `filter` 是典型的 "N:1" 操作符——上游发的 N 个值，可能最终只有 1 个能通过传给下游。如果下游说"我要 1 个"，上游给了 1 个，结果这 1 个被 `filter` 拦下了，下游实际上什么都没收到。如果不做补偿，下游会一直等，永远等不到它要的那 1 个值——这就是"配额被吞掉了却没人负责补上"的典型 bug 场景。`s.request(1)` 就是"我刚才收下的这个名额没用上，请再给我一个"。

⚠️ **踩坑提醒**：如果你自己实现一个类似 `filter` 的自定义操作符，最容易忘记的就是这一步"补偿 request"。忘了这一步的后果是：**当上游数据大量被过滤掉时，下游会莫名其妙地"卡住不动"**——因为背压配额被静静地消耗掉了，却没有对应的补偿，最终下游等待的数据永远不会到来（表现为流"假死"，既不报错也不完成）。

**同时实现 ConditionalSubscriber：** `FilterSubscriber` 不仅对下游可能是 `ConditionalSubscriber`，它自己也**总是**实现了 `tryOnNext`——即使下游不支持这个优化，上游依然可以通过 `tryOnNext` 跟它打交道：

```java
// 如果上游是 FluxArray，下游是 filter：
// 不用 tryOnNext：array 发值 → filter.onNext → predicate false → filter 调 s.request(1) → array 才继续发
// 用 tryOnNext：  array.tryOnNext → filter.tryOnNext → predicate false → 直接返回 false，array 立刻知道继续发下一个
```

用 `tryOnNext` 路径，一次过滤只需要 2 次方法调用；不用的话，需要 3 次方法调用外加一次 `request` 往返。在数据量大、过滤比例高的场景下（比如从 100 万条里筛出 100 条），这个优化能省下大量无谓的方法调用开销。

## 四、flatMap vs map：一对一 还是 一对多、并发处理

这是新人最容易搞混的两个操作符。先用一句话讲清楚区别：

> **`map` 是同步的一对一转换，就像把一个苹果榨成一杯苹果汁——一个进，一个出，当场完成，不涉及等待。**
> **`flatMap` 是异步的一对多展开，就像把一个订单拆成多个子任务，分别交给不同的人去并发处理，最后把所有人处理完的结果汇总起来送回来——一个进，可能零个、一个或多个出，而且这些结果到达的顺序完全不可预测（谁先干完谁先交货）。**

拿业务场景对比一下：

```java
// map：一对一，同步转换，没有等待
.map(user -> toVO(user))

// flatMap：一对多，异步展开，每个 user 都会触发一次新的异步请求
.flatMap(user -> userClient.fetchUserDetail(user.getId()))
```

`map` 里的 `toVO(user)` 是一个纯函数，瞬间返回结果；而 `flatMap` 里的 `userClient.fetchUserDetail(...)` 返回的是一个新的 `Mono`/`Flux`（可能是一次 HTTP 调用），需要重新订阅、等待异步结果回来。**`flatMap` 的核心工作，就是帮你管理这些"重新订阅的内部流"，并把它们的结果按到达顺序汇总起来传给下游。**

### 4.1 flatMap 的核心参数：maxConcurrency 和 prefetch

```java
final class FluxFlatMap<T, R> extends InternalFluxOperator<T, R> {
    final Function<? super T, ? extends Publisher<? extends R>> mapper;
    final int maxConcurrency;   // 同时最多订阅多少个"内部流"
    final int prefetch;         // 每个内部流预先要多少个值
}
```

- `maxConcurrency`：好比一个订单调度系统，规定"同一时刻最多只能有 4 个工人同时干活"。`flatMap(mapper, 4)` 意味着最多同时有 4 个内部 Publisher 在被订阅、处理。
- `prefetch`：每个"工人"（内部 Publisher）一开始要预先申请多少份原材料。

⚠️ **踩坑提醒**：这是生产事故高发区。假如你写 `.flatMap(user -> httpClient.callExternalApi(user))`，且上游一次性推来 10000 个用户，**如果不显式限制 `maxConcurrency`，默认值是 `Queues.SMALL_BUFFER_SIZE`（256），这依然可能瞬间打出 256 个并发 HTTP 请求**，很容易打爆下游服务或耗尽本地连接池。真实项目中调用外部接口，几乎总是应该显式指定并发数：`.flatMap(user -> httpClient.callExternalApi(user), 10)`，把并发压到一个下游能扛住的水平。

**为什么需要 maxConcurrency 限流？** 想象一下"一对多展开"如果完全不设限：上游瞬间发来 1 万个值，每个值映射成一次数据库查询——直接同时打出 1 万个数据库连接请求，连接池秒爆、数据库直接被打挂。`maxConcurrency` 就是给这个"并发展开"套上一个闸门。

### 4.2 FlatMapMain：管理并发的"调度中心"

```java
static final class FlatMapMain<T, R> extends FlatMapTracker<FlatMapInner<R>>
        implements InnerOperator<T, R> {
    final int maxConcurrency;
    final int prefetch;
    volatile @Nullable Queue<R> scalarQueue;
    volatile boolean done;
    volatile long requested;
    volatile int wip;
}
```

`onSubscribe` 时，`FlatMapMain` 会先向上游申请 `maxConcurrency` 个初始配额：

```java
public void onSubscribe(Subscription s) {
    if (Operators.validate(this.s, s)) {
        this.s = s;
        actual.onSubscribe(this);
        s.request(Operators.unboundedOrPrefetch(maxConcurrency));
    }
}
```

**逻辑很直观：如果最多能并发处理 4 个任务，那就先向上游要 4 个值来启动这 4 个并发任务。**

### 4.3 onNext：每来一个值，就展开一个新的内部流

```java
public void onNext(T t) {
    Publisher<? extends R> p = mapper.apply(t);

    if (p instanceof Callable) {
        // 标量优化：如果这个内部 Publisher 只有一个值，直接同步取出来，不用走完整订阅流程
        R v = ((Callable<R>) p).call();
        tryEmitScalar(v);
    }
    else {
        // 正常情况：创建一个新的内部订阅者，去订阅这个内部 Publisher
        FlatMapInner<R> inner = new FlatMapInner<>(this, prefetch);
        if (add(inner)) {
            p.subscribe(inner);
        }
    }
}
```

这里出现了第 04 篇提到的**标量优化**——如果 `mapper` 返回的是一个 `Mono.just(x)` 这种"只有单个值"的 Publisher（实现了 `Callable` 接口），`flatMap` 会直接调用 `call()` 拿到值，完全跳过创建 Subscription、订阅、request、onNext 这一整套流程。

**为什么这个优化很重要？** 考虑 `Flux.range(1, 1000).flatMap(x -> Mono.just(x * 2))` 这种"看起来是异步、实际上完全同步"的场景——如果没有标量优化，每个值都要走一遍完整的内部订阅生命周期，1000 个值就是 1000 次完整的订阅链路开销，性能极差。有了标量优化，这种场景几乎跟 `map` 一样快。

### 4.4 FlatMapInner：每个"内部工人"怎么申请原材料

```java
static final class FlatMapInner<R> implements InnerConsumer<R>, Subscription {
    final FlatMapMain<?, R> parent;
    final int prefetch;
    final int limit;
    long produced;

    public void onSubscribe(Subscription s) {
        ...
        s.request(Operators.unboundedOrPrefetch(prefetch));  // 一开始就申请 prefetch 个
    }

    public void request(long n) {
        long p = produced + n;
        if (p >= limit) {
            produced = 0L;
            s.request(p);   // 攒够了才批量补货，不是每次都申请
        }
        else {
            produced = p;   // 还没攒够，先记着
        }
    }
}
```

**这里有个很实用的性能优化，叫"补货策略"（replenishing）**：每个内部工人不是每处理完一个值就立刻向自己的上游要一个新的，而是**攒着**，等攒够了一定量（`limit`，通常是 `prefetch` 的 75%）才一次性批量补货。这跟你去超市囤货是一个道理——不是吃完一个鸡蛋就跑一趟超市，而是攒到快用完的时候一次性买一批，减少跑腿次数（减少 `request` 调用的次数，降低方法调用和潜在的跨线程通信开销）。

### 4.5 融合优化：内部流也能走"直接拿"的快车道

```java
public void onSubscribe(Subscription s) {
    if (Operators.setOnce(S, this, s)) {
        if (s instanceof Fuseable.QueueSubscription) {
            int m = f.requestFusion(Fuseable.ANY | Fuseable.THREAD_BARRIER);
            if (m == Fuseable.SYNC) {
                sourceMode = Fuseable.SYNC;
                queue = f;
                done = true;
                parent.drain(null);
                return;
            }
            ...
        }
        s.request(Operators.unboundedOrPrefetch(prefetch));
    }
}
```

如果内部 Publisher 支持"融合"（比如内部又是一个 `Flux.range`），`flatMap` 会尝试直接拿到它的内部队列，跳过 `onNext` 推送，直接用 `poll()` 拉取——这跟第 04 篇讲的 SYNC 融合是同一套机制，只不过这次发生在 flatMap 的内部流上。

### 4.6 drainLoop：真正的"汇总发货"逻辑

`FlatMapMain.drainLoop()` 是整个 flatMap 里最复杂的部分，它负责把所有内部工人已经完成的成果，按照下游的请求量，汇总发送出去。核心策略是**轮询（round-robin）**：

```java
void drainLoop() {
    for (;;) {
        // 1. 先把 scalarQueue（标量优化产生的结果）清空发送
        // 2. 再轮流看每一个内部工人（FlatMapInner）有没有攒了新结果，公平地轮流取
        // 3. 每发出去一批，就检查是否要向"总调度"（上游）补货
        // 4. 有进展就继续循环，没有就退出等待下次触发
    }
}
```

**为什么要轮询而不是"谁先完成就先发谁的"？** 想象你有 4 个工人同时在干活，如果每次都优先处理跑得最快的那个工人产出的结果，跑得慢的工人的成果可能永远排不上号（"饥饿"现象）。轮询保证了**公平性**——即使某个内部流产出特别快，也不会让其他内部流的结果被无限期挤压。

### 4.7 map vs flatMap 到底怎么选

| 维度 | map | flatMap |
|---|---|---|
| 转换关系 | 一对一 | 一对多（每个值可能产生 0 个、1 个或多个结果）|
| 同步/异步 | 同步（转换函数瞬间返回结果） | 异步（转换函数返回一个新的 Publisher，需要重新订阅）|
| 返回值类型 | 普通值 `R` | `Publisher<R>`（`Mono<R>` 或 `Flux<R>`）|
| 结果顺序 | 严格保持原顺序 | 不保证顺序（并发展开，谁先完成谁先到）|
| 典型场景 | 字段转换、类型映射、简单计算 | 发起新的异步调用（HTTP、DB 查询、另一个响应式流）|
| 性能开销 | 极低 | 较高（涉及内部订阅管理，需要谨慎设置并发数）|

⚠️ **踩坑提醒**：一个非常常见的错误是在 `map` 里返回一个 `Mono` 或 `Flux`：

```java
// 错误写法：map 里塞进一个 Mono，结果类型变成 Mono<Mono<UserDetail>>，嵌套了！
.map(user -> userClient.fetchUserDetailAsync(user))

// 正确写法：这种场景应该用 flatMap，把内层的 Mono 展开
.flatMap(user -> userClient.fetchUserDetailAsync(user))
```

如果你在 `map` 里返回了一个 Publisher，编译器不会报错（因为 `Mono<T>` 也是一个合法的 `T`），但你会得到一个"套娃"结构（`Mono<Mono<UserDetail>>`），下游要多解一层套才能拿到真正的值，这基本可以断定是写错了操作符。**记住一句话：转换函数如果返回的是一个新的响应式类型（`Mono`/`Flux`），永远用 `flatMap`，不要用 `map`。**

---

## 五、concatMap——排队的一对多，不许插队

`concatMap` 跟 `flatMap` 长得很像，区别在于**并发度**：`flatMap` 允许多个内部流同时跑，`concatMap` 坚持"一次只能处理一个内部流，必须等前一个彻底完成才能开始下一个"。

**类比：`flatMap` 是把订单分给多个工人并行赶工，谁先做完先交货；`concatMap` 是只有一个工人，必须严格按订单顺序一个一个做完，绝不允许插队或者交叉完成。**

```java
enum ErrorMode {
    IMMEDIATE,  // 立即报告错误
    BOUNDARY,   // 等当前内部源结束了再报错
    END         // 所有源都结束了才报错
}
```

核心的 `drain` 逻辑，靠一个 `active` 标志来严格控制"排队"行为：

```java
void drain() {
    for (;;) {
        if (!active) {   // 只有在"没人占用"的时候才取下一个值
            T v = queue.poll();
            if (v != null) {
                Publisher<? extends R> p = mapper.apply(v);
                active = true;          // 占用标志位打开
                p.subscribe(inner);     // 订阅这个新的内部流
            }
        }
        // active = true 的时候，drain 什么都不做，只能等这个内部流自己结束
    }
}
```

**`active` 就是排队叫号系统里的"当前窗口正在服务"的灯。** 只有当前这个内部流完全处理完（触发 `innerComplete`，把 `active` 重新设为 `false`）之后，才能翻牌叫下一个号。

⚠️ **踩坑提醒**：如果你把 `active` 这个限制去掉，`concatMap` 就变成了 `flatMap`（内部流之间的结果会交错）。这也是为什么理解了 `concatMap` 的 `active` 机制之后，就能一眼看穿它和 `flatMap` 唯一的本质区别——**是否允许多个内部流同时活跃**。

**什么时候该用 concatMap 而不是 flatMap？** 当你的业务逻辑严格要求"顺序处理，后一个必须等前一个完全结束才能开始"时（比如按顺序执行一系列有依赖关系的写操作），必须用 `concatMap`。如果用了 `flatMap`，即使指定 `maxConcurrency=1`，也不能完全保证语义上的等价（`flatMap` 语义上并不承诺严格顺序，只是并发度恰好是 1）；`concatMap` 是从设计上就保证了顺序性。

`concatMap` 内部还有一个很精巧的 `guard` 机制，用来防止"内部流的结果推送"和"上游的错误信号"并发冲突——两者都想给下游发信号时，用一个 CAS 变量保证同一时刻只有一个信号真正传下去，另一个会等前一个处理完再补发。这是响应式流规范"不允许并发调用下游方法"这条铁律在源码里的具体落地。

## 六、take——吃到饱了就喊停，但要讲礼貌

`take(n)` 表示"我只要前 n 个，够了就不要了"。它的实现细节里藏着一个容易被忽视但很重要的顺序问题：

```java
public void onNext(T t) {
    long r = remaining;
    if (r == 0) {
        s.cancel();
        onComplete();
        return;
    }

    remaining = --r;
    boolean stop = r == 0L;

    actual.onNext(t);   // 关键：先把值发给下游

    if (stop) {
        s.cancel();      // 再取消上游
        onComplete();    // 再告诉下游结束了
    }
}
```

**注意顺序：先 `actual.onNext(t)`，再 `s.cancel()`。** 为什么不能反过来？

如果先 `cancel()` 再 `onNext()`，在某些融合优化场景下，上游可能在收到 `cancel` 后就立即释放了内部资源（比如关闭了一个文件句柄），这时候如果你还想把最后一个值发给下游，这个值可能已经不完整或者不可用了。**先把该发的值发出去，再动手清理，是保证数据完整性的正确顺序**——就像退租之前得先把行李搬出来，而不是先剪了钥匙才想起来东西还在屋里。

`take` 还有一个很聪明的 `request` 优化：

```java
public void request(long n) {
    if (n >= this.n) {
        s.request(Long.MAX_VALUE);   // 下游要的比 take 的总数还多，直接管够
    } else {
        s.request(n);
    }
}
```

比如 `Flux.range(1, 1000000).take(10)`，当下游请求 10 个（或更多）时，既然 `take` 本身封顶就是 10 个，直接告诉上游"管够吧"（`Long.MAX_VALUE`），让上游走第 03 篇讲过的高性能 `fastPath`，然后 `take` 自己在数到第 10 个的时候主动 `cancel`。这比"精打细算地按需要多少要多少"效率更高——反正 `take` 自己会兜底控制数量，没必要让上游也精确计量。

## 七、scan——带着记忆的累加器

`scan` 跟 `map` 很像，但它多了一个"记忆"——每次转换都会用上一次的结果：

```java
public void onNext(T t) {
    T v = value;
    if (v != null) {
        t = accumulator.apply(v, t);   // 跟上一次的累加结果一起运算
    }
    value = t;
    actual.onNext(t);
}
```

举个例子，`Flux.range(1,5).scan((a, b) -> a + b)` 会依次发出 `1, 3, 6, 10, 15`（每一步都是"当前值 + 之前累加的结果"），而不是像 `reduce` 那样只在最后吐出一个总和 `15`。**`scan` 会把每一步的中间结果都发出来，`reduce` 只关心最终结果。**

一个很值得玩味的源码细节，藏在 `cancel` 方法里的注释：

```java
public void cancel() {
    s.cancel();
    //unless we want to pay a volatile, cancel() nulling out might race with onNext
    //and result in re-setting value, retaining it. So we don't null out, nor discard.
}
```

**为什么 `cancel` 的时候不顺手把 `value` 这个累加状态清空？** 因为 `cancel` 和 `onNext` 可能来自不同的线程，是并发发生的。如果 `cancel` 把 `value` 设成 null，而恰好这时候一个"迟到的" `onNext` 正在执行（上游 cancel 生效前发出的最后一个值），它可能会重新把 `value` 设置成一个新值——相当于清空动作被"复活"覆盖了，白清了。与其加一个 `volatile` 字段勉强保证一致性（还得多付出内存屏障的性能代价），Reactor 选择干脆不清理——**接受"可能有一次值被无谓保留"这个小代价，换来逻辑上的绝对正确性**，不会因为清理不彻底导致更隐蔽的 bug。

这是个很有意思的工程取舍案例：**不是所有资源清理都值得做，有时候"不做"反而是更安全的选择。**

## 八、容错类操作符：出错之后怎么办

### 8.1 onErrorResume——换一条命继续活下去

`onErrorResume` 让你在流出错时，切换到一个"备用流"继续运行，而不是让错误直接终止一切：

```java
userRepository.findById(id)
    .onErrorResume(ex -> {
        log.warn("查询失败，返回默认用户", ex);
        return Mono.just(User.DEFAULT);
    });
```

源码里最核心的设计是一个叫 `second` 的标志位：

```java
public void onError(Throwable t) {
    if (!second) {
        second = true;
        Publisher<? extends T> p = nextFactory.apply(t);   // 生成备用流
        p.subscribe(this);   // 关键：用自己重新订阅备用流
    }
    else {
        actual.onError(t);   // 备用流也失败了，这次真的没救了，直接报错给下游
    }
}
```

**这里有个很巧妙的地方：`ResumeSubscriber` 用它自己（`this`）去订阅备用流。** 这意味着当第一次 `onError` 触发时，它把自己"嫁接"到了一个全新的 Publisher 上，对下游来说完全无感知——下游依然只看到同一个 Subscriber 在正常接收数据，根本不知道背后其实已经"偷梁换柱"过一次。

⚠️ **踩坑提醒**：如果备用流自己也出错了呢？**`onErrorResume` 不支持连环恢复**——`second` 标志一旦被设置为 `true`，第二次的 `onError` 会直接原样传给下游，不会再尝试第二次恢复。**为什么要限制成只能恢复一次？** 如果不限制，一旦你的 `nextFactory` 写得有问题（比如恢复逻辑本身也会抛异常），就会陷入"错误 → 恢复 → 又错误 → 又恢复"的无限递归订阅，最终堆栈溢出。限定"只给一次改过自新的机会"，是简单又有效的防御性设计。

### 8.2 retry——重新下单，但要补齐账目

`retry(3)` 表示"出错了就重新订阅一次，最多重试 3 次"。它的实现比 `onErrorResume` 更复杂一点，因为要考虑"如果同步的错误导致无限递归怎么办"：

```java
void resubscribe() {
    if (WIP.getAndIncrement(this) == 0) {
        do {
            if (isCancelled()) return;

            long c = produced;
            if (c != 0L) {
                produced = 0L;
                produced(c);   // 把已经消费的数量报告给背压管理器，做补偿
            }

            source.subscribe(this);   // 重新订阅原始数据源
        } while (WIP.decrementAndGet(this) != 0);
    }
}
```

**这里的 `WIP`（work-in-progress）计数器是为了防止"同步递归导致栈溢出"这个真实存在的风险。** 想象一下 `Flux.error(e).retry(3)` 这种场景——`source.subscribe(this)` 内部会**同步立即**触发 `onError`，`onError` 又会调用 `resubscribe()`，`resubscribe()` 又调用 `source.subscribe(this)`……如果没有 `WIP` 保护，这就是一条无限递归的调用链，很快就会栈溢出崩溃。

`WIP` 的 CAS 操作把这条"递归链"硬生生拗成了一个"循环"：第一次调用 `getAndIncrement` 拿到 0，进入循环体开始执行；执行过程中如果同步触发了新一轮 `resubscribe`，此时 `getAndIncrement` 拿到的是 1（不是 0），不会再进入新的循环体，只是把计数器加了一下就返回；外层循环的 `decrementAndGet` 发现减完之后计数器还不是 0（因为刚才有一次"擦肩而过"的调用把它加过），于是继续再跑一轮循环——**用一个计数器把递归"拍平"成了迭代，避免了栈溢出**。这是并发编程里一个非常经典、也非常值得学习的技巧。

另一个细节：`produced` 计数器记录了这一轮重试之前已经成功处理了多少条数据，重订阅前会把这个数字"报告"给底层的背压管理器（`produced(c)`）做补偿。**为什么需要这个补偿？** 假设下游请求了 100 条数据，上游发了 30 条之后出错重试，如果不做补偿，重新订阅之后上游又会认为"还欠 100 条"，加上之前已经发过的 30 条，最终可能会多发 30 条超出下游预期的数据。`produced(c)` 保证了"已经发过的不能重复算"，重试后的请求量依然精确对应下游真正还需要的数量。

## 九、doOnEach——不改变数据，只做"顺手观察"

`doOnEach` 是一个"窥探"型操作符——它不修改流经的数据，只是在每个信号（`onNext`/`onError`/`onComplete`）到达时执行一个副作用回调，常用来做日志埋点：

```java
userRepository.findById(id)
    .doOnEach(signal -> {
        if (signal.isOnNext()) {
            log.info("查到用户: {}", signal.get());
        } else if (signal.isOnComplete()) {
            log.info("查询流程结束");
        }
    })
```

这里有一个非常值得学习的性能优化技巧：**`DoOnEachSubscriber` 自己实现了 `Signal<T>` 接口，把自身当作 `Signal` 对象传给回调函数**，而不是每次都 `new` 一个新的 `Signal` 对象：

```java
static class DoOnEachSubscriber<T> implements InnerOperator<T, T>, Signal<T> {
    @Nullable T t;

    public @Nullable T get() { return t; }
    public SignalType getType() { return SignalType.ON_NEXT; }

    public void onNext(T t) {
        this.t = t;
        onSignal.accept(this);   // this 本身就是 Signal，不需要额外分配对象
        actual.onNext(t);
    }
}
```

**为什么要这么"抠门"？** 想象一下 `Flux.range(1, 1000000).doOnEach(s -> log.debug(...))` 这种场景，如果每次 `onNext` 都要 `new Signal(...)`，100 万次调用就是 100 万个短命的 Signal 对象，对 GC（垃圾回收）造成不小的压力。通过让 `DoOnEachSubscriber` 自己"身兼数职"——既是订阅者又是信号载体，**做到了零额外对象分配**。这是 Reactor 源码里"极致抠性能"的一个典型例子，也提醒我们：在高频调用路径上，能省一次对象分配就省一次。

还有一个容易被忽略的细节——**Mono 场景下的状态机特殊处理**：

```java
static final short STATE_MONO_START = (short) 1;
```

在 Mono 语义下，`onNext` 之后紧跟着 `onComplete` 是"隐含"的规则，但某些 Mono 实现（比如 `MonoJust`）在真实调用时可能只发了 `onNext` 就完事，没有显式再发一次 `onComplete`。`doOnEach` 的用户直觉上会期望"我在 Mono 上注册的 onComplete 回调也应该被触发一次"，所以针对 Mono 场景，`DoOnEachSubscriber` 会在 `onNext` 触发之后**自动补一次** onComplete 的信号回调，弥合这种语义上的细微差异。

## 十、buffer 和 distinct：分批与去重

### 10.1 buffer——攒一批再交货

`buffer(size)` 把连续的多个值打包成一个集合再往下发，常用来做批量处理（比如攒够 100 条日志再一次性批量写库）。它有三种模式，靠 `size` 和 `skip` 两个参数的关系决定：

```java
if (size == skip) {
    return new BufferExactSubscriber<>(...);   // 每 size 个打一包，不重叠不遗漏
}
else if (skip > size) {
    return new BufferSkipSubscriber<>(...);    // 每 skip 个里取 size 个，中间跳过一些
}
else {
    return new BufferOverlappingSubscriber<>(...);  // 每 skip 个开始新的一包，包和包之间有重叠（滑动窗口）
}
```

| 模式 | 举例（size=3） | 效果 |
|---|---|---|
| Exact（size == skip） | `buffer(3)` | `[1,2,3] [4,5,6] [7,8,9]`，不重叠不遗漏 |
| Skip（skip > size） | `buffer(2, 3)` | `[1,2] [4,5] [7,8]`，每 3 个里只取前 2 个，第 3 个直接跳过 |
| Overlapping（skip < size） | `buffer(3, 1)` | `[1,2,3] [2,3,4] [3,4,5]`，像滑动窗口一样有重叠 |

`buffer` 的背压转换也很直观——下游要 n 个"批次"，上游就要转换成需要 `n * size` 个原始值：

```java
public void request(long n) {
    s.request(Operators.multiplyCap(n, size));   // 乘法同样有防溢出保护
}
```

这跟第 03 篇讲的 `addCap`（加法防溢出）是同一个思路的乘法版本——`multiplyCap` 防止 `n * size` 算出来直接溢出成负数。

### 10.2 distinct——去重，也要遵守配额补偿的规矩

`distinct()` 会记住见过的值，重复的值直接丢弃不往下传。跟 `filter` 一样，**丢弃动作也要补偿请求配额**：

```java
public void onNext(T t) {
    if (!tryOnNext(t)) {
        s.request(1);   // 重复值被丢弃了，补一个请求
    }
}
```

这跟前面 `filter` 的补偿逻辑一模一样——**任何"可能丢弃数据"的操作符，都必须在丢弃发生时向上游补偿相应的请求配额**，否则就会出现"下游永远等不到期望数量的数据"这种诡异的假死问题。这是贯穿整个 Reactor 操作符体系的一条铁律，理解了这条规律，你看任何一个新的、会过滤/丢弃数据的操作符源码时都会心里有数——**先找它在哪里丢弃数据，再确认它有没有在旁边补一句 `request(1)`**。

`FluxDistinct` 的设计比想象中更灵活，它不是写死用 `HashSet` 去重，而是通过四个可插拔的函数式接口支持自定义去重逻辑：

```java
final Function<? super T, ? extends K> keyExtractor;   // 从值里提取"去重依据"
final Supplier<C> collectionSupplier;                    // 创建去重用的容器，比如 HashSet::new
final BiPredicate<C, K> distinctPredicate;               // 判断这个 key 是不是第一次出现
final Consumer<C> cleanupCallback;                        // 用完之后怎么清理容器
```

比如你想按照"用户的手机号"去重而不是整个对象去重，可以写 `.distinct(User::getPhone)`——`keyExtractor` 就是提取手机号这个逻辑。

## 十一、归纳总结表

### 11.1 操作符核心特性对照表

| 操作符 | 类名 | 一句话讲清楚 | 背压模型 | 出错/丢弃时是否要补偿 request |
|---|---|---|---|---|
| map | FluxMap | 同步一对一转换，苹果变苹果汁 | 1:1 直接透传 | 是（如果配置了错误恢复）|
| filter | FluxFilter | 质检员，不合格就退货 | N:1，需要补偿 | 是，过滤掉一定要补 |
| flatMap | FluxFlatMap | 异步一对多，订单拆给多个工人并发干 | M:N，受 maxConcurrency 限制 | 内部自行管理 |
| concatMap | FluxConcatMap | 异步一对多，但排队不许插队 | M:1，严格顺序 | 内部自行管理 |
| take | FluxTake | 吃到饱了喊停，先上菜再撤桌 | 有限截取 | 不涉及丢弃补偿 |
| scan | FluxScan | 带记忆的累加器，每步都吐出中间结果 | 1:1 透传 | 不涉及 |
| onErrorResume | FluxOnErrorResume | 出错了换一条命接着活，但只能换一次 | 切换数据源 | 不涉及 |
| retry | FluxRetry | 出错重新下单，账目要对齐 | 重新订阅 | 用 produced 补偿数量 |
| doOnEach | FluxDoOnEach | 不改数据，顺手打个日志 | 1:1 透传 | 不涉及 |
| buffer | FluxBuffer | 攒一批再交货 | 1:N，乘法换算 | 极端情况下（容器满）会补偿 |
| distinct | FluxDistinct | 见过的不要重复上 | N:1，需要补偿 | 是，重复值一定要补 |

### 11.2 关键设计模式总结

| 设计模式 | 哪些操作符用了 | 解决了什么问题 |
|---|---|---|
| tryOnNext / ConditionalSubscriber | map、filter、take、doOnEach、distinct | 让上游直接知道"这个值有没有被消费"，省去一次 request 往返 |
| 标量优化（Callable 检查） | flatMap、concatMap | 如果内部流只有一个值，跳过整套订阅流程直接拿值 |
| WIP 计数器（CAS 串行化） | flatMap 的 drainLoop、retry 的 resubscribe、concatMap 的 drain | 把可能的递归调用拍平成循环，避免栈溢出，同时保证同一时刻只有一个线程在处理 |
| 补偿 request(1) | filter、distinct、map（错误恢复时） | 任何丢弃数据的动作，都要向上游补偿对应的请求配额，否则下游会假死 |
| 自实现 Signal（零分配） | doOnEach | 高频调用路径上避免创建大量短命对象，减轻 GC 压力 |
| 标志位防重入（second / active / done）| onErrorResume（second）、concatMap（active）、几乎所有操作符（done）| 用一个简单的布尔或整型状态位，防止终止逻辑被重复执行或信号交叉 |

一句话总结这一篇：**几乎所有操作符的复杂度，都来自于"怎么在加工数据的同时，不破坏背压协议"这一个核心矛盾**。map 因为是严格一对一，最简单；filter/distinct 因为会丢数据，必须补偿配额；flatMap/concatMap 因为要处理"一对多"，必须解决并发控制和顺序问题；retry/onErrorResume 因为涉及重新订阅，必须解决递归和账目对齐问题。下次你在业务代码里看到某个操作符行为"诡异"（比如流卡住不动、并发数超出预期、数据顺序乱了），回头对照这篇文章里对应操作符的源码逻辑，通常都能找到根因。
