# 从零到一：当你写下一行 WebFlux 代码，底层到底发生了什么？

> **Reactor Core 源码解析 · 易懂版 00**
>
> 本篇用"讲故事"的方式，带你从一个真实的 WebFlux Controller 场景出发，一步步追踪 Reactor 源码的执行过程。不需要提前精通源码，只要你写过 `Mono`/`Flux` 的基础用法就能看懂。

---

## 开场：一个你每天都在写的场景

假设你在项目里写了这样一个接口：

```java
@RestController
public class UserController {

    @Autowired
    private UserService userService;

    @GetMapping("/users/{id}")
    public Mono<User> getUser(@PathVariable Integer id) {
        return userService.getUserById(id)
                .map(user -> {
                    user.setName(user.getName().toUpperCase());
                    return user;
                });
    }
}
```

当一个 HTTP 请求打到这个接口时，从 Netty 接收请求、到 Reactor 执行你的 `map` 逻辑、再到最终返回 JSON，这条链路上到底发生了什么？

**你可能会问：我只是写了一行 `.map()`，Reactor 怎么就知道什么时候执行我的 Lambda 的？数据是谁"推"给谁的？`subscribe()` 到底干了什么？**

别急，我们从最简单的例子开始，一层层拆解。这篇文章用 7 个由浅入深的例子，把 Reactor 的执行全流程讲透。

---

## 在开始之前：你需要知道的两个阶段

Reactor 的执行分成两个泾渭分明的阶段，理解这一点至关重要：

**阶段一：装配（Assembly）** —— 你写链式调用 `.map().filter().subscribe()` 的时候，Reactor 只是在创建一堆 Java 对象，像搭积木一样把它们串起来。**此时没有任何数据流动。**

**阶段二：订阅（Subscription）** —— 当 `subscribe()` 被调用的那一刻（在 WebFlux 中，框架帮你调了），整条链才"活"过来：信号从下游往上游传，数据从上游往下游流。

用一个生活类比来理解：

> 装配阶段就像在工厂里搭建流水线——你把传送带、质检台、包装台一个接一个排好，但机器还没通电。
>
> 订阅阶段就是按下启动按钮——电通了，原材料开始从第一个工位流向最后一个工位。

记住这个类比，后面我们会反复用到。

## 示例一：最简单的链 —— 理解"装配"和"订阅"

### 从业务角度看

先用一个极简的例子把核心流程跑通：

```java
Flux.just(1, 2, 3)
    .map(n -> n * 10)
    .subscribe(n -> System.out.println(n));
// 输出：10, 20, 30
```

你可能觉得这太简单了，但请问：**这三行代码到底创建了几个对象？数据 `1, 2, 3` 是谁发出来的？`n * 10` 这个计算是在哪个方法里被调用的？**

### 装配阶段：搭积木

**第一步：`Flux.just(1, 2, 3)` 创建了什么？**

这行代码调用了 `Flux` 的静态工厂方法，最终创建了一个 `FluxArray` 对象：

```java
// Flux.java 内部
public static <T> Flux<T> just(T... data) {
    return fromArray(data);  // 最终 new FluxArray<>(data)
}
```

`FluxArray` 就是一个"积木块"，它内部存了一个数组 `[1, 2, 3]`，仅此而已。它实现了 `Fuseable` 接口（后面会讲这是个优化标记）和 `SourceProducer` 接口（标记自己是数据源头）。

**第二步：`.map(n -> n * 10)` 创建了什么？**

这行代码在 `FluxArray` 上调用 `map` 方法，创建了一个新的对象 `FluxMapFuseable`：

```java
// Flux.java 内部
public final <V> Flux<V> map(Function<? super T, ? extends V> mapper) {
    if (this instanceof Fuseable) {
        return new FluxMapFuseable<>(this, mapper);  // 走这条路，因为 FluxArray 是 Fuseable
    }
    return new FluxMap<>(this, mapper);
}
```

`FluxMapFuseable` 里面有两个关键字段：
- `source` = 上一步创建的 `FluxArray`（指向上游）
- `mapper` = `n -> n * 10`（你写的转换逻辑）

> **这里有一个容易忽略的细节**：`map()` 方法会检查上游是否实现了 `Fuseable` 接口。如果是，就创建带 Fuseable 后缀的版本。这是 Reactor 的一种性能优化，叫"操作符熔合"——两个相邻的操作符可以合并执行，减少中间对象的创建。你现在不需要完全理解熔合，知道它的存在就好。

此时的对象关系图：

```
FluxMapFuseable
  ├── source = FluxArray(array = [1, 2, 3])
  └── mapper = n -> n * 10
```

> 流水线类比：你搭好了两个工位。第一个工位（FluxArray）负责"从仓库取出原材料 1、2、3"，第二个工位（FluxMapFuseable）负责"把每个数字乘以 10"。但机器还没通电，工人还没上岗。

**第三步：`.subscribe(n -> System.out.println(n))` 干了什么？**

这一步做了两件事：先创建一个"终端消费者"对象，然后触发整条链的订阅。

```java
// 内部创建了 LambdaSubscriber
LambdaSubscriber<Integer> subscriber = new LambdaSubscriber<>(
    n -> System.out.println(n),  // 你的打印逻辑
    null,                         // 错误处理（你没传）
    null,                         // 完成处理（你没传）
    null,                         // Subscription 处理（你没传）
    Context.empty()
);
```

`LambdaSubscriber` 就是流水线的最后一个工位——"把成品拿出来展示给客户看"。

### 订阅阶段：按下启动按钮

装配完毕，现在 `subscribe()` 被调用了。接下来发生的事情可以分成几个小步骤：

#### 步骤 1：优化循环 —— 从下游往上游"串线"

Reactor 用一个 `while(true)` 循环来完成订阅，而不是递归调用。这个设计非常巧妙——我们后面在示例二中详细讨论，这里先看执行结果。

循环执行到 `FluxMapFuseable` 时，调用它的 `subscribeOrReturn` 方法：

```java
// FluxMapFuseable.subscribeOrReturn
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super R> actual) {
    // actual 就是 LambdaSubscriber
    return new MapFuseableSubscriber<>(actual, mapper);
    // 返回一个"中间工人"——MapFuseableSubscriber
}
```

这步创建了 `MapFuseableSubscriber`，它是一个"中间人"：
- `actual` 字段指向下游的 `LambdaSubscriber`（"我加工完了交给谁"）
- `mapper` 字段存着转换函数 `n -> n * 10`（"我负责做什么加工"）

循环继续往上走，发现上游 `FluxArray` 不是 `OptimizableOperator`（它是源头，不是操作符），循环结束。然后调用 `FluxArray.subscribe(MapFuseableSubscriber)`。

#### 步骤 2：源头创建 Subscription —— 原材料准备好了

`FluxArray.subscribe` 内部创建了 `ArraySubscription`：

```java
// FluxArray.subscribe 内部
s.onSubscribe(new ArraySubscription<>(s, array));
// s = MapFuseableSubscriber, array = [1, 2, 3]
```

`ArraySubscription` 就像仓库管理员——它手里有原材料 `[1, 2, 3]`，并且知道该把货交给谁（`MapFuseableSubscriber`）。

#### 步骤 3：onSubscribe 传播 —— "我准备好了！"

`ArraySubscription` 被创建后，立刻调用 `MapFuseableSubscriber.onSubscribe(ArraySubscription)`。`MapFuseableSubscriber` 做了两件事：
1. 把 `ArraySubscription` 存起来（"我知道找谁要原材料了"）
2. 调用 `LambdaSubscriber.onSubscribe(this)`（"告诉下游，我也准备好了"）

> 流水线类比：从最上游到最下游，每个工位依次喊"我准备好了！"，最终传到终端消费者。

#### 步骤 4：request —— "给我来货！"

`LambdaSubscriber` 在 `onSubscribe` 中自动调用了 `request(Long.MAX_VALUE)`——意思是"有多少给多少，我全要"：

```java
// LambdaSubscriber.onSubscribe 内部
if (subscriptionConsumer != null) {
    subscriptionConsumer.accept(s);
} else {
    s.request(Long.MAX_VALUE);  // 你没传 subscriptionConsumer，所以走这里
}
```

这个 `request` 信号沿着链条往回传：

```
LambdaSubscriber → request(MAX) → MapFuseableSubscriber → request(MAX) → ArraySubscription
```

> **你可能会问：为什么不直接发数据，还要"请求"？**
>
> 这就是响应式编程的背压（Backpressure）机制。下游告诉上游"我能处理多少"，上游按量发送。在这个例子里，`Long.MAX_VALUE` 相当于说"别限制我，全给我"，但在实际的网络请求场景中，下游可能只请求 256 个，处理完了再要下一批——防止内存被撑爆。

#### 步骤 5：数据发射 —— fastPath

`ArraySubscription` 收到 `request(Long.MAX_VALUE)` 后，进入 `fastPath()`（因为请求量是无界的，可以走快车道）：

```java
void fastPath() {
    final T[] a = array;          // [1, 2, 3]
    final Subscriber<? super T> s = actual;  // MapFuseableSubscriber

    for (int i = index; i != a.length; i++) {
        if (cancelled) return;
        T t = a[i];
        if (t == null) { s.onError(...); return; }
        s.onNext(t);              // 把 1, 2, 3 依次交给 MapFuseableSubscriber
    }
    s.onComplete();               // 发完了！
}
```

每次 `s.onNext(t)` 调用 `MapFuseableSubscriber.onNext`：

```java
// MapFuseableSubscriber.onNext
public void onNext(T t) {
    R v = mapper.apply(t);     // 1 * 10 = 10, 2 * 10 = 20, 3 * 10 = 30
    actual.onNext(v);          // 把 10, 20, 30 交给 LambdaSubscriber
}
```

`LambdaSubscriber.onNext(10)` 内部调用你传入的 `consumer.accept(10)`，也就是 `System.out.println(10)`。

最终屏幕输出 `10, 20, 30`。

### 完整时序回顾

```
装配：
  Flux.just(1,2,3)    → 创建 FluxArray
  .map(n -> n*10)      → 创建 FluxMapFuseable（source 指向 FluxArray）
  .subscribe(println)  → 创建 LambdaSubscriber

订阅：
  优化循环创建 MapFuseableSubscriber(actual=LambdaSubscriber)
  FluxArray 创建 ArraySubscription
  onSubscribe 从上游传到下游：ArraySubscription → MapFuseableSubscriber → LambdaSubscriber
  request 从下游传到上游：LambdaSubscriber → MapFuseableSubscriber → ArraySubscription
  数据从上游流到下游：ArraySubscription →[1]→ MapFuseableSubscriber →[10]→ LambdaSubscriber → 打印
                       →[2]→                    →[20]→               → 打印
                       →[3]→                    →[30]→               → 打印
  onComplete 从上游传到下游
```

> 恭喜！你已经理解了 Reactor 最核心的执行模型。后面的示例都是在这个基础上增加更多机制。

## 示例二：加上 filter —— 优化循环和补偿机制

### 从业务角度看

```java
Flux.just(1, 2, 3, 4, 5)
    .map(n -> n * 10)
    .filter(n -> n >= 30)
    .subscribe(n -> System.out.println(n));
// 输出：30, 40, 50
```

这个例子比示例一多了一个 `filter`。**关键问题：当 filter 把 10 和 20 丢掉的时候，底层发生了什么？**

### 优化循环：为什么用 while 而不用递归？

先说一个重要的架构设计。在示例一中我们提到了"优化循环"，现在来详细讲讲。

假设你写了一条 100 个操作符的链（在复杂业务中并不罕见）。如果用传统递归方式订阅：

```
op100.subscribe(subscriber)
  → op99.subscribe(wrappedSubscriber)    // 第1层栈帧
    → op98.subscribe(wrappedSubscriber)  // 第2层栈帧
      → ... 100层递归 ...               // StackOverflowError!
```

每个操作符的 `subscribe` 调用都会在 Java 调用栈上留一层。100 层可能还撑得住，但如果是 `flatMap` 嵌套 `flatMap`，链的深度可能成千上万。

Reactor 的解决方案是 `InternalFluxOperator.subscribe` 中的 `while(true)` 循环：

```java
public final void subscribe(CoreSubscriber<? super O> subscriber) {
    OptimizableOperator operator = this;
    try {
        while (true) {
            subscriber = operator.subscribeOrReturn(subscriber);
            if (subscriber == null) return;  // 操作符自己搞定了

            OptimizableOperator newSource = operator.nextOptimizableSource();
            if (newSource == null) {
                // 到达源头了，直接订阅
                operator.source().subscribe(subscriber);
                return;
            }
            operator = newSource;  // 继续下一轮
        }
    } catch (Throwable e) {
        Operators.reportThrowInSubscribe(subscriber, e);
    }
}
```

不管链有多深，所有操作符的"创建内部 Subscriber"这一步都在**同一个栈帧**里完成。O(1) 的栈深度，永远不会爆栈。

> 流水线类比：传统递归就像"我让 A 去叫 B，B 去叫 C，C 去叫 D..."——每个人都在等下一个人回话，队伍越长等得越久。优化循环就像"工头从队尾走到队头，依次拍每个人的肩膀说'准备好了'"——一个人走一遍就搞定，不管队伍多长。

### 回到这个例子：两个操作符的优化循环

```
while(true) 循环：
  迭代1: operator = FluxFilterFuseable
         创建 FilterFuseableSubscriber(actual = LambdaSubscriber)
         nextOptimizableSource() → FluxMapFuseable（上游是 OptimizableOperator）

  迭代2: operator = FluxMapFuseable
         创建 MapFuseableSubscriber(actual = FilterFuseableSubscriber)
         nextOptimizableSource() → null（FluxArray 不是 OptimizableOperator）

  循环结束 → FluxArray.subscribe(MapFuseableSubscriber)
```

两轮迭代，创建了两个内部 Subscriber，嵌套关系是：
```
MapFuseableSubscriber → FilterFuseableSubscriber → LambdaSubscriber
```

### filter 丢弃元素时的补偿请求

当数据开始流动，关键场景出现了：

```
ArraySubscription 发射 1 → MapFuseableSubscriber.onNext(1) → 变成 10
  → FilterFuseableSubscriber.onNext(10)
    → predicate.test(10) = false（10 < 30，不通过）
    → Operators.onDiscard(10, ctx)     ← 通知"有元素被丢弃了"
    → s.request(1)                     ← 关键！向上游补偿请求

ArraySubscription 发射 2 → MapFuseableSubscriber.onNext(2) → 变成 20
  → FilterFuseableSubscriber.onNext(20)
    → predicate.test(20) = false（20 < 30）
    → s.request(1)                     ← 再次补偿

ArraySubscription 发射 3 → MapFuseableSubscriber.onNext(3) → 变成 30
  → FilterFuseableSubscriber.onNext(30)
    → predicate.test(30) = true（通过！）
    → actual.onNext(30)                ← 转发给 LambdaSubscriber → 打印 30
```

**为什么 filter 丢弃时要 `request(1)`？**

> 想象你在餐厅点了 3 道菜。服务员端来一道，你尝了一口觉得不好吃退回去了。这时候你得告诉厨房"再做一道"——否则厨房以为你已经收到一道了，只会再给你做 2 道，最终你只收到 2 道菜。
>
> `request(1)` 就是在说"刚才那个不算，再给我一个"。

### SYNC 熔合：更极致的优化

在上面的分析中，filter 每丢弃一个元素都要调一次 `request(1)`，这个调用需要穿越整条操作符链。有没有更高效的方式？

有，就是 SYNC 熔合。当上游（`FluxArray`）支持同步拉取模式时，filter 可以直接用 `poll()` 从上游拉数据，而不需要等上游 `push`：

```
FilterFuseableSubscriber.poll() 内部：
  循环 {
    T v = MapFuseableSubscriber.poll()   // 问 map 要数据
              → ArraySubscription.poll() // map 再问数组要数据
                  → return array[index++]
              → return mapper.apply(v)   // map 转换后返回
    if (predicate.test(v)) return v;     // 通过就返回
    // 不通过？直接跳过，继续 poll 下一个，不需要 request(1)！
  }
```

> 流水线类比：原来的模式是"下游等上游送货"（push）。熔合模式是"下游自己去上游工位拿货"（pull）。自己拿货的好处是：如果拿到的东西不满意，直接拿下一个，不需要打电话让上游重新送一趟。

## 示例三：publishOn —— 数据是怎么跨线程的

### 从业务角度看

```java
Flux.range(1, 5)
    .map(n -> n * 2)
    .publishOn(Schedulers.parallel())
    .subscribe(n -> System.out.println(Thread.currentThread().getName() + ": " + n));
// 输出类似：parallel-1: 2, parallel-1: 4, parallel-1: 6, ...
```

上游的 `range` 和 `map` 在主线程执行，但 `subscribe` 的消费逻辑跑在了 `parallel` 线程上。**`publishOn` 是怎么做到跨线程传递数据的？**

### 核心原理：队列 + Worker 线程

`publishOn` 的本质其实很简单——一个生产者-消费者模型：

```
main 线程:  上游把数据放进一个队列（queue.offer）
parallel-1 线程:  Worker 从队列中取出数据（queue.poll），交给下游
```

> 生活类比：`publishOn` 就像外卖平台。厨师（上游）做好菜放到取餐台（队列），骑手（Worker 线程）取走送到客户手里（下游）。厨师和骑手可以同时工作，互不阻塞。

### 详细执行流程

**装配时**，创建了 `FluxPublishOn`，它有几个关键参数：
- `scheduler` = `ParallelScheduler`（线程池）
- `prefetch` = 256（预取数量，默认值）

**订阅时**，`PublishOnSubscriber` 被创建。它有几个关键字段：
- `queue`：存放数据的队列
- `worker`：从 Scheduler 借来的一个工作线程
- `wip`（work-in-progress）：一个 CAS 计数器，确保同一时刻只有一个线程在消费队列

**数据流动**：

```
main 线程：
  FluxRange 发射 1 → MapFuseableSubscriber.onNext(1) → 变成 2
    → PublishOnSubscriber.onNext(2)
      → queue.offer(2)                    ← 数据进队列
      → trySchedule()                     ← 尝试调度 Worker
        → WIP 从 0 CAS 到 1 → 成功！
        → worker.schedule(this)           ← 安排 Worker 线程执行 run()

  FluxRange 发射 2 → ... → 变成 4
    → PublishOnSubscriber.onNext(4)
      → queue.offer(4)
      → trySchedule()
        → WIP.getAndIncrement() 返回 1（不是 0）→ 已经有人在干活了，不重复调度

  ... 类似地，5、6、7、8、10 也入队 ...

parallel-1 线程：
  PublishOnSubscriber.run()
    → 循环 poll 队列：
      → queue.poll() = 2 → LambdaSubscriber.onNext(2) → 打印 "parallel-1: 2"
      → queue.poll() = 4 → LambdaSubscriber.onNext(4) → 打印 "parallel-1: 4"
      → ...
```

### WIP 的精妙设计

`trySchedule` 中的 `WIP.getAndIncrement(this) != 0` 检查非常巧妙。它解决了一个问题：**当多个元素快速入队时，怎么保证只调度一次 Worker？**

```java
void trySchedule(...) {
    if (WIP.getAndIncrement(this) != 0) {
        // WIP 之前不是 0，说明已经有线程在消费了，直接返回
        return;
    }
    // WIP 之前是 0，我是第一个，负责调度 Worker
    worker.schedule(this);
}
```

> 类比：想象一个公告栏。第一个发现公告栏是空的（WIP=0）的人负责去叫骑手过来取餐。后来的人看到公告栏上已经有标记了（WIP>0），就不用再叫了——骑手已经在路上了。

### prefetch 和补货机制

`PublishOnSubscriber` 在 `onSubscribe` 时会向上游请求 `prefetch`（默认 256）个数据。当消费了 75% 的预取量（即 192 个）时，会再向上游请求一批：

```
if (consumed == limit) {  // limit = prefetch * 75% = 192
    s.request(consumed);  // 告诉上游"再给我 192 个"
    consumed = 0;
}
```

> 类比：超市货架容量是 256 瓶饮料。当卖出了 192 瓶（75%），就通知仓库"再送一批 192 瓶过来"。不等卖完再补货，是为了避免货架空置——类比到 Reactor，就是避免 Worker 线程空转等待数据。

## 示例四：subscribeOn —— 把"搭流水线"这件事搬到另一个线程

### 从业务角度看

```java
Mono.fromCallable(() -> {
        // 假设这是一个阻塞的数据库调用
        return userRepository.findById(1);
    })
    .subscribeOn(Schedulers.boundedElastic())
    .subscribe(user -> System.out.println(user));
```

**你可能会问：`subscribeOn` 和 `publishOn` 有什么区别？**

一句话总结：
- **`publishOn` 影响下游** —— 改变的是数据发给下游时用哪个线程。上游该在哪个线程还是在哪个线程。
- **`subscribeOn` 影响上游** —— 改变的是"订阅上游"这个动作用哪个线程。如果上游是同步源（比如阻塞 DB 调用），那数据发射也在这个线程上。

> 厨房类比：`publishOn` 是"换了一个骑手来送菜"——厨师没变，还是在原来的厨房做菜。`subscribeOn` 是"换了一个厨师来做菜"——厨师变了，做菜的厨房也变了。

### 执行流程

```java
// subscribeOrReturn 内部
public CoreSubscriber<? super T> subscribeOrReturn(CoreSubscriber<? super T> actual) {
    Worker worker = scheduler.createWorker();
    SubscribeOnSubscriber<T> parent = new SubscribeOnSubscriber<>(source, actual, worker, ...);
    actual.onSubscribe(parent);   // 在当前线程告诉下游"准备好了"
    worker.schedule(parent);       // 在 Worker 线程上执行 parent.run()
    return null;                   // 返回 null！优化循环到此为止
}
```

注意 `return null`！这意味着 `subscribeOn` 不让优化循环继续往上走——它自己在 Worker 线程上调用 `source.subscribe(this)`：

```java
// SubscribeOnSubscriber.run() —— 在 boundedElastic 线程上执行
public void run() {
    source.subscribe(this);  // 在 Worker 线程上订阅上游
}
```

所以上游的整个订阅过程（包括 `onSubscribe`、`request`、`onNext`）都在 `boundedElastic` 线程上执行。对于阻塞的 DB 调用，这正好避免了阻塞 Netty 的 EventLoop 线程。

### 为什么多个 subscribeOn 只有最上面那个生效？

```java
flux.subscribeOn(A).subscribeOn(B).subscribe();
```

执行过程：
1. `subscribeOn(B)` 先执行，在 B 线程上订阅 `subscribeOn(A)`
2. `subscribeOn(A)` 在 B 线程收到订阅后，又创建了 A 线程，在 A 线程上订阅真正的源

最终源是在 A 线程上被订阅的。所以**离源头最近的 `subscribeOn` 决定了源的执行线程**。

> 类比：你让实习生 B 去叫大厨 A 过来做菜。不管你让几个实习生中间传话，最终做菜的还是大厨 A。

⚠️ **踩坑提醒**：在 WebFlux 项目中，千万不要在 Netty EventLoop 线程上执行阻塞操作（JDBC、Thread.sleep 等）。如果必须调用阻塞 API，一定要用 `subscribeOn(Schedulers.boundedElastic())` 把它挪到弹性线程池上。否则 EventLoop 被阻塞后，整个服务器的吞吐量会断崖式下降。

## 示例五：onErrorResume —— 出错了怎么办

### 从业务角度看

```java
// 真实场景：先查主库，主库出错了降级查缓存
public Mono<User> getUser(int id) {
    return userRepository.findById(id)
        .onErrorResume(ex -> {
            log.warn("主库查询失败，降级到缓存", ex);
            return cacheService.getUserFromCache(id);
        });
}

// 等效的简化示例
Flux.range(1, 5)
    .map(n -> {
        if (n == 3) throw new RuntimeException("boom");
        return n;
    })
    .onErrorResume(e -> Flux.just(99))
    .subscribe(n -> System.out.println(n));
// 输出：1, 2, 99
```

**你可能会问：`onErrorResume` 和 try-catch 有什么区别？它怎么在运行时"切换"到另一个数据源？**

### 核心：ResumeSubscriber 的"二次订阅"

`onErrorResume` 在装配时创建了 `FluxOnErrorResume`，它的核心是 `ResumeSubscriber`。这个 Subscriber 里有一个关键的 `boolean second` 字段，用来跟踪当前是"第一次"还是"第二次"。

```java
// ResumeSubscriber 核心逻辑
public void onError(Throwable t) {
    if (!second) {
        second = true;  // 标记：我要切换了！

        Publisher<? extends T> fallback = nextFactory.apply(t);
        // nextFactory = e -> Flux.just(99)
        // fallback = Flux.just(99)

        fallback.subscribe(this);  // 用同一个 ResumeSubscriber 订阅备用源！
    } else {
        actual.onError(t);  // 备用源也出错了？那没办法了，向下传
    }
}
```

执行过程：

```
FluxRange 发射 1 → map(1) = 1 → ResumeSubscriber.onNext(1) → 打印 1
FluxRange 发射 2 → map(2) = 2 → ResumeSubscriber.onNext(2) → 打印 2
FluxRange 发射 3 → map(3) → 抛出 RuntimeException("boom")
  → ResumeSubscriber.onError(boom)
    → second = true
    → Flux.just(99).subscribe(this)  ← 用同一个 Subscriber 订阅备用源
      → ResumeSubscriber.onSubscribe(新的 Subscription)  ← 注意：second 为 true 时不再通知下游
      → ResumeSubscriber.onNext(99) → 打印 99
      → ResumeSubscriber.onComplete() → 完成
```

**巧妙之处**：`ResumeSubscriber` 用 `second` 标记来区分第一次订阅和第二次订阅。第一次 `onSubscribe` 时会通知下游（`actual.onSubscribe(this)`），第二次就不通知了——因为下游已经在第一次时收到了 Subscription，不需要再通知。

> 类比：你在网上买了一本书，物流说丢了（onError）。电商平台没有让你重新下单，而是直接从另一个仓库补发了一本（fallback.subscribe）。你的订单号（Subscription）没变，快递员（ResumeSubscriber）也没变，只是发货仓库换了。

⚠️ **踩坑提醒**：`onErrorResume` 只恢复一次。如果备用源也出错，错误会直接传给下游。这是通过 `second` 布尔值保证的——防止无限恢复导致死循环。

## 示例六：flatMap —— 一变多的并发魔法

### 从业务角度看

```java
// 真实场景：根据用户 ID 列表批量查询用户详情
Flux.fromIterable(userIds)
    .flatMap(id -> userRepository.findById(id))  // 每个 ID 发起一次查询
    .collectList()
    .subscribe(users -> System.out.println(users));

// 简化示例
Flux.range(1, 3)
    .flatMap(n -> Flux.range(n * 10, 2))
    .subscribe(n -> System.out.println(n));
// 可能输出：10, 11, 20, 21, 30, 31（顺序不保证！）
```

**你可能会问：`flatMap` 和 `map` 有什么区别？**

- `map`：一对一转换。一个 Integer 进去，一个 String 出来。
- `flatMap`：一对多转换。一个 Integer 进去，一个 `Flux<Integer>`（或 `Mono<Integer>`）出来，然后 flatMap 帮你"拍平"——把多个内部流的数据合并到一个流里。

### 核心：FlatMapMain 和多个 FlatMapInner

`flatMap` 的内部结构比前面的操作符复杂得多：

```
FlatMapMain（总调度员）
  ├── actual = LambdaSubscriber（下游）
  ├── mapper = n -> Flux.range(n*10, 2)
  ├── maxConcurrency = 256（最多同时订阅 256 个内部流）
  ├── inners = [FlatMapInner1, FlatMapInner2, ...]（活跃的内部订阅者）
  └── mainQueue（内部流的数据汇集到这里）
```

执行过程：

```
FluxRange 发射 1 → FlatMapMain.onNext(1)
  → mapper.apply(1) = Flux.range(10, 2)
  → 创建 FlatMapInner → 订阅 Flux.range(10, 2)
  → FlatMapInner 收到 10, 11 → 汇报给 FlatMapMain → 传给下游

FluxRange 发射 2 → FlatMapMain.onNext(2)
  → mapper.apply(2) = Flux.range(20, 2)
  → 创建另一个 FlatMapInner → 订阅 Flux.range(20, 2)
  → FlatMapInner 收到 20, 21 → 汇报给 FlatMapMain → 传给下游

FluxRange 发射 3 → FlatMapMain.onNext(3)
  → 创建又一个 FlatMapInner → 订阅 Flux.range(30, 2)
  → ...
```

因为多个内部流可能并发产生数据，所以最终的输出顺序是不确定的——`10, 20, 11, 30, 21, 31` 都有可能。这就是 `flatMap` 的"交错"特性。

⚠️ **踩坑提醒**：如果你需要保证顺序，用 `concatMap` 而不是 `flatMap`。`concatMap` 会等一个内部流完成后才订阅下一个，保证输出顺序与输入顺序一致。但代价是没有并发能力——性能可能更差。

### maxConcurrency 安全阀

`flatMap` 的 `maxConcurrency` 参数（默认 256）限制了同时活跃的内部流数量。当活跃数达到上限时，上游的新元素会被暂停（不再 `request`），直到某个内部流完成、释放一个槽位。

> 类比：一个呼叫中心最多同时处理 256 个电话。电话打爆了？后面的客户先排队等（上游暂停），等有客服挂了电话再接新的。

## 示例七：Flux.create —— 当你需要自己控制数据发射

### 从业务角度看

```java
// 真实场景：把回调式 API 转成响应式流
Flux<String> eventFlux = Flux.create(sink -> {
    eventBus.register(event -> {
        sink.next(event.getData());   // 把回调里的数据"推"进 Reactor 流
    });
    eventBus.onClose(() -> sink.complete());
}, FluxSink.OverflowStrategy.BUFFER);
```

**你可能会问：`Flux.create` 和 `Flux.just`/`Flux.range` 有什么区别？**

`just` 和 `range` 的数据是预先确定的——你在装配时就知道会发射什么。`create` 给你一个 `sink`，你可以在任意时刻、任意线程往里面推数据。这让你能把传统的回调 API、事件监听器等桥接到 Reactor 世界。

### 五种背压策略

`Flux.create` 的第二个参数是背压策略——当上游产生数据的速度超过下游消费的速度时，怎么处理？

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| `BUFFER` | 全部缓冲到无界队列中 | 数据量可控，不能丢数据 |
| `DROP` | 超出下游处理能力的数据直接丢弃 | 允许丢数据，比如实时指标采样 |
| `LATEST` | 只保留最新的一个未消费数据 | 类似于"最新股价"——只关心最新值 |
| `ERROR` | 超出能力时直接报错终止 | 严格模式，不允许任何数据丢失 |
| `IGNORE` | 完全忽略背压，直接推送 | 确定下游能处理任意量的场景 |

> 餐厅类比：
> - **BUFFER**：所有订单都排队，厨师慢慢做（风险：单子堆到天花板，内存溢出）
> - **DROP**：来不及做的单子直接扔掉
> - **LATEST**：只做最新的一单，之前没做的单子全作废
> - **ERROR**：订单超过 10 张就关门不接了
> - **IGNORE**：不管做不做得完，统统接下来

### SerializedFluxSink：多线程安全

当你从多个线程调用 `sink.next()` 时，Reactor 用 `SerializedFluxSink` 来保证线程安全。它使用了一个经典的 MPSC（Multi-Producer Single-Consumer）模式：

```java
// SerializedFluxSink.next 内部简化
public FluxSink<T> next(T t) {
    if (WIP.compareAndSet(this, 0, 1)) {
        // 我是第一个写入者，直接推送
        sink.next(t);
        if (WIP.decrementAndGet(this) == 0) {
            return this;  // 没有其他人排队，直接返回
        }
    } else {
        // 有人在推送了，我把数据放进 MPSC 队列排队
        mpscQueue.offer(t);
        if (WIP.getAndIncrement(this) != 0) {
            return this;  // 已经有人在排空队列了，我放完就走
        }
    }
    drainLoop();  // 我来负责排空队列
    return this;
}
```

这个设计保证了即使多个线程同时调用 `sink.next()`，Reactive Streams 规范要求的"`onNext` 不能并发调用"也不会被违反。

⚠️ **踩坑提醒**：`Flux.create` 的 `BUFFER` 策略使用无界队列。如果上游持续高速产生数据而下游处理不过来，队列会无限增长，最终导致 OOM（OutOfMemoryError）。生产环境建议配合 `.onBackpressureBuffer(maxSize)` 设置上限，或者改用 `DROP`/`LATEST` 策略。

## 归纳总表

### 七个示例的核心机制对照

| 示例 | 核心问题 | 关键机制 | 线程模型 | 关键类 |
|------|----------|----------|----------|--------|
| 一：just+map | 最简链的执行全流程 | 装配→订阅→onSubscribe→request→onNext | 单线程 | FluxArray, FluxMapFuseable, MapFuseableSubscriber |
| 二：+filter | 优化循环、丢弃元素时怎么办 | while(true) 优化循环、request(1) 补偿、SYNC 熔合 | 单线程 | FluxFilterFuseable, FilterFuseableSubscriber |
| 三：publishOn | 数据怎么跨线程 | 队列 + Worker 线程、WIP CAS、prefetch 补货 | 跨线程 | FluxPublishOn, PublishOnSubscriber |
| 四：subscribeOn | 订阅过程怎么换线程 | Worker 线程上执行 source.subscribe() | 跨线程 | MonoSubscribeOn, SubscribeOnSubscriber |
| 五：onErrorResume | 出错后怎么切换数据源 | ResumeSubscriber 的 second 标记、二次订阅 | 单线程 | FluxOnErrorResume, ResumeSubscriber |
| 六：flatMap | 一变多的并发管理 | FlatMapMain + N 个 FlatMapInner、maxConcurrency | 可并发 | FluxFlatMap, FlatMapMain, FlatMapInner |
| 七：create+背压 | 自定义数据源、多线程安全 | 五种 OverflowStrategy、MPSC SerializedFluxSink | 多线程 | FluxCreate, BufferAsyncSink, SerializedFluxSink |

### 信号传播方向速查表

| 信号 | 传播方向 | 说明 |
|------|----------|------|
| `subscribe()` | 下游 → 上游 | 触发订阅链的建立 |
| `onSubscribe(Subscription)` | 上游 → 下游 | "我准备好了"，传递 Subscription |
| `request(n)` | 下游 → 上游 | "给我 n 个数据"，背压信号 |
| `onNext(t)` | 上游 → 下游 | 数据元素的传递 |
| `onError(e)` | 上游 → 下游 | 错误信号 |
| `onComplete()` | 上游 → 下游 | 完成信号 |
| `cancel()` | 下游 → 上游 | "我不要了"，取消订阅 |

### 操作符内部 Subscriber 的通用模板

如果你想理解任何一个 Reactor 操作符的源码，可以套用这个分析框架：

| 分析维度 | 要问的问题 |
|---------|-----------|
| 装配时 | 创建了什么对象？存了哪些字段？ |
| subscribeOrReturn | 返回 null 还是非 null？创建了哪种内部 Subscriber？ |
| onSubscribe | 是否有熔合协商？是否创建队列？ |
| onNext | 核心业务逻辑是什么？是否需要背压补偿？ |
| request | 直接透传还是有自己的逻辑？ |
| 线程模型 | 有没有 Worker 线程？有没有队列做跨线程桥梁？ |
| 错误处理 | done 标记怎么用？onError 时做什么清理？ |

掌握这个框架后，你就能自己去读 Reactor 的任何一个操作符的源码了。
